# Project Guide for AI Assistants

## Project
Personal Training Management Platform — a gym class scheduling app with 3 roles (Admin, Coach, Coachee).

## Tech Stack
- **Backend:** Node.js 22 LTS + TypeScript + Express + Prisma + PostgreSQL
- **Frontend:** React 18 + Vite + TypeScript + TailwindCSS v4 + React Router v6 + TanStack React Query v5
- **Testing:** Vitest + Supertest (unit/integration), Playwright (E2E)
- **Infra:** Docker Compose, Render (deployment)
- **Tooling:** Biome (lint/format)

## Architecture: Hexagonal (Ports & Adapters)
- `src/domain/` — Pure entities + domain services (zero external deps)
- `src/application/` — Use case orchestrators
- `src/infrastructure/` — Adapters (Prisma repos, Express controllers, auth, calendar, FCM)
- `src/config/` — DI container, env config

## Key Conventions
1. All files in PascalCase for components/entities, camelCase for utilities
2. Class duration is ALWAYS 60 minutes
3. Gym capacity: max 2 individual + 1 group simultaneous
4. Google Calendar event titles: individual = "coachee name - level", group = "Group class - level"; description includes assigned coach, recurrence status, notes, and enrolled coachees (group)
5. Error responses: `{ error: { code, message, ref } }` — no stack traces
6. All dependencies pinned to EXACT versions (no ranges)
7. No raw SQL — Prisma parameterized queries only
8. API under `/api/v1/` prefix
9. Class times are stored as UTC instants; user-entered wall-clock times are interpreted in the gym timezone (Europe/Madrid, DST-aware). Google Calendar events carry `timeZone: Europe/Madrid`; recurrence windows and available-slots math use Madrid wall-clock hours (see `TimeZoneMath.ts` / frontend `gymDateTime.ts`)

### Spec-kit
- `/speckit.specify` — Create or refine a feature specification
- `/speckit.clarify` — Ask clarifying questions on an incomplete spec
- `/speckit.plan` — Generate an implementation plan from a spec
- `/speckit.tasks` — Decompose a plan into actionable tasks
- `/speckit.implement` — Execute implementation tasks
- `/speckit.constitution` — Update the project constitution
- `/speckit.analyze` — Analyze code quality against constitution
- `/speckit.checklist` — Generate implementation checklists
- `/speckit.converge` — Converge diverged specs with implementation
- `/speckit.taskstoissues` — Convert tasks to Linear issues

## Spec-Driven Development (SDD) Workflow
1. Create feature branch: `.specify/scripts/bash/create-new-feature.sh "description"`
2. Write spec: `/speckit.specify` (creates `specs/<NNN>-feature-name/spec.md`)
3. Review spec gate — approve before proceeding
4. Plan: `/speckit.plan` (creates `plan.md` and research)
5. Review plan gate — approve before proceeding
6. Tasks: `/speckit.tasks` (creates `tasks.md`)
7. Implement: `/speckit.implement` — execute tasks in priority order

All specs live in `specs/` (one subdirectory per feature). Feature branches follow pattern `NNN-feature-name`.

## Branch Naming
- Features: `<NNN>-<short-description>` (e.g., `003-auth-user-foundation`)
- The feature number is auto-assigned by `create-new-feature.sh`
- Use the script rather than naming branches manually

## Commit Messages
Use conventional commits: `type(scope): message` (e.g., `feat(classes): add POST /classes endpoint`).
Allowed types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`, `security`.

## PR Process
1. Every PR must pass: `biome check` → `tsc --noEmit` → `vitest run` → `npm audit --audit-level=high`
2. PRs MUST reference the Linear issue (pattern `COACHER-N`) in the title or body.
3. If authored by or substantially generated by an AI agent, disclose this in the PR description.
4. Constitution compliance (`.specify/memory/constitution.md`) must be verified before merge.

## Linear MCP
This project uses Linear for issue tracking. Issue IDs follow pattern COACHER-N.

## Governing Principles
See `.specify/memory/constitution.md` for non-negotiable project principles covering domain purity, test-first, security-by-default, API contract consistency, dependency integrity, and governance rules.
