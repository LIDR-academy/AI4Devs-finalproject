# Research: Coachee Calendar Interactions

**Phase 0 output** for `specs/016-coachee-calendar-interactions/`. No `NEEDS CLARIFICATION` markers remain in the spec; the decisions below are design choices grounded in the actual frontend codebase, the documented API contracts, and the story's hard boundary (backend is complete, frontend only).

## 2. Key design decisions

### D1 — Waitlist eligibility for gray blocks comes from `GET /classes/:id` (coacheeStatus), not a new list field
- **Decision**: the calendar list endpoint (`GET /classes`) returns `visibility` only — it does **not** include `coacheeStatus`. The eligible-gray decision ("group full + within reach" / "individual slot occupied + within reach") needs `coacheeStatus.isWithinReach` and `isOnWaitingList`, which only `GET /classes/:id` provides (routes `classes.ts:225` wires `coacheeStatus` only on the detail route). The interaction modal therefore fetches class detail on open via the existing `useClassDetail(id)` hook and derives the waitlist action from that detail's `coacheeStatus`. No backend change.
- **Rationale**: preserves the story's explicit "backend is done, frontend only" boundary; `useClassDetail` already exists (`queryKey: ["classes", id]`), the detail DTO already carries `coacheeStatus`, and the modal opening is the natural moment to load it. The modal can render immediately from list data and refine the action once detail arrives.
- **Alternatives considered**: extending `GET /classes` to return `coacheeStatus` (rejected — backend change out of scope); deriving reach client-side from `level.sortOrder` (rejected — duplicates backend rules, Constitution §domain purity of the *server* rules); offering the waitlist on every gray slot and letting the backend error (rejected — spec FR-009 says non-eligible slots offer no waitlist option and explain why, backend rejection is only the fallback).
### D2 — Card predicate: render relevant gray busy + canceled informational entries (extend `coacheeWeekView.ts`)

- **Decision (refined post-implementation per user feedback)**: replace the blue/green-only `isCoacheeRelevant` filter with `isCalendarClass(cls, coacheeLevelSortOrder)`, which keeps blue and green plus gray busy **only when the class is relevant to the Coachee** — a group class within ±1 level of the Coachee's level (waitlist-eligible, e.g. a full group), matched client-side from `level.sortOrder` + the Coachee's own level. Canceled classes render as informational. Busy blocks for classes not relevant or related to the Coachee (occupied individual slots, out-of-reach groups) are dropped client-side — the calendar no longer shows busy entries a Coachee can never act on. The **card state**, not the visibility filter, decides the action.
- **Rationale**: the story requires gray busy blocks for classes the Coachee can waitlist; showing busy blocks for every occupied/out-of-reach slot (full-week "visual truth") was overridden by the explicit requirement that a Coachee not see busy blocks from classes unrelated to them. `level.sortOrder` + the Coachee's level (from `/auth/me` + `/levels`) replicate the server's `isWithinReach` rule exactly (diff ≤ 1, GROUP only), so the filter is server-consistent without a backend change.
- **Alternatives considered**: keeping the filter blue/green-only and querying gray separately (rejected — the list already returns gray); a second reach endpoint (rejected — backend change); rendering gray and letting the modal explain (rejected — the user asked to hide irrelevant busy blocks entirely).

### D3 — Calendar card interaction: a single `ClassInteractionModal` (detail → action → confirmation)
- **Decision**: one modal component, `ClassInteractionModal.tsx`, opened by tapping any calendar card. It renders:
  - class details: type, time (gym timezone), level (group), Coach, and — for green entries — `spotsAvailable = capacity - enrollmentCount`;
  - a primary action derived by a pure helper from (visibility, status, detail.coacheeStatus): blue → **cancel**, green → **join**, gray eligible → **join/leave waiting list**, gray ineligible / canceled → informational (no action, explain why);
  - an embedded confirmation step reusing the established hand-rolled overlay pattern (`fixed inset-0 z-[110]`, backdrop, `max-w-md` card) that appears after the action is chosen and before the mutation fires (two-step: "details → action button → confirm dialog").
- **Rationale**: one component keeps the tap surfaces, eligibility logic, confirmation UX, and error toasting in one testable place; matches the existing modal conventions in `CoacheeClassCard`, `JoinableClassList`, and `MyWaitingLists`; the two-step confirm satisfies spec FR-010 (every action needs a confirmation dialog) while still showing class details for the waitlist (spec FR-007).
- **Alternatives considered**: separate CancelModal / JoinModal / WaitlistModal (rejected — three near-identical components, more duplication); reusing the Home `CoacheeClassCard.ConfirmDialog` verbatim (rejected — Home's dialog lacks the detail view and eligibility handling the calendar needs; the confirm pattern is copied, not shared, keeping Home's component untouched to avoid regressions).

### D4 — Pure decision + optimistic-transform helpers in `domain/utils/calendarInteraction.ts`
- **Decision**: a pure module with two functions:
  1. `deriveCalendarInteraction({ classType, status, visibility, coacheeStatus, enrollmentCount, capacity })` → `{ kind: "cancel" | "join" | "waitlist-join" | "waitlist-leave" | "info", reason?: "canceled" | "out-of-reach" | "not-open" | null }` — the single source of truth for what a card/modal offers (blue→cancel, green→join, gray+within-reach+full-group→waitlist-join, gray+within-reach+occupied-individual→waitlist-join, already on list→waitlist-leave, else info).
  2. `applyOptimisticClassUpdate(cls, action)` → a copy of the class with the optimistic post-action state (join→blue+isEnrolled+enrollmentCount+1; cancel→green/gray+isEnrolled=false+enrollmentCount-1; waitlist-join→isOnWaitingList=true+waitingListCount+1; waitlist-leave→isOnWaitingList=false+waitingListCount-1), with visibility re-derived per D4-transitions.
- **Rationale**: Constitution §domain purity + testability — pure functions with no React/Query imports, 100% branch coverage, and deterministic rollback math. The mutation hooks become thin adapters (D5), keeping all decision logic unit-testable in the existing `node` vitest env.
- **Alternatives considered**: putting the transitions inline in each hook (rejected — duplicated, untestable without a renderer); reusing `classCardState.ts` verbatim (rejected — it treats individual/out-of-reach as `none` and doesn't model the eligibility-aware waitlist action the modal needs; it stays for Home).

### D5 — Centralized optimistic mutation adapter `infrastructure/hooks/optimisticClassMutation.ts`
- **Decision**: a single helper that builds the React Query lifecycle for an id-triggered class mutation:
  - `onMutate(classId)`: snapshot every `["classes"]`-prefixed query (`queryClient.getQueriesData`); for each cached entry matching `classId`, replace the class with `applyOptimisticClassUpdate(cls, action)`; return the snapshot for rollback. Handles both list datasets (`{ data: TrainingClass[] }`) and the single-class detail (`["classes", id]`).
  - `onError`: restore the snapshot (rollback) and let the caller surface the mapped toast.
  - `onSettled/unvalidate`: keep the existing `invalidateQueries(["classes"])` / `(["classes"], ["waiting-lists"], ["coachee","dashboard"])` behavior on success.
- All four hooks (`useJoinClass`, `useCancelEnrollment`, `useJoinWaitingList`, `useLeaveWaitingList`) adopt it. This means Home cards (which consume the same hooks) also gain rollback-safe optimistic state — consistent behavior, one implementation.
- **Rationale**: the story explicitly requires optimistic updates with rollback (spec FR-012/FR-013) and the four hooks are shared between the calendar and Home; centralizing avoids four copies of the same snapshot/rollback logic. Matches the existing `invalidateWaitingListQueries` precedent in `useJoinWaitingList.ts`.
- **Alternatives considered**: per-hook optimistic code (rejected — duplication); a QueryClient-level `mutationCache.onError` global (rejected — loses per-action rollback granularity and isn't how the rest of the app handles mutations).

### D6 — Testing: add `jsdom` + Testing Library for component tests, keep node-env pure tests
- **Decision**: widen `vitest.config.ts` to `include: ["src/**/*.test.{ts,tsx}"]` (keep the default `environment: "node"`) and mark component-test files with a per-file `// @vitest-environment jsdom`. Add pinned devDependencies: `jsdom`, `@testing-library/react`, `@testing-library/dom`, `@testing-library/user-event`, `@testing-library/jest-dom`. Component tests cover the modal: opens on card tap, shows details, cancel/join flows confirm before submitting, eligible-gray offers waitlist (join/leave), ineligible-gray shows info, optimistic update reflects and error rolls back (render a `QueryClientProvider` wrapper per test).
- **Rationale**: the story explicitly requires "Frontend component/hook tests for the modal flows and optimistic-update/rollback behavior"; today vitest only runs `node`-env `.test.ts` with zero `.test.tsx`. A per-file jsdom annotation keeps the existing pure tests untouched (no env risk to `classCardState.test.ts`, `gymDateTime.test.ts`, etc.). New deps are dev-only and pinned exact per Constitution §V.
- **Alternatives considered**: global jsdom environment (rejected — could perturb existing node/env tests, e.g. `pullGesture.test.ts`); Playwright E2E for the flows (rejected — the story asks for component/hook tests; with zero `jsdom` today, Testing Library unit coverage is the faster, foldable choice; quickstart still covers manual E2E).

### D7 — Confirmation copy + error messages (reuse, don't invent)
- **Decision**: reuse `enrollmentErrorMessage` for join/cancel and `waitingListErrorMessage` for waitlist join/leave; reuse `extractErrorCode`; toast on success ("You joined the class.", "You left the class.", "You joined the waiting list.", "You left the waiting list.") and mapped error toasts on failure. Confirmation copy mirrors the established `dialogCopy()` in `CoacheeClassCard.tsx:223-264` (join/cancel/waiting-list/leave titles, bodies, labels) so the calendar and Home say the same thing.
- **Rationale**: deterministic, already-tested message maps; consistent voice across surfaces; no new error strings invented. Spec FR-018 (surface backend rejection as clear feedback) is satisfied by the maps.

## 3. Test & validation strategy

- **Red-Green** (Constitution §II): write `calendarInteraction.test.ts` first covering every branch of `deriveCalendarInteraction` (blue/cancel, green/join, gray full-group+reach→waitlist-join, gray occupied-individual+reach→waitlist-join, gray already-on-list→waitlist-leave, gray out-of-reach→info/out-of-reach, canceled→info/canceled, individual unoccupied→info/not-open) and every transition of `applyOptimisticClassUpdate` (join, cancel green, cancel gray, waitlist-join, waitlist-leave — each asserting visibility, `coacheeStatus`, `enrollmentCount`, `waitingListCount`). Confirm failing → implement → green. Target 100% branch coverage on the pure module.
- `optimisticClassMutation.test.ts`: with a real `QueryClient` (same pattern as `useJoinWaitingList.test.ts`), seed `["classes", ...]` datasets, invoke the built onMutate, assert the cached class flips to the optimistic state; then invoke onError and assert the exact snapshot is restored; assert non-target classes are untouched; assert the single-detail cache shape is handled.
- `ClassInteractionModal.test.tsx` (jsdom): open on green card → shows level, Coach, spots; confirm → mutation fired; blue card → cancel confirm; eligible gray → waitlist join/leave confirm with class details; ineligible gray → info text, no waitlist option; error → rollback + mapped toast.
- `coacheeWeekView.test.ts` (extended): predicate includes blue/green/gray/canceled.
- Manual validation via `quickstart.md`.
- CI gates: `frontend: npm run typecheck && npm run lint && npm test` (plus the repo PR gate `biome check → tsc --noEmit → vitest run → npm audit`).

## 4. Risks / mitigations

- **Eligibility depends on a second fetch**: the modal opens from list data but decides the waitlist action from `GET /classes/:id`. Mitigation: render details immediately, show the action once detail resolves (brief loading state in the modal); the cache key `["classes", id]` means repeat opens are instant. Risk is low at single-gym scale (list is ≤ 100 classes/week).
- **Optimistic state drifting from server truth**: rollback on error + invalidation on success reconcile any divergence (spec FR-015). Mitigation: the pure transform is branch-tested; rollback restores the exact snapshot object; the quickstart verifies a forced-failure reverts the calendar.
- **Double-tap / concurrent actions**: guard the mutation and the modal confirm (disable while pending) to prevent duplicate enrollments/waitlist entries (spec FR-014).
- **Home regression via shared hooks**: `useJoinClass`/`useCancelEnrollment`/`useJoinWaitingList`/`useLeaveWaitingList` power Home cards too; the new optimistic onMutate/onError must not break their existing invalidate-on-success behavior. Mitigation: keep `onSuccess` invalidations identical, only add onMutate/onError; existing hook tests (`useJoinWaitingList.test.ts`) keep passing; Home manual scenarios rerun from quickstart.
- **jsdom/toolchain**: adding Testing Library touches the vitest config — the existing 10 `.test.ts` files must stay green under the widened include and default node env; component tests carry the jsdom annotation so no global env switch.
- **Timezone correctness**: no new time math — the modal formats `startTime` via the existing gym-timezone helpers (`formatNextClassTime` / `Intl` with `Europe/Madrid`); no DST logic added.
