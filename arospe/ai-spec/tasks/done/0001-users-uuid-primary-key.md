# [0001] Convert `users` primary key to UUID (v7), cascading to passkeys, sessions & permission morph key

## Description
Implement [ADR 0001](../../../docs/decisions/0001-uuid-primary-keys.md) for the **`users`** table:
convert its primary key from `bigint` auto-increment to a **UUID (v7)** generated by Laravel's
native `HasUuids` trait, and cascade the type change to every real dependent — `passkeys.user_id`,
`sessions.user_id`, and `spatie/laravel-permission`'s `model_has_roles` / `model_has_permissions`
morph key. `users` is the only already-migrated table among the seven UUID entities, so this is a
**breaking alteration-with-backfill** (not a fresh `create_table`), done via new migrations that
never touch the historical `create_*` files.

## Type
backend | includes database-expert: **yes**

## Files to create/modify

Migrations (new files — **never** hand-edit the historical `create_*` migrations). Exact
`Schema::table()` mechanics are `backend-expert`/`database-expert`'s to write in Phase 3; listed
here with one-line purpose and required ordering:

**5 migrations** (corrected during Phase 2: the original 4-file plan had migration 1 destroying
`users.id` before migrations 2 & 4 could join against the old bigint id to backfill their own
columns — `code-reviewer` caught the sequencing bug; the fix keeps the old id around as
`legacy_id` until every dependent has consumed it, then finalizes in a new migration 5):

1. `database/migrations/<ts>_convert_id_to_uuid_in_users_table.php` — rename `users.id` →
   `legacy_id` (keeps its `bigint`/`AUTO_INCREMENT`/PRIMARY KEY exactly as-is, just renamed); add
   a nullable, unique-indexed `uuid` `CHAR(36)` column; backfill it for existing rows. Does
   **not** touch the primary key or drop anything. No FK drop needed here — the passkeys FK safely
   keeps pointing at the renamed column (MySQL 8.0.19+/8.4 propagates FK metadata through
   `RENAME COLUMN`).
2. `database/migrations/<ts>_convert_user_id_to_uuid_in_passkeys_table.php` — **drop the passkeys
   FK here** (it now points at `users.legacy_id`); retype `passkeys.user_id` `bigint`→`uuid` via
   temp column + backfill by joining on `users.legacy_id` + drop old + rename. **Does not re-add
   the FK** (moved to migration 5).
3. `database/migrations/<ts>_convert_user_id_to_uuid_in_sessions_table.php` — same
   temp-column-backfill-rename pattern for `sessions.user_id`, joining on `users.legacy_id` (no FK
   exists here today, so self-contained).
4. `database/migrations/<ts>_convert_model_morph_key_to_uuid_in_permission_tables_table.php` —
   backfill `model_has_roles`/`model_has_permissions`'s new `model_uuid` (config-driven name) by
   joining on `users.legacy_id` for rows where `model_type` is `App\Models\User::class`; drop old
   `model_id`; rebuild each table's composite primary key and index. Read the column name from
   `config('permission.column_names.model_morph_key')` **(dynamically — matching the vendored
   migration's defensive style — do not hardcode)**. Both tables empty today → no-op now, but
   written generically.
5. `database/migrations/<ts>_finalize_uuid_primary_key_on_users_table.php` — **new file**: drop
   `users.legacy_id` (its data has now been consumed by migrations 2–4); rename `uuid` → `id`; set
   `id` as the PRIMARY KEY; **re-add the passkeys FK** (`user_id` → `users.id`, `cascadeOnDelete()`)
   now both sides are UUID. This is the only point where `users` leaves its dual-column state
   (satisfying the ADR's "no dual-column end state") and where the passkeys FK reappears.

> **Column-state-per-file (for the Phase 3 implementer):** after migration 1, `users` holds both
> `legacy_id` (bigint, still the actual PK) and `uuid` (not yet PK) simultaneously, and stays in
> that state through migrations 2–4 (all of which read `legacy_id` to backfill their own tables)
> until migration 5 finalizes it.

Config (separate step, **own commit**, must ship **before** migration 4 and be followed by
`php artisan config:clear`):

- `config/permission.php` — rename `column_names.model_morph_key` from `model_id` to `model_uuid`
  (exactly what that file's own inline comment already anticipates).

Backend code:

- `app/Models/User.php` — add `use Illuminate\Database\Eloquent\Concerns\HasUuids;` import; add
  `HasUuids` to the trait-use list (alphabetically between `HasRoles` and `Notifiable`, matching
  the file's ordering and Pint style); change the `@property` PHPDoc for `id` from `int` to
  `string`. Nothing else changes — **do not** add `$keyType`/`$incrementing` properties (the trait
  overrides those as methods); `#[Fillable]`/`#[Hidden]`/`casts()` untouched.
- `app/Concerns/ProfileValidationRules.php` — **real bug this migration would otherwise
  introduce**: widen `profileRules(?int $userId = null)` and `emailRules(?int $userId = null)` to
  `?string $userId = null`. Called from `app/Livewire/Settings/Profile.php` as
  `$this->profileRules($user->id)`; once `$user->id` is a UUID string, the `?int` hint is a real
  type violation (Larastan level 7) that would silently break the "ignore my own email" uniqueness
  check on profile update. No logic change inside — `Rule::unique(...)->ignore($userId)` accepts a
  string id fine.

Confirmed **no change needed** (documented so reviewers don't re-open them):
`database/factories/UserFactory.php` (never sets `id`; trait auto-populates pre-insert);
`app/Livewire/Settings/Security.php`'s `?int $deletingPasskeyId` and `id: int` array-shape (both
refer to `passkeys.id`, which stays `bigint` — only the `user_id` FK changes); no other Fortify
action or Livewire component int-type-hints a user id; no first-party `Passkey` model exists
(passkeys are reached only via the vendored `PasskeyAuthenticatable` trait).

- [ ] Tests written and green (new UUID tests + all listed regressions, incl. the new ProfileUpdate assertion).

- [ ] **Known limitation — rollback is data-lossy (accepted, human-confirmed, not a defect):** per ADR 0001 there is **no *permanent* `legacy_id` column** — the `legacy_id` created in migration 1 is transient and dropped by the finalize migration (5). Consequently:
  - The actual, irreversible data loss happens specifically in **migration 5's `down()`**: it drops the passkeys FK it added, drops the `id` PK, renames `id` → `uuid`, and recreates an **empty** `legacy_id` shell — the exact point the original bigint values become unrecoverable.
  - Migrations **2 / 3 / 4's `down()`** reverse structurally but **without value fidelity**: once migration 5's rollback has already emptied `legacy_id`, there is nothing meaningful to rejoin against. So the accepted loss now extends to **all four backfilled columns** (`users.id`, `passkeys.user_id`, `sessions.user_id`, and the permission morph key), not just `users.id`.
  - Migration **1's `down()` is fully lossless in isolation** (it only renamed/added, never dropped/destroyed) — noted for anyone worried about that specific step.
  - A passing `migrate:rollback` across the set must **not** be mistaken for a safe, lossless operation. This tradeoff was explicitly chosen by the human product owner over keeping a permanent `legacy_id` audit column.
- [ ] **Backfill location noted:** backfill is written inline in each migration's `up()` (not a separate seeder/command), justified by the tiny data volume and tight coupling to the column-rename choreography — flagged as worth revisiting if this pattern is reused against a table with real production volume.
