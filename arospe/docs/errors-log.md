# Errors Log

A structured log of real mistakes made in this project and the concrete rule adopted to avoid repeating them. Not a general bug tracker — only entries that produced a lasting convention belong here.

## Entry format

Newest entry first, directly below this line. Every entry uses this exact structure:

```markdown
## <short problem title> — <YYYY-MM-DD>
- **Context**: what was being worked on
- **What happened**: observed symptom/error
- **Root cause**: why it happened
- **Fix applied**: what changed, with a file path or commit/PR reference
- **How to avoid it next time**: a concrete, actionable rule — link to a `conventions/` doc if one covers it
```

## A doc's "this app has no X yet" claim outlived the X by two tasks — 2026-08-13

- **Context**: task 0004 Phase 5 (`code-reviewer`) reviewing the Users list/editor backend, which introduced `app/Policies/UserPolicy.php`.
- **What happened**: [`testing/backend/feature-integration-tests.md`](testing/backend/feature-integration-tests.md) carried a section headed "Authorization: today vs. once Policies exist" asserting two things that were false: "This app has no `app/Policies/` yet" (true only until this task) and that `spatie/laravel-permission` is "**not yet attached** to `App\Models\User`" — which had been false since **task 0002**, two tasks earlier. The second claim actively misled: it told a test author that role-based authorization was untestable when `HasRoles`, two seeded roles and a 38-permission catalog had been live for weeks. Grepping the tree during the fix turned up **two more copies of the same false claim**, in [`testing/qa/what-not-to-test.md`](testing/qa/what-not-to-test.md) and [`testing/qa/risk-based-testing.md`](testing/qa/risk-based-testing.md) — three independent statements of it, all in `docs/testing/`, none of which the task-0002 docs pass touched.
- **Root cause**: the claim was phrased as a **negative statement about the whole repo** ("there is no X"), inside documents nobody would think to open when adding X. The docs-sync pass after task 0002 followed the change→doc mapping table — `HasRoles` usage maps to `architecture/authorization.md`, which *was* updated correctly — and a mapping table can only route you to the docs that **describe** a change, never to the unrelated docs that happen to **assert the change hasn't happened**. Nothing failed and no test broke, so all three copies stayed reachable only by whoever happened to read those files.
- **Fix applied**: rewrote the section as "Authorization tests" in [`testing/backend/feature-integration-tests.md`](testing/backend/feature-integration-tests.md), stating the three real layers (route middleware, permissions, policies) with the rules that follow, and corrected the Authorization bullet in [`testing/qa/what-not-to-test.md`](testing/qa/what-not-to-test.md) and question 4 of [`testing/qa/risk-based-testing.md`](testing/qa/risk-based-testing.md).
- **How to avoid it next time**: **do not write a bare negative claim about the repo in a doc that does not own that subject** — say "authorization today is X (see [authorization.md])" rather than "there is no authorization yet", so the sentence goes stale into a *link* instead of into a lie. When a negative claim is genuinely the point (as in [api/routes.md](api/routes.md)'s "no REST API yet"), it belongs in the doc that owns the topic and must name what would replace it. And in every docs-sync pass, before relying on the change→doc mapping table alone, grep the whole tree for the thing you just introduced — `grep -rn "no app/Policies\|not yet\|does not exist yet\|todavía" docs/` — because the docs that need fixing are precisely the ones that never mentioned the feature by name.

## A redundant `users_uuid_unique` index survived the UUID primary-key conversion — 2026-08-12

- **Context**: task 0003 (`ai-spec/tasks/.../0003-users-status-and-email-verification-lifecycle.md`) investigating index cost before deciding whether `users.status` needed one.
- **What happened**: `php artisan db:table users` shows the `id` column covered **twice** — once by `primary`, and again by a leftover `users_uuid_unique` (`btree, unique`). Every insert therefore writes a wholly redundant `CHAR(36)` unique index.
- **Root cause**: the UUID conversion set (see [database/migrations.md](database/migrations.md#the-real-users-conversion-alteration-not-create_table)) created the transient column in `2026_07_22_100001_convert_id_to_uuid_in_users_table.php` as `$table->uuid('uuid')->unique()`, and `2026_07_22_100005_finalize_uuid_primary_key_on_users_table.php` renamed it to `id` and promoted it to PRIMARY **without dropping that unique index**. A rename carries indexes along with the column, and promoting a column to PRIMARY does not absorb or replace an existing unique index on it — so the two coexist silently. Nothing fails; it is pure write amplification, which is exactly why it survived review.
- **Fix applied**: **not fixed** — recorded here and confirmed empirically (it was only a suspicion when the story was written). Dropping it is a follow-up task, since it is schema debt unrelated to the story that found it.
- **How to avoid it next time**: **in a multi-step column conversion, the finalize migration owns the cleanup of every index the intermediate steps created.** When a transient column is given `->unique()` only to guarantee uniqueness *during* the transition, the step that promotes it to PRIMARY must `dropUnique([...])` first. Verify with `php artisan db:table <table>` — not by reading the migrations — that the resulting index list is exactly what you intended; the migration diff will not show you an index that nobody removed.

## A test asserted against a fixture address that the local `.env` also pointed `SUPER_ADMIN_EMAIL` at — 2026-08-12

- **Context**: task 0003, running the full suite locally (`sail test`) against this repo's real developer `.env`.
- **What happened**: two tests in `tests/Feature/Seeders/DatabaseSeederTest.php` — "seeding a production/staging environment creates no `test@example.com` fixture user" — failed locally while passing in CI. A `test@example.com` row existed after seeding, but not from the fixture gate they were testing.
- **Root cause**: this repo's local `.env` sets `SUPER_ADMIN_EMAIL` to the same address as the fixture account. With that config ambient, `RolePermissionSeeder::bootstrapSuperAdmin()`'s **provision** branch created a `test@example.com` row through a completely different code path than the one under test. The tests read config from the developer's environment instead of pinning the value they depend on, so their result varied with `.env`.
- **Fix applied**: both tests now neutralize the ambient value first — `config(['auth.super_admin.email' => null])` — which makes `bootstrapSuperAdmin()` a documented no-op (`! filled($email)`) and leaves only `DatabaseSeeder`'s own environment gate under test. See the two commented calls in [`tests/Feature/Seeders/DatabaseSeederTest.php`](../tests/Feature/Seeders/DatabaseSeederTest.php).
- **How to avoid it next time**: **a test that depends on a config key must set that key, including setting it to `null`/empty when "unset" is the state it assumes.** Never rely on a key being absent from the environment the suite happens to run in — `.env` is developer-specific and CI's is not the same file. This applies to every seeder and bootstrap test that branches on config; see [testing/qa/risk-based-testing.md](testing/qa/risk-based-testing.md) for the wider "what varies between environments?" question.

## A row carrying the configured email was treated as proof of mailbox ownership — 2026-08-09

- **Context**: task 0002 (`ai-spec/tasks/.../0002-seed-roles-permissions-catalog.md`), bootstrapping the `Super Admin` role from `SUPER_ADMIN_EMAIL` in `database/seeders/RolePermissionSeeder.php`.
- **What happened**: the Phase 3 implementation looked up `User::where('email', $email)->first()` and granted `Super Admin` to whatever row came back (warning and skipping when nothing matched). `appsec-auditor` flagged it as a privilege-escalation path: a `users` row merely *carrying* an address proves nothing about who controls that mailbox.
- **Root cause**: leaving `SUPER_ADMIN_EMAIL` unset at first deploy is a documented, supported state, and self-registration is enabled — so during that window anyone can register the address the operator intends to use later. Worse, `App\Livewire\Settings\Profile::updateProfileInformation()` lets any signed-in user point their **existing** account at an arbitrary address: it nulls `email_verified_at` but writes the new address to `users.email` immediately, with no re-verification. Either way the squatter is handed Super Admin the moment an operator sets the config and reseeds.
- **Fix applied**: the lookup in [`database/seeders/RolePermissionSeeder.php`](../database/seeders/RolePermissionSeeder.php) now carries `whereNotNull('email_verified_at')`, so verification is part of the **match condition** rather than a check bolted on afterwards, and a fifth branch was added for the address being occupied by an *unverified* account: abort loudly (console error + `Log::warning`), grant the role to nobody, insert no second account, send no mail, and `return` rather than throw so the roles and the 38-permission catalog still commit. The full decision tree is documented in [architecture/authorization.md](architecture/authorization.md#super-admin-bootstrap); the general rule is in [security/seeder-safety.md](security/seeder-safety.md#a-matching-row-is-not-proof-of-ownership).
- **How to avoid it next time**: **an existing row with the right email is not proof of mailbox ownership.** Any code that grants privilege by matching a configured or user-supplied address must require proof of control — `whereNotNull('email_verified_at')` — as part of the query, not as a follow-up `if`. When neither granting (unproven ownership) nor creating (address taken) is safe, abort with a `return` and an operator-actionable message; never throw from inside a seeder transaction that also writes required application data, and never resolve the ambiguity on the seeder's own initiative by verifying, renaming, or deleting the occupying account.
- **Update — 2026-08-12 (task 0003): the second half of this vector is now closed at the source.** The profile screen no longer writes an unverified address into `users.email` at all: `App\Livewire\Settings\Profile::updateProfileInformation()` routes every email change through `App\Actions\Users\RequestEmailChange`, which parks the new address in `users.pending_email` and mails a signed, address-bound, 60-minute link to *that* address; only `App\Actions\Users\ConfirmEmailChange` — reached by using the link — writes `users.email` and sets `email_verified_at`. The `if ($user->isDirty('email')) { $user->email_verified_at = null; }` branch is gone. **The rule above does not relax.** `users.email` alone still is not proof of anything (an administrator may create a user with an unverified initial address); what task 0003 guarantees is narrower and is exactly what the seeder relies on: **`users.email` together with a non-null `email_verified_at`** means the address was proven, because no *change* to `users.email` can land without its own verification link being used. Keep the `whereNotNull('email_verified_at')` in the lookup. See [architecture/authentication.md](architecture/authentication.md#pending-email-changes).

## Gherkin scenarios written with a generic "I" and bundled multi-action steps — 2026-07-21

- **Context**: `product-owner` agent writing the first project-level PRD (`docs/PRD/PRD.md`), covering five epics with Gherkin scenarios per capability.
- **What happened**: several scenarios used a generic, roleless `Given I have permission to manage products` / `When I create, rename, and delete...` style — no named business-role actor, and multiple distinct actions (create + rename + delete) bundled into a single scenario instead of one scenario per action.
- **Root cause**: `docs/workflow.md`'s User Story template shows a bare `Given <context> / When <action> / Then <expected result>` Gherkin skeleton with no actor or single-action guidance. This project already had the right rules written down — rule 1 ("Imperative vs. declarative scenarios", which models good examples as third-person business-role actors like "a registered user", never "I") and rule 3 ("Single When per scenario") in [testing/frontend/gherkin-guidelines.md](testing/frontend/gherkin-guidelines.md#1-imperative-vs-declarative-scenarios) — but that file frames itself as a browser-test-translation guide, and nothing in `workflow.md` or the `product-owner` agent definition pointed there when writing PRD/User-Story-level Gherkin, so the existing rules weren't applied outside `tests/Browser/`.
- **Fix applied**: rewrote every scenario in `docs/PRD/PRD.md` to open with a named business-role actor (e.g. `Given a catalog administrator`, not `Given I ...`) and to cover exactly one action per scenario, splitting bundled CRUD scenarios into one scenario per operation (e.g. "Create a product category" / "Rename a product category" / "Delete a product category" instead of one scenario doing all three). Added a cross-reference from `docs/workflow.md`'s User Story template to `testing/frontend/gherkin-guidelines.md`.
- **How to avoid it next time**: [testing/frontend/gherkin-guidelines.md](testing/frontend/gherkin-guidelines.md)'s rules 1 and 3 apply to **every** Gherkin scenario written in this project, not just browser-test translations — PRDs (`docs/PRD/`) and per-task User Stories (`ai-spec/tasks/`) included. Before writing or reviewing any scenario: open with a named business-role actor (`a catalog administrator`, `a store customer`, never `I`), and if a scenario needs a second `When`, split it into two scenarios instead.
