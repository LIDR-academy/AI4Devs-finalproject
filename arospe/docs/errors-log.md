## GitHub Actions' Ubuntu runner ships `libheif` with no AVIF encoder, so Imagick silently wrote a 0-byte `.avif` — 2026-09-06

- **Context**: `feature-entrega2-ARP` branch, no story in progress — just pushing to GitHub after `sail artisan test` had reported the whole suite green locally.
- **What happened**: the same suite failed in the `tests` GitHub Actions workflow, with exactly one failure: `Tests\Unit\Actions\Media\GenerateImageConversionsTest > the generated .avif file is genuinely AVIF, asserted on the ISO-BMFF ftyp brand bytes` — `expect(substr($avifBytes, 4, 4))->toBe('ftyp')` got `''` instead. `substr()` of an empty/near-empty string returns `''`, so the real fact is that `$result['avif_path']`'s stored content was essentially **0 bytes** on the runner, not merely mis-formatted. `App\Actions\Media\GenerateImageConversions::__invoke()` never noticed anything wrong: `$disk->put($avifPath, $image->encode(new AvifEncoder)->toString())` writing an empty string still returns `true`, so the `?: throw new RuntimeException(...)` guard next to it (see [conventions/base-standards.md](conventions/base-standards.md), story 0019 Phase 4 finding F-3) never fires — an empty write and a successful write are indistinguishable to that check.
- **Root cause**: since a recent GitHub-hosted Ubuntu runner image update, `libheif` ships with AVIF **decode** support only — its AVIF **encoder** plugins (`libheif-plugin-aomenc` for the AV1/libaom codec, and siblings) were split into separate packages that Ubuntu does **not** install by default, confirmed against [actions/runner-images#13728](https://github.com/actions/runner-images/issues/13728) (closed by GitHub as "not planned" — this is accepted upstream behavior, not a transient outage). Imagick therefore still *registers* AVIF as a known format (an `extension_loaded('imagick')`/`Imagick::queryFormats('AVIF')` check would report success) but silently produces an empty blob the moment it actually tries to **encode** one, rather than throwing. This project's own Sail image (`docker/8.5/Dockerfile`) installs `php8.5-imagick` via a plain `apt-get install`, which pulls the AVIF encoder plugin in as a `Recommends` dependency — so the encoder has always been present locally, and this gap was invisible until the first real CI run exercising it. It is the same underlying codepath, but a different mechanism, from [the 2026-08-28 Imagick resource-limit entry](#an-imagick-resource-limit-was-requested-in-the-wrong-unit-masked-by-the-hosts-own-policyxml-silently-clamping-it--2026-08-28) — that one was a wrong resource-limit *unit* masked by a stricter local `policy.xml`; this one is a missing *codec* on the CI host that Sail's own `apt-get install` happens to satisfy as a side effect nobody asked for.
- **Fix applied**: added an `Install libheif AVIF encoder plugin` step to [`.github/workflows/tests.yml`](../../.github/workflows/tests.yml) (`sudo apt-get update && sudo apt-get install -y libheif-plugin-aomenc`), placed immediately after the existing `Setup PHP` step (which already carries the `extensions: imagick` correctness input from story 0019 — see [testing/ci/pipeline-integration.md](testing/ci/pipeline-integration.md)) and before `Run Tests`, so both matrix legs (PHP 8.4 and 8.5) get the encoder before any test runs. The step is deliberately independent of `Setup PHP`'s own extension-resolution mechanism (`shivammathur/setup-php`), since the missing piece is a system library plugin, not a PHP extension.
- **How to avoid it next time**: **when a test that decodes or encodes through a system-library-backed format (an image/video codec, a font renderer, a compression algorithm) passes under Sail but fails only in CI, suspect the underlying system library the extension links against before suspecting the test or the application code — and check decode and encode as two separately-installable capabilities, not one.** A format being *registered* (`queryFormats()`, `extension_loaded()`) proves nothing about whether every operation on it is wired to a real codec; only exercising the actual operation (as this project's own byte-signature assertion already does, per [security/image-upload-processing.md](security/image-upload-processing.md)) catches the gap. This is the **second** Imagick/AVIF-specific CI-vs-local environment mismatch on this exact codepath in two weeks — a future change touching `GenerateImageConversions` or its CI step should treat "verify on a real GitHub Actions run, not only Sail" as a standing requirement for this one action, not a one-off diagnostic.

## `DB::transaction($fn, attempts: N)` retried a closure that mutated a model created outside it, producing a silent lost update reported as success — 2026-09-04

- **Context**: story 0029 (product variants — core backend). The same remediation that added `product_variants`' cross-table SKU-collision locking also added `attempts: 3` to three `DB::transaction()` calls (`CreateProduct`, `CreateProductVariant`, `UpdateProduct`), so the fixed lock order those transactions rely on converges under a real deadlock instead of 500-ing on the first collision.
- **What happened**: `appsec-auditor`'s Phase 4 re-audit — re-auditing the fix as new code, per the entry below on this same log — reproduced that `UpdateProduct`'s own retry was unsafe. Its closure captures `$skuChanged = $product->sku !== $sku` and then calls `$product->update([...])`, where `$product` is an `Eloquent` model **created outside the closure** and passed in as a parameter. Executed rather than reasoned about: on attempt 1, `update()` runs and `syncOriginal()` fires; on attempt 2 (after a rollback from a genuine `1213` or, far more likely, a `Lock wait timeout exceeded`), `$product->sku !== $sku` now reads `false` and `isDirty()` after `fill()` also reads `false` — so `update()` issues **no SQL at all**, the SKU re-derivation cascade is skipped entirely (`$skuChanged` gates it), and the action **returns a `Product` whose in-memory attributes show the new values** while nothing was actually written or rolled forward. A silent lost update, reported to the caller as a success. `App\Actions\Products\SyncProductGallery` shares the exact same shape (`forceFill(...)->save()` on the same outside-the-closure instance), so the featured-image/gallery write is lost with it.
- **Root cause**: `attempts: N` makes the closure **retryable**, and a retry restores the database to its pre-attempt state but does **not** reset any PHP object the closure mutated on a prior attempt — `Model::update()`/`save()` calls `syncOriginal()` on success regardless of whether the surrounding transaction later rolls back, so a second attempt reads its own first attempt's dirty-tracking as the baseline and silently no-ops. This is invisible by construction: `save()` on a model with nothing dirty is a **successful** no-op, not an error, so nothing throws and nothing logs. The two other `attempts: 3` sites in the same remediation (`CreateProduct`, `CreateProductVariant`) do **not** have this problem, because both build the row they mutate **inside** the closure via `forceCreate()` — a retried attempt there re-does real work rather than skipping it, the distinguishing property that makes `attempts: N` safe on one sibling and unsafe on another that looks identical from the outside.
- **Fix applied**: `UpdateProduct`'s `DB::transaction()` call now takes **no** retry parameter at all, with a comment above it naming this hazard so nobody re-adds `attempts: N` without re-deriving the analysis first — see [`app/Actions/Products/UpdateProduct.php`](../app/Actions/Products/UpdateProduct.php). The alternative fix considered and rejected was the key-passing shape `App\Actions\SalesRegions\SetSalesRegionActive` already established (pass **keys** into the closure, re-fetch every row the closure mutates from inside it, on every attempt) — not adopted here because `UpdateProduct` returns the caller's own `$product` instance and its cascade reads `$skuChanged` from a pre-mutation attribute, so re-shaping the action's return contract to close this window costs more than removing the retry outright. Full reproduction, the executed before/after table, and a second, coupled finding (`attempts` is silently inert on a **nested** `DB::transaction()` — only the outermost transaction's `attempts` ever fires, so `App\Livewire\Products\Editor::save()`'s own outer transaction, once story 0031 ships it, must **not** get an `attempts:` of its own without first fixing this same closure shape one level up) are in [security/derived-column-invariants.md](../security/derived-column-invariants.md#what-the-remediation-introduced-a-retried-transaction-is-a-retry-safe-unit-or-it-is-a-lost-update).
- **How to avoid it next time**: **adding `attempts: N` to a `DB::transaction()` call is a change to the closure's contract, not a flag — before adding it, check that every model, collection or accumulator the closure writes to was either created *inside* it or is re-fetched by key at the top of it, on every attempt.** The two safe shapes in this codebase: build/insert the row inside the closure (`forceCreate()`/`create()`, as `CreateProduct`/`CreateProductVariant` do), or pass primitive keys into the closure and re-read every row from the database as the closure's own first statement (as `SetSalesRegionActive` does). An Eloquent model instantiated *outside* the closure and mutated *inside* it is the common, easy-to-miss case, and it fails **silently** rather than loudly — there is no exception to catch, because a non-dirty `save()` is defined to succeed.

## An action's own parameter default reintroduced the omission ambiguity its stricter collaborator was built to close — 2026-09-01

- **Context**: story 0024, `App\Actions\Products\CreateProduct`/`UpdateProduct` wrapping `App\Actions\Products\SyncProductGallery` — the single writer of `products.featured_media_id` and every `product_media` row, whose own contract (D-17) is deliberately strict: the ordered gallery array it receives is the **complete, authoritative** new state, never a delta, so an omitted id is a detach and an empty array is "clear the whole gallery".
- **What happened**: the first implementation gave `CreateProduct`'s/`UpdateProduct`'s `$featuredMediaId`/`$orderedGalleryMediaIds` parameters ordinary PHP defaults (`= null`, `= []`) — the reflexive shape for "this field is optional". `appsec-auditor`'s Phase 4 audit round 1 flagged it as **F-1** (Medium): any caller that simply omitted the two arguments — a future queued job, a partial form submit, a test written before the gallery UI existed — would reach `SyncProductGallery` with an empty array and a `null` featured id, silently detaching every existing image and nulling the featured image, with no error and no way to distinguish "the caller meant to clear the gallery" from "the caller never mentioned it". The re-audit found the identical shape a second time (**F-6**) on `UpdateProduct`'s `$description` parameter, which had kept `CreateProduct`'s `= null` default even though the two actions are not equivalent for that field: on **create**, omitting `description` and "no description" are the same real state (a brand-new product genuinely starts empty), so the default is safe there and was deliberately kept; on **update**, omitting it does not mean "clear the description" — it usually means the caller never touched that field — so the identical-looking default silently wipes an existing description on a partial-field update.
- **Root cause**: `SyncProductGallery`'s whole design point is that **omission from its input is a decision, never left ambiguous** — that is what "complete, authoritative array" means. A default on the *wrapping* action's own signature reopens exactly the ambiguity the stricter collaborator exists to remove, one layer closer to the real caller: the collaborator can no longer tell "the actor explicitly submitted an empty gallery" from "the actor never mentioned the gallery at all", because both now produce the identical call. The `$description` case shows the same root cause without any collaborator in the picture at all — a full-replacement field on an **update** path has the identical property (omission from the payload is ambiguous between "clear it" and "leave it"), so the rule is not really about `SyncProductGallery` specifically.
- **Fix applied**: both `CreateProduct` and `UpdateProduct` now require `$featuredMediaId`/`$orderedGalleryMediaIds` with **no default** — a caller must always state intent, matching `SyncProductGallery`'s own contract. `UpdateProduct`'s `$description` parameter lost its `= null` default (F-6); `CreateProduct`'s keeps it, deliberately, with a docblock recording *why* the two actions are allowed to differ on this one parameter. See [`app/Actions/Products/CreateProduct.php`](../app/Actions/Products/CreateProduct.php) and [`UpdateProduct.php`](../app/Actions/Products/UpdateProduct.php).
- **How to avoid it next time**: **a default is safe on a parameter only when omitting it and the default's own value denote the *same real-world state* for every call site that will ever use it — never merely "this field is optional" as a convenience.** Two concrete checks. **(a)** When an action wraps a collaborator whose contract treats its input as complete and authoritative (a full-replace `sync()`, an ordered array, any "this is everything" shape), the wrapping action must not supply a default for the parameter it forwards — the collaborator's own strictness is undone the moment something upstream of it can omit the value silently. **(b)** On an **update** path specifically, a default that was correct on the matching **create** action does not transfer by symmetry — "no value yet" (create) and "value not being touched" (update) are different states, and only the first one is safely represented by a default. This is [the "absence in a payload from a partially-visible form is not a decision" family](#a-guard-took-the-state-it-was-guarding-as-a-parameter-reopening-its-own-hole-one-level-up--2026-08-20) arriving from a new direction: there the ambiguity lived in the *payload a partially-visible UI form submits*; here it lives one layer lower, in the *action's own parameter defaults*, with no form or UI involved at all.

## An absolutely-positioned element with no explicit `top` takes its static position from DOM order, and can silently occlude a sibling — 2026-08-31

- **Context**: story 0022 (shared searchable multi-select component), building the results dropdown in [`resources/views/livewire/components/searchable-multi-select.blade.php`](../resources/views/livewire/components/searchable-multi-select.blade.php). The dropdown is `position: absolute` (D10's forced manual-popover shape — see [the debounce entry below](#a-livewire-directive-modifiers-duration-cannot-be-interpolated-as-part-of-a-component-tags-attribute-name--2026-08-31) for that deviation's own story) and carries no explicit `top-*` utility, relying on document flow for its offset — the same `mt-1`-only shape `wysiwyg-editor.blade.php`'s own link popover already uses.
- **What happened**: while the dropdown block was written directly after the search `<flux:input>` and before the chip row, opening it with any rendered height at all — including just the empty-state message — visually and interactively covered the chip row beneath it. `Livewire::test()` and the whole component-level Feature suite stayed green throughout, because neither ever renders real CSS; the defect surfaced only in a real browser test, as a Playwright click on a chip's remove control hanging until the tool's own actionability timeout — no PHP error, no console error, no failed HTTP request anywhere to point at.
- **Root cause**: `position: absolute` removes an element from normal flow for layout purposes, but its **static position** — the position it would have occupied had it stayed `static` — is still derived from DOM order, and nothing in this markup ever overrode that with an explicit `top`. The dropdown and the chip row are siblings; because the dropdown appeared first in source order, its static-position offset placed it directly over the chip row the moment it had any height, silently occluding the remove buttons underneath. `document.elementFromPoint()` at a chip's own remove-control coordinates returned the dropdown's empty-state `<div>`, not the button — confirmed by direct browser reproduction, the identical diagnostic the [`disabled:cursor-not-allowed` entry](errors-log-archive.md#disabledcursor-not-allowed-on-a-flux-button-was-never-the-cursor-the-user-saw--2026-08-16) further down this log already used to find a different DOM-vs-markup mismatch.
- **Fix applied**: the dropdown block in `resources/views/livewire/components/searchable-multi-select.blade.php` was moved to render **after** the chip area in source order, with no CSS change at all — the fix is purely a reordering, because it is the static-position fallback that moved. An inline comment above the dropdown records the exact failure (including the `elementFromPoint()` result) and forbids moving it back "for readability" without re-verifying.
- **How to avoid it next time**: **an absolutely-positioned element with no explicit `top`/`left` takes its placement from where it sits in the DOM, not from where it visually appears to sit relative to a sibling — fix an occlusion like this by reordering the markup, not by reaching for a `top` value, unless the offset genuinely needs to vary at runtime.** More generally: **when a real-browser click hangs on Playwright's own actionability timeout with no error anywhere in the stack, suspect occlusion before suspecting a broken handler** — `document.elementFromPoint()` at the target control's real on-screen coordinates is the fast, direct way to find out what the browser actually thinks is on top, and it is a diagnostic a `Livewire::test()`-only suite structurally cannot run. This is the same "the DOM's own ground truth disagrees with what the markup intends" lesson the `pointer-events`/`tooltip`-presence entries below already establish, arriving here through document flow instead of a Flux prop.

## A Livewire directive modifier's duration cannot be interpolated as part of a component tag's attribute NAME — 2026-08-31

- **Context**: story 0022, wiring `$debounceMs` (a per-consumer configurable prop, default 300) into the search input's debounce. The obvious form is `wire:model.live.debounce.{{ $debounceMs }}ms="search"`, mirroring the literal `wire:model.live.debounce.300ms` this app already uses elsewhere.
- **What happened**: `code-reviewer`'s Phase 2 INVEST review (finding B1) caught the shape before Phase 3 wrote real code around it — but it is worth recording because the *shape itself* had already been silently worked around twice, undocumented: [`resources/views/livewire/media/gallery.blade.php`](../resources/views/livewire/media/gallery.blade.php) hard-codes a literal `wire:model.live.debounce.300ms`, and [`resources/views/livewire/components/wysiwyg-editor.blade.php`](../resources/views/livewire/components/wysiwyg-editor.blade.php) sidesteps the whole shape by debouncing through a hand-rolled Alpine `setTimeout()` instead. Neither prior file states *why* a dynamic duration was avoided; story 0022's own implementation is the first to write the reason down, in [`resources/views/livewire/components/searchable-multi-select.blade.php`](../resources/views/livewire/components/searchable-multi-select.blade.php)'s file-banner comment.
- **Root cause**: Blade's `ComponentTagCompiler` parses a component tag's attribute **names** with the regex `[\w\-:.@%]+`, which does not include `{`, `}` or `$` — so an interpolated `wire:model.live.debounce.{{ $debounceMs }}ms` attribute *name* is not a shape `compileComponentTags()` can parse at all, because that compiler runs before Blade's own `{{ }}` echo compiler ever sees the string. This is a **different** failure from the three `livewire/blaze` attribute-*value*-folding traps already in this log (the bare-`@disabled`, the conditionally-bound `tooltip`, and the two-`@directive()` entries below): those are about a value not compiling correctly inside a folded Flux tag; this is about a dynamic segment inside the attribute's own **name**, which no Blade component tag — Flux-folded or not — can ever parse, because the tag compiler never gets as far as evaluating anything for a name it cannot even tokenize.
- **Fix applied**: `resources/views/livewire/components/searchable-multi-select.blade.php` uses a plain (non-`.live`) `wire:model="search"` for deferred binding, plus a hand-rolled Alpine `x-on:input="clearTimeout(searchDebounceTimeout); searchDebounceTimeout = setTimeout(() => $wire.set('search', $event.target.value), {{ $debounceMs }})"` — the same debounce mechanism `wysiwyg-editor.blade.php` already established, now stated as the *reason* rather than merely followed. `{{ $debounceMs }}` interpolates cleanly here because it sits inside an ordinary attribute **value** (`x-on:input="..."`), the shape Blade *does* compile correctly throughout this file — the file's own banner comment states the distinction explicitly so a future reader does not "fix" the working value-interpolation back into the broken name-interpolation form for consistency.
- **How to avoid it next time**: **a `wire:*.debounce.Xms`-style Livewire directive *modifier* is part of the attribute's name, and a value that must vary per consumer (a prop, not a compile-time constant) cannot be interpolated into it — reach for a hand-rolled Alpine `setTimeout()` + `$wire.set(...)` instead**, the mechanism `wysiwyg-editor.blade.php` already established, and write the reason into a comment rather than leaving the next reader to rediscover it by trial and error. This generalizes past debounce: **any Livewire directive whose configuration lives in its modifier chain (`.debounce.Xms`, `.throttle.Xms`, …) is fixed at compile time and cannot vary per component instance** — a literal duration works, a property never will.

## A bare `@disabled(...)`/`:disabled="..."` inside a `<flux:button>` tag's attribute list corrupts the whole compiled view — 2026-08-31

- **Context**: story 0021 (shared WYSIWYG rich-text editor), building the eight-button toolbar in [`resources/views/livewire/components/wysiwyg-editor.blade.php`](../resources/views/livewire/components/wysiwyg-editor.blade.php). It corrupts the tag's **whole** attribute string into invalid PHP, which is a PHP **syntax error** that breaks the entire compiled view — not merely that one button's disabled state, and not a silent mis-render like the two traps immediately below. - **Root cause**: `livewire/blaze` (already implicated in the two entries directly below this one) folds `@blaze`-annotated Flux components at compile time, and its component-tag compiler parses a tag's raw attribute list **before** the general Blade directive pass runs. `@disabled(...)`/`:disabled="..."` written as if it were an ordinary attribute is not a form that parser tolerates inside a folded tag — it does not resolve to a conditional `disabled=""` the way it would on a native HTML element; it corrupts the compiled attribute string outright.
- **Fix applied**: every one of the toolbar's eight controls in `resources/views/livewire/components/wysiwyg-editor.blade.php` is written as a full `@if ($disabled) <flux:button ... disabled /> @else <flux:button ... x-on:mousedown.prevent="..." /> @endif` pair — two complete, separately-compiled tags — rather than one tag carrying a conditional `disabled` attribute. - **How to avoid it next time**: **in this codebase, never write a bare `@disabled(...)` directive directly inside a `<flux:*>` component tag's attribute list — branch the whole tag with `@if`/`@else` instead**, exactly as the `tooltip`-presence trap and the `cursor-not-allowed!` placement rule immediately below already establish for other props on the same kind of tag. This one is easier to catch than its two siblings only because it throws outright rather than silently mis-rendering — but only for whoever renders the page first, which in an untested branch may be a real user.

- **Root cause — as recorded at the time, and now known to be wrong; see the correction below**: minimally reproduced outside this story's own markup — `<x-button wire:click="foo(@js($id), @js($flag))" />` against a trivial `<button {{ $attributes }}>` component renders the attribute unprocessed, verified via `Blade::render()`. The conclusion drawn was: *a single `@directive(...)` call inside a Blade component tag's plain attribute string compiles correctly; two of them in the same attribute value do not*, attributed to `ComponentTagCompiler::getAttributesFromAttributeString()` regex-scanning the raw attribute string before the general compiler pass runs. That framing also required a carve-out for this repo's own `x-show="matchesFilter(@js(...), @js(...))"` on a `<flux:table.row>`, which has two and works — and the carve-out was a hedge ("not a value fed into the component tag's own attribute list the same way") rather than a mechanism, which is the tell. **What is not in doubt, and is the whole practical content of this entry:** the conversion really did make every row toggle a silent no-op in a real browser, reverting to `{{ \Illuminate\Support\Js::from(...) }}` really did fix it, and a `{{ }}` echo compiles in every shape tested.
- **Fix applied**: reverted the three converted `wire:click="setActive(...)"` attributes in [`resources/views/livewire/sales-regions.blade.php`](../resources/views/livewire/sales-regions.blade.php) to `{{ \Illuminate\Support\Js::from(...) }}` (the pre-existing, proven-correct form), each with an inline comment recording the finding so a future pass doesn't "fix" them back to `@js()` for consistency a second time. `openEditModal(@js(...))` and `setDefault(@js(...))` — each carrying exactly **one** `@js()` call — were left unchanged; they were never the problem.
- **How to avoid it next time**: **prefer `{{ }}` echo expressions over `@directive(...)` calls for any dynamic value inside a Blade *component tag* attribute** (`<x-foo attr="...">`, `<flux:foo attr="...">`) — the correction below narrows *why* (the count is not the discriminator, and an anonymous `<x-…>` tag is the shape that provably breaks), but the safe form is unchanged and is what the repo ships. > | Shape | Result |
> | --- | --- |
> | `<flux:switch wire:click="setActive(@js($region['id']), @js(! $region['isActive']), '')" />` — **the exact shipped expression**, two `@js()`, array subscripts, leading `!` | **compiles**, both paths → `wire:click="setActive('ID1', true, '')"` |

Neither half of "one is fine, two are not" survives, and the hedge about `x-show` was explaining something that never needed explaining. **What made the shipped screen go dead is therefore not established**, and it is deliberately not being guessed at here — the broken state was never committed (the Phase 5 commit contains the comment and the already-reverted markup, so `git show` cannot reconstruct it), and this project's own [hedge rule](#a-reviewers-correction-replaced-an-accurate-technical-explanation-with-a-wrong-one-unverified--2026-08-24) says an unverified mechanism written up confidently is worse than an open question written up plainly.
>
> **What survives unchanged, and is what to act on:** the incident, the symptom (a silent no-op with no PHP error, no console error and no failed request), the fix, and the two rules in the bullet above — prefer `{{ }}` echoes for dynamic values in a component-tag attribute, and **verify the compiled output rather than the absence of an error** before trusting any attribute-syntax cleanup. - **Context**: no story — routine iteration on the full Pest suite from two separate Claude Code sessions on 2026-08-24, one running `./vendor/bin/sail artisan test` directly and one dispatching a `backend-expert`/`backend-qa` pair to run "revert-checks + full suite".

Documented the per-checkout requirement, and the further requirement that **each `git worktree` needs its own database name** (`testing1`, `testing2`, …) since all worktrees share one MySQL container, in [testing/worktree-databases.md](testing/worktree-databases.md).
- **How to avoid it next time**: **a database-flag whose safety depends on a file that might not exist is not a guardrail — verify the fallback path, not just the happy path, before trusting a `--env=` / `--database=` flag to isolate anything.** For this specific gap: never run `artisan migrate:fresh` (or any other destructive artisan command) against `--env=testing` without first confirming `.env.testing` exists and points somewhere other than the shared dev database — `cat .env.testing | grep DB_DATABASE` before the destructive command, not after. Two corollaries for anyone opening a new worktree: read [testing/worktree-databases.md](testing/worktree-databases.md) before running tests there, and if a suite run ever fails with a symptom that looks like "the schema is stale/corrupted", treat that as a signal to check *which* database actually received the last `migrate:fresh` before running another one — the diagnosis in this incident was right, but nobody checked which database the fix would land on.

## A reviewer's "correction" replaced an accurate technical explanation with a wrong one, unverified — 2026-08-24

- **Context**: story 0015a's Phase 5 code review. `code-reviewer` flagged Larastan level 7 failing on `App\Livewire\Users\Index::isAdministratorRoleSelected()`'s `isset($this->roleId)` check (finding F-1), and in the same finding challenged the *docblock's* explanation of why the check is needed — it said a forged `->set('roleId', null)` leaves a direct `$this->roleId` read throwing `Livewire\Exceptions\PropertyNotFoundException`, and the reviewer called this "likely wrong for a public typed property with a default value", without executing anything to confirm.

- **Fix applied**: a third review pass verified the real mechanism by execution and the docblock in `app/Livewire/Users/Index.php` was corrected back to the accurate explanation (no reflection; `PropertyNotFoundException` via `Component::__get()`/`__isset()`), with a note recording that a Phase 5 pass previously replaced it with a wrong one. This is a case of the review process itself introducing a defect that the original text did not have — worth watching for specifically when a review's fix is to *documentation or a comment* rather than to behaviour, since no test can catch a wrong sentence the way `phpstan`/`pest` catch a wrong `if`.

- **Fix applied**: the whole file was rewritten before any code was written (commit `66a5b88`), with every surviving finding re-verified by reading the real file at `HEAD` and each disposition recorded in a new **"What re-verification changed"** table — F4 halved, F7 re-scoped, F8's instruction explicitly *withdrawn* in writing with the errors-log entry it would have violated cited inline, F10 re-scoped to the ordering with a no-mail-on-rollback constraint, F12 recorded as **closed by 0008a and dropped**, F17 reduced to its test half, F13 split out to its own story `0015a`, F18 deferred by human decision. The line numbers it kept are labelled a reading aid, with Phase 3 required to re-locate each site.
- **How to avoid it next time**: **before a deferred story enters Phase 3, re-verify every finding it carries against `HEAD` by opening the file it cites — and record the disposition of each, including "already closed", in the task file itself.** Four concrete habits. **(a)** Write a finding as the **property that must hold**, never as the patch that would have held it; a patch is only valid against the tree it was written on, and there is no way to tell from reading it. **(b)** Treat a line number in a stored task as a reading aid, never a locator — if the cited line does not contain what the finding describes, the finding is stale until proven otherwise, not merely misnumbered. **(c)** When a deferred instruction contradicts something already in `docs/` — this log, a security page, a convention — **the docs win and the instruction is withdrawn in writing**, so the next reader sees a decision rather than an omission. **(d)** Record the closed findings rather than deleting them; "F12 was closed by 0008a" is the sentence that stops it being re-raised by the next audit. This is a fourth direction of the drift family this log already tracks — [a doc outliving the feature it denied](errors-log-archive.md#a-docs-this-app-has-no-x-yet-claim-outlived-the-x-by-two-tasks--2026-08-13), [a doc outliving the bug it described](#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20), [code drifting from a rule the doc still states correctly](#wrapping-existing-code-in-a-dbtransaction-moved-a-cache-flush-nobody-had-written--2026-08-21) — and the one with the longest fuse, because a backlog item can sit stale for months while looking exactly as authoritative as the day it was filed.

## Wrapping existing code in a `DB::transaction()` moved a cache flush nobody had written — 2026-08-21

- **Context**: task 0012 (module/sidebar access gating). Its Phase 4 audit re-read `App\Livewire\Roles\Index` because the story's cache-staleness tests exercise it, and found a Medium in code the story neither wrote nor changed. The rule it violates has been documented on this project's own security pages since task 0002 — [security/authorization-patterns.md](security/authorization-patterns.md#flush-the-permission-cache-after-the-transaction-commits-never-inside-it), *"Flush the permission cache after the transaction commits, never inside it"* — complete with the ✅ two-flush code shape and the reason (`config/permission.php` caches the whole roles+permissions graph for 24 hours on the **shared** `database` store).
- **What happened**: `saveRole()` and `deleteRole()` shipped with the ❌ shape that page names — the permission cache flushed only *inside* their `DB::transaction()`, never after the `COMMIT`. On the shared store this fails **open** on a revocation: a concurrent request landing in the window between the in-transaction flush and the commit misses the cache, reads the pre-commit rows, and re-caches the escalated grant for 24 hours. It survived story 0010's three-round Phase 4 audit, the whole of story 0011, and a Phase 5 code review of each.
- **Root cause**: **the flush at issue was never written by this repo.** Neither method contains a flush the author chose to place; `syncPermissions()` fires one internally, and `App\Models\Role`'s `deleted` event fires the other. Both were correctly post-commit until story 0010's own Phase 4 finding F4 — an unrelated atomicity concern ("a failure between the rename and the permission sync must not leave a role persisted with the wrong set") — wrapped the existing statements in `DB::transaction()`. That wrapper relocated a side effect **with no flush line appearing, moving or disappearing anywhere in the diff**, so a reviewer grepping the change for `forgetCachedPermissions` found nothing and correctly concluded there was nothing to check. Compounding it, the regression is untestable by construction: `phpunit.xml` pins `CACHE_STORE=array`, making the permission cache per-process in tests, so the suite was 618/618 green with the window wide open — and stays 618/618 green today if either fix line is deleted.
- **Fix applied**: `app(PermissionRegistrar::class)->forgetCachedPermissions()` added immediately after each `DB::transaction()` call in [`app/Livewire/Roles/Index.php`](../app/Livewire/Roles/Index.php) (commit `0a53acb`), each under a multi-line comment naming the finding and linking the rule — the mitigation for a fix no test can pin, matching `RolePermissionSeeder`'s identical precedent. The security page now also carries the three real call sites and the generalized ⚠️.
- **How to avoid it next time**: **adding a `DB::transaction()` around existing code is a change to every side effect that code already performed — audit each of them, including the ones the diff does not show.** Vendor calls are exactly where this bites, because their side effects are invisible at the call site: a cache flush, an event dispatch, a queued job, a broadcast, a `Storage` write, or a mail send that was outside a transaction is now inside one, and each has its own correct side of the commit. Two habits. **(a)** When a finding's remedy is a *wrapper* rather than a new statement, list what the wrapped code calls and what each of those does beyond returning — this is the cheapest form of the "[audit the remediation as new code](errors-log-archive.md#two-of-the-three-security-audit-rounds-found-the-flaw-in-the-previous-rounds-fix--2026-08-19)" rule already recorded below, applied to the one shape where the diff itself hides the change. **(b)** Before writing the fix, grep `docs/security/` for the call you are about to move — the rule broken here was already written down, with the correct code, on a page the breaking story cited for other reasons. This is the third direction of the doc/code drift family this log records: [a doc outliving the feature it denied](errors-log-archive.md#a-docs-this-app-has-no-x-yet-claim-outlived-the-x-by-two-tasks--2026-08-13), [a doc outliving the bug it described](#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20), and now **code drifting away from a rule the doc still states correctly** — the only one of the three that a re-read of the doc cannot catch, because the doc is not wrong.

## A count-based assertion over rendered HTML counted a wrapper element it never meant to include — 2026-08-21

- **Context**: task 0011 (Roles & permissions UI). Its Phase 4 security audit established a rule worth keeping — that a **presence** assertion ("this permission's checkbox is still there") cannot catch a *second*, unrelated checkbox also going missing, so the regression test for "the catalog renders in full except one withheld value" must assert a **count**: rendered checkboxes == catalog size, minus exactly the withheld set. Two such tests were added to `tests/Feature/Roles/IndexUiTest.php`.
- **What happened**: both were written as `substr_count($html, 'value="')` — every `value="` attribute in the whole rendered page. Phase 5 flagged it (finding **F-4**) as correct only by coincidence: nothing *else* in the create/edit modal happens to emit that attribute today, so a future `flux:select` or hidden input would move the number with no real omission occurring. The obvious fix — scope it to the checkbox element — then walked into a second trap of its own: the Flux-rendered element is `<ui-checkbox …>`, but `flux:checkbox.group` also emits a `<ui-checkbox-group>` wrapper, whose opening tag **starts with the same string**. Counting `'<ui-checkbox'` therefore over-counts by exactly one, and does so silently: the number is off by a constant, so the test still passes or fails as a block and never looks wrong.
- **Root cause**: the assertion was designed from what the *Blade source* writes (`<flux:checkbox value="…">`) rather than from what the browser receives. Flux components are not one-to-one with their rendered output — a group renders a custom element of its own — and a substring count has no notion of element boundaries, so a child's tag name being a prefix of its parent's is invisible to it. The generic hazard is that a count assertion fails **quietly by a constant**: unlike a presence assertion, which is either satisfied or not, an over-count that is stable across runs reads as the true number and gets baked into whatever expectation makes the test green.
- **Fix applied**: both assertions rescoped to `substr_count($html, '<ui-checkbox ')` — with the **trailing space**, which is what excludes `<ui-checkbox-group` — after tracing the actual rendered markup rather than the stub (commit `48dbf54`). The expected values (`$catalogSize - 1` for a non-Super-Admin, `$catalogSize` for a Super Admin) are unchanged and were re-verified against the real render. The security rule the tests exist for is in [security/authorization-patterns.md](security/authorization-patterns.md#a-control-omitted-from-the-dom-is-safe-only-for-the-one-value-whose-guard-preserves-an-omission).
- **How to avoid it next time**: **a count assertion over rendered HTML must be scoped by a string that cannot match a sibling or wrapper element, and both the selector *and* the expected number must be read off the real rendered output before the test is trusted.** Three concrete habits. **(a)** Dump the HTML once and grep it, rather than deriving the selector from the Blade source — this repo's two 2026-08-16 Flux/Blaze entries below already establish that a Flux component's real output cannot be predicted from its stub, and the same holds for its element names. **(b)** When the selector is an element name, include the delimiter that ends it (`'<ui-checkbox '`, not `'<ui-checkbox'`); custom-element naming makes `<x>` a prefix of `<x-group>` routinely, and Flux's `*.group` components are the standing example. **(c)** Prove the count can be wrong: temporarily remove one item and confirm the number moves by exactly one. A count assertion that has never been observed changing is the same vacuous-coverage failure as [the `arch()` rule below](errors-log-archive.md#a-pest-arch-rule-over-an-array-of-namespaces-shipped-green-while-proving-nothing--2026-08-18), arriving through a different door.

## Both of this project's per-change quality gates are scoped by default, and both silently passed — 2026-08-20

- **Context**: task 0010 (Roles & permissions management — backend). The story's own code was implemented, tested and merged onto `feature-entrega2-ARP`; its Phase 4 security audit and Phase 5 code review then ran against that merged state.
- **What happened**: two independent gates that [conventions/base-standards.md](conventions/base-standards.md#quality-gates) names as mandatory reported success while the thing they exist to catch was present.
  - **The test gate.** Only the Roles-scoped tests were ever run (`php artisan test --filter=…`, which the same conventions page recommends as "the narrowest relevant test(s) first"). The **full** suite was not run once between the story's first merge and the Phase 4 re-audit — and when it finally was, `tests/Feature/Authorization/SuperAdminRoleConfigSourceOfTruthTest.php` was **red**, on a completely unrelated pre-existing test this story had broken.
  - **The formatting gate.** `vendor/bin/pint --dirty --format agent` — the exact command the conventions page mandates — reported clean while three test files carried real violations (`fully_qualified_strict_types`, `ordered_imports`). A plain `vendor/bin/pint --format agent` found them immediately. They reached Phase 5 as finding **F-1**, blocking.
- **Root cause**: the same one twice — **each gate's default scope is narrower than the change it is gating, and a narrowed gate reports "pass", not "not checked".** `--dirty` inspects only files with *uncommitted* changes, so it becomes a no-op the moment the work is committed: the more disciplined the committing, the less the gate sees. `--filter` inspects only the tests whose names match, so it can never observe a change's effect on the rest of the suite. Both are correct as *iteration* tools and both are wrong as *completion* gates, and nothing in their output distinguishes the two uses. The test failure additionally had two compounding causes, each individually invisible: story 0010's own holder-count guard applies to **every** role rather than only to the custom roles the story was about, and the developer's ambient `SUPER_ADMIN_EMAIL` provisioned a second, unaccounted-for Super Admin holder — the identical ambient-config sensitivity [the 2026-08-12 entry below](errors-log-archive.md#a-test-asserted-against-a-fixture-address-that-the-local-env-also-pointed-super_admin_email-at--2026-08-12) already names, in a test written before that entry existed.
- **Fix applied**: the Pint violations were fixed by an unscoped `vendor/bin/pint --format agent` run (commit `fcff6dd`, "style(roles): fix Pint violations and correct three stale docblocks"). [`tests/Feature/Authorization/SuperAdminRoleConfigSourceOfTruthTest.php`](../tests/Feature/Authorization/SuperAdminRoleConfigSourceOfTruthTest.php) gained `config(['auth.super_admin.email' => null]);` in its `beforeEach` (matching what `tests/Feature/Seeders/DatabaseSeederTest.php` already did) and an explicit `removeRole()` before the deletion its scenario is actually about, each with a comment naming the cause. [conventions/base-standards.md](conventions/base-standards.md#quality-gates) now distinguishes the iteration form of each gate from the completion form.
- **How to avoid it next time**: **a gate that takes a scope argument must be run twice — narrow while iterating, and unscoped before the work is declared done — and "the narrow run passed" is never evidence about anything outside its scope.** Concretely, before a story leaves Phase 3: run `vendor/bin/pint --format agent` (no `--dirty`) and `php artisan test` (no `--filter`), in that order, and treat those two runs — not the filtered ones — as the record. Two corollaries. **(a) `--dirty` is inversely coupled to commit hygiene**, so it fails hardest exactly when the workflow is being followed best; never let it be the last formatting check on a committed branch. **(b) A guard that a story adds "for its own feature" almost never applies only to that feature.** `guardAgainstHolders()` was specified as part of the roles-CRUD story and reads as scoped to it, but it is a model-event listener on `App\Models\Role` and therefore binds every role in every test in the repo. When a story registers a model event, an observer, a global scope, or middleware, the blast radius is the whole suite by construction — that alone is sufficient reason to run it.

## A planned test asserted a refusal by `verified`, a middleware that refuses nobody in this app — 2026-08-20

- **Context**: task 0040, moving `users.index` out of `routes/web.php` into its own `routes/users.php`. Phase 1's QA contribution specified one new test to guard the relocation: an unverified user hitting `route('users.index')` should be redirected to `route('verification.notice')`, so that hand-copying the `Route::middleware(['auth', 'verified'])->group(...)` block into a new file could not silently drop `verified`.
- **What happened**: Phase 3's red-test step wrote that test and it did not behave as a red test at all. Proven mechanically rather than argued: with `verified` temporarily removed from the new file's group entirely, the test's outcome was **bitwise identical** to the unmodified group — same 403 from `can:users.view`, same message. The assertion it was built on could never distinguish a correct relocation from one that had lost `verified`, so it was reverted rather than kept, and this story shipped with no new test at all.
- **Root cause**: `App\Models\User` does not implement `Illuminate\Contracts\Auth\MustVerifyEmail` — the import sits commented out at the top of [`app/Models/User.php`](../app/Models/User.php) — and Laravel's stock `EnsureEmailIsVerified` only acts when `$request->user() instanceof MustVerifyEmail`. That condition is `false` for every actor in this app, so `verified` is a **structural no-op on every route that carries it**; account usability is enforced at sign-in through `users.status` instead. None of that was newly discovered here: [architecture/authentication.md](architecture/authentication.md#account-status-and-activation) has stated it in one plain sentence since task 0007. The test was designed from the middleware's *name* and from the route group's *appearance*, and nobody opened the doc that already answered the question.
- **Fix applied**: no code change — the test was reverted and the story's "Tests to perform" section rewritten with a Phase 3 correction note recording why the case was dropped rather than left as dead coverage (`ai-spec/tasks/.../0040-move-users-route-to-own-file.md`). The four pre-existing HTTP-level tests in `tests/Feature/Users/IndexTest.php` (guest → login redirect, no permission → 403, permission → 200, Super Admin bypass → 200) already cover every outcome that actually holds, and re-running them unmodified *is* the regression check for a pure relocation.
- **How to avoid it next time**: **before writing a test that asserts a middleware refuses someone, confirm that middleware can refuse anyone in this app — a middleware being present on a route is not evidence that it is live.** The cheap proof is the one Phase 3 ran: delete the middleware, re-run the test, and see whether the outcome changes; if it does not, the test carries no signal no matter which way it is written. `verified` is the known dead one here and will stay dead until `User` implements `MustVerifyEmail`, so any future story that copies an `auth` + `verified` group into a new area file — task 0010's `routes/roles.php` is the next one — must not plan a `verified` test either. This is the same class as the vacuous `arch()` rule two entries below (an assertion that cannot fail is not coverage); the added angle is that the control under test may not exist at all, and that the answer was already written down in the doc that owns it — check [architecture/authentication.md](architecture/authentication.md) before designing an auth-middleware test case.

## A guard took the state it was guarding as a parameter, reopening its own hole one level up — 2026-08-20

- **Context**: task 0009, `App\Actions\Roles\EnforceAdministratorPermissionGrant` — the action that refuses a role-save payload newly granting `roles.manage-administrators` to anyone but the Super Admin. Three Phase 4 audit rounds; each round's findings were against the **previous round's fix**, not against the original implementation.
- **What happened**: round 1 found F1 — the guard only asked whether the submitted payload *contained* the protected permission. Since `Role::syncPermissions()` replaces a role's entire permission set, and story 0011's toggle is never rendered to a non-Super-Admin at all, a broad administrator editing an unrelated field on a role that legitimately held the permission submitted a payload **omitting** it, silently revoking a Super Admin's grant. The fix introduced a "before" snapshot so the action could diff. Round 2 then failed that fix: the snapshot arrived as a caller-supplied `array $currentPermissionNames` parameter (N2 — a caller asserting an untrue "before" makes a new grant look pre-existing), the two snapshots were normalised asymmetrically so the diff silently mismatched (N3), and the membership check did not flatten nested arrays/Collections the way `syncPermissions()`'s own vendor code does, proven live to bypass the guard entirely (N1). Round 3 passed, after one more: the replacement `?Role $role` parameter had shipped with a `= null` default, so a forgotten third argument at a future call site would silently mean "nothing is currently granted" (NR1).
- **Root cause**: two, compounding. (1) **The guard trusted its caller for the very state it existed to protect.** "What does this role currently hold" is the input the whole decision turns on; accepting it as a parameter makes the guard only as strong as every present and future call site. (2) **Each fix was reviewed against the finding it answered rather than as new code with its own attack surface** — the diff logic was read as "does this close F1?", and it did, so nobody asked where its *new* inputs came from. F1 itself had a third root cause worth naming separately: nothing in the payload distinguishes "the actor chose to remove this" from "the actor was never shown this", and a full-replace `sync*()` collapses the two.
- **Fix applied**: the `array $currentPermissionNames` parameter was replaced by `?Role $role` (nullable, **no default**), and [`app/Actions/Roles/EnforceAdministratorPermissionGrant.php`](../app/Actions/Roles/EnforceAdministratorPermissionGrant.php) now loads the "before" state itself with `$role->load('permissions')` — removing N2 and N3 structurally rather than validating around them. `normalizeNames()` applies the identical `Collection::make(...)->flatten()` pass `HasPermissions::collectPermissions()` uses, so no shape can be invisible to the check while still being honoured by the sync. F1's own resolution — *preserve* an omitted-but-already-granted permission rather than deny the request — was **not** derivable from the spec, and was decided by the human mid-audit (asked explicitly, chose preserve); the choice is recorded in the code's docblock, in [architecture/authorization.md](architecture/authorization.md#who-may-grant-a-permission--the-meta-rule-layer), and in the task file's implementation record. Both durable rules are in [security/authorization-patterns.md](security/authorization-patterns.md#a-full-set-sync-behind-a-partially-visible-form-must-preserve-what-the-actor-cannot-see).
- **How to avoid it next time**: three concrete rules. **(1) A guard must derive the state it guards, never accept it** — take the model and read it (`load()`, not `loadMissing()`), and treat any "current state" parameter in an authorization signature as the finding itself. **(2) The "audit the remediation as new code" rule from the entry below is not a one-off — it is now the observed norm.** Two consecutive stories have needed three Phase 4 rounds, each catching the previous round's own fix, so budget for the extra rounds rather than treating round 2 as a formality. What this story adds to it: the highest-risk remediation is one that introduces a **new input** (a parameter, a snapshot, a cache), because that input's provenance was never in scope for the original review. **(3) When a full-replace `sync*()` is driven by a form that shows the actor only part of the set, absence is not a decision** — diff both directions and authorize adding and removing separately, and when "preserve" versus "deny" is a product judgement rather than a security one, stop and ask the human instead of picking; an unrecorded choice reads as an oversight to the next auditor.
