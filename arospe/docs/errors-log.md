# Errors Log

A structured log of real mistakes made in this project and the concrete rule adopted to avoid repeating them. Not a general bug tracker — only entries that produced a lasting convention belong here.

## Entry format

Newest entry first, directly below this line. Every entry uses this exact structure:

```markdown
## <short problem title> — <YYYY-MM-DD>
- **Context**: what was being worked on
- **What happened**: observed symptom/error
- **Root cause**: why it happened
- **Fix applied**: what changed, with a file path or commit/PR reference
- **How to avoid it next time**: a concrete, actionable rule — link to a `conventions/` doc if one covers it
```

## One docs pass reported two gaps that were not there, both marked "verified" — 2026-08-29

- **Context**: story 0019's Phase 6 (`docs-keeper`). The pass went looking for what the story had missed — a good instinct, and the one this log's own [bare-negative-claim entry](#a-docs-this-app-has-no-x-yet-claim-outlived-the-x-by-two-tasks--2026-08-13) asks for. It reported two findings, framed them as this doc set's sharpest, and marked each as checked against the tree rather than reasoned about. **Neither gap existed.**
- **What happened**: both false claims shipped, spread across four pages, and stood for a whole story until story 0020's Phase 2 INVEST review read the docs as prerequisites and noticed they contradicted the code it was about to extend. (Phase 2 caught the first; this Phase 6 pass found the second while verifying the correction to the first.)
  1. **"`App\Actions\Auth\LogRefusedPrivilegedAttempt` appears nowhere in `app/Livewire/Media/` or `app/Actions/Media/` — verified by grep at this story's Phase 6, not assumed."** `Gallery.php` imports it and calls it twice; `StoreUploadedImage.php` uses it too. Both files carry comments naming *this very docs finding* as the reason (`Phase 6 docs-keeper finding: …`) — so the finding was real when raised, it was acted on, and only the write-up was never revisited.
  2. **"`media` shipped without its `roles.modules.media` translation leaf, so the Roles permission matrix renders the raw key in both locales"** — presented as this page's long-predicted ❌ finally arriving for real. `lang/en/roles.php` has `'media' => 'Media'` and `lang/es/roles.php` has `'media' => 'Medios'`, both in story 0019's own tree, both untouched since. This one was never true at any point.
- **Root cause**: four things, and the first two are what make this a *pair* rather than one slip.
  - **A pass hunting for gaps grades its own findings on how sharp they are, not on whether they hold.** Both were written up as the pass's most valuable output — one "the sharpest ⚠️ of this pass", the other "the exact ❌ this page predicts, arriving for real" — and a finding that lands that well does not get re-read. Note the second was *especially* attractive because the docs already predicted it; a claim that confirms an existing prediction gets less scrutiny, not more.
  - **The claims were hedged in the direction that made them *more* trusted.** "Verified by grep, not assumed" is the sentence a reader stops at. A confident method claim attached to a false conclusion is worse than a bare assertion, because it forecloses the check. Compare [the 2026-08-24 entry](#a-reviewers-correction-replaced-an-accurate-technical-explanation-with-a-wrong-one-unverified--2026-08-24), where a *hedge* was the tell that nobody ran the code; here the opposite framing produced the same outcome.
  - **For finding 1, the fix was rebased into the earlier feature commit**, so `git log` shows `feat(media): …` before `docs: Phase 6 sync …`. Anyone checking chronology concludes the doc is the later, authoritative word about the earlier code — the exact inverse of what happened. `git log` order is not evidence about which of two files was written last, and on a rebasing workflow it is systematically misleading.
  - **A docs pass that files a finding has the strongest reason to re-read its own write-up and the weakest prompt to do so** — the finding *succeeded*, which feels like completion. This is [the 2026-08-20 audit-authored-page entry](#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20) one level over: there a Phase 4 page outlived the Phase 5 fix; here a Phase 6 page outlived a fix *its own author requested*.
- **Fix applied**: the refusal-logging ⚠️ in [architecture/authorization.md](architecture/authorization.md#mediapolicy--the-fourth-policy-and-the-first-behind-no-route-at-all) is now a ✅ describing the shipped state (six gated component methods plus both actions, pinned by `tests/Feature/Media/RefusalLoggingTest.php`); the same page's `mount()`-exclusion list, which named `Media\Gallery::mount()` as a fourth *unlogged* `mount()`, now records it as the deliberate counter-case that **does** log; the translation-leaf ⚠️ is corrected on both [architecture/authorization.md](architecture/authorization.md#the-media-module-and-what-a-catalog-amendment-costs) and [conventions/naming.md](conventions/naming.md#translation-keys). All four rewritten **in place with what they used to say**, never deleted — the underlying rules were correct and are kept; only the claim that this story violated them was wrong. [README.md](README.md)'s index entries corrected in the same pass.
- **How to avoid it next time**: **a docs pass owns re-verifying every gap it reports, before the story closes — including the ones that got fixed, because a successful finding invalidates the sentence that reported it and nothing else will.** Four concrete habits. **(a) Re-run the literal command a doc claims to have run**, at the end of the pass, on every "verified by grep / by execution" claim the pass itself wrote. It takes seconds and it is the only check that catches either of these. **(b)** Write a gap as a ❌/✅ pair from the start, so a fix has a slot to land in rather than requiring the framing sentence to be rewritten — [the 2026-08-20 entry](#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20)'s rule, and the one that would have made finding 1 cost a line instead of a story. **(c) Treat a finding that confirms an existing prediction as needing *more* verification, not less.** Finding 2 was appealing precisely because the docs had forecast it for three stories; that is a reason to check it twice. **(d) Never date a doc's claim by commit order on a workflow that rebases.** If a doc and the code disagree, the code is right — read the file, not the log. This is the same family as the [deferred-findings entry](#a-deferred-storys-findings-were-claims-about-a-tree-that-no-longer-existed-and-one-of-them-would-have-reopened-a-bug-in-this-log--2026-08-23) — a claim about a tree, outliving the tree — with the shortest fuse of any of them: one of these was false on the day it was written, and the other never true at all.

## Two `@directive(...)` calls in one Blade component tag's attribute string silently fail to compile — 2026-08-26

- **Context**: story 0018 (Sales Regions UI), Phase 5 code review finding N8 — a non-blocking "pick one, `@js()` matches `users.blade.php`" style nit against three `wire:click="setActive({{ \Illuminate\Support\Js::from(...) }}, {{ \Illuminate\Support\Js::from(...) }}, '')"` calls on `<flux:switch>` row controls, converted to `wire:click="setActive(@js($region['id']), @js(! $region['isActive']), '')"` for consistency with the file's other single-argument `@js()` calls (`openEditModal(@js(...))`, `setDefault(@js(...))`).
- **What happened**: every row's active/inactive toggle switch became a silent no-op — no PHP error, no JavaScript console error, no failed HTTP request. `Livewire::test(Index::class)->call('setActive', ...)` (direct component call) worked correctly, so the story's own component-level Feature tests never caught it; only a browser test asserting a *rendered outcome* after a real click did, and even that took several rounds to isolate because every earlier symptom (a stale count, an unchanged `is_active`) looked exactly like ordinary async/timing flakiness — the same failure shape this repo has genuinely hit before (see the `->waitForEvent('networkidle')` entries below). Dumping the real compiled HTML settled it: `wire:click="setActive(@js($region['id']), @js(! $region['isActive']), '')"` rendered **byte-for-byte as written**, `@js(...)` completely unprocessed, so Livewire tried to parse a JavaScript-illegal action-call string and dropped it.
- **Root cause — as recorded at the time, and now known to be wrong; see the correction below**: minimally reproduced outside this story's own markup — `<x-button wire:click="foo(@js($id), @js($flag))" />` against a trivial `<button {{ $attributes }}>` component renders the attribute unprocessed, verified via `Blade::render()`. The conclusion drawn was: *a single `@directive(...)` call inside a Blade component tag's plain attribute string compiles correctly; two of them in the same attribute value do not*, attributed to `ComponentTagCompiler::getAttributesFromAttributeString()` regex-scanning the raw attribute string before the general compiler pass runs. That framing also required a carve-out for this repo's own `x-show="matchesFilter(@js(...), @js(...))"` on a `<flux:table.row>`, which has two and works — and the carve-out was a hedge ("not a value fed into the component tag's own attribute list the same way") rather than a mechanism, which is the tell. **What is not in doubt, and is the whole practical content of this entry:** the conversion really did make every row toggle a silent no-op in a real browser, reverting to `{{ \Illuminate\Support\Js::from(...) }}` really did fix it, and a `{{ }}` echo compiles in every shape tested.
- **Fix applied**: reverted the three converted `wire:click="setActive(...)"` attributes in [`resources/views/livewire/sales-regions.blade.php`](../resources/views/livewire/sales-regions.blade.php) to `{{ \Illuminate\Support\Js::from(...) }}` (the pre-existing, proven-correct form), each with an inline comment recording the finding so a future pass doesn't "fix" them back to `@js()` for consistency a second time. `openEditModal(@js(...))` and `setDefault(@js(...))` — each carrying exactly **one** `@js()` call — were left unchanged; they were never the problem.
- **How to avoid it next time**: **prefer `{{ }}` echo expressions over `@directive(...)` calls for any dynamic value inside a Blade *component tag* attribute** (`<x-foo attr="...">`, `<flux:foo attr="...">`) — the correction below narrows *why* (the count is not the discriminator, and an anonymous `<x-…>` tag is the shape that provably breaks), but the safe form is unchanged and is what the repo ships. Use `{{ }}` echo expressions instead when more than one dynamic value must land in the same attribute string (`{{ \Illuminate\Support\Js::from($a) }}, {{ \Illuminate\Support\Js::from($b) }}` is the safe, already-idiomatic form here), or split the attribute across `:wire:click="..."` colon-bound dynamic syntax if the whole value is a single PHP expression. A "pick one style for consistency" cleanup on a component-tag attribute is not risk-free — verify the compiled HTML output (not just the absence of a PHP/console error) before trusting it, exactly as [the entry above](#a-verification-record-that-lists-two-of-three-quality-gates-is-a-record-of-two-gates--2026-08-26) already argues for the quality gates: a passing component-level test here proved nothing, because `Livewire::test()->call(...)` never goes through the compiled Blade view's `wire:click` attribute at all.

> **Correction — 2026-08-26, same day, during story 0018's Phase 6 docs pass.** This entry was verified before being carried forward, per this log's own [re-verify-what-a-story-wrote-about-itself rule](#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20), and **the stated rule does not reproduce — in either direction.** Executed against `HEAD` in this project's own container, twice over: once through `Blade::render()` and once through the **real file-view compilation path** (a throwaway view registered with `View::addNamespace()`, so the `ComponentTagCompiler` + cached-compile route the app actually uses, not just the string compiler).
>
> | Shape | Result |
> | --- | --- |
> | `<flux:switch wire:click="setActive(@js($region['id']), @js(! $region['isActive']), '')" />` — **the exact shipped expression**, two `@js()`, array subscripts, leading `!` | **compiles**, both paths → `wire:click="setActive('ID1', true, '')"` |
> | `<flux:button wire:click="openEditModal(@js($region['id']))" />` — one `@js()` | compiles, both paths |
> | `<flux:table.row x-show="matchesFilter(@js(...), @js(...))" />` — the "carve-out" | compiles; **needed no carve-out** |
> | `<x-placeholder-pattern wire:click="foo(@js($a))" />` — an anonymous `x-` component, **one** `@js()` | **UNCOMPILED**, literal `@js(...)` in the output |
> | `<x-app-logo wire:click="foo(@js($a), @js($b))" />` — anonymous, two | UNCOMPILED |
> | any of the above with `{{ \Illuminate\Support\Js::from(...) }}` | compiles, every time |
>
> So the count is not the discriminator; the *component* is. A `flux:` tag compiles `@js()` at any count, and a plain anonymous `<x-…>` tag compiles it at **no** count. Neither half of "one is fine, two are not" survives, and the hedge about `x-show` was explaining something that never needed explaining. **What made the shipped screen go dead is therefore not established**, and it is deliberately not being guessed at here — the broken state was never committed (the Phase 5 commit contains the comment and the already-reverted markup, so `git show` cannot reconstruct it), and this project's own [hedge rule](#a-reviewers-correction-replaced-an-accurate-technical-explanation-with-a-wrong-one-unverified--2026-08-24) says an unverified mechanism written up confidently is worse than an open question written up plainly.
>
> **What survives unchanged, and is what to act on:** the incident, the symptom (a silent no-op with no PHP error, no console error and no failed request), the fix, and the two rules in the bullet above — prefer `{{ }}` echoes for dynamic values in a component-tag attribute, and **verify the compiled output rather than the absence of an error** before trusting any attribute-syntax cleanup. Add one: **`@js()` inside an anonymous `<x-…>` component's attribute is broken outright** — that half *is* now verified by execution, at any count, and it is the shape the original minimal repro actually hit.

## A verification record that lists two of three quality gates is a record of two gates — 2026-08-26

- **Context**: story 0017 (Sales Region tax configuration backend). [conventions/base-standards.md](conventions/base-standards.md#quality-gates) names three gates every PHP change passes, in order: `php artisan test`, `vendor/bin/pint`, and **Larastan level 7** (`phpstan.neon`, over `app/`, `bootstrap/app.php`, `config/`, `database/`, `routes/`). The story ran three separate, explicitly-recorded verification passes before review — the Phase 3 reconciliation, the Phase 4 fix, and the Phase 4 re-audit round 2 — each ending in a written line of the form *"full suite re-run unscoped: N/N passed; `pint --test --format agent` (unscoped): passed"*.
- **What happened**: **gate 3 was never run.** Not run-and-passed, not run-and-deferred — absent from all three records, and nobody noticed across two `appsec-auditor` rounds and the story author's own re-verification. `code-reviewer` ran it for the first time at Phase 5 and it **failed**: two errors, both in `App\Livewire\SalesRegions\Index::save()`, where `SalesRegion::find($replacementDefaultId)` widens to `SalesRegion|Collection|null` because `Model::find()` accepts an array-ish key and `$replacementDefaultId` came straight out of `$validated[...]` as `mixed`. Real, shipped code, three phases past implementation, in the method the whole story is about.
- **Root cause**: **the record was of what was run, and it was read as a record of what passed.** Two gates reported green, the sentence describing them was long and specific and quantified (`869/869 passed, 2434 assertions`), and a specific, confident record is exactly what stops a reader asking what is *not* in it. Two things made it survivable for so long. The two gates that were run are the two with **loud, immediate, per-file feedback loops** — the ones a developer reaches for while iterating anyway — while Larastan is the one nothing else prompts you to run. And the missing gate is not silent forever: `.github/workflows/tests.yml` runs `composer types:check`, so CI would have failed this eventually. That is the mitigation, not the excuse — it means the omission cost a late catch rather than a shipped bug, and it also means nobody could have inferred the gap from a green local run, because there is no green local run to inspect.
- **Fix applied**: every value read out of `$validated` in `Index::save()` is now narrowed to `(string)` at the point of use, matching `App\Livewire\Users\Index::save()`'s own existing convention for the same read; re-run clean (commit `df377d0`). The story's Phase 5 section records the first clean Larastan run it ever had.
- **How to avoid it next time**: **a verification record must name all three gates and the result of each, including "not run" — a gate absent from the record is a gate that did not run, and should be read that way by whoever reads it next.** Concretely, the closing line of any phase that claims verification is three clauses, never two:

  ```bash
  php artisan test                    # unscoped — not --filter
  vendor/bin/pint --format agent      # unscoped — not --dirty
  vendor/bin/phpstan analyse          # level 7, per phpstan.neon — the one nothing else reminds you of
  ```

  Three notes on why this is a *different* entry from [the scoped-gates one below](#both-of-this-projects-per-change-quality-gates-are-scoped-by-default-and-both-silently-passed--2026-08-20) rather than a restatement of it. **(a)** That entry is about a gate that **ran** and reported "pass" while looking at almost nothing; this one is about a gate that never ran at all, which no amount of widening a `--filter` or dropping a `--dirty` would have caught. **(b)** It generalises past this repo's three commands: **an omission is invisible in a record of positives.** A phase that lists what it did, however precisely, carries no information about what it skipped — so any checklist worth having is enumerated by the checklist, not reconstructed from the report. **(c)** The rule binds a *reviewer* as much as an author: `code-reviewer`'s Phase 5 opening move should be to diff the phases' verification records against the three-gate list, which is the cheapest check in this whole workflow and the one that found this.
## A missing `.env.testing` file let a self-healing `migrate:fresh` wipe the shared dev database — 2026-08-26

- **Context**: no story — routine iteration on the full Pest suite from two separate Claude Code sessions on 2026-08-24, one running `./vendor/bin/sail artisan test` directly and one dispatching a `backend-expert`/`backend-qa` pair to run "revert-checks + full suite".
- **What happened**: the first session's suite run failed with `deleted_at column not found`, diagnosed (reasonably, on the symptom alone) as "the test database is in a corrupted state from a previous concurrent run". It ran `./vendor/bin/sail artisan migrate:fresh --env=testing --force` to reset it — and that command dropped and recreated all 16 tables in the **real development database**, `arospe`, not a testing one. `information_schema.TABLES` showed the table-creation timestamps land in an identical 4-second window twice more that same day (07:29 and again at 23:43, the second during the background suite-run agent's own work), each time wiping whatever had accumulated since — roles, permissions, the sales-region catalog, and every user, including the self-registered account created in between. Nobody noticed until a later session opened the app against an empty `arospe` two days later.
- **Root cause**: this repo's `phpunit.xml` sets `DB_DATABASE=testing`, but that `<env>` block only takes effect when Pest/PHPUnit itself boots the framework — it does nothing for a bare `artisan` command. Laravel's `--env=testing` flag makes `LoadEnvironmentVariables` look for a `.env.testing` file; when none exists (this project never had one), it silently falls back to loading the plain `.env`, whose `DB_DATABASE` is `arospe`. So `--env=testing` looked like the correct, safety-conscious way to reset "the test database" and was in fact indistinguishable from omitting the flag entirely. The agent's self-diagnosis ("the DB is corrupted, let me refresh it") was a reasonable read of the symptom and is not the mistake — the mistake is that the command it reached for to fix that had no guardrail stopping it from targeting production-adjacent data.
- **Fix applied**: created `.env.testing` (gitignored, one per checkout — see `.gitignore`) pointing `DB_DATABASE=testing` at a dedicated database, verified by re-running the exact failing command (`migrate:fresh --env=testing --force`) and confirming it now creates tables in `testing` while `arospe` is untouched. Restored `arospe` with `php artisan db:seed` (roles, the 38-permission catalog, the sales-region catalog, and the Super Admin grant). Documented the per-checkout requirement, and the further requirement that **each `git worktree` needs its own database name** (`testing1`, `testing2`, …) since all worktrees share one MySQL container, in [testing/worktree-databases.md](testing/worktree-databases.md).
- **How to avoid it next time**: **a database-flag whose safety depends on a file that might not exist is not a guardrail — verify the fallback path, not just the happy path, before trusting a `--env=` / `--database=` flag to isolate anything.** For this specific gap: never run `artisan migrate:fresh` (or any other destructive artisan command) against `--env=testing` without first confirming `.env.testing` exists and points somewhere other than the shared dev database — `cat .env.testing | grep DB_DATABASE` before the destructive command, not after. Two corollaries for anyone opening a new worktree: read [testing/worktree-databases.md](testing/worktree-databases.md) before running tests there, and if a suite run ever fails with a symptom that looks like "the schema is stale/corrupted", treat that as a signal to check *which* database actually received the last `migrate:fresh` before running another one — the diagnosis in this incident was right, but nobody checked which database the fix would land on.

## A scope exclusion named screens while the story edited a class those screens share — 2026-08-24

- **Context**: story 0015b, adding a structured `Log::warning` line to every authorization and rate-limit refusal on the Users and Roles admin screens. Its task file carried an explicit exclusion — *"The `settings/*` screens and `App\Livewire\Settings\*` are not in scope"* — written before its own **Q5** decision, which brought five **domain actions** into scope so that a future non-dashboard caller would inherit the logging. Both statements were reviewed and both passed Phase 2's INVEST gate.
- **What happened**: `appsec-auditor`'s Phase 4 audit **FAILed** the first implementation on a Medium (F-1). `App\Actions\Users\RequestEmailChange` — one of the five actions Q5 brought in — is called by `App\Livewire\Users\Index` (in scope, permission-gated) **and** by `App\Livewire\Settings\Profile::updateProfileInformation()` (`settings/profile`, `auth`-only, self-service, no permission gate at all). Instrumenting the action therefore instrumented the excluded caller, and the new log call sat on a rate-limit refusal branch: since `RateLimiter::attempt()` does not consume once the limit is exhausted, every retry past the third re-entered that branch for free. Any authenticated user could drive unbounded log writes at zero cost, from a screen the story had declared out of scope, using a hardening feature as the amplifier.
- **Root cause**: **the exclusion was phrased in terms of *screens*, and the story's unit of change was a *class*.** Those are only the same thing while nothing is shared, and the whole point of Q5 — the [action-owns-the-rule convention](conventions/base-standards.md#an-authorization-rule-belongs-to-the-action-not-to-one-of-its-callers) — is that these actions are deliberately callable from more than one place. Nobody reconciled the two sentences because each is correct read alone; the contradiction only exists in the intersection, and nothing in the task file, the INVEST review or the implementation brief asks who else calls a file being edited. The consequence direction is what made it a security finding rather than noise: an in-scope caller is permission-gated and self-limiting, while the inherited one is reachable by every authenticated account in the app.
- **Fix applied**: not a scope exclusion — a **log ceiling**, so both callers keep the same trace, bounded. A second, 1-attempt `RateLimiter::attempt()` on a distinct key prefix gates the **log call only**, never the real limit, at `RequestEmailChange`'s three refusal sites and (for symmetry, so the shape cannot silently diverge later) `CreateUser`'s rate-limit site — see [`app/Actions/Users/RequestEmailChange.php`](../app/Actions/Users/RequestEmailChange.php). Phase 5 finding **R-3** then narrowed the aggregate limiter's ceiling key from target-only to `(target, actor)`, matching its two siblings, so a second administrator's refusal against an already-logged target is still recorded. The pattern and its three rules are documented in [architecture/authorization.md](architecture/authorization.md#a-shared-actions-rate-limit-refusal-needs-a-log-ceiling).
- **How to avoid it next time**: **before writing a scope exclusion, resolve it against the *files* the story will edit — `grep -rn "ClassName" app/` for every class in scope — and state the exclusion in terms of classes, not screens.** A screen-shaped exclusion is unenforceable the moment the story touches shared code, and this repo's conventions actively produce shared code: an action exists precisely so more than one caller can reach it. Two corollaries. **(a) Adding an unbounded side effect to a shared class is a capability grant to its *least*-privileged caller, not its most.** Ask who the weakest caller is, then ask what they can now make happen for free — a log write, a mail send, a queued job, a cache write all qualify. **(b) When the answer is "this caller shouldn't get the feature", prefer *bounding* the side effect over *excluding* the caller** — the exclusion re-splits one rule into two implementations, which is the drift this project's conventions spend most of their effort preventing. This is the shared-code half of the family recorded below: [wrapping existing code in a `DB::transaction()`](#wrapping-existing-code-in-a-dbtransaction-moved-a-cache-flush-nobody-had-written--2026-08-21) is about a change the diff hides, where this one is fully visible in the diff — what is hidden is the caller list of the file it lands in.

## A reviewer's "correction" replaced an accurate technical explanation with a wrong one, unverified — 2026-08-24

- **Context**: story 0015a's Phase 5 code review. `code-reviewer` flagged Larastan level 7 failing on `App\Livewire\Users\Index::isAdministratorRoleSelected()`'s `isset($this->roleId)` check (finding F-1), and in the same finding challenged the *docblock's* explanation of why the check is needed — it said a forged `->set('roleId', null)` leaves a direct `$this->roleId` read throwing `Livewire\Exceptions\PropertyNotFoundException`, and the reviewer called this "likely wrong for a public typed property with a default value", without executing anything to confirm.
- **What happened**: acting on that unverified challenge, the docblock was rewritten to say the property is cleared "via reflection" and that a direct read throws PHP's own native "must not be accessed before initialization" `Error` instead. This is what got committed (`30fdecc`). It was wrong on both counts, and worse than the text it replaced: the original `PropertyNotFoundException` claim was **correct**. A second, independent `code-reviewer` pass verified this by execution — `unset()`-ing the property and reading it directly from inside the class threw exactly `PropertyNotFoundException`, because `HandleComponents::setComponentPropertyAwareOfTypes()` does a plain `unset($component->$property)` (no reflection), and PHP routes a read of an `unset()` *declared* property through the magic methods even from inside the declaring class — `Livewire\Component::__get()` throws `PropertyNotFoundException`, and `isset()` observes that state only because `Component::__isset()` catches it internally, not because nothing is thrown.
- **Root cause**: a review finding phrased as "likely wrong" was treated as a confirmed defect and answered with a plausible-sounding replacement, without either side running the one command that would have settled it (a `tinker` call reading the property after `unset()`). The generic mechanism this repo already tracks — [a patch is only valid against the tree it was written on](#a-deferred-storys-findings-were-claims-about-a-tree-that-no-longer-existed-and-one-of-them-would-have-reopened-a-bug-in-this-log--2026-08-23) — applies here in a narrower form: **a review finding phrased with a hedge ("likely", "probably") is a claim to verify, not a claim to act on directly**, and verifying it is cheap when the claim is about concrete runtime behaviour.
- **Fix applied**: a third review pass verified the real mechanism by execution and the docblock in `app/Livewire/Users/Index.php` was corrected back to the accurate explanation (no reflection; `PropertyNotFoundException` via `Component::__get()`/`__isset()`), with a note recording that a Phase 5 pass previously replaced it with a wrong one. The `@phpstan-ignore isset.property` suppression itself was never wrong — only the prose explaining why it is needed.
- **How to avoid it next time**: **when a review finding hedges its own technical claim ("likely", "should be", "I'd expect"), verify it by execution before writing a fix around it — a hedge is a flag that nobody ran the code, not a lower-confidence fact to trust anyway.** For a claim about which PHP exception a specific line throws, the cheapest verification is always the same: reproduce the exact state (`unset()` the property, call the method, read `get_class($e)`) rather than reasoning from how the mechanism *ought* to work. This is a case of the review process itself introducing a defect that the original text did not have — worth watching for specifically when a review's fix is to *documentation or a comment* rather than to behaviour, since no test can catch a wrong sentence the way `phpstan`/`pest` catch a wrong `if`.

## A deferred story's findings were claims about a tree that no longer existed, and one of them would have reopened a bug in this log — 2026-08-23

The line numbers it kept are labelled a reading aid, with Phase 3 required to re-locate each site.

This is a fourth direction of the drift family this log already tracks — [a doc outliving the feature it denied](#a-docs-this-app-has-no-x-yet-claim-outlived-the-x-by-two-tasks--2026-08-13), [a doc outliving the bug it described](#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20), [code drifting from a rule the doc still states correctly](#wrapping-existing-code-in-a-dbtransaction-moved-a-cache-flush-nobody-had-written--2026-08-21) — and the one with the longest fuse, because a backlog item can sit stale for months while looking exactly as authoritative as the day it was filed.

## Wrapping existing code in a `DB::transaction()` moved a cache flush nobody had written — 2026-08-21

- **Context**: task 0012 (module/sidebar access gating). Its Phase 4 audit re-read `App\Livewire\Roles\Index` because the story's cache-staleness tests exercise it, and found a Medium in code the story neither wrote nor changed. The rule it violates has been documented on this project's own security pages since task 0002 — [security/authorization-patterns.md](security/authorization-patterns.md#flush-the-permission-cache-after-the-transaction-commits-never-inside-it), *"Flush the permission cache after the transaction commits, never inside it"* — complete with the ✅ two-flush code shape and the reason (`config/permission.php` caches the whole roles+permissions graph for 24 hours on the **shared** `database` store).
- **What happened**: `saveRole()` and `deleteRole()` shipped with the ❌ shape that page names — the permission cache flushed only *inside* their `DB::transaction()`, never after the `COMMIT`. On the shared store this fails **open** on a revocation: a concurrent request landing in the window between the in-transaction flush and the commit misses the cache, reads the pre-commit rows, and re-caches the escalated grant for 24 hours. It survived story 0010's three-round Phase 4 audit, the whole of story 0011, and a Phase 5 code review of each.
- **Root cause**: **the flush at issue was never written by this repo.** Neither method contains a flush the author chose to place; `syncPermissions()` fires one internally, and `App\Models\Role`'s `deleted` event fires the other. Both were correctly post-commit until story 0010's own Phase 4 finding F4 — an unrelated atomicity concern ("a failure between the rename and the permission sync must not leave a role persisted with the wrong set") — wrapped the existing statements in `DB::transaction()`. That wrapper relocated a side effect **with no flush line appearing, moving or disappearing anywhere in the diff**, so a reviewer grepping the change for `forgetCachedPermissions` found nothing and correctly concluded there was nothing to check. Compounding it, the regression is untestable by construction: `phpunit.xml` pins `CACHE_STORE=array`, making the permission cache per-process in tests, so the suite was 618/618 green with the window wide open — and stays 618/618 green today if either fix line is deleted.
- **Fix applied**: `app(PermissionRegistrar::class)->forgetCachedPermissions()` added immediately after each `DB::transaction()` call in [`app/Livewire/Roles/Index.php`](../app/Livewire/Roles/Index.php) (commit `0a53acb`), each under a multi-line comment naming the finding and linking the rule — the mitigation for a fix no test can pin, matching `RolePermissionSeeder`'s identical precedent. The security page now also carries the three real call sites and the generalized ⚠️.
- **How to avoid it next time**: **adding a `DB::transaction()` around existing code is a change to every side effect that code already performed — audit each of them, including the ones the diff does not show.** Vendor calls are exactly where this bites, because their side effects are invisible at the call site: a cache flush, an event dispatch, a queued job, a broadcast, a `Storage` write, or a mail send that was outside a transaction is now inside one, and each has its own correct side of the commit. Two habits. **(a)** When a finding's remedy is a *wrapper* rather than a new statement, list what the wrapped code calls and what each of those does beyond returning — this is the cheapest form of the "[audit the remediation as new code](#two-of-the-three-security-audit-rounds-found-the-flaw-in-the-previous-rounds-fix--2026-08-19)" rule already recorded below, applied to the one shape where the diff itself hides the change. **(b)** Before writing the fix, grep `docs/security/` for the call you are about to move — the rule broken here was already written down, with the correct code, on a page the breaking story cited for other reasons. This is the third direction of the doc/code drift family this log records: [a doc outliving the feature it denied](#a-docs-this-app-has-no-x-yet-claim-outlived-the-x-by-two-tasks--2026-08-13), [a doc outliving the bug it described](#a-security-page-documented-the-vulnerable-code-as-current-because-it-was-written-before-its-own-fix--2026-08-20), and now **code drifting away from a rule the doc still states correctly** — the only one of the three that a re-read of the doc cannot catch, because the doc is not wrong.

## A count-based assertion over rendered HTML counted a wrapper element it never meant to include — 2026-08-21

- **Context**: task 0011 (Roles & permissions UI). Its Phase 4 security audit established a rule worth keeping — that a **presence** assertion ("this permission's checkbox is still there") cannot catch a *second*, unrelated checkbox also going missing, so the regression test for "the catalog renders in full except one withheld value" must assert a **count**: rendered checkboxes == catalog size, minus exactly the withheld set. Two such tests were added to `tests/Feature/Roles/IndexUiTest.php`.
- **What happened**: both were written as `substr_count($html, 'value="')` — every `value="` attribute in the whole rendered page. Phase 5 flagged it (finding **F-4**) as correct only by coincidence: nothing *else* in the create/edit modal happens to emit that attribute today, so a future `flux:select` or hidden input would move the number with no real omission occurring. The obvious fix — scope it to the checkbox element — then walked into a second trap of its own: the Flux-rendered element is `<ui-checkbox …>`, but `flux:checkbox.group` also emits a `<ui-checkbox-group>` wrapper, whose opening tag **starts with the same string**. Counting `'<ui-checkbox'` therefore over-counts by exactly one, and does so silently: the number is off by a constant, so the test still passes or fails as a block and never looks wrong.
- **Root cause**: the assertion was designed from what the *Blade source* writes (`<flux:checkbox value="…">`) rather than from what the browser receives. Flux components are not one-to-one with their rendered output — a group renders a custom element of its own — and a substring count has no notion of element boundaries, so a child's tag name being a prefix of its parent's is invisible to it. The generic hazard is that a count assertion fails **quietly by a constant**: unlike a presence assertion, which is either satisfied or not, an over-count that is stable across runs reads as the true number and gets baked into whatever expectation makes the test green.
- **Fix applied**: both assertions rescoped to `substr_count($html, '<ui-checkbox ')` — with the **trailing space**, which is what excludes `<ui-checkbox-group` — after tracing the actual rendered markup rather than the stub (commit `48dbf54`). The expected values (`$catalogSize - 1` for a non-Super-Admin, `$catalogSize` for a Super Admin) are unchanged and were re-verified against the real render. The security rule the tests exist for is in [security/authorization-patterns.md](security/authorization-patterns.md#a-control-omitted-from-the-dom-is-safe-only-for-the-one-value-whose-guard-preserves-an-omission).
- **How to avoid it next time**: **a count assertion over rendered HTML must be scoped by a string that cannot match a sibling or wrapper element, and both the selector *and* the expected number must be read off the real rendered output before the test is trusted.** Three concrete habits. **(a)** Dump the HTML once and grep it, rather than deriving the selector from the Blade source — this repo's two 2026-08-16 Flux/Blaze entries below already establish that a Flux component's real output cannot be predicted from its stub, and the same holds for its element names. **(b)** When the selector is an element name, include the delimiter that ends it (`'<ui-checkbox '`, not `'<ui-checkbox'`); custom-element naming makes `<x>` a prefix of `<x-group>` routinely, and Flux's `*.group` components are the standing example. **(c)** Prove the count can be wrong: temporarily remove one item and confirm the number moves by exactly one. A count assertion that has never been observed changing is the same vacuous-coverage failure as [the `arch()` rule below](#a-pest-arch-rule-over-an-array-of-namespaces-shipped-green-while-proving-nothing--2026-08-18), arriving through a different door.

## A guard took the state it was guarding as a parameter, reopening its own hole one level up — 2026-08-20

- **Context**: task 0009, `App\Actions\Roles\EnforceAdministratorPermissionGrant` — the action that refuses a role-save payload newly granting `roles.manage-administrators` to anyone but the Super Admin. Three Phase 4 audit rounds; each round's findings were against the **previous round's fix**, not against the original implementation.
- **What happened**: round 1 found F1 — the guard only asked whether the submitted payload *contained* the protected permission. Since `Role::syncPermissions()` replaces a role's entire permission set, and story 0011's toggle is never rendered to a non-Super-Admin at all, a broad administrator editing an unrelated field on a role that legitimately held the permission submitted a payload **omitting** it, silently revoking a Super Admin's grant. The fix introduced a "before" snapshot so the action could diff. - **Root cause**: two, compounding. (1) **The guard trusted its caller for the very state it existed to protect.** "What does this role currently hold" is the input the whole decision turns on; accepting it as a parameter makes the guard only as strong as every present and future call site. - **How to avoid it next time**: three concrete rules. **(1) A guard must derive the state it guards, never accept it** — take the model and read it (`load()`, not `loadMissing()`), and treat any "current state" parameter in an authorization signature as the finding itself. **(2) The "audit the remediation as new code" rule from the entry below is not a one-off — it is now the observed norm.** Two consecutive stories have needed three Phase 4 rounds, each catching the previous round's own fix, so budget for the extra rounds rather than treating round 2 as a formality. What this story adds to it: the highest-risk remediation is one that introduces a **new input** (a parameter, a snapshot, a cache), because that input's provenance was never in scope for the original review. **(3) When a full-replace `sync*()` is driven by a form that shows the actor only part of the set, absence is not a decision** — diff both directions and authorize adding and removing separately, and when "preserve" versus "deny" is a product judgement rather than a security one, stop and ask the human instead of picking; an unrecorded choice reads as an oversight to the next auditor.

## Two of the three security-audit rounds found the flaw in the *previous* round's fix — 2026-08-19

- **Context**: task 0008a, which relocated the Administrator-tier authorization out of `App\Livewire\Users\Index` and into [`App\Actions\Users\CreateUser`](../app/Actions/Users/CreateUser.php) / [`UpdateUser`](../app/Actions/Users/UpdateUser.php). - **Root cause**: three compounding causes, none of them carelessness. **(1) A relocation is scoped by what moved, not by what the destination now owns.** The spec said "move the Administrator guard", so the Administrator guard moved — and nobody asked what *else* an action that now owns its own authorization is responsible for. - **Fix applied**: `Role::isSuperAdminRoleRow()` added as the row-shaped counterpart to `isAdministratorRole()`; both actions now `Gate::authorize()` the whole operation and refuse the Super Admin tier by **direct throw** rather than through `Gate`; `UpdateUser` refuses a target that currently holds Super Admin as well as a submission that assigns it, moves `$user->load('roles')` to the literal first statement of `__invoke()`, compares status against `getRawOriginal()`, and wraps its writes in `DB::transaction()`. The two durable rules are written up in [security/authorization-patterns.md](security/authorization-patterns.md#a-rule-that-must-bind-a-super-admin-actor-must-be-a-direct-throw-not-a-gate-check) and [the section below it](security/authorization-patterns.md#authorization-that-consults-a-relation-must-reload-it-before-the-first-check-reads-it); the shipped placement is documented in [architecture/authorization.md](architecture/authorization.md#the-guard-belongs-to-the-action-not-to-the-caller).
- **How to avoid it next time**: **re-audit a security fix as new code, not as a diff against a finding — and keep re-auditing until a round finds nothing.** A round that only re-tests the reported finding will confirm the fix and miss what the fix introduced; budget for the extra rounds rather than treating round 2 as a formality. Two concrete checks that would each have caught a finding here on the first pass. **(a) When a guard moves into a class, enumerate every privileged value that class can now write — not only the one the story is about.** "Which role can this action assign?" has three answers here (ordinary, Administrator, Super Admin) and the story's title only named one. **(b) For every authorization check, name the statement that last wrote the state it reads, and confirm it runs above it.** Relation hydration, `getOriginal()` vs `getRawOriginal()`, and an in-memory attribute a caller may have pre-staged are all state a check silently trusts; ordering is part of the guard, not an implementation detail. See also the `getPrevious()`-not-`getOriginal()` entry below — the same class of "which source is this reading, and when?" mistake, from a third direction.

## A Pest `arch()` rule over an array of namespaces shipped green while proving nothing — 2026-08-18

- **Context**: task 0008. The story's central invariant is that `App\Models\Role` is the *only* role model class application code may use — a direct `Spatie\Permission\Models\Role` import reaches the same `roles` table carrying none of the Super Admin guards, so it is a live bypass. ## A listener read the pre-save value with `getOriginal()`, which `save()` had already overwritten — 2026-08-17

- **Context**: task 0007 Phase 4 (`appsec-auditor`). The story turned `users.status` from a badge label into an access-control state, which made [`App\Listeners\ActivateVerifiedUser`](../app/Listeners/ActivateVerifiedUser.php) — the single `Inactive` → `Active` transition — a privilege-granting control for the first time. Its only guard was `$user->status !== UserStatus::Inactive`, and both the listener and [architecture/authentication.md](architecture/authentication.md#account-status-and-activation) described that guard as what "stops a verification from silently undoing an administrator's suspension".
- **What happened**: two mistakes, one on top of the other. First, the guard was written against the wrong half of the problem: it does cover `Suspended`, but `Inactive` is *also* a state an administrator sets deliberately from the Users editor, and for that state the condition is not a guard — it is the trigger. Since `App\Actions\Users\ConfirmEmailChange` fires `Verified` from the deliberately session-less `email-change.confirm` route, a deactivated user could reactivate themselves with nothing but a 60-minute-old pending-email link (verified by execution: `BEFORE: status=inactive` → `AFTER: status=active`). Second, the audit's own first fix — `is_null($user->getOriginal('email_verified_at'))` — was **wrong**, and only broke `EmailVerificationTest` and `PasswordResetTest` once it was actually run; reading it, it looks obviously correct.
- **Root cause**: `Model::save()` ends in `finishSave()`, which calls `syncOriginal()` unconditionally after *every* successful save. Every caller that fires `Verified` writes `email_verified_at` and calls `save()` before firing the event on that same instance, so by the time the listener runs, `getOriginal()` already holds the value that was just written. A `getOriginal()`-based guard therefore always finds a non-null "original" and refuses every legitimate first verification — it fails closed, which is why it produced test failures rather than a security hole, but it would have silently disabled activation entirely. What does survive is `$this->previous`, populated by `syncChanges()` from inside `performUpdate()` *before* `finishSave()` runs, and read with `getPrevious()`.
- **Fix applied**: `ActivateVerifiedUser` now requires the user to have *never* been verified, read from `getPrevious()` and failing closed when the key is absent. Both producers — [`app/Actions/Fortify/ResetUserPassword.php`](../app/Actions/Fortify/ResetUserPassword.php) and [`app/Actions/Users/ConfirmEmailChange.php`](../app/Actions/Users/ConfirmEmailChange.php) — carry a comment recording that their `save()` must remain the last dirty write before the event. The full rule and its four constraints are in [security/login-status-enforcement.md](security/login-status-enforcement.md#status-is-now-an-access-control-state--every-inactive--active-transition-is-a-privilege-grant).
- **How to avoid it next time**: two rules, both concrete. **(1) In a listener or observer that runs after `save()`, the pre-change value is `getPrevious()`, never `getOriginal()`** — `getOriginal()` means "as of the last sync", and a successful save *is* a sync. It comes with constraints worth checking before relying on it: it only carries attributes that were dirty on the last save (so `array_key_exists()` first and fail closed), `syncChanges()` replaces it wholesale on each dirty save, `performInsert()` never populates it, and a `ShouldQueue` listener loses it entirely because `SerializesModels` re-fetches the model. **(2) When a column stops being descriptive and starts denying access, re-audit every write to it as a privilege grant** — including the ones that were reviewed and approved while it was still cosmetic. Ask what the state *denies* and who can undo it, not what it is called; a single enum case carrying two meanings ("never proved their mailbox" and "an administrator turned this off") cannot be guarded by testing the case alone.

## A `null` Livewire property bound to a native `<select>` silently dropped the user's own pick — 2026-08-16

- **Context**: story 0006 (Users list + create/edit modal UI), after the story had already been reviewed and closed. The create/edit form's Role and Status fields are `flux:select` elements bound with a bare `wire:model` to `App\Livewire\Users\Index::$roleId` / `$status`, which were declared `public ?string $roleId = null;` and `public ?UserStatus $status = null;`.
- **What happened**: a real user filling in the create form picked "Administrator" for Role and "Active" for Status, saw both dropdowns displaying exactly those values, clicked Save — and got `The role id field is required.` and `The status field is required.`. The server had received neither value. It reproduced 100% of the time whenever the option the user picked happened to be the **first** non-placeholder option — which is precisely the one a user naturally reaches for — and not at all otherwise.
- **Root cause**: `null` is not an "empty value" to a native `<select>`. Livewire's `wire:model` (the Alpine `x-model` get/set installed by `js/directives/wire-model.js` in `vendor/livewire/livewire/dist/livewire.js`) assigns the property's dehydrated value straight onto the element's `.value`, and `HTMLSelectElement.value = null` coerces to the literal string `"null"`, which matches no `<option>` — including the `disabled selected` placeholder, whose value is `""`. Verified directly in a headless browser rather than reasoned about: that assignment moves `selectedIndex` from `0` (the placeholder) to `-1`, after which the real rendered page visually settled on the first non-placeholder option ("Administrator", first role alphabetically). Because the browser had **already** selected that option before the user ever touched the control, the user's click on that same option produced no value delta, so no native `change` event fired, so Livewire's `dataSet(component.$wire, 'roleId', ...)` never ran, and the property stayed `null` server-side while the UI showed the "right" answer. Nothing errored anywhere in the stack, which is exactly why nothing caught it: `Livewire::test()->set('roleId', ...)` writes the property directly and never touches a DOM element at all, and the browser-automation `selectOption()` API used during earlier manual checking does not reproduce the initial-value quirk either. Only genuine keyboard/mouse interaction against the real rendered DOM exposes it, so "the two selects render and can be picked" being eyeballed as working during review was consistent with the bug.
- **Fix applied**: both properties lost their nullability in [`app/Livewire/Users/Index.php`](../app/Livewire/Users/Index.php) — `public string $roleId = '';`, where the empty string is the "nothing chosen yet" sentinel and matches the placeholder `<option value="">` exactly, and `public UserStatus $status = UserStatus::Inactive;`, since a status enum has no empty-string equivalent and a user always has *some* real status (a new one defaults to the same value `users.status`'s own column default carries — see [database/schema.md](database/schema.md#users)). `openEditModal()` now assigns `''` rather than `null` for a target with no role, and the Status `<flux:select>` in [`resources/views/livewire/users.blade.php`](../resources/views/livewire/users.blade.php) dropped its `:placeholder` prop, which had become unreachable markup. Both properties carry a docblock stating why they must never be null.
- **How to avoid it next time**: **a Livewire property bound with a bare `wire:model` to a native form control must never actually be `null` — give it a real "empty" value in the same type the DOM expects** (an empty string for a nullable string, a real default case for an enum), because the framework assigns the dehydrated value into `.value` and a JS `null` stringifies to `"null"`, desynchronising the browser's own selection state from what the server believes. Two corollaries, both of which are why this survived review: `Livewire::test()->set()` can never detect it (it bypasses the DOM entirely), and neither can a browser test driven through a `selectOption()`-style API — the failure mode is a **missing** `change` event, so it takes either a test that drives the control the way a person does and then asserts the *server-side* value, or a human clicking the first option.
- **Update — 2026-08-24 (task 0015): `$status` has since changed *type*, and the rule above is exactly what constrained how.** It is now `public string $status = UserStatus::Inactive->value;`, retyped because Livewire's `EnumSynth` hydrates a forged backing value through `$type::from($value)` **before** validation runs, so a typed enum property turned a tampered `status` into an unhandled `\ValueError` instead of a validation error (finding F8). The story's own first draft prescribed `public ?UserStatus $status` — which would have reopened this entry's bug — and that instruction was withdrawn in writing once this entry was re-read. The shipped form is non-nullable and defaults to a **real backing value**, never `''`: the rule holds, only the type moved. See [the deferred-findings entry at the top of this log](#a-deferred-storys-findings-were-claims-about-a-tree-that-no-longer-existed-and-one-of-them-would-have-reopened-a-bug-in-this-log--2026-08-23).

- **Context**: adding the per-row disabled edit/delete actions to the Users list ([`resources/views/livewire/users.blade.php`](../resources/views/livewire/users.blade.php)), which needed an "Action not allowed" tooltip on the disabled branch only.

Confirmed by dumping the actually-rendered HTML, not inferred from the stub.
- **Root cause**: `livewire/blaze` (v1.0.12) is installed in this project, and it really does perform compile-time folding of the Flux Blade components that carry a `@blaze(...)` annotation — `vendor/livewire/flux/stubs/resources/views/flux/with-tooltip.blade.php` opens with `@blaze(fold: true, unsafe: ['tooltip:position', 'tooltip:kbd', 'tooltip'])`, and those annotations are **not** the no-ops they would be in a Blaze-less install. That stub decides whether to wrap the slot (`if ($tooltip): <flux:tooltip :content="$tooltip">`) from a value produced by `Flux::forwardedAttributes()` plus Blaze's compiled attribute handling, which treats the prop as **present whenever `tooltip=` / `:tooltip=` is written on the tag at all**, regardless of what the bound expression evaluates to at runtime. The view carries a comment recording why the straightforward binding is not used.
- **How to avoid it next time**: **in this codebase a Flux prop that controls whether a wrapping element renders — `tooltip` on `flux:button` is the known one — cannot be driven by a conditionally-`null` bound value, because Blaze's compiled output does not re-evaluate the prop's *presence* per render the way plain Blade would.** Express the condition in the template's structure (two branches, one that writes the attribute or wrapper and one that omits it entirely), never as `:prop="$cond ? … : null"`, and never by wrapping an attribute in a Blade directive inside the tag. And verify by rendering the page and reading the real HTML: a Blaze-folded component's behaviour cannot be predicted from the stub's own `@if` alone.

## A redundant `users_uuid_unique` index survived the UUID primary-key conversion — 2026-08-12

- **Context**: task 0003 (`ai-spec/tasks/.../0003-users-status-and-email-verification-lifecycle.md`) investigating index cost before deciding whether `users.status` needed one.
- **What happened**: `php artisan db:table users` shows the `id` column covered **twice** — once by `primary`, and again by a leftover `users_uuid_unique` (`btree, unique`). Every insert therefore writes a wholly redundant `CHAR(36)` unique index.
- **Root cause**: the UUID conversion set (see [database/migrations.md](database/migrations.md#the-real-users-conversion-alteration-not-create_table)) created the transient column in `2026_07_22_100001_convert_id_to_uuid_in_users_table.php` as `$table->uuid('uuid')->unique()`, and `2026_07_22_100005_finalize_uuid_primary_key_on_users_table.php` renamed it to `id` and promoted it to PRIMARY **without dropping that unique index**. A rename carries indexes along with the column, and promoting a column to PRIMARY does not absorb or replace an existing unique index on it — so the two coexist silently. Nothing fails; it is pure write amplification, which is exactly why it survived review.
- **Fix applied**: dropped by task 0014 (`ai-spec/tasks/done/0014-drop-redundant-users-uuid-unique-index.md`) via [`database/migrations/2026_08_17_132646_drop_redundant_uuid_unique_index_from_users_table.php`](../database/migrations/2026_08_17_132646_drop_redundant_uuid_unique_index_from_users_table.php), whose `up()` drops `users_uuid_unique` by its explicit name (not the column-derived form, which would target a name that never existed) and whose `down()` restores it exactly. `users.id` now carries a single `PRIMARY` index — reverified with `php artisan db:table users`.
- **How to avoid it next time**: **in a multi-step column conversion, the finalize migration owns the cleanup of every index the intermediate steps created.** When a transient column is given `->unique()` only to guarantee uniqueness *during* the transition, the step that promotes it to PRIMARY must `dropUnique([...])` first. Verify with `php artisan db:table <table>` — not by reading the migrations — that the resulting index list is exactly what you intended; the migration diff will not show you an index that nobody removed.

## A row carrying the configured email was treated as proof of mailbox ownership — 2026-08-09

- **Context**: task 0002 (`ai-spec/tasks/.../0002-seed-roles-permissions-catalog.md`), bootstrapping the `Super Admin` role from `SUPER_ADMIN_EMAIL` in `database/seeders/RolePermissionSeeder.php`.
- **What happened**: the Phase 3 implementation looked up `User::where('email', $email)->first()` and granted `Super Admin` to whatever row came back (warning and skipping when nothing matched). `appsec-auditor` flagged it as a privilege-escalation path: a `users` row merely *carrying* an address proves nothing about who controls that mailbox.
- **Root cause**: leaving `SUPER_ADMIN_EMAIL` unset at first deploy is a documented, supported state, and self-registration is enabled — so during that window anyone can register the address the operator intends to use later. Worse, `App\Livewire\Settings\Profile::updateProfileInformation()` lets any signed-in user point their **existing** account at an arbitrary address: it nulls `email_verified_at` but writes the new address to `users.email` immediately, with no re-verification. Either way the squatter is handed Super Admin the moment an operator sets the config and reseeds.
- **Fix applied**: the lookup in [`database/seeders/RolePermissionSeeder.php`](../database/seeders/RolePermissionSeeder.php) now carries `whereNotNull('email_verified_at')`, so verification is part of the **match condition** rather than a check bolted on afterwards, and a fifth branch was added for the address being occupied by an *unverified* account: abort loudly (console error + `Log::warning`), grant the role to nobody, insert no second account, send no mail, and `return` rather than throw so the roles and the 38-permission catalog still commit. The full decision tree is documented in [architecture/authorization.md](architecture/authorization.md#super-admin-bootstrap); the general rule is in [security/seeder-safety.md](security/seeder-safety.md#a-matching-row-is-not-proof-of-ownership).
- **How to avoid it next time**: **an existing row with the right email is not proof of mailbox ownership.** Any code that grants privilege by matching a configured or user-supplied address must require proof of control — `whereNotNull('email_verified_at')` — as part of the query, not as a follow-up `if`. When neither granting (unproven ownership) nor creating (address taken) is safe, abort with a `return` and an operator-actionable message; never throw from inside a seeder transaction that also writes required application data, and never resolve the ambiguity on the seeder's own initiative by verifying, renaming, or deleting the occupying account.
- **Update — 2026-08-12 (task 0003): the second half of this vector is now closed at the source.** The profile screen no longer writes an unverified address into `users.email` at all: `App\Livewire\Settings\Profile::updateProfileInformation()` routes every email change through `App\Actions\Users\RequestEmailChange`, which parks the new address in `users.pending_email` and mails a signed, address-bound, 60-minute link to *that* address; only `App\Actions\Users\ConfirmEmailChange` — reached by using the link — writes `users.email` and sets `email_verified_at`. The `if ($user->isDirty('email')) { $user->email_verified_at = null; }` branch is gone. **The rule above does not relax.** `users.email` alone still is not proof of anything (an administrator may create a user with an unverified initial address); what task 0003 guarantees is narrower and is exactly what the seeder relies on: **`users.email` together with a non-null `email_verified_at`** means the address was proven, because no *change* to `users.email` can land without its own verification link being used. Keep the `whereNotNull('email_verified_at')` in the lookup. See [architecture/authentication.md](architecture/authentication.md#pending-email-changes).
