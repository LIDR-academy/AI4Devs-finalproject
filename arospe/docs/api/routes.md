## Why this file exists

This app has **no `routes/api.php`** and no `Illuminate\Http\Resources\Json\JsonResource` classes — there is nothing that fits `api/<resource>.md` yet. This file documents the real contract surface that exists today: server-rendered/Livewire routes, one domain controller, plus the auth routes registered by `laravel/fortify` and `laravel/passkeys`. When real API resource controllers are added, split this file into `api/<resource>.md` per resource and update this file to link to them, per the placement rule in the `docs-maintainer` skill.

Full current route list can always be regenerated with `php artisan route:list`.

## App-owned routes

Declared in [`routes/web.php`](../../routes/web.php) and the seven per-area files it requires, [`routes/settings.php`](../../routes/settings.php), [`routes/roles.php`](../../routes/roles.php), [`routes/users.php`](../../routes/users.php), [`routes/sales-regions.php`](../../routes/sales-regions.php), [`routes/product-categories.php`](../../routes/product-categories.php), [`routes/product-attribute-types.php`](../../routes/product-attribute-types.php) and [`routes/products.php`](../../routes/products.php). One file per functional area is now the convention: a new module screen gets its own `routes/<area>.php` with its own `auth` + `verified` group, `require`d from `web.php`, rather than another entry in a growing `web.php`.

**Adding a gated module route for a later epic?** The three subsections below describe what `users.index`, `roles.index` and `sales-regions.index` *are*; the reusable shape they establish — one `can:<permission>` per route as the plain alias string, plus the three alternatives rejected (Spatie's `permission:`, a group-level gate, and Laravel's `->can()` route sugar) and the four vendor-verified properties that come with it — is owned by [architecture/authorization.md](../architecture/authorization.md#the-copyable-module-gate-pattern-and-the-three-alternatives-rejected), not repeated here. Task 0012 pinned the first two routes' behaviour end to end in [`tests/Feature/Authorization/ModuleRouteAccessTest.php`](../../tests/Feature/Authorization/ModuleRouteAccessTest.php) — cross-gate independence in both directions, the Super Admin bypass on each, the two refusals asserted to name no permission, and a revoke/grant taking effect on the next HTTP request — without changing either route's URI, name or middleware. Task 0017 did **not** extend that file; `sales-regions.index`'s own four-case HTTP block (guest → login, no permission → 403, holder → 200, Super Admin holding zero permission rows → 200) lives in [`tests/Feature/SalesRegions/IndexTest.php`](../../tests/Feature/SalesRegions/IndexTest.php) instead, which is a gap worth knowing about rather than a decision: the cross-gate independence assertions that make `ModuleRouteAccessTest` valuable are still written against two routes, not three.

### `users.index` — the first permission-gated route

Every other app-owned route gates on *being signed in*; this one is the first to gate on a **catalog permission**. Since task 0040 it lives in its own [`routes/users.php`](../../routes/users.php) — one file per functional area, required from `web.php` exactly the way `settings.php` is — inside that file's own `auth` + `verified` group:

```php
// routes/users.php
Route::middleware(['auth', 'verified'])->group(function () {
    Route::livewire('users', UsersIndex::class)
        ->middleware(['can:users.view'])
        ->name('users.index');
});
```

**`can:users.view`, not `permission:users.view`** — the two express the same rule but are not interchangeable on a `Route::livewire(...)` route. Livewire re-applies route middleware to `/livewire/update` round-trips only for classes on its `PersistentMiddleware` allow-list, which carries Laravel's `Authorize` (`can:`) but not Spatie's `PermissionMiddleware`; gating with `permission:` would protect the initial `GET /users` only, leaving every `save()` / `deleteUser()` unauthorized at the route layer. The route file carries an inline comment saying so — do not "normalise" it. See [architecture/authorization.md](../architecture/authorization.md#gating-a-livewire-route-use-can-never-permission).

Nine consequences for anyone reading this table as a contract — the full authorization reasoning behind all of them lives in [architecture/authorization.md](../architecture/authorization.md) and is only summarized here:

- **The middleware column understates what protects this route** (`verified` isn't Livewire-persistent either). [`App\Livewire\Users\Index`](../../app/Livewire/Users/Index.php) re-authorizes in `mount()` and as the first statement of every mutating and disclosing method, including the three modal openers (`openCreateModal()` → `create`, `confirmDelete()` → `delete`, `openEditModal()` → `updateSensitiveAttributes` for a non-self target). `CreateUser`/`UpdateUser` additionally self-authorize the whole write, including the Administrator-tier rules. See [architecture/authorization.md#the-guard-belongs-to-the-action-not-to-the-caller](../architecture/authorization.md#the-guard-belongs-to-the-action-not-to-the-caller).
- **Five operations also require a recently confirmed password** (step-up, since task 0015a): changing another user's role/status/email, deleting a user, and creating an Administrator-tier user. Enforced in-method (`password.confirm` isn't Livewire-persistent either), not via route middleware. A direct caller gets **423 Locked**; the dashboard redirects to `route('password.confirm')`. Full exemptions and mechanism in [architecture/authorization.md#step-up-authentication--the-third-layer](../architecture/authorization.md#step-up-authentication--the-third-layer).
- **Both Users modals warn before the administrator commits** when that confirmation is stale — `data-test="edit-modal-reconfirm-notice"`, `data-test="delete-modal-reconfirm-notice"`, `data-test="create-modal-reconfirm-notice"` (the last only for an Administrator-tier role selection), each a `flux:callout` with no password field. Select them by hook, never translated copy. Predicate and rationale: [architecture/authorization.md#the-ui-hint-reuses-the-guards-own-predicate](../architecture/authorization.md#the-ui-hint-reuses-the-guards-own-predicate). One DOM knock-on: the role `<flux:select>` is bound with `wire:model.live`, unlike every other field on this form, so the create-form notice can round-trip before Save.
- **The view behind it renders the whole screen.** `resources/views/livewire/users.blade.php` — the *flat* path Livewire resolves for `App\Livewire\Users\Index`, per the [`Index`-in-a-subfolder exception](../conventions/naming.md#exception-a-component-named-index-resolves-to-its-parent-folders-name) — consumes the component's public surface (`$users` rows of `{id, name, email, pendingEmail, role, status, canEdit, canDelete}` — `$users` itself is `#[Locked]`, as are `$editingPendingEmail` / `$deletingUserId` / `$deletingUserName` — plus `usersSummary()` and `roleOptions()`) and renders: a header with the live total/active count and a primary "New user" button; a `flux:table` of users (initials `flux:avatar`, name over email with a muted pending-address notice beneath it when `pendingEmail` is set, the role name or an em dash when the user has none, a `flux:badge` coloured per `UserStatus` — `lime`/`zinc`/`red` — and per-row edit/delete actions rendered enabled or disabled according to that row's `canEdit`/`canDelete`); a create/edit modal (name, email, a role `flux:select` fed by `roleOptions()`, a status `flux:select` over `UserStatus::cases()`); a delete-confirmation modal naming the target; and an explicit empty state when `$users` is empty. Both modals' inner content is wrapped in `@if ($showModal)` / `@if ($showDeleteModal)` so only one "Cancel" control is ever in the DOM.
- **Its row actions are icon-only, so they are not selectable by visible text.** Each carries an `aria-label` plus a `data-test="edit-user-{id}"` / `data-test="delete-user-{id}"` hook — target those hooks from a browser test, never the button label. Both `wire:click` arguments are passed through `@js(...)`, which is mandatory rather than stylistic: a value interpolated into a `wire:*` attribute lands in a JavaScript evaluator, where Blade's HTML escaping is undone by the parser. See [security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md).
- **A row action the acting user may not perform renders `disabled`, not merely failing on click.** Current contract: `canEdit` is `$user->is(Auth::user()) || Gate::allows('updateSensitiveAttributes', $user)`, `canDelete` is `Gate::allows('delete', $user)`. One known, accepted drift: a **Super Admin actor** viewing a **Super Admin-holding target** sees `canEdit` render `true` (the `Gate::before` bypass) while `UpdateUser` refuses the save on click — enabled-then-refused, never the reverse. This is a UI hint layered on top of the component's own authorization, never a replacement for it; full history and the `Gate::allows()`-not-`Gate::authorize()` rule are in [architecture/authorization.md#gateallows-in-a-list-query-is-a-ui-hint-not-a-layer](../architecture/authorization.md#gateallows-in-a-list-query-is-a-ui-hint-not-a-layer). The `data-test` hook is present on both branches, so a browser test selects the row action the same way regardless of whether it is enabled.
- **Nobody deletes their own account from this screen, and the guard is not in the policy.** `deleteUser()` returns early — a silent no-op that closes the confirmation modal and leaves the account intact — when the target `is()` the acting user, sitting **above** `Gate::authorize('delete', …)` on purpose (a `UserPolicy` rule would be undone by the actor's own `Gate::before` bypass). An actor whose own row holds `Administrator` never reaches the no-op — `confirmDelete()`'s gate refuses them first. Rationale and the Phase 5 finding behind the modal-close behaviour: [architecture/authorization.md#a-rule-that-must-bind-a-super-admin-actor-cannot-go-through-gate](../architecture/authorization.md#a-rule-that-must-bind-a-super-admin-actor-cannot-go-through-gate).
- **Two markup rules the disabled branch establishes, both non-obvious and both load-bearing.** The disabled action is written as a separate `@if`/`@else` branch wrapped in an explicit `<flux:tooltip>` rather than as one button carrying a bound `:tooltip="$cond ? … : null"`: with `livewire/blaze` installed, a Flux prop that decides whether a wrapper renders counts as *present* whenever the attribute is written on the tag at all, so the conditional binding produced an empty tooltip bubble on every enabled row. And the `cursor-not-allowed!` class sits on that `flux:tooltip` wrapper, not on the button — Flux's own `disabled:pointer-events-none` takes a disabled button out of hit-testing, so a cursor rule placed there is never rendered. Both are recorded with their verification method in [errors-log.md](../errors-log.md); do not "simplify" either back into the obvious form.
- **`/users` is linked from the sidebar only to a user holding `users.view`.** [`resources/views/layouts/app/sidebar.blade.php`](../../resources/views/layouts/app/sidebar.blade.php) no longer names this route at all: it renders `<x-sidebar-nav />`, which resolves the entry from [`config/modules.php`](../../config/modules.php)'s `items.users` and renders it only when `Gate::any(['users.view'])` passes — the same single ability this route's own `can:` gate enforces, pinned to it by a test rather than by convention. The registry pattern is documented in [architecture/authorization.md#the-second-half-of-a-module-gate-the-sidebar-registry](../architecture/authorization.md#the-second-half-of-a-module-gate-the-sidebar-registry), not here.

### `roles.index` — the second permission-gated route

Task 0010 (the route and the component behind it), task 0011 (the view it renders). Declared in its own [`routes/roles.php`](../../routes/roles.php), the same shape `users.index` established:

```php
// routes/roles.php
Route::middleware(['auth', 'verified'])->group(function () {
    // `can:roles.manage`, not Spatie's `permission:` — same reason as
    // `users.index` in routes/users.php: Livewire 4's PersistentMiddleware
    // allowlist carries Laravel's `Authorize` (`can:`) but not Spatie's
    // `PermissionMiddleware`, so a `permission:`-gated route would protect
    // the initial GET only, leaving every saveRole()/deleteRole()
    // /livewire/update round-trip unauthorized. See
    // docs/architecture/authorization.md.
    Route::livewire('roles', RolesIndex::class)
        ->middleware(['can:roles.manage'])
        ->name('roles.index');
});
```

The `can:`-not-`permission:` rule is identical to `users.index`'s and the inline comment restating it is deliberate duplication — a reader auditing one route file must not have to open the other to learn why. See [architecture/authorization.md](../architecture/authorization.md#gating-a-livewire-route-use-can-never-permission).

Nine consequences for anyone reading this table as a contract:

- **The middleware column understates what protects it, exactly as it does for `users.index`.** `verified` and `can:` behave differently on Livewire's `/livewire/update` endpoint, so [`App\Livewire\Roles\Index`](../../app/Livewire/Roles/Index.php) authorizes against [`App\Policies\RolePolicy`](../../app/Policies/RolePolicy.php) as the first statement of **every** public method — `mount()`, both modal openers, `saveRole()`, `confirmDeleteRole()` and `deleteRole()` — including the two that only *disclose* a role's name and permission set. That, not the table row, is the real contract.
- **The view behind it renders the whole screen** (task 0011, table restyled afterward). `resources/views/livewire/roles.blade.php` — the *flat* path Livewire resolves for `App\Livewire\Roles\Index`, per the [`Index`-in-a-subfolder exception](../conventions/naming.md#exception-a-component-named-index-resolves-to-its-parent-folders-name); there is no `livewire/roles/index.blade.php` and creating one would be a silently unused duplicate — renders: a header with a live `trans_choice('roles.index.summary', …)` role count and a primary "New role" button; a `flux:table` of roles (name, a `trans_choice('roles.index.permission_count', …)` cell over the eager-loaded `permissions` relation, the `users_count` holder count including trashed holders, and per-row edit/delete actions rendered enabled or disabled from that row's `canEdit`/`canDelete`); a create/edit modal (a `flux:input` for the name, then a single `flux:checkbox.group` wrapping a **permission matrix** — a `flux:table` with one row per module and one `flux:checkbox` column per CRUD action, plus any non-CRUD permission listed separately beneath it); a delete-confirmation modal; and an explicit empty state (`roles.index.empty`) when no custom role exists. Both modals' inner content is wrapped in `@if ($showModal)` / `@if ($showDeleteModal)` so only one "Cancel" control is ever in the DOM, matching `users.blade.php`.
- **The module matrix is derived in the view, never hardcoded.** `$this->permissionOptions` is a *flat*, name-ordered collection; the Blade file splits each permission's name on its first dot and, when the action segment is one of the four seeded CRUD verbs (`view`/`create`/`edit`/`delete`), places it in the matrix at `[module][action]`. A new seeded module therefore needs no view change, and a module missing one of the four actions renders an empty cell rather than an undefined-index error — the grid is built from `RolePermissionSeeder::ACTIONS`, not assumed complete. Anything whose action segment isn't one of the four (today: `roles.manage`, and `roles.manage-administrators` for a Super Admin actor) falls out of the grid by construction into a separate list rendered below the table, not a fifth ragged column. Labels are still **composed**, not one key per permission: `__('roles.modules.<module>').' — '.__('roles.actions.<action>')`, with each kebab-case segment mapped to its snake_case key at render time (`aria-label` on a matrix cell's checkbox, `:label` on a listed one) — see [conventions/naming.md](../conventions/naming.md#translation-keys).
- **The delete modal branches on the holder count and renders no destructive button at all while holders exist.** The count is read off the already-loaded `$this->roles` row matching `$deletingRoleId` — no second query — and the destructive button additionally requires that row to have resolved at all (`$deletingRole !== null`), so a role deleted or reassigned between page load and click fails **closed** rather than reading as zero holders (task 0011 Phase 4 finding F3). An inline `<flux:error name="deletingRoleId" />` outlet renders `deleteRole()`'s own server-side re-check for exactly that race; the `name` and `selectedPermissionIds` validation errors render through Flux's own `wire:model` error integration on `flux:input` / `flux:checkbox.group`, so they need no manual outlet.
- **The component's public surface, which the view consumes**: `$name` and `$selectedPermissionIds` (the form's two bound fields, the only non-`#[Locked]` writable state besides `$showModal` / `$showDeleteModal`), the `#[Locked]` `$editingRoleId` / `$deletingRoleId` / `$deletingRoleName` / `$canGrantAdministratorLevel`, and the two `#[Computed]` properties `roles()` (`selectable()`-scoped, `web`-guard-scoped, `withCount('users')` including trashed holders, `with('permissions')`, plus the per-row `canEdit` / `canDelete` pseudo-attributes described below) and `permissionOptions()` (the **full, unfiltered** `web` permission catalog — see the ⚠️ in [architecture/authorization.md](../architecture/authorization.md#the-second-grant-meta-rule-you-cannot-grant-what-you-do-not-hold) before filtering it, and the bullet below for the single value the *view* is allowed to withhold).
- **A row action the acting user may not perform renders `disabled`, and its `data-test` hook is present either way.** Since task 0011, `roles()` appends `canEdit` = `Gate::allows('update', $role)` and `canDelete` = `Gate::allows('delete', $role)` to each row — the same `RolePolicy` abilities `openEditModal()` / `confirmDeleteRole()` authorize against, so the disabled state matches what a click would do in every case but one. **The exception:** a **Super Admin** actor sees the seeded `Administrator` row's *delete* control render enabled, because `Gate::before` only defers when the ability's *target* is the **Super Admin** role, so `RolePolicy::delete()`'s categorical Administrator refusal never runs for that actor — the model-event guard refuses the click with a 403 instead. Accepted drift, always enabled-then-refused and never the reverse; it and the three-tier table behind it are in [architecture/authorization.md](../architecture/authorization.md#the-administrator-tiers-immutability-name-locked-undeletable-permissions-still-editable), and `tests/Feature/Roles/IndexUiTest.php` pins all three tiers as a dataset. The row actions are icon-only, so they carry an `aria-label` plus `data-test="edit-role-{id}"` / `data-test="delete-role-{id}"` on **both** the enabled and the disabled branch — target those hooks, never a button label — with both `wire:click` arguments passed through `@js(...)` per [security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md). The two Flux/Blaze markup rules `users.blade.php` established (an explicit `<flux:tooltip>` wrapper instead of a conditionally-bound `:tooltip` prop, and `cursor-not-allowed!` on that wrapper rather than on the `pointer-events-none` button) are reused verbatim here; do not "simplify" either.
- **The permission catalog renders in full, with exactly one deliberate omission.** Every checkbox a role currently holds must come back in the payload, because `saveRole()`'s two transformer actions disagree about what an omission means — filtering the catalog to what the actor may grant would turn that disagreement into a silent revoke. The one value the view *does* withhold is `roles.manage-administrators`, removed by a single `->reject()` applied to the flat collection **before** the module matrix is built (never a per-item `@if` inside the render loop, so no module row can render with an empty cell) for anyone failing `grantAdministratorPermission`. It is absent from the DOM rather than disabled, and it is safe to omit only because `EnforceAdministratorPermissionGrant` preserves that one permission on omission. The full rule is in [security/authorization-patterns.md](../security/authorization-patterns.md#a-control-omitted-from-the-dom-is-safe-only-for-the-one-value-whose-guard-preserves-an-omission) — read it before withholding a second control.
- **Two refusals are not 403s, and a caller must not assert one status for all of them.** Deleting a role that still has holders is a **409** (`App\Exceptions\RoleInUseException` from the model guard) or a validation error naming the exact count via `trans_choice('roles.index.delete_blocked', …)` when it comes through `deleteRole()`; the self-lockout refusal (stripping `roles.manage` from a role the actor holds) is likewise a `ValidationException`, not an authorization failure. Everything genuinely authorization-shaped — a forged id targeting a protected tier, a payload granting a permission the actor lacks — is a 403, and each of those is reachable only by tampering, so the view carries no inline outlet for them.
- **`/roles` is linked from the sidebar only to a user holding `roles.manage`, and its whole "Settings" group disappears with it** (task 0013). The link was added after the view shipped and nested inside a collapsible "Settings" group rather than sitting beside `/users` at the top level; that group is still `expandable`, still carries the `cog-6-tooth` icon and still auto-expands on `roles.*`, but all of it — heading included — now comes from [`config/modules.php`](../../config/modules.php)'s `groups.settings` + `items.roles` and is rendered by `<x-sidebar-nav />`. Because the component filters items *before* grouping them, a user without `roles.manage` gets no "Settings" heading at all rather than an empty one; "Roles & permissions" is that group's only entry today, with more (e.g. billing details) expected to join it later. The entry gates on the **same single ability** the route does, test-pinned. Access is still refused by `can:roles.manage` on the route and re-checked inside the component — hiding the link is presentation only. See [architecture/authorization.md](../architecture/authorization.md#the-second-half-of-a-module-gate-the-sidebar-registry).

### `sales-regions.index` — the third permission-gated route

Task 0017 (the route, the component and its actions), task 0018 (the screen it renders and its sidebar entry). The first route of PRD Epic 2's Products/Taxes domain, and the first one added *after* [the copyable module-gate pattern](../architecture/authorization.md#the-copyable-module-gate-pattern-and-the-three-alternatives-rejected) was written down — so it is the pattern's first real test, not a new precedent. Declared in its own [`routes/sales-regions.php`](../../routes/sales-regions.php), the same shape `users.index` and `roles.index` use:

```php
// routes/sales-regions.php
use App\Livewire\SalesRegions\Index as SalesRegionsIndex;   // aliased: `Index` is ambiguous across areas

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:sales-regions.view`, not Spatie's `permission:` — same reason as
    // users.index / roles.index: ... /livewire/update round-trip unauthorized.
    Route::livewire('taxes/sales-regions', SalesRegionsIndex::class)
        ->middleware(['can:sales-regions.view'])
        ->name('sales-regions.index');
});
```

Three things about the declaration itself. **The URI is nested (`/taxes/sales-regions`) while the route name is flat (`sales-regions.index`)**, deliberately: the URI satisfies PRD §2.1's "a section *inside* the Taxes area, not a top-level sidebar item" without requiring a parent Taxes screen to exist yet, and the name stays aligned with the `sales-regions.*` permission module slug. Do not rename either half — 0018 links to `route('sales-regions.index')`. **The `can:`-not-`permission:` comment is duplicated verbatim from `routes/roles.php`**, which is the convention, not an oversight: a reader auditing one area file must not have to open another to learn why. And **the `Index` import is aliased** (`as SalesRegionsIndex`), matching both existing area files, because `Index` is ambiguous across three areas now.

Twenty consequences for anyone reading this table as a contract — the first nine are task 0017's backend contract, the last eleven task 0018's screen. **Two claims that were true here until task 0018 and are now false, recorded rather than quietly overwritten:** this subsection said "this story ships the backend only" and described [`resources/views/livewire/sales-regions.blade.php`](../../resources/views/livewire/sales-regions.blade.php) as a deliberate **placeholder** (`<p>{{ count($regions) }}</p>`), and it said the route had no sidebar entry. Task 0018 replaced that file wholesale and added the registry entry, so `GET /taxes/sales-regions` now renders the full screen and is linked from the sidebar — the same arc `users.blade.php` completed between tasks 0004 and 0006.

- **The middleware column understates what protects this route, exactly as it does for the other two.** `verified` and `can:` behave differently on Livewire's `/livewire/update` endpoint, so [`App\Livewire\SalesRegions\Index`](../../app/Livewire/SalesRegions/Index.php) re-authorizes in **every** method that mutates or discloses, before it reads or writes anything: `mount()` asks `viewAny` through a plain `Gate::authorize()`, and `openEditModal()`, `save()`, `setDefault()` and `setActive()` each resolve their target with `findOrFail()` and then ask `update` on it. (`closeModal()` is the one public method with no check — it only resets the component's own form state and, since task 0018, its `replacementDefaultId` validation error; see the `closeModal()` bullet below.) `save()` and `setActive()` additionally authorize the **replacement default** row when one is named, because promoting it is their effect too, not only `SetSalesRegionActive`'s — and since Phase 4's re-audit both do so *before* either action runs, not after the first write. That, not the table row, is the real contract.
- **The write path is protected twice over, and this time it was designed that way rather than retrofitted.** All three domain actions — [`UpdateSalesRegion`](../../app/Actions/SalesRegions/UpdateSalesRegion.php), [`SetDefaultSalesRegion`](../../app/Actions/SalesRegions/SetDefaultSalesRegion.php), [`SetSalesRegionActive`](../../app/Actions/SalesRegions/SetSalesRegionActive.php) — authorize `update` themselves as their own first statement, so a direct call from an Artisan command, queued job or future second component inherits the same guard. That is task 0008a's [action-owns-the-rule convention](../conventions/base-standards.md#an-authorization-rule-belongs-to-the-action-not-to-one-of-its-callers) applied up front; this story is the first where it was not a finding.
- **One permission tier gates every mutation.** `sales-regions.edit` covers the rate/description/code edit, the enable/disable toggle *and* the default swap alike — there is no second, stricter tier the way `roles.manage-administrators` gates part of the Users screen, because the seeded catalog holds no candidate string and inventing one would be a `RolePermissionSeeder` change rather than a component detail. `sales-regions.create` and `sales-regions.delete` are seeded and deliberately **unused**: the catalog is fixed by [story 0016](../database/schema.md#sales_regions)'s seeder, and this screen has no create path and no delete path at all. [`App\Policies\SalesRegionPolicy`](../../app/Policies/SalesRegionPolicy.php) therefore defines exactly two abilities, `viewAny` and `update`.
- **Every refusal is logged, and the shape is proven identical to the other two screens' rather than merely plausible.** This is the first screen built to [the "third admin screen" recipe](../architecture/authorization.md#copyable-what-a-third-admin-screen-inherits) instead of retrofitted into it: every `Gate` refusal routes through `App\Actions\Auth\LogRefusedPrivilegedAttempt::authorize()` with `target_type: 'sales_region'`, and the two non-`Gate` refusals call `->log()` immediately above their `throw` with the snake_case reasons `default_must_be_active` and `default_deactivation_requires_replacement`. `tests/Feature/SalesRegions/RefusalLoggingTest.php` set-equates this screen's context keys against an existing screen's in one `Log::spy()` session. `mount()` is the one deliberate exclusion, inheriting the recipe's own reasoning verbatim: the route's `can:sales-regions.view` checks the identical ability and `can:` **is** on Livewire's `PersistentMiddleware` allow-list, so a refusal there is unreachable over HTTP.
- **A permitted mutation logs a success line too, and the three are deliberately not identical.** `save()` writes `Log::info('Sales region updated', …)`, `setDefault()` `'Sales region default changed'`, and `setActive()` `'Sales region active state changed'` (carrying an extra `active` context key) — split apart at Phase 5 review, because a single shared message left an operator unable to tell a rate edit from a default move from a deactivation. They are component-level, matching `Roles\Index`, not inside the actions.
- **Two refusals on this screen are not 403s.** Marking an **inactive** entry as the default, and disabling the current default without naming an active replacement, are both `ValidationException`s keyed on the component's `replacementDefaultId` property — so they land in the form's error bag rather than rendering a 500. The key must stay a real declared public property: Livewire's `SupportValidation::dehydrate()` filters the persisted error bag through `Utils::hasProperty()`, so an error keyed on a name the component does not declare is silently dropped on the next round-trip. Copy for both lives in [`lang/en/sales-regions.php`](../../lang/en/sales-regions.php) / [`lang/es/sales-regions.php`](../../lang/es/sales-regions.php).
- **The component's public surface is the contract story 0018 binds to, and it is now pinned by tests rather than by prose.** `$regions` (`#[Locked]`, one row per entry with the twelve keys `id, slug, code, name, description, rate, kind, parentId, isDefault, isActive, sortOrder, canEdit`), the `#[Locked]` `$editingRegionId`, the writable `$showModal` / `$code` / `$description` / `$rate` / `$active` / `$replacementDefaultId`, the `#[Computed] replacementCandidates()` (active regions *except* the row being edited), and the five public methods. Three tests in `tests/Feature/SalesRegions/IndexTest.php` pin the row shape, `canEdit`'s agreement with the policy, and `replacementCandidates()`'s two exclusions — added at Phase 5 review, since a regression in any of the three would otherwise have passed every other test in the file.
- **No `wire:model`-bound property is ever `null`, uniformly.** `$code`, `$description` and `$rate` are plain `string` (`''` meaning "not configured"), `$active` a plain `bool`, `$replacementDefaultId` a plain `string` whose `''` matches a placeholder `<option value="">`. This is [the errors-log's `null`-property/native-`<select>` entry](../errors-log-archive.md#a-null-livewire-property-bound-to-a-native-select-silently-dropped-the-users-own-pick--2026-08-16) applied to every control rather than case-by-case, before the markup that would expose it exists. The consequence 0018 inherits: `$rate === ''` is *not* `null`, so the component converts it explicitly before calling the action, and a Spanish-locale decimal comma is normalised to a dot as the first statement after authorization and **before** `validate()` — normalising inside the action instead would let the validation rule reject the un-normalised value.
- **`canEdit` per row is a UI hint, never a layer.** `loadRegions()` writes `Gate::allows('update', $region)` onto each row — `allows()`, never `authorize()`, which would throw while rendering a list. There is no `canDelete`, because no delete affordance exists. Unlike the Users and Roles screens, this hint has **no accepted drift**: `SalesRegionPolicy::update()` ignores its target entirely and decides on the permission alone, so the hint and the click cannot disagree today. That equivalence is a property of the policy having no target-dependent branch, not a guarantee — see [the policy's own docblock](../../app/Policies/SalesRegionPolicy.php), which records what must be re-verified the day one is added. **Task 0018 is where that hint first has a rendered consumer**, and it holds: a `canEdit === false` row renders its edit, toggle *and* set-default controls disabled, and `tests/Feature/SalesRegions/IndexRenderingTest.php` asserts all three.
- **The view behind it renders the whole screen** (task 0018). `resources/views/livewire/sales-regions.blade.php` — the *flat* path Livewire resolves for `App\Livewire\SalesRegions\Index`, per the [`Index`-in-a-subfolder exception](../conventions/naming.md#exception-a-component-named-index-resolves-to-its-parent-folders-name) — consumes the component's public surface and renders **two tables plus a modal**: a header with a live `:active active of :total total entries` summary; an **active/grouped table** (code chip, name, description, right-aligned `tabular-nums` rate, an `Active` `flux:switch`, and edit + set-default row actions), in which España's five fiscal territories are nested beneath their parent row and collapsed/expanded by a **client-side Alpine** chevron with no round trip (default-open); a **collapsed "Show all countries (N)" section**, closed on first paint, holding the ~248 seeded-but-inactive countries behind an Alpine text filter over name/code; the edit modal; and an explicit empty state (`sales-regions.index.empty`). The whole active/inactive block is wrapped in `@if ($allRegions->isEmpty())` / `@else`, matching `roles.blade.php` — unreachable in production, since the seeder always populates ~254 rows, and kept anyway because the lang key already existed with no consumer (Phase 5 finding N2).
- **Row membership of the two tables is derived from `isActive` — with one deliberate exception that is a security fix, not a styling choice.** A **top-level row that has children stays in the active/grouped table regardless of its own `isActive`** (Phase 4 finding F-1, Medium). Without that carve-out, deactivating "España" from its own inline toggle moved it to the collapsed section, and because the five fiscal territories render *beneath their parent's row* rather than independently, the whole group — including whichever child holds `is_default` and every configured rate — vanished from both tables at once, with no way to see or restore it short of a direct database query. The partition keys off `$childrenByParent->keys()`; a childless country still partitions on `isActive` alone. Related: the header's summary counts `isActive` across **every** row rather than per table, so it can never report table membership as state (F-2).
- **Its row controls are icon-only, so they are not selectable by visible text** — `data-test="edit-region-{id}"`, `toggle-active-region-{id}`, `set-default-region-{id}`, `expand-region-{id}` on the chevron, `rate-region-{id}` on the rate cell, and `default-badge-region-{id}` on the amber badge; the collapsed section adds `show-all-countries-toggle` / `show-all-countries-filter`, and the modal `modal-active-switch` / `modal-replacement-select`. Every row hook is present on **both** the enabled and the disabled branch, so a test selects the same control either way. `rate-region-{id}` exists specifically because a page-global `assertSee('0%')` matches inside `10%`/`100%` (Phase 5 finding N3) — assert a rate through the row-scoped hook, never against the whole page. Both Flux/Blaze traps [errors-log.md](../errors-log.md) records are applied verbatim: an explicit `<flux:tooltip>` wrapper on the disabled branch rather than a conditionally-bound `:tooltip`, and `cursor-not-allowed!` on that wrapper rather than on the `pointer-events-none` button.
- **The disabled toggle carries one of two different tooltips, and the difference is the contract.** A row the actor may not edit gets `sales-regions.index.action_not_allowed` ("Action not allowed", matching the Users and Roles screens verbatim since Phase 4 finding F-4); the **current default's** row gets `default_toggle_tooltip`, which routes the administrator to the entry's edit form to name a replacement rather than merely refusing. Both are asserted by content, not just by "is it disabled" (Phase 5 finding N5).
- **Disabling the current default is possible only inside the edit modal, and the refusal has two rendering sites that can never both appear.** The modal reveals a replacement `flux:select` (fed by `replacementCandidates()`) via `x-show="! $wire.active"` the moment the modal's active switch is flipped off, so the `replacementDefaultId` error lands next to a field that is on screen. For the race where an inline row toggle hits a row that became the default between paint and click, a **page-level `<flux:error name="replacementDefaultId" />` outlet** renders above the table under `@unless ($showModal)` — the guard is what keeps the message from rendering twice.
- **`closeModal()` clears that error, and the omission was a real bug** (Phase 5 finding B1, blocking). Livewire persists the error bag across requests via `SupportValidation::dehydrate()`/`hydrate()`, so before the fix a refused save followed by *Cancel* left the stale message rendering in the page-level outlet indefinitely, with no field and no context — the exact orphaned refusal the outlet exists to prevent, produced by the control added to prevent it. `App\Livewire\SalesRegions\Index::closeModal()` now also calls `resetValidation('replacementDefaultId')`. This is task 0018 editing task 0017's component class — the one cross-story edit in the story, recorded rather than worked around with a second markup flag.
- **The modal's active control is a plain `<input type="checkbox">` bound with `wire:click="$toggle('active')"`, and both halves of that are deliberate.** It is not a `<flux:switch>` because a Flux `<ui-switch>` dispatches its own `input`/`change` events with `bubbles: false`; it is not `wire:model` because under real-browser automation a bare `wire:model` on this control left the DOM's own `wire:snapshot` — the ground truth of what the next request sends — stuck at the pre-click value while the checkbox's DOM state and `$wire.active` both read correctly. The other three modal fields (`code`, `description`, `rate`) use plain `wire:model` and are unaffected. `$toggle` opens no second write path: it is client-side sugar over `$set`, writing the same `updates` payload `wire:model` does, and `#[Locked]` binds it unchanged — see [security/livewire-authorization.md](../security/livewire-authorization.md#confirmed-safe-wireclicktoggleprop-is-the-same-write-channel-as-wiremodel-and-locked-still-binds-it).
- **The rate input is `type="text" inputmode="decimal"`, never `type="number"`,** so a Spanish-locale `21,5` reaches the wire payload with its comma intact for the component's own normalisation to act on. A native number input performs its own client-side parsing and the comma never arrives. This is invisible to `Livewire::test()->set('rate', '21,5')`, which writes the property directly — only `tests/Browser/SalesRegionsIndexTest.php` can catch a regression here.
- **The rate cell is rendered by string manipulation and never a float cast**: `$region['rate'] === null ? '—' : rtrim(rtrim($region['rate'], '0'), '.').'%'`. The `decimal:3` cast returns a **string**, and an unconfigured rate (`NULL`, an em dash) must stay distinguishable from a real `0.000` (`0%`) — the naive `@if ($region['rate'])` renders both identically.
- **Three `wire:click="setActive(...)"` attributes deliberately use `{{ \Illuminate\Support\Js::from(...) }}` rather than `@js(...)`, and must not be "unified".** Two `@directive(...)` calls inside one Blade **component tag's** attribute value silently fail to compile, leaving the literal text in the rendered attribute and turning every row toggle into a no-op with no PHP or JavaScript error — found, minimally reproduced and written up in [errors-log.md](../errors-log.md#two-directive-calls-in-one-blade-component-tags-attribute-string-silently-fail-to-compile--2026-08-26). The single-argument `openEditModal(@js(...))` / `setDefault(@js(...))` calls carry exactly one and are correct as they stand. Each of the three sites carries an inline comment saying so.
- **`/taxes/sales-regions` is linked from the sidebar only to a user holding `sales-regions.view`** (task 0018). [`config/modules.php`](../../config/modules.php) gained a **new `groups.taxes` group** (heading `navigation.groups.taxes`, icon `receipt-percent`, non-expandable while it holds one entry) plus an `items.sales_regions` entry (icon `globe-americas`, `route` `sales-regions.index`, `current_when` `sales-regions.*`, `permissions` **exactly** `['sales-regions.view']` — the single ability the route's own `can:` enforces). The registry key is `sales_regions`, **snake_case**: it is the project's first genuinely multi-word registry key, and the same identifier is simultaneously the config key, the `lang/*/navigation.php` leaf and the rendered `data-test="sidebar-link-sales_regions"` hook. Only the *values* stay kebab-case, because they are not registry keys. `tests/Feature/Navigation/SidebarModuleGatingTest.php` pins the entry three ways beyond the two generic drift guards that already covered it for free: a role holding exactly `sales-regions.view` sees both hooks, a role holding the related-but-different `sales-regions.edit` sees **neither**, and the Taxes group vanishes entirely (heading included) for a role without the ability. Nothing about the route's contract changed — hiding the link is presentation only. **This is the task-0018 shipped shape, not the current one: story 0080's registry restructuring retired the standalone `groups.taxes` group entirely and moved `items.sales_regions` into the new `store_settings` cluster** (within a `store` group), alongside the future Shipping entry — see [`architecture/authorization.md`](../architecture/authorization.md#the-second-half-of-a-module-gate-the-sidebar-registry) for the real, shipped schema. The entry's own key, `permissions`, `route` and `current_when` values are unchanged by that move.

### `product-categories.index` — the fourth permission-gated route

Story 0025, this screen's own doc-sync pass. The first UI story to call [`ProductCategoryPolicy`](../architecture/authorization.md#productcategorypolicy--the-fifth-policy-and-the-first-to-gain-its-call-site-in-a-later-story-than-the-one-that-created-it) and the three `app/Actions/ProductCategories/*` actions story 0023 shipped with no consumer. Declared in its own [`routes/product-categories.php`](../../routes/product-categories.php), the same shape `users.index`/`roles.index`/`sales-regions.index` use:

```php
// routes/product-categories.php
use App\Livewire\ProductCategories\Index as ProductCategoriesIndex;   // aliased: `Index` is ambiguous across areas,
// exactly like routes/roles.php's and routes/sales-regions.php's own imports
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:products.view`, not Spatie's `permission:` -- same reason as
    // users.index / roles.index / sales-regions.index: Livewire 4's
    // PersistentMiddleware allowlist carries Laravel's `Authorize` (`can:`)
    // but not Spatie's `PermissionMiddleware`, so a `permission:`-gated
    // route would protect the initial GET only, leaving every
    // save()/deleteProductCategory() /livewire/update round-trip
    // unauthorized. See docs/architecture/authorization.md.
    Route::livewire('product-categories', ProductCategoriesIndex::class)
        ->middleware(['can:products.view'])
        ->name('product-categories.index');
});
```

Eleven consequences for anyone reading this table as a contract:

- **The middleware column understates what protects this route, exactly as it does for the other three.** `verified` and `can:` behave differently on Livewire's `/livewire/update` endpoint, so [`App\Livewire\ProductCategories\Index`](../../app/Livewire/ProductCategories/Index.php) re-authorizes in every method that mutates or discloses: `mount()` asks `viewAny`, `openCreateModal()`/`save()` ask `create` (or `update` on `save()`'s edit branch), `openEditModal()` asks `update` against a freshly resolved target, and `confirmDelete()`/`deleteProductCategory()` ask `delete` against a freshly resolved target. **All five methods gate**, matching [security/livewire-authorization.md](../security/livewire-authorization.md#gate-at-the-top-of-every-method-that-mutates-or-discloses)'s "every method that mutates *or* discloses" rule at full strength — the story's own OQ-4 had asked whether the two disclosure-only openers needed to gate at all, recommending "follow the shipped Users precedent" of gating only `save()`/`deleteUser()`, but that recommendation cited a snapshot of `Users\Index` from the story's 2026-08-18 Three Amigos debate, before task 0015 (closed 2026-08-24) added authorization to `Users\Index`'s own three modal openers. The shipped screen here gates every opener, which is consistent with the *current* Users precedent rather than the stale one OQ-4 described.
- **The write path is protected twice over, and — like `sales-regions.index` — it was designed that way rather than retrofitted.** All three domain actions — [`CreateProductCategory`](../../app/Actions/ProductCategories/CreateProductCategory.php), [`RenameProductCategory`](../../app/Actions/ProductCategories/RenameProductCategory.php), [`DeleteProductCategory`](../../app/Actions/ProductCategories/DeleteProductCategory.php) — now authorize their own operation as their first statement, discharging the hand-off story 0023 recorded (see [database/schema.md](../database/schema.md#product_categories)). Each constructor-injects `App\Actions\Auth\LogRefusedPrivilegedAttempt` and passes `targetType: 'product_category'` explicitly, since `resolveTarget()` auto-resolves only `User` and `Role` instances. A future Artisan command, queued job or REST controller inherits the identical refusal the dashboard gets.
- **In `DeleteProductCategory`, the new authorization call runs *before* the in-use product count, and the order is load-bearing.** The in-use block ([database/schema.md § `product_categories`](../database/schema.md#product_categories)) is a domain invariant, not an authorization rule, and stays a `ValidationException` rather than a `Gate` denial — but the count it discloses is data, and computing it before the `delete` gate has run would leak the number to an actor who does not even hold `products.delete`. Reversing the order would turn a clean 403 into a business message ("this category is used by 12 products") available to anyone reaching the method.
- **The component's public surface**: `$productCategories` (deliberately **unlocked** — display-only, documented in its own docblock, the identical rationale [security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md) already records for `Users\Index::$users`: every mutating method re-reads its target with `findOrFail()` and re-authorizes, so nothing here is ever read for a decision), the `#[Locked]` `$editingCategoryId` (assigned only from `$target->id`, never the raw method argument — what makes the id fed to `ProductCategoryValidationRules::uniqueNormalisedName()`'s `->ignore()` server-authoritative), `$showModal`, the plain `string $name` form field (never `?string`), and the delete-modal trio `$showDeleteModal`/`#[Locked] $deletingCategoryId`/`#[Locked] $deletingCategoryName`.
- **The view behind it renders the whole screen.** [`resources/views/livewire/product-categories.blade.php`](../../resources/views/livewire/product-categories.blade.php) — the **flat** path Livewire resolves for `App\Livewire\ProductCategories\Index`, per the [`Index`-in-a-subfolder exception](../conventions/naming.md#exception-a-component-named-index-resolves-to-its-parent-folders-name) — renders: a header with a primary "New category" button (no live count/summary line — OQ-2 resolved "no header summary", since nothing in the PRD or the brief asked for one and, unlike Users, there is no second dimension to summarise); a `flux:table` of categories (name, product count, and icon-only edit/delete row actions rendered enabled or disabled from that row's `canEdit`/`canDelete`); a create/edit modal whose only field is `name`; a delete-confirmation modal naming the target; and an explicit empty state (`data-test="product-categories-empty-state"`) when the catalog is empty. Both modals' inner content is wrapped in `@if ($showModal)` / `@if ($showDeleteModal)` so only one "Cancel" control is ever in the DOM, matching `users.blade.php`/`roles.blade.php`.
- **The product count is shown but is never used to disable the delete action.** `loadProductCategories()`'s `productCount` (from `withCount('products')`) is purely informational — pre-disabling delete on `productCount > 0` would visually conflate the in-use refusal (a domain invariant) with the `canEdit`/`canDelete` authorization UI hint, which exists precisely to mirror what a `Gate::authorize()` call would do. Letting the actor attempt the delete and read the exact count in the modal is what satisfies the PRD's own wording, which requires the *message* to state the count.
- **The blocked-delete refusal renders inline in the still-open delete modal.** `deleteProductCategory()` carries no `try`/`catch` around the action call — `DeleteProductCategory`'s `ValidationException`, keyed on `productCategoryId`, is the one exception Livewire already routes into the component's error bag with no plumbing at the call site, and the throw aborts the method before `closeDeleteModal()` ever runs, which is what keeps the modal open by construction rather than by an explicit flag. The view binds `@error('productCategoryId')` to a `<flux:callout variant="danger" data-test="product-category-delete-blocked">`, the same non-field-error-key pattern `settings/security.blade.php`'s `@error('setupData')` block already establishes. `closeDeleteModal()` also calls `resetErrorBag('productCategoryId')`, or a stale block message would leak into the next delete attempt on a different, unblocked category.
- **No confirm-and-proceed or force-delete control exists anywhere on the screen, and none can be added client-side.** `DeleteProductCategory::__invoke()` takes no `bool $force` parameter — the refusal is architecturally impossible to bypass from the UI, not merely absent from this screen's markup (story 0024b's D-14).
- **Its row actions are icon-only, so they are not selectable by visible text.** Each carries an `aria-label` plus a `data-test="edit-product-category-{id}"` / `data-test="delete-product-category-{id}"` hook, present on **both** the enabled and the disabled branch, so a test selects the same control regardless of state. Both `wire:click` arguments are passed through `@js(...)` — mandatory, not stylistic, since a value interpolated into a `wire:*` attribute lands in a JavaScript evaluator that undoes Blade's HTML escaping (see [security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md)). The two Flux/Blaze markup rules `users.blade.php`/`roles.blade.php`/`sales-regions.blade.php` already established are reused verbatim: an explicit `<flux:tooltip>` wrapper on the disabled branch rather than a conditionally-bound `:tooltip` prop, and `cursor-not-allowed!` on that wrapper rather than on the `pointer-events-none` disabled button — both documented in [errors-log.md](../errors-log.md).
- **`canEdit`/`canDelete` per row are UI hints, never a layer, and they cannot drift from what a click would do.** `loadProductCategories()` writes `Gate::allows('update'|'delete', $category)` onto each row — the *same* policy methods `save()`/`deleteProductCategory()` authorize against — following [Gate::allows() in a list query is a UI hint, not a layer](../architecture/authorization.md#gateallows-in-a-list-query-is-a-ui-hint-not-a-layer). Like `SalesRegionPolicy`, `ProductCategoryPolicy::update()`/`delete()` ignore their target entirely, so this hint has **no accepted drift** — a property of the policy having no target-dependent branch, not a guarantee.
- **`/product-categories` is linked from the sidebar only to a user holding `products.view`.** [`config/modules.php`](../../config/modules.php) gained an `items.product_categories` entry (icon `tag`, `route` `product-categories.index`, `current_when` `product-categories.*`, `permissions` **exactly** `['products.view']` — the single ability the route's own `can:` enforces), with matching leaves in `lang/{en,es}/navigation.php`. [`resources/views/layouts/app/sidebar.blade.php`](../../resources/views/layouts/app/sidebar.blade.php) was **not** touched by story 0025 — this is the registry's "append data, never behavior" claim holding for a fourth entry in a row, following the mechanism task 0013 built. Nothing about the route's contract changed — hiding the link is presentation only. **It shipped as a flat item in the `groups.platform` group; story 0080's registry restructuring retired that group and nests it inside the `products` cluster instead** (within the new `store` group), alongside `products` and `product_attribute_types` — see [`architecture/authorization.md`](../architecture/authorization.md#the-second-half-of-a-module-gate-the-sidebar-registry) for the real, shipped schema.

### `products.index`, `products.create` and `products.edit` — the fifth permission-gated route family

Story 0027, this screen's own doc-sync pass. The first UI story to call [`ProductPolicy`](../architecture/authorization.md#productpolicy--the-sixth-policy-and-the-second-built-entirely-for-a-screen-that-does-not-exist-yet)'s `viewAny` ability, and the first to give every one of the four Products-domain shared components (`Media\Gallery`, `Components\WysiwygEditor`, `Components\SearchableMultiSelect`, `ProductPolicy` itself) a real caller at once. Declared in a new [`routes/products.php`](../../routes/products.php), the same shape the other five area files use — the first to put **two routes on one component**:

```php
// routes/products.php
use App\Livewire\Products\Editor as ProductEditor;
use App\Livewire\Products\Index as ProductsIndex;
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:products.view`, not Spatie's `permission:` -- same reason as every other gated
    // area file: Livewire 4's PersistentMiddleware allowlist carries `can:` but not
    // `permission:`, so every /livewire/update round-trip would run unauthorized under the
    // latter. The finer create/update/delete abilities are authorized inside the components.
    Route::livewire('products', ProductsIndex::class)
        ->middleware(['can:products.view'])
        ->name('products.index');

    Route::livewire('products/create', ProductEditor::class)
        ->middleware(['can:products.view'])
        ->name('products.create');

    Route::livewire('products/{product}/edit', ProductEditor::class)
        ->middleware(['can:products.view'])
        ->name('products.edit');
});
```

**`products.create` and `products.edit` resolve the same `App\Livewire\Products\Editor` class**, which branches on whether `mount()` received a route-model-bound `Product` — the first repeat of a component across two route names in this app (`routes/roles.php`, `sales-regions.php` and `product-categories.php` all alias their one `Index` import for a different reason, ambiguity across areas; here the ambiguity is the *second* route needing the identical component). `Route::livewire()` is a plain `Route::get()` macro, so route-model binding behaves normally and `HasUuids` makes a malformed non-UUID `{product}` a 404 before any query runs.

Thirteen consequences for anyone reading this table as a contract:

- **The middleware column understates what protects these routes, exactly as it does for the other four.** `verified` and `can:` behave differently on `/livewire/update`, so both components re-authorize on every method that mutates or discloses. `Products\Index::mount()` asks `viewAny`; `confirmDelete()`/`deleteProduct()` ask `delete` against a freshly `findOrFail()`d target. `Products\Editor::mount()`, `save()` and the two gallery-selection listeners (`setFeaturedImage()`, `addGalleryImages()`) each authorize their own first statement — `create`/`update` on `Product` for `mount()`/`save()`, `viewAny` on `Media::class` for the two listeners (see the `WysiwygEditor` subsection below for why a page-globally-registered `#[On]` listener needs its own gate rather than trusting the host page's `@can` wrapper).
- **`Editor::mount()`'s gate is reachable over HTTP, unlike `Index::mount()`'s.** `Index::mount()` asks `viewAny`, the *same* ability the route's own `can:products.view` already enforces, so a real HTTP actor who would fail it never reaches `mount()` at all — the check is only reachable through a direct `Livewire::test()` call. `Editor::mount()` asks the *finer* `create`/`update` ability: an actor holding only `products.view` passes the route's coarser middleware and reaches `mount()`, where they are refused — a refusal that **is** reachable over HTTP and is logged through `LogRefusedPrivilegedAttempt` for exactly that reason.
- **`ProductPolicy` now has real call sites for all four abilities.** `viewAny` (this story's `mount()`s), `create`/`update` (`Editor::mount()`/`save()`, layered over `CreateProduct`/`UpdateProduct`'s own self-authorization) and `delete` (`Index::confirmDelete()`/`deleteProduct()`, layered over `DeleteProduct`'s). See [architecture/authorization.md](../architecture/authorization.md#productpolicy--the-sixth-policy-and-the-second-built-entirely-for-a-screen-that-does-not-exist-yet) for what "layered over" means here — every gate in this story is a **second** layer, not the only one, since 0024's actions self-authorize.

The region picker is `<livewire:components.searchable-multi-select :option-resolver="\App\Actions\Products\SearchSalesRegions::class" wire:model="regionIds" .../>`, the exact class-string 0022's own consumer example names.

Declared in its own [`routes/product-attribute-types.php`](../../routes/product-attribute-types.php), the same shape every prior area file uses:

```php
// routes/product-attribute-types.php
use App\Livewire\Products\AttributeTypes\Index as ProductAttributeTypesIndex;   // aliased: `Index` is
// ambiguous across areas, exactly like every other area file's own import
use Illuminate\Support\Facades\Route;

Route::middleware(['auth', 'verified'])->group(function () {
    // `can:products.view`, not Spatie's `permission:` -- same reason as every other
    // gated route in this app: Livewire 4's PersistentMiddleware allowlist carries
```

Thirteen consequences for anyone reading this table as a contract:

- **The middleware column understates what protects this route, exactly as it does for every other gated screen.** `verified` and `can:` behave differently on Livewire's `/livewire/update` endpoint, so [`App\Livewire\Products\AttributeTypes\Index`](../../app/Livewire/Products/AttributeTypes/Index.php) re-authorizes in every method that mutates or discloses: `mount()` asks `viewAny`, `openCreateModal()`/`save()` (create branch) ask `create`, `openEditModal()`/`save()` (edit branch) ask `update` against a freshly resolved target, and `confirmDelete()`/`deleteType()` ask `delete` against a freshly resolved target. **All six methods gate**, matching [security/livewire-authorization.md](../security/livewire-authorization.md#gate-at-the-top-of-every-method-that-mutates-or-discloses)'s "every method that mutates *or* discloses" rule at full strength — including `openEditModal()`, which discloses the type's whole value list before any write.
- **The write path is protected twice over, designed that way from Phase 1 rather than retrofitted.** All three domain actions — [`CreateProductAttributeType`](../../app/Actions/Products/CreateProductAttributeType.php), [`UpdateProductAttributeType`](../../app/Actions/Products/UpdateProductAttributeType.php), [`DeleteProductAttributeType`](../../app/Actions/Products/DeleteProductAttributeType.php) — authorize their own operation as their first statement, each constructor-injecting `App\Actions\Auth\LogRefusedPrivilegedAttempt` and passing `targetType: 'product_attribute_type'` explicitly (`resolveTarget()` auto-resolves only `User` and `Role`). A fourth action in the same folder, `App\Actions\Products\SyncProductAttributeValues`, deliberately authorizes **nothing** — the codebase's fifth shipped instance of "a collaborator invoked only by an already-authorized action needs no gate of its own"; see [architecture/authorization.md](../architecture/authorization.md#productattributetypepolicy--the-seventh-policy-and-the-first-whose-no-policy-recommendation-was-reversed-at-phase-2).

This view renders `$deletingTypeUsageCount` only inside the reactive blocked-delete message below, never as a proactive line in the confirmation dialog, matching `product-categories.blade.php`'s identical choice for its own in-use block.
- **Since story 0030a, `openEditModal()` also computes a per-row usage notice with one bulk query, never one query per row.** [`App\Models\ProductAttributeValue::variantUsageCounts()`](../../app/Models/ProductAttributeValue.php) is called once with the type's own value ids and assigned to `$valueUsageCounts` — see [database/schema.md](../database/schema.md#product_attribute_values) for how this bulk, display-oriented query differs from the type-level and per-value in-use queries story 0029a already shipped over the same pivot. A row with no persisted id yet (an `addValue()`-created row) never renders the notice; the count read is guarded the same way `$rowHook` itself is, to avoid a PHP deprecation notice on undefined-key array access rather than crash.
- **A fourth `@error(...)` outlet, keyed `sku`, renders whichever refusal 0029's already-shipped SKU re-derivation cascade throws when a rename changes a derived SKU** — `derived_sku_taken`, `derived_sku_empty_segment`, `derived_sku_too_long`, or the translated unique-violation race message, all already produced by `SyncProductAttributeValues::reDeriveVariantSkusForRenamedValues()`/`DeriveVariantSku::checked()` (story 0029, unchanged here) and reused as-is with **no new translation key**. One generic `<flux:callout>`, styled like the two existing `@error('values')`/`@error('productAttributeTypeId')` precedents immediately beside it, renders whichever message fires with no per-message branching — the modal stays open and nothing is written, since 0029's transaction rolls back the whole rename on any of the four. Its `:heading="$message"` binding is deliberately **colon-bound**, unlike its two older siblings' `heading="{{ $message }}"` form: the double-brace form double-HTML-encodes a literal quote character inside `$message` under this Flux-folded tag (verified by `Blade::render()` execution), which is exactly what `derived_sku_empty_segment`'s own copy — the one message of the four containing a literal quote — exposes. This is a latent, pre-existing, non-security quirk on the two older callouts, left unchanged since neither's current copy contains a quote.
- **Both modal openers now call `resetValidation()` as their own last statement**, closing a Phase 4 audit finding: dismissing the modal via its `wire:model`-bound `$showModal` directly — the X control or a click outside, bypassing `closeModal()` entirely — left a stale `sku`/`values` error from a previously refused save rendering against a different, unrelated type on reopen, since Livewire persists the error bag across that round trip.
- **Two in-use guards story 0029a added to the backend now have their rendering, discharging that story's own explicit hand-off** ("the markup rendering the blocked-delete message is 0030's"). Deleting a type still backing any product variant throws a `ValidationException` keyed `productAttributeTypeId` — rendered as a `flux:callout` inside the still-open delete modal, the identical `@error('productAttributeTypeId')` pattern `product-categories.blade.php` already established for its own in-use block, naming the exact variant count via `trans_choice('products.variants.type_in_use', ...)`. Removing a value still backing any variant throws on the whole-array key `values` (not a per-row key, since the guard runs after the diff has already decided which ids are being deleted) — rendered as a `flux:callout` inside the still-open create/edit modal via `@error('values')`, naming the count via `products.variants.value_in_use`. Both refusals leave every other field's edits in place, since the whole save is one transaction that never partially applies (D-A5).
- **`removeValue()` and `moveValue()` take a stable, server-generated `key`, never an array index** — the single most important detail the UI sibling story inherits. Each value row is assigned `(string) Str::uuid()` once, when the row is created (`addValue()`, or read from the database in `openEditModal()`), and that key is what `wire:key` and every row-targeting method argument must use. Removing row 1 by *index* would shift row 2 into index 1, reuse the DOM node keyed `1`, and leave the browser's own input showing the old value while the server holds the new one — the standard Livewire foot-gun this design avoids entirely rather than works around.
- **`canEdit`/`canDelete` per row are UI hints, never a layer, and cannot drift from what a click would do.** `loadTypes()` writes `Gate::allows('update'|'delete', $type)` onto each row — the *same* policy methods `save()`/`deleteType()` authorize against. Like `SalesRegionPolicy`/`ProductCategoryPolicy`, `ProductAttributeTypePolicy::update()`/`delete()` ignore their target entirely, so this hint has **no accepted drift** — a property of the policy having no target-dependent branch, not a guarantee.
- **Two of this screen's `ValidationException`s are not row-shaped errors a naive read would expect.** A duplicate value within the same type surfaces as a validation error on `values.*.value` (`distinct:ignore_case`, run only after the array's size and each row's shape have already passed — see [database/schema.md](../database/schema.md#product_attribute_values)'s Phase 4 findings subsection), never as an unhandled `QueryException` reaching the caller; and a race that slips past `distinct:ignore_case` is caught at the composite `UNIQUE(product_attribute_type_id, value)` index by `SyncProductAttributeValues`, which converts SQLSTATE `23000` into the identical `ValidationException` shape rather than letting a raw database error surface.
- **Since story 0030 this route has a `config/modules.php` entry** (`items.product_attribute_types`, gated on exactly `['products.view']`) and matching `lang/{en,es}/navigation.php` leaves — closing the linkless half-state the App-owned-routes preamble above records, the same split `sales-regions.index` sat in between tasks 0017 and 0018. **It shipped as a flat `group: platform` item; story 0080's registry restructuring retired that group and nests it inside the `products` cluster instead** (within the new `store` group), alongside `products` and `product_categories`.

### `App\Livewire\Media\Gallery` — a gated surface with no route, and how a consumer embeds it

Story 0019 (the backend) and story 0020 (the modal itself). **There is no row for this in the table above and there never will be one**: [PRD §2.3](../PRD/PRD.md) makes the Shared Media Gallery a component Products and Blog *embed*, not a page. It is documented here anyway because it is the app's first contract surface that is real, permission-gated and **invisible to `php artisan route:list`** — a reader auditing "what is reachable and what protects it" from the table alone would miss it entirely.

**The consumer contract (story 0020's D2) is the deliverable, because stories 0021 and 0027 bind to it without re-deciding any of it.** Four attributes and one listener is the *entire* integration surface:

```blade
{{-- D12: the consumer decides whether the child renders at all. --}}
@can('viewAny', \App\Models\Media::class)
    <livewire:media.gallery
        wire:model="showFeaturedGallery"
        wire:key="featured-image-gallery"
        :multi="false"
        select-event="featured-image-selected"
        :confirm-label="__('products.featured_image.confirm_label')"
    />
@endcan
```

```php
#[On('featured-image-selected')]
public function setFeaturedImage(array $media): void { /* $media[0] */ }
```

Nine consequences for anyone binding to this, or adding a method to it:

- **`@can` at the consumer site is a *layer*, not the gate.** A bare `Gate::authorize('viewAny', …)` in `mount()` with no wrapper would **403 the entire host page** for anyone who can reach the product editor but lacks `media.view` — an unrelated-permission failure dressed up as a security control. The wrapper is what makes the child's absence graceful; the component's own gates are what make it safe. Hiding a control is never the control ([security/livewire-authorization.md](../security/livewire-authorization.md#gate-at-the-top-of-every-method-that-mutates-or-discloses)).
- **Every method that discloses or mutates re-authorizes on *every* round trip, and this is stricter than a routed screen needs to be.** `mount()`, `toggleSelect()`, `confirmSelection()` ask `viewAny`; `startEditing()` and `updateMediaDetails()` ask `update`; `upload()` asks `create`. All six log their refusal through `App\Actions\Auth\LogRefusedPrivilegedAttempt`. This is [story 0020's Phase 4 finding **F-1** (Medium)](../architecture/authorization.md#a-routeless-livewire-component-has-no-per-request-authorization-backstop): the first implementation gated `mount()` only — sufficient for `users.index`/`roles.index`/`sales-regions.index`, whose routes' `can:` **is** replayed on `/livewire/update`, and **not** sufficient here, where nothing is.
- **`tiles()` fails *closed* instead of throwing, and that asymmetry is deliberate.** It is reached from `render()`, where an `AuthorizationException` would take down the **host** page — exactly what the `@can` layer exists to prevent — so a revoked actor gets an empty array. The two explicit user actions next to it (`toggleSelect()`, `confirmSelection()`) throw and log like every other screen in this app.
- **The event name is consumer-supplied, and that is forced rather than stylistic.** `$this->dispatch($name)` fires a bubbling DOM event routed by Livewire's own `#[On($name)]`; `->to(Gallery::class)` was **verified impossible** for this purpose — `dispatchTo()` resolves by *component name*, so it broadcasts to **every** mounted `Gallery`, and story 0027's product editor embeds two. Two instances on one page must not receive each other's selection.
- **The payload is one shape in both modes — always a list**, `array<int, array{id, title, description, url, webpUrl, avifUrl, width, height}>`. Single-select dispatches a list of exactly one (`$media[0]`); a bare object for single mode was rejected so a listener's signature never depends on a prop set elsewhere. It is **re-fetched from the database at confirm time**, never assembled from what the grid rendered, so a tampered or since-deleted id is silently dropped rather than erroring.
- **`$search` is the only client-writable property besides `$pendingUploads`** and the inline-edit fields; `$multi`, `$selectEvent`, `$confirmLabel`, `$selectedIds` and `$editingMediaId` are all `#[Locked]`. `$open` is the `#[Modelable]` boolean the host toggles, and `cancel()`/`confirmSelection()` close the modal from this side by writing it.
- **Two caps, neither of which may ever drop a staged selection.** The grid renders at most **60** tiles, `latest()` first, with a `data-test="media-results-truncated"` notice when it truncates; one upload batch carries at most **3** files (`MAX_FILES`, lowered from 5 by a Phase 4 re-audit that *measured* five 4000×4000 encodes at **34.8 s** against PHP's 30 s `max_execution_time` default — three measured ~21 s). `$selectedIds` is component state, never a projection of the rendered grid, so neither cap nor a search filter can touch it; the footer count is the only on-screen evidence a filtered-out tile is still staged.
- **Its `data-test` hooks, all icon-only or dynamic and therefore not selectable by visible text**: `media-search`, `media-upload-button`, `media-dropzone`, `media-upload-progress-transport` / `media-upload-progress-processing` (D8's two distinct in-flight phases — only the first has a percentage), `media-tile-{id}` (carrying `aria-pressed`, the assertable selection state — never a CSS class), `media-selection-count`, `media-results-truncated`, `media-empty-state`, `media-cancel`, `media-confirm`, and the inline editor's `edit-media-{id}` / `edit-media-form-{id}` / `save-media-{id}` / `cancel-edit-media-{id}`. Every id interpolated into a `wire:*` argument goes through `@js()` ([security/blade-livewire-output-encoding.md](../security/blade-livewire-output-encoding.md)), and a disabled control's tooltip is a written-out `<flux:tooltip>` wrapper on its own branch — both traps [errors-log.md](../errors-log.md) records, reused verbatim.
- ⚠️ **A role without `media.view` loses the gallery silently.** Under the `@can` wrapper there is no "Add image" affordance, no error and no explanation — the host screen simply has one fewer control. Latent today (every seeded `Administrator` holds all four `media.*` permissions), and real the moment custom roles become common. Recorded here rather than discovered in support.

### `App\Livewire\Components\WysiwygEditor` — the gallery's first real consumer, and the second routeless gated component

Story 0021. **This is also not in the table above and never will be**: same reasoning as `Gallery` immediately above it — no route, reached only over `/livewire/update`, embedded by a host screen. It is worth its own subsection rather than a bullet under `Gallery`'s because it sits **one layer further out**: `WysiwygEditor` *is* a `Gallery` consumer (it embeds `<livewire:media.gallery>` itself, single-select, D4 in the story's own task file), and it is in turn embedded by the product/blog editors that are `WysiwygEditor`'s own consumers — [0027](../../ai-spec/tasks/done/0027-products-list-and-editor-ui.md), [0061](../../ai-spec/tasks/0061-blog-posts-core-crud-backend.md), [0077](../../ai-spec/tasks/0077-product-editor-language-tabs-ui.md) and [0079](../../ai-spec/tasks/0079-blog-post-editor-language-tabs-ui.md). A reusable rich-text toolbar (Bold, Italic, Underline, H2, bullet list, numbered list, link, "Insert image") whose output is HTML a future column stores; the eight-action set and the exact tag set it may emit are fixed by [PRD §2.3](../PRD/PRD.md#23-shared-media-gallery)'s design reference and by the story's own D2, not repeated here.

```blade
<livewire:components.wysiwyg-editor
    wire:model="description"
    wire:key="product-description-editor"
    :label="__('products.description_label')"
/>
```

Seven consequences for anyone binding to this, or adding a method to it:

- **`$value` (the `#[Modelable]` HTML) is deliberately not `#[Locked]`, for the same reason `Gallery`'s `$search` is not** — it is the model binding a consumer's own `wire:model` writes through, and it is untrusted HTML by construction. **This is a hard, load-bearing dependency rather than a detail to skim**: nothing in this component sanitizes `$value` — it cannot, without duplicating [0024a](../../ai-spec/tasks/done/0024a-product-description-html-sanitization.md)'s `symfony/html-sanitizer` allow-list — so **no consumer may bind `wire:model` to a persisted column until that column's own write path runs a server-side sanitizer first.** **Corrected 2026-09-02 (story 0024a)** — this bullet previously credited "0027 and 0077" with already discharging the dependency "via `SanitizeProductDescription` in their `Create`/`UpdateProduct` actions", written speculatively before that class existed and naming the wrong stories as its origin: `CreateProduct`/`UpdateProduct` are [0024](../../ai-spec/tasks/done/0024-products-core-crud-backend.md)'s own actions, and 0027 has none of its own. `App\Actions\Products\SanitizeProductDescription` is **0024a's** class, and its first two real call sites are 0024's `CreateProduct` and `UpdateProduct` — sanitizing `description` before validation on every write — which is what actually discharges this dependency for `products.description` today. See [security/html-sanitization.md](../security/html-sanitization.md) for the mechanism. **Confirmed 2026-09-03 (story 0027):** the product editor binds `<livewire:components.wysiwyg-editor wire:model="description" .../>` and its `save()` calls `CreateProduct`/`UpdateProduct` for every write — no second write path was opened, so it inherited the guarantee for free exactly as predicted rather than needing a sanitizer call of its own; **0061, 0076, 0077 and 0079 remain not yet built**, each recording its own planned use of the class in its own task file (0061 reusing this exact config for the blog `body` column, 0076 adding a second call site behind a model-event layer, 0077/0079 each constructor-injecting the class directly into a Livewire component) rather than being a verified consumer today.
- **The component embeds its own `Gallery` child, `@can`-wrapped exactly as 0020's D12 requires of any embedder**, single-select (`:multi="false"`) — "insert one image at the cursor" has no multi-select reading. The "Insert image" toolbar button itself is **not** hidden for a user lacking `media.view`; it renders `disabled` inside an explicit `<flux:tooltip>` (the tooltip-presence Flux/Blaze trap applies here too — see [errors-log.md](../errors-log.md)), matching every other disabled-row-action convention in this app. The other seven toolbar actions are pure client-side formatting and are unaffected by media permissions.
- **The embedded gallery's `select-event` is derived per mount, never a literal — and this corrects the rationale story 0020's own D2 states for why two galleries on one page never cross-wire.** 0020 D2 credits "DOM bubbling plus `#[On(...)]`" with the disambiguation; that is not the real mechanism. Livewire registers **every** `#[On]`/`$listeners` entry as a page-global `window.addEventListener(name, handler)`, for every mounted component instance — the event **name string** is the only thing separating two listeners, verified directly against `vendor/livewire/livewire/dist/livewire.js`. A component that nests a re-entrant `Gallery` child with a **fixed** literal `select-event` would have every mounted instance receive every other instance's confirmed image the moment a second one is mounted on the same page (a product's short and long description, say). `WysiwygEditor::mount()` derives `'wysiwyg-image-selected-'.$this->getId()` instead, and the matching `#[On('{galleryEvent}')]` on `insertImage()` resolves the whole placeholder from the component's own persisted state on every request — not merely its first one, which matters because `insertImage()` is reached from a **separate** `/livewire/update` round trip than `mount()`, after the modal has already opened. **Any future component nesting a re-entrant `Gallery` (or any other child whose confirm event must not cross-wire) must derive a per-instance-unique event name the same way — a fixed literal is a name collision waiting for a second mounted instance, and it will not show up in a single-instance test.**
- **`openGallery()` and `insertImage()` gate themselves as their own first statement** — `Gate::authorize('viewAny', Media::class)` via `App\Actions\Auth\LogRefusedPrivilegedAttempt`, matching `Gallery`'s own routeless-component pattern ([security/livewire-authorization.md](../security/livewire-authorization.md#the-routeless-case-a-component-with-no-route-has-no-per-request-backstop-at-all)) rather than trusting the host page's `@can` wrapper to be the only perimeter (a Phase 4 security-audit fix, finding F-2 — the first implementation gated neither method). `insertImage()` additionally **re-fetches** the selected item from `Media::query()->find(...)` rather than trusting the client-supplied `url`/`title` fields — the same "derive, never accept" rule `Gallery::confirmSelection()` already follows for its own dispatch payload — so a tampered, malformed or since-deleted id collapses to a silent no-op.
- **The editable region is `wire:ignore`d — the app's first use of that directive.** Livewire must never diff or re-render a `contenteditable` region a user is actively typing into, or it fights the browser's own editing. The convention this establishes (a client-owned region, seeded from the server once and synced back at defined points only, never continuously) is documented in [conventions/base-standards.md](../conventions/base-standards.md#a-wireignored-client-owned-region--the-apps-first-instance). One consequence a consumer must know: because the region is `wire:ignore`d, **a server-side write to `$value` does not appear in the editor** — a consumer resetting its form by nulling the bound property sees the editor keep its old content. There is no programmatic content-replacement hook.
- **Its `data-test` hooks are static strings, and the component's own root carries a per-instance scoping hook**: `data-test="wysiwyg-editor-{{ $this->getId() }}"` on the outermost `<div>`, with every toolbar/region hook (`wysiwyg-bold`, `wysiwyg-italic`, `wysiwyg-underline`, `wysiwyg-h2`, `wysiwyg-bullet-list`, `wysiwyg-numbered-list`, `wysiwyg-link`, `wysiwyg-link-url`, `wysiwyg-link-apply`, `wysiwyg-insert-image`, `wysiwyg-editor-region`) present on every mounted instance — exactly the same duplication trap [playwright-setup.md](../testing/frontend/playwright-setup.md#a-page-embedding-the-same-component-twice-duplicates-every-data-test-hook) already documents for `Gallery`. A browser test against a page mounting two editors must scope its selector to the containing instance's root, never query a hook page-wide.
- ⚠️ **Every button on the toolbar is written as a full `@if ($disabled) … @else … @endif` pair of separately-compiled `<flux:button>` tags, never one tag carrying a conditional `@disabled(...)` directive.** A bare `@disabled(...)` directive call inside a Flux component tag's attribute list does not compile there the way it would on a plain HTML tag — it corrupts the whole tag's attribute string into invalid PHP, a syntax error breaking the entire compiled view. **Narrowed 2026-09-04 (story 0027):** a colon-bound `:disabled="..."` attribute expression is *not* the same shape and is safe on a `<flux:*>` tag at any value — `resources/views/livewire/products/editor.blade.php`'s gallery-reorder buttons use exactly that form and render correctly, verified by execution. Only a `@directive(...)` call written where an attribute is expected breaks. See [errors-log.md](../errors-log.md#a-bare-disableddisabled-inside-a-fluxbutton-tags-attribute-list-corrupts-the-whole-compiled-view--2026-08-31).

### `email-change.confirm` — the first app-owned route deliberately outside `auth`

Every other `settings/*` route sits inside one of this file's two `auth` groups. This one is registered at the **file's top level**, next to `well-known.passkeys`, and its complete middleware list is `signed` + `throttle:6,1` — nothing else:

```php
// routes/settings.php — file top level, NOT inside either Route::middleware([...])->group(...)
Route::get('settings/email/confirm/{user}/{hash}', ConfirmEmailChangeController::class)
    ->middleware(['signed', 'throttle:6,1'])
    ->name('email-change.confirm');
```

The omission is the point, not an oversight: what the link proves is control of the **mailbox** (signed, address-bound, single-use, 60 minutes), not an authenticated session. Requiring `auth` would deadlock the case an administrator most needs it for — changing the address of an `Inactive` user, who cannot sign in and so could never reach the link that would activate them. `tests/Feature/Settings/EmailChangeTest.php` carries a dedicated "reachable while signed out" test precisely because every other test in that file runs `actingAs()` and would miss the regression.

Two more facts about this route:

- **It is also this repo's first signed route with a route-model-bound parameter**, which is why `bootstrap/app.php` now globally prepends `ValidateSignature` ahead of `SubstituteBindings` in the middleware priority list — otherwise a tampered `{user}` would 404 (binding failure) while any other tampering 403s, an oracle for "does this user id exist". The reasoning and the verified side effects across the whole `web` pipeline are in [security/signed-link-verification.md](../security/signed-link-verification.md#validatesignature-must-run-before-substitutebindings).
- **It responds in two shapes.** A tampered or expired link fails the signature check with a **403**; a still-validly-signed link whose address no longer matches (replay, supersede, cancel) is refused by the controller with a **302** to `profile.edit` carrying a `status` flash. Don't assert 403 for both.

The controller behind it is the repo's first domain controller — the convention it establishes (an HTTP boundary in front of an `app/Actions/` class) is documented in [conventions/base-standards.md](../conventions/base-standards.md#controllers-sit-in-front-of-actions-not-instead-of-them).
