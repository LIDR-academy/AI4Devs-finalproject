# 0001. UUID (v7) primary keys for domain entities

## Status
Accepted

## Context
Seven domain entities need public, non-sequential identifiers that are safe to expose in URLs and APIs without leaking row counts or enabling enumeration:

- `users` — the only one of the seven that already exists in code today (see [database/schema.md](../database/schema.md) and [`App\Models\User`](../../app/Models/User.php)), currently keyed by a `bigint` auto-increment `id`.
- Products, Product Variants, Product Categories — future, PRD Epic 2 (see [../PRD/PRD.md](../PRD/PRD.md)), not yet implemented.
- Blog Categories, Blog Tags, Blog Posts — future, PRD Epic 4 (see [../PRD/PRD.md](../PRD/PRD.md)), not yet implemented.

The naive way to get a non-sequential key is a random UUIDv4, but this app runs on MySQL/InnoDB (see [database/schema.md](../database/schema.md)), where every table is physically stored as a clustered index ordered by its primary key. A random PK forces inserts into arbitrary points of that index, causing page splits, index fragmentation, and write amplification — a real, measurable cost at scale, not a theoretical one.

## Decision
All seven entities use a **UUID version 7 as their sole primary key**, generated by **Laravel 13's native `HasUuids` trait** (`Illuminate\Database\Eloquent\Concerns\HasUuids`), whose default `newUniqueId()` returns `Str::uuid7()`.

- **UUIDv7 is time-ordered.** Its leading bits are a Unix millisecond timestamp, so new keys sort monotonically and inserts append to the end of the clustered index — the same locality benefit an auto-increment key gives, while remaining a literal, standard UUID.
- **The UUID replaces the primary key entirely.** Migrations declare a single `$table->uuid('id')->primary();`. There is no separate internal `bigint` and no dual-column pattern.
- **Model requirement:** add `use HasUuids;` to the model's trait list. Do **not** also declare `$keyType` / `$incrementing` properties — the trait's `HasUniqueStringIds` concern overrides `getKeyType()` / `getIncrementing()` as methods, so the properties would be redundant. The `@property` PHPDoc for `id` is typed `string`, not `int`.
- **Route-model binding** needs no syntax change (`{model}` still binds on `id`), but `resolveRouteBindingQuery()` validates the parameter with `Str::isUuid()` before querying, so a malformed non-UUID route parameter now yields a `ModelNotFoundException` (404) immediately instead of a doomed query.
- **Factories** need no change — the trait populates the key just before insert, exactly as auto-increment models never set `id` in their factory `definition()` today.

The concrete model/migration convention this implies is documented in [conventions/base-standards.md](../conventions/base-standards.md#uuid-primary-keys-convention-to-follow-not-yet-in-the-repo) and [database/migrations.md](../database/migrations.md#upcoming-convention-uuid-primary-keys).

## Alternatives considered
- **ULID** (via `HasUlids`) — rejected. A `database-expert` initially suggested it for its time-ordering, but ULID is a Crockford-base32 string, not a literal RFC-4122 UUID; it would introduce a second, non-standard identifier format. Once UUIDv7's native time-ordering was confirmed to solve the exact index-locality problem ULID was proposed for, ULID lost its only advantage while keeping its interoperability cost.
- **Random UUIDv4** — rejected. It reintroduces the MySQL clustered-index fragmentation and write-amplification this decision exists to avoid.
- **Dual column (internal `bigint` PK + separate public `uuid`)** — rejected. It adds a second ID concept and extra join/lookup complexity that isn't justified at this project's scale, and it doesn't match this codebase's single-primary-key migration style.

## Consequences
- Six of the seven entities are greenfield: they are simply created with a UUID PK from day one, with no migration complexity.
- `users` is the one non-greenfield case. Converting `users.id` from `bigint` to UUID is a **breaking alteration migration requiring a data backfill**, not a fresh `create_table`, and it cascades to three real dependents that must change in the same unit of work. Each cascade is a **new alteration migration** against the existing table — never a hand-edit of the original already-run `create_*` migration file:
  - `passkeys.user_id` — its target column definition is `foreignUuid('user_id')->constrained()->cascadeOnDelete()`, applied by a new alteration migration; do not edit `2024_01_01_000000_create_passkeys_table.php` in place.
  - `sessions.user_id` — its column type must change symmetrically to keep matching `users.id`, applied by a new alteration migration; do not edit `0001_01_01_000000_create_users_table.php` in place.
  - `spatie/laravel-permission`'s polymorphic `model_has_roles` / `model_has_permissions` tables — their `model_id` morph key is `unsignedBigInteger` today. Two separate steps are required and must not be conflated: (1) set `config/permission.php`'s `column_names.model_morph_key` to the new name (e.g. `model_uuid`) so the package *queries* the right column, and (2) physically rename and retype the column to `uuid` in a **new** migration (e.g. `convert_model_morph_key_to_uuid_in_permission_tables_table`) that alters the existing tables. The config change alone does not touch the schema. Never edit the vendored, already-run `2026_07_12_181045_create_permission_tables.php` in place — see its warning in [database/migrations.md](../database/migrations.md#package-vendored-migrations).
- This `users` migration work is scheduled for Epic 1's actual TDD implementation (per [workflow.md](../workflow.md)), not now. It is flagged here so whoever implements it is not surprised that it is more than a one-line change.
- Keys are UUID strings stored as `CHAR(36)` (36 bytes — Laravel's `$table->uuid()` maps to `CHAR(36)` in MySQL, per `MySqlGrammar::typeUuid()`) rather than 8-byte bigints — a larger index/FK footprint, in exchange for enumeration-safe public identifiers and preserved insert locality.
