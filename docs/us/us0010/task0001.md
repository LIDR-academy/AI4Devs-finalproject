# TASK0001 — Backend: endpoints historial de bookings y confirmar asistencia

## User Story Padre
[US0010](us0010.md) — Ver historial + confirmar asistencia

## Descripción
Implementar endpoint para listar bookings del cliente autenticado y endpoint para confirmar asistencia (transición confirmed → completed).

## Detalles de Implementación
- **Capa**: Backend
- **Componentes afectados**: `backend/Controllers/BookingsController.cs`, `backend/Domain/Services/BookingService.cs`
- **Endpoint(s)**:
  - `GET /api/bookings/me?status=&page=&pageSize=`
  - `POST /api/bookings/{id}/complete`

## Pasos Técnicos
1. GET /api/bookings/me:
   - Autenticado: filtra por client_id del JWT
   - Filtro opcional por status
   - Incluir datos del artista (nombre, avatar, slug)
   - Incluir flag `hasReview: bool` (existe Review para ese booking)
   - Ordenar: próximas primero (booking_date > now), luego históricas desc
   - Paginación: page, pageSize (default 10)
2. POST /api/bookings/{id}/complete:
   - Validar: booking pertenece al usuario autenticado
   - Validar: status == 'confirmed'
   - Validar: booking_date < ahora (fecha ya pasó)
   - Transición: status → 'completed'
   - Retornar booking actualizado
3. Lógica de negocio:
   - No se puede completar un booking futuro
   - No se puede completar un booking cancelado
   - Solo el cliente owner puede completar
4. Tests TDD:
   - GET me: retorna solo bookings del usuario autenticado
   - GET me: incluye hasReview flag
   - GET me: ordenamiento correcto (próximas primero)
   - Complete: transición exitosa si fecha pasó y status confirmed
   - Complete: falla si fecha futura (400)
   - Complete: falla si otro usuario (403)
   - Complete: falla si status no es confirmed (409)

## Criterios de Done
- [ ] Listado retorna solo bookings del usuario autenticado
- [ ] Flag hasReview incluido
- [ ] Confirmar asistencia funciona con validaciones correctas
- [ ] No permite completar bookings futuros
- [ ] Tests TDD completos
- [ ] Paginación correcta
