# 📖 Historia de Usuario: US-032 — Escaneo de Código de Barras en Extracción de Bodega

## 👤 Rol del Usuario
Como operario autorizado (Personal de Bodega/Cocina),

## 🎯 Objetivo / Valor de Negocio
Quiero escanear el código de barras de un insumo con la cámara de la tablet al registrar una extracción de bodega, para seleccionar el insumo correcto sin tener que buscarlo por nombre en una lista larga, reduciendo errores de selección y tiempo perdido durante el rush operativo.

## 📌 Justificación (Gap Analysis)
Hoy `WarehouseExtractionModal` exige buscar el insumo por nombre en un selector — con un catálogo grande, esto es lento bajo presión de servicio. El escaneo por cámara es una capacidad de software puro (sin hardware nuevo) que acelera el flujo de extracción ya existente, sin cambiar su lógica de negocio de fondo (Invariante 1 de stock negativo, etc. — todo sigue igual, solo cambia cómo se selecciona el insumo).

## 🗣️ Decisiones de Negocio Consultadas con el Humano (Guard 28)
*   **Pregunta 1:** Si el código escaneado no coincide con ningún insumo del catálogo, ¿qué debe pasar?
*   **Respuesta:** Se ofrece la opción de crear un Insumo nuevo vinculado a ese código — nunca se descarta el escaneo en silencio.
*   **Pregunta 2:** Dado que hoy el Non-Goal #4 del PRD excluye "Integración de Hardware Físico" (escáneres/balanzas USB/Bluetooth), ¿el escaneo por cámara integrada del dispositivo cuenta como una excepción a documentar formalmente?
*   **Respuesta:** Sí — aclarado explícitamente en `docs/01_product_definition/02_prd.md` §4 (Non-Goal #4): excluye hardware dedicado, la cámara ya integrada del dispositivo queda fuera de esa exclusión.
*   **Pregunta 3:** Cuando un operario `KITCHEN_STAFF` (no `ADMIN`) escanea un código sin match, ¿puede crear el Insumo nuevo él mismo, o queda pendiente para que un `ADMIN` lo complete?
*   **Respuesta:** Solo `ADMIN` completa el alta — mismo patrón de rol que ya rige `POST /api/v1/stock/insumos` (`TK-057`). `KITCHEN_STAFF` solo ve el aviso de "sin match" y el código escaneado; no se persiste ningún registro "pendiente" en backend — el `ADMIN` lo da de alta después usando el formulario existente, con el campo `barcode` disponible para completarlo a mano si el operario le comunicó el código, o volviendo a escanearlo él mismo.

## 🥒 Criterios de Aceptación (BDD - Sintaxis Gherkin)

### Escenario 1: Escaneo Exitoso — Insumo Preseleccionado
- **Given** Un insumo "Leche Entera 1L" con `barcode: "7791234567890"` registrado en el catálogo.
- **When** El operario abre `WarehouseExtractionModal`, activa el escaneo por cámara y enfoca un código de barras que decodifica a `"7791234567890"`.
- **Then** El sistema consulta `GET /api/v1/stock/insumos/by-barcode/7791234567890`, encuentra el insumo y lo preselecciona en el formulario de extracción, permitiendo continuar el flujo normal (elegir sector, cantidad, confirmar).

### Escenario 2: Código Sin Match — Aviso, Sin Bloqueo del Flujo Manual
- **Given** Un código de barras `"9999999999999"` que no existe en ningún insumo del catálogo.
- **When** El operario `KITCHEN_STAFF` escanea ese código.
- **Then** El sistema responde `404 Not Found`, el frontend muestra un aviso no bloqueante ("Código no encontrado en el catálogo — solicita a un Administrador que lo dé de alta") y el operario puede seleccionar el insumo manualmente para continuar la extracción sin interrupción.

### Escenario 3 (Edge Case — Rol): ADMIN da de alta el Insumo con el código ya capturado
- **Given** Un `ADMIN` autenticado que abre `+ Nuevo Insumo` tras el aviso del Escenario 2.
- **When** Completa el formulario incluyendo `barcode: "9999999999999"` y confirma.
- **Then** El sistema crea el insumo con ese código (`POST /api/v1/stock/insumos`), y un escaneo posterior de ese mismo código lo encuentra correctamente.
