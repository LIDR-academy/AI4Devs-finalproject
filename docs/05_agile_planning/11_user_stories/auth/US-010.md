# 📝 US-010: Gestión Mínima de Personal (Alta y Bloqueo de Operarios)

> **Navegación del Framework SDD:**  
> [⬅️ Volver a US-001 (auth/US-001.md)](./US-001.md) | [📖 Índice de Historias de Usuario (indice_user_stories.md)](../indice_user_stories.md) | [Siguiente: Índice de Tickets (12_tickets/indice_tickets.md)](../../12_tickets/indice_tickets.md) ➡️

---

## 🗣️ Narrativa (Comportamiento y Negocio)
**Como** Administrador del restaurante (Rol: ADMIN),  
**Cuando** contrato un nuevo operario de cocina o necesito retirar el acceso de uno existente,  
**Quiero** poder dar de alta una cuenta con nombre, rol y PIN, y bloquear o reactivar cuentas existentes desde la API sin intervención manual sobre la base de datos,  
**Para** mantener el control de acceso al día sin depender de un despliegue de código ni de un operador técnico externo.

---

## 🚦 Precondiciones
- El solicitante debe estar autenticado con un token JWT válido y rol `ADMIN`.
- Debe existir al menos un administrador activo en el sistema (ver [US-012: Bootstrap del Primer Administrador](#) — cubierto técnicamente por `TK-051`, ticket sin historia de usuario dedicada por ser un habilitador de infraestructura).

---

## 🧪 Criterios de Aceptación (BDD Gherkin)

@critical @smoke
### Escenario 1: Alta exitosa de un nuevo operario (Happy Path)
*   **Given** que un Administrador autenticado envía nombre `"Nuevo Operario"`, rol `KITCHEN_STAFF` y PIN `"4321"`
*   **When** invoca `POST /api/v1/auth/users`
*   **Then** el sistema crea la cuenta con estado `ACTIVE`, retorna `HTTP 201 Created`
*   **And** el operario puede autenticarse inmediatamente con el PIN asignado vía `POST /api/v1/auth/login-pin`.

@critical
### Escenario 2: Bloqueo de un operario existente
*   **Given** que existe un operario activo `"Carlos Gomez"`
*   **When** un Administrador invoca `PATCH /api/v1/auth/users/{id}/status` con `{ "action": "BLOCK" }`
*   **Then** el sistema cambia el estado del operario a `BLOCKED` y retorna `HTTP 200 OK`
*   **And** cualquier intento posterior de login de ese operario es rechazado con `HTTP 403 Forbidden`.

@edge
### Escenario 3: Control de acceso estricto (QA Edge Case Senior)
*   **Given** que un usuario autenticado con rol `KITCHEN_STAFF` (no `ADMIN`) intenta crear o bloquear un usuario
*   **When** invoca `POST /api/v1/auth/users` o `PATCH /api/v1/auth/users/{id}/status`
*   **Then** el sistema rechaza la operación con `HTTP 403 Forbidden`
*   **And** si el `id` del operario objetivo no existe, el sistema retorna `HTTP 404 Not Found` en vez de crear un registro parcial.

---

## 🔒 Criterios de Aceptación No Funcionales (NFRs)
*   **Seguridad:** El PIN nunca se persiste en texto plano; reutiliza el mismo mecanismo de hash con salt por usuario que `US-001`.
*   **Idempotencia de Estado:** Bloquear un operario ya bloqueado (o reactivar uno ya activo) no debe fallar ni duplicar efectos secundarios.
*   **Auditoría:** Todo cambio de estado debe quedar reflejado inmediatamente en el resultado de `GET /api/v1/auth/users` equivalente (consulta directa del estado actual, sin caché obsoleto).

---

## 📊 Evaluación INVEST

*   **[I]ndependiente:** Sí. No requiere la existencia de insumos ni remanentes; solo depende de `US-001` (autenticación) como prerrequisito de control de acceso.
*   **[N]egociable:** Sí. El conjunto de roles asignables o el formato exacto del PIN pueden ajustarse en refinamiento.
*   **[V]aliosa:** Sí. Sin esta historia, dar de alta o baja personal exigía editar directamente la base de datos o el script de seed, bloqueando la operación real del restaurante.
*   **[E]stimable:** Sí. Reutiliza el hash de PIN y el middleware JWT ya existentes de `US-001`.
*   **[S]mall (Pequeña):** Sí. Dos endpoints CRUD acotados sobre la entidad `User` ya existente.
*   **[T]estable:** Sí. Verificable mediante pruebas de integración sobre `POST /api/v1/auth/users` y `PATCH /api/v1/auth/users/{id}/status`.

## 📌 Nota de Alcance
Esta historia cubre únicamente el backend (`TK-049`). La interfaz de administración táctil/web para gestionar personal (alta, bloqueo, listado) **no ha sido implementada** — queda registrada como deuda pendiente en la [Matriz de Trazabilidad](../../13_matriz_trazabilidad.md).
