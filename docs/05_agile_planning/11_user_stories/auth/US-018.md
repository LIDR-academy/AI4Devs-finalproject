# 📖 US-018: Recuperación de Acceso y Reseteo de PIN del Administrador por Email

> **Navegación del Framework SDD:**  
> [📖 Índice de Historias de Usuario](../indice_user_stories.md) | [Siguiente: TK-077](../../12_tickets/auth/TK-077.md)

---

## 📝 Descripción de la Historia

**Como** Administrador del Restaurante (`ADMIN`),  
**Quiero** solicitar el restablecimiento de mi PIN de acceso mediante mi correo electrónico verificado recibiendo un token de un solo uso con expiración de 15 minutos,  
**Para** recuperar el control operativo del sistema de forma autónoma y segura en caso de olvido de clave o bloqueo de cuenta por intentos fallidos, sin depender de acceso manual a la consola del servidor.

---

## 🎯 Criterios de Aceptación (BDD Gherkin)

### Escenario 1: Solicitud exitosa de restablecimiento de PIN para un Administrador registrado
```gherkin
Given que existe un usuario con rol "ADMIN" y correo verificado "admin@restostock.com"
When el usuario envía una solicitud POST a "/api/v1/auth/forgot-pin" con el payload:
  """json
  { "email": "admin@restostock.com" }
  """
Then el sistema responde con HTTP 200 y mensaje genérico "Si el correo coincide con un administrador registrado, se enviaron instrucciones de recuperación."
And se genera un token criptográfico de recuperación firmado con expiración a los 15 minutos
And se despacha un correo electrónico con el enlace de recuperación (Magic Link) que contiene el token.
```

### Escenario 2: Mitigación de enumeración de usuarios en solicitud de recuperación
```gherkin
Given que un atacante envía una solicitud POST a "/api/v1/auth/forgot-pin" con un correo inexistente "hacker@desconocido.com"
When la API procesa la petición
Then el sistema responde exactamente con HTTP 200 y el mismo mensaje genérico "Si el correo coincide con un administrador registrado, se enviaron instrucciones de recuperación."
And no se envía ningún correo ni se filtran detalles sobre la existencia del usuario en el sistema.
```

### Escenario 3: Restablecimiento exitoso de PIN mediante token válido
```gherkin
Given que un Administrador tiene un token de recuperación válido no expirado
When el Administrador envía una solicitud POST a "/api/v1/auth/reset-pin" con el payload:
  """json
  {
    "token": "TOKEN_VALIDO_DE_15_MINUTOS",
    "newPin": "9876"
  }
  """
Then el sistema responde con HTTP 200 y mensaje "PIN de administrador actualizado exitosamente."
And el PIN del Administrador se actualiza con el nuevo hash salado en la base de datos
And el estado del Administrador pasa a "ACTIVE" y su contador de intentos fallidos se resetea a 0
And el token de recuperación queda invalidado de forma permanente (One-Time Use).
```

### Escenario 4: Rechazo por token expirado o alterado
```gherkin
Given que han transcurrido más de 15 minutos desde la emisión del token de recuperación
When el usuario intenta enviar una solicitud POST a "/api/v1/auth/reset-pin" con el token expirado
Then el sistema responde con HTTP 401 Unauthorized bajo formato RFC 7807
And el mensaje de error indica "El token de recuperación es inválido o ha expirado."
And el PIN del usuario no sufre modificaciones.
```
