# 📖 Historia de Usuario: US-023 — Navegación por Rutas y Shell de Aplicación FEFO

## 👤 Rol del Usuario
Como operario autorizado o administrador que usa RestoStock en una pantalla táctil de cocina o en el backoffice,

## 🎯 Objetivo / Valor de Negocio
Quiero que la aplicación tenga una barra de navegación de nivel superior con direcciones propias (Inventario, Estaciones, Recetas, Reportes, Ajustes) en lugar de un único tablero con menús y paneles superpuestos, para orientarme de un vistazo sobre dónde estoy, poder usar el botón "atrás" del navegador, recargar sin perder la sección, y compartir un enlace directo a la pantalla que estoy usando.

## 📌 Justificación (Iniciativa de Diseño)
Cierra la tercera lámina ("Aplicación") de la propuesta visual Sistema FEFO validada por el humano en `US-022`, que quedó explícitamente fuera de alcance de esa historia por ser una decisión de arquitectura de información aparte del sistema de color/tipografía. Hoy `apps/frontend/src/App.tsx` es una sola página: el tablero de cocina con ~10 modales y un menú desplegable de Administración; no existe ninguna librería de routing. Adoptar rutas reales requiere una enmienda al stack manifest (Guard 24), aprobada por el humano el 2026-09-02 (`docs/00_stack_manifest.md` v1.13.0).

## 🗣️ Decisiones de Negocio y Fuentes Técnicas Consultadas con el Humano (Guard 24 / 28 / 34)
*   **Pregunta 1 (Guard 24):** ¿Se adopta una librería de routing y cuál?
*   **Respuesta:** Sí — `react-router-dom@7.18.3` con data router (`createBrowserRouter` + `RouterProvider`). Se descartó `react-router@8.x` por exigir React 19 (el stack fija React 18). Enmienda registrada en `docs/00_stack_manifest.md` §4 v1.13.0.
*   **Pregunta 2 (Guard 34):** ¿Fuente autoritativa para redactar las reglas de codificación de react-router?
*   **Respuesta:** Documentación oficial `reactrouter.com`. `SK-27` sintetiza `docs/04_governance_and_quality/rules/react-router_rules.md` estrictamente desde ahí.
*   **Pregunta 3 (Guard 28 — arquitectura de información):** ¿Cómo se mapean las 5 etiquetas de nav a las features existentes?
*   **Respuesta:** Inventario = Tablero FEFO de cocina (remanentes activos) · Estaciones = extracción de bodega (operario) + gestión de ubicaciones (ADMIN) + catálogo/reabastecimiento de insumos (ADMIN) · Recetas = Recetario — consulta para todos, alta de recetas para ADMIN (`features/recipes`) · Reportes = dashboard de mermas y KPIs · Ajustes = configuración del restaurante + gestión de usuarios + roles + historial de movimientos.
*   **Pregunta 4 (Guard 28 — control de acceso por ruta):** ¿Qué rutas quedan restringidas y a qué rol?
*   **Respuesta:** Reportes y Ajustes solo `ADMIN` a nivel de **ruta** (`<ProtectedRoute>` redirige a `/` si falta el rol). Inventario, Estaciones y Recetas visibles para cualquier operario autenticado, pero las **acciones administrativas dentro de esas rutas** (crear insumo, reabastecer, crear receta, gestionar ubicaciones — todas con `requireRole('ADMIN')` en backend) se renderizan condicionalmente por rol: un operario no-ADMIN ve las vistas de consulta sin esos botones (resuelto en `TK-085-FE` tras el hallazgo D-1 de `AUDIT-DEV-003` — un botón que devuelve 403 es regresión de UX, no "cero regresión funcional"). Es el mismo gating que aplicaba el menú de Administración, ahora repartido entre la capa de ruta y la de acción.
*   **Pregunta 5 (Guard 28 — alcance de la migración):** ¿Los flujos que hoy son modales pasan a ser rutas?
*   **Respuesta:** No. Solo las secciones de nivel superior son rutas. Las operaciones transitorias (Extraer de Bodega, Preparar Receta, Conciliar Turno, Descartar) siguen como modales lanzados desde su ruta padre.
*   **Pregunta 6 (Guard 28 — tratamiento espacial):** ¿Se adopta la barra lateral tipo comanda (wordmark vertical + perforaciones) de la lámina?
*   **Respuesta:** Sí, se adopta el shell completo.
*   **Relación con `US-015` (Dynamic RBAC, `TK-073`, aún no implementada):** `<ProtectedRoute>` compara `currentUser.role` por ahora; cuando `US-015` entregue permisos granulares y autoredirección por perfil, la guarda de ruta se realinea a ese modelo sin rehacer el shell.

## 🥒 Criterios de Aceptación (BDD - Sintaxis Gherkin)

### Escenario 1: Deep-link y botón "atrás" del navegador
- **Given** un operario autenticado que está en Inventario (`/`).
- **When** navega a Recetas con la barra superior, recarga la página, y luego pulsa el botón "atrás" del navegador.
- **Then** tras la recarga sigue en Recetas (la URL es `/recetas`), y el botón "atrás" lo devuelve a Inventario sin recargar toda la aplicación (transición de ruta cliente).

### Escenario 2: Ruta protegida por rol
- **Given** un operario con rol distinto de `ADMIN`, autenticado.
- **When** intenta abrir `/reportes` escribiendo la URL directamente.
- **Then** el sistema lo redirige a `/` sin renderizar el contenido de Reportes, de forma consistente con el gating que hoy hace el menú de Administración.

### Escenario 3: El shell no rompe ningún flujo funcional existente
- **Given** cualquier flujo actual (login PIN, extracción de bodega, conciliación de turno, gestión de usuarios).
- **When** se ejecuta ese flujo dentro de la nueva estructura de rutas.
- **Then** el flujo se completa igual que antes y la suite de tests frontend existente pasa sin modificar ninguna aserción de comportamiento (solo se permiten ajustes de tests que dependían de que todo viviera en una sola página).

### Escenario 4: Sesión ausente
- **Given** un dispositivo sin sesión activa.
- **When** se abre cualquier ruta (`/`, `/estaciones`, `/reportes`, …).
- **Then** se muestra `PinLoginModal` (comportamiento actual), y tras autenticarse el usuario aterriza en la ruta que había pedido.
