# 📖 Historia de Usuario: US-024 — Contenido de Ruta Inline y Consistente

## 👤 Rol del Usuario
Como administrador que navega el shell de rutas del Sistema FEFO,

## 🎯 Objetivo / Valor de Negocio
Quiero que Reportes y cada sección de Ajustes se abran como una página normal dentro de la aplicación —no como una ventana emergente flotante con overlay oscuro— y que cada sección tenga su propia dirección enlazable, para navegar de forma coherente con el resto de la app (Inventario, Estaciones, Recetas ya se ven así) y poder recargar o compartir el enlace directo a una sección concreta de Ajustes.

## 📌 Justificación (Corrección de `US-023`)
`US-023` (`TK-085-FE`) montó los componentes existentes bajo rutas **sin reescribirlos** (alcance frontend-only). `ReportsDashboard` estaba construido como `<Modal>` (se abría desde el menú Administración), así que `/reportes` renderiza un overlay flotante `position: fixed; z-index: 1000` mientras `/estaciones` y `/recetas` se ven inline — **inconsistencia visible**, detectada por el humano durante la verificación en vivo del stack Docker (`09_live_stack_verification_workflow.md`). Además `/ajustes` es una única pantalla con 5 modales lanzados desde tarjetas, sin URL propia para cada sección.

## 🗣️ Decisiones de Negocio Consultadas con el Humano (Guard 28)
*   **Pregunta 1:** ¿Estructura de `/ajustes` con las 5 secciones inline — sub-rutas, pestañas con `?tab=`, o pestañas sin URL?
*   **Respuesta:** **Sub-rutas deep-linkables** — `/ajustes/configuracion`, `/ajustes/personal`, `/ajustes/roles`, `/ajustes/movimientos`, `/ajustes/catalogo`, con barra de pestañas compartida. Coherente con el objetivo de `US-023` (rutas enlazables + botón atrás).
*   **Pregunta 2:** ¿Formalización en el backlog?
*   **Respuesta:** Nueva `US-024` con `TK-089-FE` (`/reportes` inline) y `TK-090-FE` (`/ajustes` inline con sub-rutas).
*   **Pregunta 3 (control de acceso):** ¿Cambia el gating de rol?
*   **Respuesta:** No. `/reportes` y las 5 sub-rutas de `/ajustes` siguen tras `<ProtectedRoute requiredRole="ADMIN">`. Los `if (userRole !== 'ADMIN')` internos de los paneles quedan como código muerto para el montaje en ruta (ya lo cubre `ProtectedRoute`) y se limpian (Guard 5) — los paneles no se montan en ningún otro punto tras `US-023`.
*   **Pregunta 4 (qué se queda como modal):** Los formularios/acciones transitorias —alta de operario, alta de insumo/receta, reabastecimiento, edición de configuración, confirmaciones de borrado, selectores— **siguen siendo `<Modal>`** lanzados desde dentro de su ruta.

## 🥒 Criterios de Aceptación (BDD - Sintaxis Gherkin)

### Escenario 1: Reportes se muestra inline
- **Given** un administrador autenticado.
- **When** navega a Reportes por la barra superior.
- **Then** el dashboard de mermas se renderiza inline dentro del `<main>` del shell — sin overlay oscuro, sin card flotante centrada, sin botón "X" de cerrar; se sale navegando a otra sección.

### Escenario 2: Sub-ruta de Ajustes deep-linkable + botón atrás
- **Given** un administrador que abre `/ajustes/personal` directamente en la barra de direcciones y recarga la página.
- **When** luego pulsa "Movimientos" en la barra de pestañas de Ajustes y después el botón "atrás" del navegador.
- **Then** la recarga lo mantiene en Personal (URL `/ajustes/personal`); pulsar "Movimientos" cambia la URL a `/ajustes/movimientos`; "atrás" lo devuelve a `/ajustes/personal` — todo por transición de ruta cliente, sin recargar la app completa.

### Escenario 3: Acceso por rol conservado
- **Given** un operario con rol distinto de `ADMIN`.
- **When** escribe `/ajustes/roles` en la barra de direcciones.
- **Then** el sistema lo redirige a Inventario (`/`) sin renderizar el contenido.

### Escenario 4: Cero regresión funcional
- **Given** cualquier flujo administrativo (crear operario, editar configuración, dar de alta un insumo, consultar el historial de movimientos).
- **When** se ejecuta dentro de la nueva estructura inline/sub-rutas.
- **Then** el flujo se completa igual que antes y la suite de tests frontend existente pasa sin modificar aserciones de comportamiento (solo ajustes de tests que dependían de la forma modal).
