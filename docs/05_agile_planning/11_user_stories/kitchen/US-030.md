# 📖 Historia de Usuario: US-030 — Catálogo de Motivos de Consumo

## 👤 Rol del Usuario
Como Administrador General.

## 🎯 Objetivo / Valor de Negocio
Quiero mantener un catálogo de motivos de consumo (crear, editar la etiqueta, activar/desactivar), para que el equipo de cocina siempre elija de una lista consistente al declarar por qué consumió un insumo — en vez de texto libre disperso que no sirve para analizar dónde se va el inventario.

## 📌 Justificación (Gap Analysis)
`ADR-004`: el consumo manual (`US-004`) y la varianza de cierre de turno (`US-008`) van a exigir un motivo estructurado. Ese catálogo necesita un dueño (el Administrador) y una pantalla de gestión — mismo patrón ya usado para roles (`US-015`).

## 🗣️ Decisiones de Negocio Consultadas con el Humano (Guard 28)
*   **Desactivar, nunca borrar (ADR-004 §3.1):** un motivo referenciado por movimientos históricos no puede desaparecer; `isActive = false` lo saca del selector sin romper el pasado.
*   **Semilla editable:** arranca con motivos típicos (`Preparación de plato`, `Degustación / prueba`, `Cortesía a cliente`, `Error de manipulación`, `Otro`), editables/desactivables después.
*   **Alcance:** este catálogo es solo para `consume` y la varianza de conciliación de turno (`US-004`/`US-008`) — los descartes existentes no lo usan (por ahora).

## 🔗 Dependencias
*   Prerrequisito de **US-004** y **US-008** (amendadas por `ADR-004`).

## 🥒 Criterios de Aceptación (BDD - Sintaxis Gherkin)

### Escenario 1: Listado de Motivos Activos (Cualquier Autenticado)
- **Given** el catálogo tiene 5 motivos activos y 1 desactivado.
- **When** cualquier usuario autenticado consulta `GET /api/v1/consumption-reasons`.
- **Then** el sistema devuelve solo los 5 activos, sin el desactivado.

### Escenario 2: Administrador Crea un Motivo Nuevo
- **Given** el Administrador está autenticado.
- **When** ejecuta `POST /api/v1/consumption-reasons` con `{ "label": "Ajuste de porción" }`.
- **Then** el sistema crea el motivo con `isActive = true` por defecto y lo devuelve con `201`.

### Escenario 3: Administrador Desactiva un Motivo (Edge Case)
- **Given** un motivo "Cortesía a cliente" ya fue usado en 3 consumos históricos.
- **When** el Administrador ejecuta `PUT /api/v1/consumption-reasons/:id` con `{ "isActive": false }`.
- **Then** el motivo deja de aparecer en `GET /api/v1/consumption-reasons` (listado activo) pero los 3 movimientos históricos que lo referencian no se alteran.

### Escenario 4: Rol no-ADMIN no puede administrar el catálogo (Edge Case)
- **Given** un operario con rol `KITCHEN_STAFF` autenticado.
- **When** intenta `POST /api/v1/consumption-reasons` o `PUT /api/v1/consumption-reasons/:id`.
- **Then** el sistema responde `403 Forbidden`; el `GET` sigue permitido (lectura para cualquier autenticado).
