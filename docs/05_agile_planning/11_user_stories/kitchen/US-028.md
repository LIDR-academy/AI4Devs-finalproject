# 📖 Historia de Usuario: US-028 — Cierre de Preparación de Receta

## 👤 Rol del Usuario
Como Operario de Cocina o Administrador autenticado.

## 🎯 Objetivo / Valor de Negocio
Quiero cerrar una preparación de receta declarando cuántas porciones produje realmente y, por cada ingrediente extraído, cuánto **sobró y dónde lo guardé** y cuánto se **descartó y por qué**, para que el sistema deje constancia trazable de lo que pasó con cada insumo — quién lo preparó, dónde quedó físicamente el sobrante y el motivo de cada merma — cerrando la brecha que hoy hace que "usé una receta" sea invisible en la auditoría.

## 📌 Justificación (Gap Analysis)
Hoy `ConsumeRecipeUseCase` descuenta por cascada FEFO sin registrar ningún `StockMovement`, sin vínculo con la extracción, sin declaración de sobrante ni de dónde quedó, y sin motivo de merma. El único punto de conciliación físico-vs-sistema es el cierre de turno (US-008), demasiado tarde y demasiado grueso.

## 🗣️ Decisiones de Negocio Consultadas con el Humano (Guard 28)
*   **Consumo asumido (#5):** `consumido = extraído − sobrante − merma`. El operario NO declara el consumo; declara sobrante y merma.
*   **Cuadre exacto (#9):** `extraído = consumido + sobrante + merma` debe cuadrar exactamente (Decimal). Un ítem que no cuadra rechaza el cierre.
*   **Ubicación del sobrante (agregado del humano):** por cada ingrediente con `leftoverQty > 0`, el operario elige un `StorageLocation` de destino: un área de cocina, o un sub-sector de bodega **solo si el remanente está "intacto"**.
*   **"Intacto" = ambas condiciones (#6):** cero consumo registrado (`currentQuantity == initialQuantity`) **Y** el operario marca "envase sin abrir". Solo entonces la opción "devolver a bodega" está disponible.
*   **Reloj FEFO del sobrante (#10):** al reubicar el sobrante que queda en cocina, se **conserva** el `expirationDate` original.
*   **Merma con motivo obligatorio:** si `wastedQty > 0`, `wasteReason` es obligatorio.
*   **Cierre opcional (#7):** una preparación puede quedar `OPEN`; la conciliación de turno la absorbe.
*   **Quién cierra (#8):** cualquier `KITCHEN_STAFF` o `ADMIN`; se registra `closedByOperatorId` y `closedAt`.
*   **Atomicidad (#3.5):** el cierre muta varios agregados → una única frontera transaccional (`IUnitOfWork`, C-DEV-006-1).
*   **Abandono:** `POST /:id/abandon` cierra sin conciliar; los remanentes quedan `ACTIVE`, pierden el `recipePreparationId`, no se asume merma.

## 🔗 Dependencias
*   Depende de **US-027** (preparación abierta) y **US-026** (áreas de cocina de catálogo).
*   Comparte la migración de `Remanente` (FK `storageLocationId`, `isPristine`) con US-026 / US-027.

## 🥒 Criterios de Aceptación (BDD - Sintaxis Gherkin)

### Escenario 1: Cierre con Sobrante en Cocina y Merma con Motivo (Happy Path)
- **Given** Una `RecipePreparation` `OPEN` de `"Pizza Margarita"`, `plannedPortions = 8`, con un `Remanente` de 2.000 KG de Mozzarella en `"Mesa de Preparación"`.
- **When** El operario `"usr-op-002"` cierra la preparación con `actualPortions = 8` y, para Mozzarella: `leftoverQty = 0.300` en `"Heladera Principal"`, `wastedQty = 0.100`, `wasteReason = "recorte no aprovechable"`.
- **Then** El sistema, en una sola transacción:
  - calcula `consumedQty = 2.000 − 0.300 − 0.100 = 1.600`,
  - registra `StockMovement` `CONSUMPTION_RECIPE` por `1.600` KG,
  - descarta `0.100` KG del remanente → `StockMovement` `DISCARD_RECIPE_PREP` con el motivo,
  - deja el `Remanente` con `currentQuantity = 0.300`, `status = ACTIVE`, `storageLocationId = "Heladera Principal"`, `recipePreparationId = null` (vuelve al pool FEFO), `expirationDate` sin cambios,
  - registra `TRANSFER_KITCHEN` (el sobrante cambió de área),
  - materializa el `RecipePreparationItem`,
  - marca la `RecipePreparation` `CLOSED` con `closedByOperatorId = "usr-op-002"`, `closedAt`, `actualPortions = 8`,
  - responde `HTTP 200` con el detalle conciliado.

### Escenario 2: Rechazo por Cuadre Incorrecto (Edge Case)
- **Given** Un `Remanente` de 2.000 KG extraído para la preparación.
- **When** El operario cierra con `leftoverQty = 0.500` y `wastedQty = 0.100` para un consumo teórico que dejaría `1.400` (suma `2.000` ✓)… pero declara `leftoverQty = 0.800` (suma `1.400 + 0.800 + 0.100 = 2.300 ≠ 2.000`).
- **Then** El sistema responde `HTTP 400` (`sobrante + merma no puede superar lo extraído` / cuadre inválido) y no cierra nada.

### Escenario 3: Devolución a Bodega Solo si el Remanente está Intacto
- **Given** Un `Remanente` de 2.000 KG extraído para la preparación, **sin consumo** (`currentQuantity == initialQuantity`), y el operario marca "envase sin abrir".
- **When** Cierra con `leftoverQty = 2.000`, `leftoverLocationId = "Bodega de Secos"` (`type = WAREHOUSE`).
- **Then** El sistema cierra el `Remanente` (`status = EXHAUSTED` o equivalente), re-incrementa `WarehouseStock ("insumo", "Bodega de Secos")` en `2.000`, registra `RETURN_TO_WAREHOUSE`, `consumedQty = 0`, `wastedQty = 0`.

### Escenario 4: Devolución a Bodega Bloqueada si Hubo Consumo (Edge Case)
- **Given** Un `Remanente` de 2.000 KG con `0.500` KG ya consumidos en otra operación (no está intacto).
- **When** El operario intenta cerrar con `leftoverLocationId` apuntando a un sub-sector de bodega.
- **Then** El sistema responde `HTTP 422` (`solo un remanente intacto puede devolverse a bodega`); el desplegable de destino no debería haber ofrecido bodega para esa línea.

### Escenario 5: Cierre sin Sobrante ni Merma
- **Given** Un `Remanente` de 1.600 KG extraído, consumo teórico exacto `1.600`.
- **When** El operario cierra con `leftoverQty = 0`, `wastedQty = 0`.
- **Then** `consumedQty = 1.600`; se registra `CONSUMPTION_RECIPE`; el `Remanente` queda `EXHAUSTED`; la preparación `CLOSED`.

### Escenario 6: Abandono de Preparación
- **Given** Una `RecipePreparation` `OPEN` con 2 remanentes vinculados.
- **When** El operario ejecuta `POST /api/v1/kitchen/recipe-preparations/:id/abandon`.
- **Then** La preparación pasa a `ABANDONED`; los 2 remanentes quedan `ACTIVE` con `recipePreparationId = null`; no se registra merma; el tablero deja de mostrarla en "en curso".

### Escenario 7: Preparación Abierta al Cierre de Turno
- **Given** Una `RecipePreparation` `OPEN` cuando el Administrador ejecuta la conciliación de turno (US-008).
- **When** Se cuenta físicamente el remanente vinculado y hay una diferencia.
- **Then** La conciliación de turno la trata como cualquier remanente activo (`ShiftReconciliationItem` + `DISCARD` / `SHIFT_RECONCILIATION_VARIANCE`); la preparación no bloquea el cierre de turno.
