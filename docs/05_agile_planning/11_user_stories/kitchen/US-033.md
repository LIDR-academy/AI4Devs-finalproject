# 📖 Historia de Usuario: US-033 — Registro de Temperatura de Refrigeración al Iniciar Turno

## 👤 Rol del Usuario
Como operario de cocina (Staff),

## 🎯 Objetivo / Valor de Negocio
Quiero registrar la temperatura que leo en el termómetro físico de cada refrigerador/congelador al iniciar mi turno, para dejar evidencia de cumplimiento de seguridad alimentaria que hoy no existe en ningún lado del sistema.

## 📌 Justificación (Gap Analysis)
RestoStock audita movimientos de stock, mermas y conciliación de turno, pero no tiene ningún registro de las condiciones de conservación (temperatura) bajo las que se almacenan los insumos — un vacío real frente a estándares de seguridad alimentaria de la industria. Esta historia cierra ese hueco con el mínimo esfuerzo posible: reutiliza el `StorageLocation` ya existente (cada refrigerador/congelador ya es un sub-sector registrado) y el patrón de auditoría ya establecido (`StockMovement`/`ShiftReconciliation`).

## 🗣️ Decisiones de Negocio Consultadas con el Humano (Guard 28)
*   **Pregunta 1:** ¿Cómo se captura la temperatura — hay algún sensor o integración de hardware?
*   **Respuesta:** No. 100% manual — el operario lee el termómetro físico ya instalado en el equipo y tipea el número. Ninguna integración de sensor/IoT (consistente con el Non-Goal #4 del PRD).
*   **Pregunta 2:** ¿Un valor fuera de rango seguro debe bloquear el inicio de turno, o solo advertir?
*   **Respuesta:** Solo advierte — nunca bloquea. El valor queda registrado y visible en el reporte de auditoría para revisión posterior; el operario siempre puede continuar su turno.
*   **Pregunta 3:** ¿Qué rango se considera seguro?
*   **Respuesta:** El estándar de la industria (FDA Food Code): `REFRIGERATOR` ≤ 4.00°C, `FREEZER` ≤ -18.00°C.
*   **Pregunta 4 (control de acceso, derivada del patrón ya aprobado en `US-020`/Reportes):** ¿quién puede consultar el histórico de lecturas?
*   **Respuesta:** Solo `ADMIN` — mismo patrón de rol que el resto de reportes de auditoría (`GET /api/v1/stock/movements`, `GET /api/v1/reports/rotation-metrics`). Registrar una lectura nueva sí lo puede hacer cualquier operario autenticado (es quien está físicamente en cocina al iniciar turno).

## 🥒 Criterios de Aceptación (BDD - Sintaxis Gherkin)

### Escenario 1: Lectura Dentro de Rango Seguro
- **Given** Un operario autenticado frente al sub-sector "Refrigerador Principal Cocina" (`StorageLocation` existente).
- **When** Registra una lectura de `3.5°C` con `unitType: REFRIGERATOR`.
- **Then** El sistema crea el `TemperatureLog` con `isWithinSafeRange: true`, sin ninguna advertencia visual, y el operario continúa su turno con normalidad.

### Escenario 2 (Edge Case): Lectura Fuera de Rango — Advertencia, Sin Bloqueo
- **Given** El mismo sub-sector.
- **When** El operario registra una lectura de `7.2°C` con `unitType: REFRIGERATOR` (por encima del umbral de `4.00°C`).
- **Then** El sistema crea el `TemperatureLog` con `isWithinSafeRange: false`, el frontend muestra una alerta visual no bloqueante, y el operario puede continuar e iniciar su turno igualmente — el registro queda disponible para que un `ADMIN` lo revise después en el reporte de auditoría.

### Escenario 3 (Control de Acceso): Consulta de Histórico Restringida a ADMIN
- **Given** Un operario `KITCHEN_STAFF` autenticado (no `ADMIN`).
- **When** Intenta consultar `GET /api/v1/kitchen/temperature-logs`.
- **Then** El sistema responde `403 Forbidden`.
