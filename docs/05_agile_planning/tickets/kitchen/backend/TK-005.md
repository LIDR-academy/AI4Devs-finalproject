# 🎫 TK-005: Implementación del Slice de Consumo Parcial de Remanentes

## 📝 Descripción
Este ticket habilita la funcionalidad de descontar cantidades de insumos abiertos (remanentes) a medida que son consumidos en las preparaciones cotidianas de la cocina. Si un consumo reduce la cantidad de un remanente a cero exacto, el sistema debe cambiar automáticamente su estado a agotado (`CONSUMED`), retirándolo del tablero activo.

*   **ID US Relacionada:** `US-004`
*   **Módulo / Vertical Slice:** `kitchen` (Servicio y Línea)
*   **Estimación (Story Points):** 3
*   **Prioridad MoSCoW:** Must Have
*   **Prerrequisitos:** `TK-001`, `TK-003` (Requiere existencia de remanentes)

---

## 🔀 Alcance de Modificación (Hexagonal Layers)
*   **Domain:** Lógica interna en la entidad `Remanente` para realizar restas de cantidades físicas de forma segura (sin permitir stock negativo) y transición de estado a `CONSUMED` si corresponde.
*   **Application:** Caso de uso `RecordConsumptionUseCase` que orquesta la carga del consumo.
*   **Infrastructure:** Endpoint `POST /api/kitchen/consumption`, esquema de Zod `RecordConsumptionSchema` y tests de integración simulando consumos acumulativos parciales.

---

## ⚠️ Mitigación de Riesgos Técnicos
1.  **Condición de Carrera en Descuentos:** Si dos operarios registran consumos concurrentes sobre el mismo remanente que tiene `0.5` KG (uno consume `0.3` y otro `0.4`), el remanente podría terminar con saldo negativo (`-0.2`) o un error silencioso de sobre-consumo. Implementar una transacción Prisma con bloqueo pesimista en la base de datos o un esquema de control de concurrencia optimista.
2.  **Pérdida de Precisión Decimal (IEEE 754):** Queda estrictamente prohibido realizar operaciones matemáticas sobre tipos flotantes nativos de JavaScript (`number`). Utilizar la clase `Decimal` (por ejemplo, mediante la librería `decimal.js`) para toda aritmética de consumos, asegurando el mapeo con el tipo `Decimal(12, 4)` de Prisma.

## ✅ Criterios de Aceptación & DoD (Definition of Done)

### Criterio de Aceptación 1: Consumo parcial exitoso (Happy Path)
*   **Given** un remanente activo con cantidad de "1.7500" KG
*   **When** se registra un consumo parcial de "0.2500" KG
*   **Then** la base de datos actualiza el stock a "1.5000" KG
*   **And** el remanente permanece en estado `ACTIVE`.

### Criterio de Aceptación 2: Agotamiento de remanente (Flujo Alternativo)
*   **Given** un remanente activo con cantidad de "0.2500" KG
*   **When** se registra un consumo de "0.2500" KG
*   **Then** la cantidad del remanente se establece en "0.0000" KG
*   **And** su estado se modifica automáticamente a `CONSUMED`.

### Criterio de Aceptación 3: Exceso de consumo rechazado (Flujo Alternativo Error)
*   **Given** un remanente activo con cantidad de "0.5000" KG
*   **When** se intenta consumir "1.0000" KG
*   **Then** la API responde con `422 Unprocessable Entity`
*   **And** no se modifica el remanente.

### DoD Estricto:
1.  **TDD Compliance:** Desarrollar los tests del caso de uso en rojo verificando las 3 transiciones del flujo (consumo parcial, consumo agotador y rechazo por saldo insuficiente) antes de programar la lógica del dominio.
2.  **Seguridad:** Validar autenticación JWT de la API con rol mínimo `OPERATOR`.
