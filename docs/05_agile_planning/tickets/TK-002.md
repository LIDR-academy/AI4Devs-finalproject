# 🎫 TK-002: Implementación de Autenticación de Operarios por PIN

## 📝 Descripción
Este ticket consiste en la implementación del flujo de autenticación táctil rápido en cocina mediante un PIN de 4 dígitos. Se debe validar el identificador del usuario, recuperar el hash del PIN y compararlo utilizando `bcrypt`. Si la validación es correcta, se emitirá un token JWT de sesión con una vigencia de corta duración (12 horas).

*   **ID US Relacionada:** `US-001`
*   **Módulo / Vertical Slice:** `auth` (Autenticación y Sesiones)
*   **Estimación (Story Points):** 3
*   **Prioridad MoSCoW:** Must Have
*   **Prerrequisitos:** `TK-001` (Core base)

---

## 🔀 Alcance de Modificación (Hexagonal Layers)
*   **Domain:** Definición del agregado `User`, su valor objeto `Pin` con lógica de encriptación y validación interna, e interfaz del repositorio `IUserRepository`.
*   **Application:** Caso de uso `AuthenticateByPinUseCase` que valida el PIN y genera el JWT token.
*   **Infrastructure:** Endpoint de la API `POST /api/auth/pin`, validador de Zod `AuthPinSchema`, adaptador de repositorio `PrismaUserRepository` y test de integración del caso de uso.

---

## ⚠️ Mitigación de Riesgos Técnicos
1.  **Ataques de Fuerza Bruta por PIN corto (4 dígitos):** Implementar un límite de intentos fallidos en el backend (ej. máximo 5 intentos fallidos antes de bloquear temporalmente el login por 15 minutos) para mitigar el ataque de fuerza bruta directa en la tablet de cocina.
2.  **Timing Attacks (Ataques de Temporización):** Asegurar que las comparaciones del PIN se realicen mediante métodos de tiempo constante de `bcrypt` para evitar que un atacante determine dígitos del PIN midiendo diferencias de tiempo de respuesta de la API.

---

## ✅ Criterios de Aceptación & DoD (Definition of Done)

### Criterio de Aceptación 1: Autenticación exitosa (Happy Path)
*   **Given** que existe un operario activo "Carlos Gomez" con el PIN "1234" hashed
*   **When** se realiza una petición a `POST /api/auth/pin` con el cuerpo conteniendo su ID y PIN "1234"
*   **Then** la API responde con estado `200 OK`
*   **And** entrega un token JWT de acceso (válido por 12 horas) junto con el perfil público del usuario.

### Criterio de Aceptación 2: Rechazo por credenciales incorrectas (Flujo Alternativo)
*   **Given** un operario activo "Carlos Gomez" con el PIN "1234" hashed
*   **When** se realiza la llamada pasándole el PIN "9999"
*   **Then** la API responde con estado `401 Unauthorized`
*   **And** no se emite ningún token de acceso.

### DoD Estricto:
1.  **TDD Compliance:** Diseñar y hacer fallar previamente la prueba de encriptación del PIN antes de guardarlo en base de datos.
2.  **Seguridad:** El código del PIN del usuario **nunca** se almacena en texto plano en la base de datos ni se retorna en las respuestas de la API.
