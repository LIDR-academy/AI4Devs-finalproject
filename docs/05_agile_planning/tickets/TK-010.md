# 🎫 TK-010: Implementación del Módulo de Reportes y Analítica de Mermas

## 📝 Descripción
Este ticket implementa el vertical slice de analítica e informes de desperdicio (`reports`). El objetivo es proveer un endpoint REST `GET /api/reports/waste` que permita al administrador consultar la cantidad total de inventario desechado (mermas físicas) agrupado por ingrediente y motivo en un rango de fechas.

*   **ID US Relacionada:** `US-009`
*   **Módulo / Vertical Slice:** `reports`
*   **Estimación (Story Points):** 3
*   **Prioridad MoSCoW:** Should Have
*   **Prerrequisitos:** `TK-001`, `TK-006` (Requiere el registro de mermas e insumos funcionando)

---

## 🔀 Alcance de Modificación (Hexagonal Layers)
*   **Domain:**
    *   Definición de la entidad/VO de dominio `WasteSummary` que modela el consolidado de desperdicio.
    *   Interfaz del puerto `IReportRepository` con la firma `getWasteReport(startDate: Date, endDate: Date): Promise<WasteSummary[]>`.
*   **Application:**
    *   Caso de uso `GetWasteReportUseCase` que encapsula el flujo de consulta del reporte, inyectando el repositorio de datos.
*   **Infrastructure:**
    *   Endpoint Express `GET /api/reports/waste`.
    *   Esquema Zod para validar `startDate` y `endDate` (verificar formato ISO y que `startDate <= endDate`).
    *   Adaptador concreto `PrismaReportRepository` que realiza la agregación (`groupBy` y `sum` sobre `StockMovement` filtrando por tipo `DISCARD` y rango temporal, uniendo con `insumos` para recuperar nombres/marcas).
    *   Enrutador `routes.ts` del slice montado en el enrutador global de la aplicación.

---

## ⚠️ Mitigación de Riesgos Técnicos
1.  **Agregaciones en Memoria vs. Base de Datos:** Agrupar y sumar miles de registros de movimientos de stock cargándolos todos en memoria de Node.js saturaría la memoria del servidor de la API. Mitigar esto delegando el agrupamiento y la sumatoria directamente al motor de la base de datos (PostgreSQL) usando el método `groupBy` y la función agregada `sum` de Prisma, garantizando respuestas instantáneas y de bajísimo consumo de red y memoria.
2.  **Incoherencia de Fechas y Zona Horaria:** Los filtros por fecha pueden retornar discrepancias si no se procesan en UTC de forma consistente. Mitigar esto forzando que los query params se validen como fechas ISO 8601 válidas en UTC, y arrojando error HTTP 400 mediante Zod si la fecha de inicio es posterior a la fecha de fin.

## ✅ Criterios de Aceptación & DoD (Definition of Done)

### Criterio de Aceptación 1: Consulta del reporte consolidado exitoso
*   **Given** que existen descartes registrados de Queso Mozzarella y Salsa de Tomate
*   **When** el administrador consulta `GET /api/reports/waste` con un rango de fechas válido
*   **Then** la API responde con una lista agrupada de desperdicios
*   **And** las cantidades físicas se presentan serializadas como strings (ej. `"3.5000"`) para evitar pérdida de precisión
*   **And** retorna `200 OK`.

### Criterio de Aceptación 2: Rechazo de rangos de fechas inválidos
*   **Given** un administrador autenticado
*   **When** realiza la petición con `startDate` posterior a `endDate`
*   **Then** la API valida e interrumpe el flujo antes de consultar la base de datos
*   **And** responde con `400 Bad Request` indicando el error de validación sintáctica.

### DoD Estricto:
1.  **TDD Compliance:** Escribir las pruebas de integración en rojo (usando mocks o base de datos de test) para `GetWasteReportUseCase` verificando la sumatoria y el rango de fechas antes de escribir el código de producción, según `docs/03_governance_and_quality/08_restostock_testing_strategy.md`.
2.  **Seguridad:** Validar que el endpoint requiere autenticación JWT con rol requerido **`ADMIN`** y rechazar cualquier petición de cocineros/operarios con `403 Forbidden`, de acuerdo con `docs/03_governance_and_quality/07_restostock_security_strategy.md`.
3.  **Serialización de Precisión:** Verificar que el total descartado (`totalDiscardedQuantity`) se devuelva estrictamente como una cadena de texto en la respuesta JSON.
