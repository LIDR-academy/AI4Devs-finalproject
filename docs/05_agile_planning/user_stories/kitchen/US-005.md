# 📝 US-005: Registro de Descartes y Mermas

## 👤 Historia de Usuario
**Como** operario de cocina (Staff),  
**quiero** registrar el descarte total de un remanente activo indicando la causa específica del desperdicio (vencimiento, caída, contaminación, etc.),  
**para** retirar el insumo del inventario de forma segura y proveer datos precisos para el reporte de mermas administrativas.

---

## 🎯 Criterios de Aceptación (BDD Gherkin)

### Escenario 1: Descarte exitoso de remanente activo (Happy Path)
*   **Given** que el operario está autenticado en el sistema
*   **And** existe un remanente activo de `Queso Mozzarella` con cantidad de `1.5000` KG en cocina
*   **When** el operario registra un descarte con la razón `EXPIRATION` (vencido)
*   **Then** el sistema actualiza la cantidad del remanente a `0.0000` KG
*   **And** cambia el estado del remanente a `DISCARDED`
*   **And** registra un movimiento de tipo `DISCARD` en el historial de transacciones con la firma del usuario y la causa del descarte.

### Escenario 2: Intento de descarte sobre un remanente inexistente (Flujo Alternativo)
*   **Given** que el operario está autenticado en el sistema
*   **When** el operario intenta registrar un descarte sobre un ID de remanente inexistente
*   **Then** el sistema rechaza la transacción con un código de error de entidad no encontrada
*   **And** no realiza ninguna actualización en la base de datos.

### Escenario 3: Rechazo de descarte sobre remanente previamente consumido o descartado
*   **Given** que el operario está autenticado en el sistema
*   **And** existe un remanente en estado `CONSUMED` o `DISCARDED`
*   **When** el operario intenta registrar un descarte sobre dicho remanente
*   **Then** el sistema rechaza la transacción con un código de error de estado inválido
*   **And** no realiza ninguna actualización ni modificación en la base de datos.

---

## 🎨 Restricciones de UX/UI
*   **Selector de Causa por Iconos:** En lugar de una lista desplegable pequeña, proveer botones grandes con iconos representativos para cada motivo de descarte (ej: un reloj de arena para `EXPIRATION`, un plato cayendo para `CONTAMINATION`, etc.) para agilizar la selección táctil.
*   **Advertencia Destacada:** Al seleccionar el motivo, se debe requerir una confirmación secundaria (Modal de doble verificación) antes de cambiar permanentemente el estado a `DISCARDED`.

---


## 📊 Evaluación INVEST

*   **[I]ndependiente:** Sí. No depende de los flujos de consumo o de catálogo maestro directamente para operar.
*   **[N]egociable:** Sí. La lista de motivos de mermas (`DiscardReason`) puede ampliarse o modificarse según las necesidades de auditoría del restaurante.
*   **[V]aliosa:** Sí. Permite cuantificar las pérdidas monetarias exactas causadas por vencimientos o malas prácticas en cocina.
*   **[E]stimable:** Sí. La lógica de negocio está bien acotada y las razones de descarte están modeladas a través de enums.
*   **[S]mall (Pequeña):** Sí. Es un endpoint de mutación que actualiza el estado y genera un registro de log.
*   **[T]estable:** Sí. Se verifica fácilmente mediante pruebas unitarias y de integración que comprueben que la cantidad remanente se pone en cero y se guarda la razón correcta.
