# 🎟️ TK-105: Reporte de Mermas de Preparación + Auditoría del Consumo Ad-hoc (Backend)

> [⬅️ US-029](../../../11_user_stories/reports/US-029.md) | [📖 Índice](../../indice_tickets.md)

## 📝 Descripción
Endpoint de reporte que agrega `RecipePreparationItem` por receta / ingrediente / motivo (cantidad + valorización `$` + % de merma) y consumo real vs. teórico por receta. Además, cerrar la deuda del `ConsumeRecipeUseCase` legacy: emitir `CONSUMPTION_RECIPE` por remanente afectado y ejecutarse en una frontera transaccional.

*   **US:** `US-029` · **Slice:** `reports` + `kitchen` · **SP:** 5 · **MoSCoW:** Should Have · **Prioridad:** 🟢 P2 · **Diferible**
*   **Prerrequisitos:** `TK-104` (datos de cierre), `TK-078` (patrón de valorización), `TK-098` (`IStockUnitOfWork`)

## 🔀 Alcance (Hexagonal)

### Application
*   Nuevo `GetPreparationWasteReportUseCase` — agrupa `RecipePreparationItem` (join `Recipe`, `Insumo.unitCost`) por receta → ingrediente → `wasteReason`; devuelve cantidad, `$` valorizado, `% merma = wasted / extracted`; marca las líneas sobre `SystemSettings.preparationWasteAlertPercent`.
*   Sub-reporte consumo real vs. teórico: por receta, `Σ(RecipeIngredient.quantity × actualPortions)` vs. `Σ RecipePreparationItem.consumedQty`.
*   `ConsumeRecipeUseCase` (legacy) — reescrito para: (a) correr dentro de `IStockUnitOfWork.runExtraction` (o análogo) — atomicidad all-or-nothing (C-DEV-006-1); (b) por cada remanente afectado en la cascada FEFO, `recordMovement({ type: 'CONSUMPTION_RECIPE', fromLoc: <área remanente>, ... recipeId })`.

### Infrastructure
*   `SystemSettings`: `+ preparationWasteAlertPercent Int @default(5)` — **migración dedicada** (pequeña, additiva) + `settings.controller.ts` Zod + UI de ajustes (TK-105-FE).
*   `PrismaReportRepository` / query repo: consultas de agregación.
*   `reports.routes.ts` / `reports.controller.ts`: `GET /api/v1/reports/preparation-waste?startDate=&endDate=`. Rol `ADMIN`.
*   `openapi.yaml` / `07_api_specification.md`: nuevo endpoint + schema; `CONSUMPTION_RECIPE` documentado en la lista de tipos de movimiento.

## ✅ DoD
1. **TDD:** agregación por receta/ingrediente/motivo con valorización; línea sobre umbral marcada, **sin** notificación; consumo real vs. teórico; `ConsumeRecipeUseCase` emite `CONSUMPTION_RECIPE` y revierte por completo ante stock insuficiente del 2º ingrediente.
2. **RFC 7807**; mutation ≥ 70 % por archivo domain/application (incluye el `ConsumeRecipeUseCase` reescrito, hoy sin cobertura de movimientos).

## 📌 Notas de implementación
*   **Corrección de un bug latente de atomicidad en el fake InMemory de `IStockUnitOfWork`** (descubierto por el propio test de atomicidad de este ticket, no algo buscado): `Remanente`/`RecipePreparation` mutan sus props in-place (`consumeQuantity`, `close`, `abandon`, `relocateLeftover`, `returnToWarehouse`), pero el `withSnapshot` de `InMemoryStockRepository` solo clonaba el `Map` (referencias compartidas) — una mutación de un agregado anterior en el mismo `work()` sobrevivía al rollback si un agregado posterior fallaba. Se agregó `cloneRemanente`/`cloneRecipePreparation` para que el snapshot clone también el contenido. Afecta (retroactivamente, en positivo) la corrección de `runExtraction`/`runPreparationClose` con ≥2 remanentes, no solo `runAdhocConsumption`.
*   `RecipePreparationItem.insumoId` no tiene relación Prisma declarada (evita una migración solo para el reporte) — `PrismaReportRepository` resuelve nombre/costo del insumo con una segunda consulta (`loadInsumoMap`).
*   `parseDateRange` extraído a `apps/backend/src/application/reports/parseDateRange.ts`, compartido por los 3 casos de uso de `reports` (antes triplicado).
*   `IStockUnitOfWork` gana `runAdhocConsumption` (tercera frontera transaccional, junto a `runExtraction`/`runPreparationClose`) — `ConsumeRecipeUseCase` ya no depende de `IRemanenteRepository` directo.
