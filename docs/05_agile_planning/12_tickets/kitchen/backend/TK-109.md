# 🎟️ TK-109: Motivo en Varianza Negativa de Conciliación + Fix de Superávit (Backend)

> [⬅️ US-008](../../../11_user_stories/kitchen/US-008.md) | [📖 Índice](../../indice_tickets.md)

## 📝 Descripción
`PerformShiftReconciliationUseCase`: una línea con varianza **negativa** (conteo físico < teórico) exige `reasonId` (catálogo `TK-107`) — sin él, `400` y **ninguna línea del cierre se procesa**. De paso, corrige un bug real: una línea con varianza **positiva** (superávit) hoy no actualiza `Remanente.currentQuantity` — pasa a hacerlo, sin exigir motivo (no es una pérdida).

*   **US:** `US-008` v1.1.0 · **Slice:** `kitchen` · **SP:** 5 · **MoSCoW:** Should Have · **Prioridad:** 🟡 P1
*   **Prerrequisitos:** `TK-107`

## 🔀 Alcance (Hexagonal)

### Domain
*   `Remanente.increaseQuantity(amount: DecimalQuantity): void` — nuevo método; exige `status === 'ACTIVE'`; suma a `currentQuantity`; no toca `isPristine` (un recuento con superávit no es una manipulación del remanente).
*   Reutiliza `InactiveConsumptionReasonException` / `EntityNotFoundException` de `TK-108` para el motivo.

### Application
*   `PerformShiftReconciliationUseCase.reconcilePhysicalCount`: valida `reasonId` presente cuando `varianceDecimal.isNegative()` — si falta, lanza antes de mutar nada (**toda la operación revierte** — frontera transaccional; ver Nota). Cuando `varianceDecimal.isPositive()`, llama `remanente.increaseQuantity(varianceDecimal)`. El `StockMovement` `SHIFT_RECONCILIATION_VARIANCE` de una línea negativa lleva `reasonId` + `reason` (notas).
*   **Nota de atomicidad:** hoy este caso de uso escribe remanente-por-remanente sin `IStockUnitOfWork` (deuda preexistente, fuera del estricto alcance de `ADR-004`) — si la validación de motivo debe fallar **antes** de tocar cualquier remanente, valida **todas** las líneas primero (sin efectos secundarios) y solo después aplica las mutaciones — evita el escenario "se aplicaron 2 líneas y la 3ª rechazó a mitad de camino".

### Infrastructure
*   `performShiftReconciliationSchema` (Zod): `items[].reasonId` opcional a nivel de schema (la obligatoriedad depende de la varianza, se valida en el dominio/aplicación — igual patrón que la merma de `TK-104`).
*   `openapi.yaml` / `07_api_specification.md`.

## ✅ DoD
1. **TDD:** varianza negativa sin `reasonId` → `400`, cierre completo revertido (ninguna línea aplicada); varianza negativa con `reasonId` → aplica y registra; varianza positiva → `currentQuantity` sincronizado, sin exigir motivo; mezcla de líneas positivas/negativas en un mismo cierre.
2. RFC 7807; mutation ≥ 70 % por archivo domain/application (incluye `Remanente.increaseQuantity`, hoy sin cobertura).
3. **Commit:** `fix(kitchen): require a reason on negative reconciliation variance and sync surplus (TK-109)`.

## 📌 Notas de implementación
*   **Fase de validación separada de la fase de aplicación (nota de atomicidad del propio ticket):** `prepareReconciliationItems` resuelve cada remanente y calcula su varianza (solo lectura) y valida el motivo de las líneas negativas — si cualquiera falla, **nada** se ha mutado todavía. Solo si las `n` líneas pasan la validación, `applyReconciliation` mutas remanente-por-remanente. Confirmado con un test explícito: una línea positiva + una negativa sin motivo en el mismo cierre → **ninguna de las dos** se aplica.
*   **`ConsumptionReasonRequiredException` (400, nueva):** distinta de `EntityNotFoundException`/`InactiveConsumptionReasonException` (reutilizadas de `TK-108`) — cubre el caso "no vino `reasonId` en absoluto" para una línea con varianza negativa.
*   **`Remanente.increaseQuantity`:** guarda de `status === 'ACTIVE'` reutilizando `ExcessConsumptionException` (mismo criterio que `relocateLeftover`/`returnToWarehouse`/`discard` en el propio archivo, aunque semánticamente el nombre de la excepción no encaja perfecto con un ajuste de superávit — se prefirió consistencia con el patrón existente sobre introducir una excepción nueva solo para este guard). No toca `isPristine`.
*   **`StockMovement.reasonId` en varianza positiva:** se deja `undefined` explícitamente (no se exige ni se persiste un motivo para el superávit) — el campo ya existía desde la migración de `TK-108`, sin migración nueva en este ticket.
*   **`buildKitchenController` (complejidad ESLint):** al enhebrar `consumptionReasonRepository` también hacia `PerformShiftReconciliationUseCase`, la función superó el límite de complejidad ciclomática (11 > 10). Se extrajo `buildReasonDependentUseCases` (agrupa `ConsumeRemanenteUseCase` + `PerformShiftReconciliationUseCase`, ambos con la misma guarda `remanenteRepository && consumptionReasonRepository`) — 0 warnings nuevos.
*   **Sin migración nueva:** `StockMovement.reasonId` ya existía (`TK-108`); este ticket es puramente de lógica de aplicación + dominio.
*   **`07_api_specification.md` §2.9:** el payload/respuesta de ejemplo documentados no coincidían con la implementación real (`operatorId` faltante, `insumoId` en vez de `remanenteId`, forma de respuesta distinta) — corregido de paso al tocar este endpoint, deuda preexistente no exigida por el DoD.
*   DoD #2 mutation ≥ 70 % por archivo: verificado (`PerformShiftReconciliationUseCase`, `Remanente`, `ConsumptionReasonRequiredException` — los archivos domain/application tocados).
