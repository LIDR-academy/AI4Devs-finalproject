# 🎟️ TK-118: `DiscardRemanenteUseCase` — Id Determinista + Motivo de Descarte Validado

> [⬅️ US-005](../../../11_user_stories/kitchen/US-005.md) | [📖 Índice de Tickets](../../indice_tickets.md)

## 📝 Descripción
**Remediación técnica** (C-DEV-006-4 — no cambia ninguna regla de negocio nueva, corrige un defecto de un caso de uso ya entregado). Detectado al analizar la deuda pendiente de motivos de descarte pedida por el humano tras cerrar `TK-117`: `DiscardRemanenteUseCase` seguía usando `` `mov-discard-${Date.now()}` `` como id de movimiento — el mismo patrón de colisión de PK que `AUDIT-DEV-006` F-3 ya corrigió en `RecordExtractionUseCase`/`RestockInsumoUseCase`/`CreateLocationUseCase` (`TK-099`/`TK-101`), pero que ese barrido no cubrió por no tocar este use case. De paso, el motivo de descarte (`reason`) no se validaba en el backend (`z.string().min(1)` aceptaba cualquier texto no vacío) pese a que el frontend (`DiscardModal.tsx`) solo ofrece 3 valores fijos.

*   **Slice:** `kitchen` backend · **SP:** 2 · **Prioridad:** 🟡 P1 — bug de colisión de PK confirmado, mismo patrón que un hallazgo ya crítico en otro módulo.
*   **Decisión de producto del humano:** el motivo de descarte se mantiene como catálogo **fijo en código**, no administrable — a diferencia de `ConsumptionReason` (ADR-004). Se descartó explícitamente extender ese catálogo a descartes en este ticket.

## 🔀 Alcance
*   `DiscardRemanenteUseCase`: nuevo parámetro de constructor `idGenerator: IdGenerator`; `` `mov-discard-${Date.now()}` `` → `idGenerator.next('mov-discard')`.
*   `kitchen.routes.ts`: `new DiscardRemanenteUseCase(remanenteRepository, cryptoIdGenerator)`.
*   `kitchen.controller.ts`: `discardRemanenteSchema.reason` pasa de `z.string().min(1)` a `z.enum(['EXPIRATION', 'DAMAGED', 'QUALITY_FAIL'])`.
*   `openapi.yaml` / `07_api_specification.md`: documentan el enum fijo y el nuevo caso `400` (motivo inválido, no solo ausente).

## ✅ Criterios de Aceptación & DoD
1. **TDD:** dos descartes concurrentes generan movimientos con ids distintos (reproduce la clase de bug); un motivo fuera del catálogo fijo devuelve `400` sin mutar el remanente.
2. Sin regresiones; mutation score 100% en el archivo tocado (Guard 11).
3. **Breaking change deliberado y documentado:** `oasdiff breaking` marca `reason` como "restricted to enum" — confirmado y aceptado, no oculto (mismo criterio que `TK-108`/ADR-004).
4. **Commit:** `fix(kitchen): deterministic discard movement id + validate fixed discard-reason enum (TK-118)`.

## 📌 Notas de implementación
*   **Único call site de producción** (`kitchen.routes.ts`) actualizado; no había tests que construyeran `DiscardRemanenteUseCase` directamente, todos pasan por `createApp()`.
*   **Mutation score 100%** (`DiscardRemanenteUseCase.ts`) tras reforzar las aserciones existentes (`toLoc`, prefijo del id, mensaje de `EntityNotFoundException`) — partió en 72.73% (≥70%, ya pasaba el gate) pero se llevó a 100% antes de cerrar.
*   El motivo de descarte del **descarte directo desde bodega** (`WarehouseExtractionModal` → `purpose: DIRECT_DISCARD`) es un concepto distinto (texto libre, `RecordExtractionUseCase`) — no se toca en este ticket, no hay confusión de alcance con el catálogo fijo de `DiscardModal`/`DiscardRemanenteUseCase`.
