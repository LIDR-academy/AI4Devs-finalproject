# 🎟️ TK-111: Vista Previa de Disponibilidad por Ingrediente de Receta (Backend)

> [⬅️ US-007](../../../11_user_stories/kitchen/US-007.md) | [📖 Índice](../../indice_tickets.md)

## 📝 Descripción
`GET /api/v1/kitchen/recipes/:id/availability?portions=N`: para cada ingrediente de la receta, retorna cantidad requerida (`RecipeIngredient.quantity × portions`) vs. disponible (suma de remanentes activos de ese insumo). Puramente de lectura — reutiliza exactamente el mismo cálculo que ya hace `ConsumeRecipeUseCase.consumeIngredient` antes de decidir si consume, pero sin mutar nada.

*   **US:** `US-007` v1.1.0 · **Slice:** `kitchen` · **SP:** 3 · **MoSCoW:** Should Have · **Prioridad:** 🟡 P1
*   **Prerrequisitos:** ninguno (reutiliza repositorios ya existentes: `IRecipeRepository`, `IInsumoRepository`, `IRemanenteQueryRepository`)

## 🔀 Alcance (Hexagonal)

### Application
*   `GetRecipeAvailabilityUseCase` (nuevo): por cada `RecipeIngredient`, resuelve `insumo` (nombre/unidad) vía `IInsumoRepository.findById` y `activeRemanentes` vía `IRemanenteQueryRepository.findActiveRemanentes(undefined, insumoId)`; suma `currentQuantity`; `isSufficient = disponible >= requerido`. `EntityNotFoundException` (404) si la receta no existe.

### Infrastructure
*   `kitchen.controller.ts`: nuevo handler `getRecipeAvailability`; query `portions` validado (`z.coerce.number().int().positive().optional().default(1)`, mismo criterio que el body de `consumeRecipeSchema`).
*   `kitchen.routes.ts`: `GET /recipes/:id/availability` — lectura, abierta a cualquier autenticado (mismo criterio que `/remanentes-activos`), montada junto a `recipes/:id/consume`.
*   `openapi.yaml` / `07_api_specification.md`.

## ✅ DoD
1. **TDD:** ingrediente con stock suficiente → `isSufficient=true` con las cantidades correctas; ingrediente sin ningún remanente activo → `isSufficient=false`, `availableQuantity="0"`, nombre/unidad resueltos igual vía `IInsumoRepository` (no depende de que haya remanentes); varios ingredientes, algunos suficientes y otros no → `isFullyAvailable` refleja el AND de todos; receta inexistente → `404`; `portions` afecta la cantidad requerida proporcionalmente.
2. RFC 7807 en el 404; sin mutaciones (el caso de uso no debe llamar a ningún método de escritura del repositorio — verificado con un spy/mock que falla el test si se invoca).
3. Mutation ≥ 70 % por archivo domain/application.
4. **Commit:** `feat(kitchen): recipe ingredient availability preview endpoint (TK-111)`.

## 📌 Notas de implementación
*   **`remanenteRepository` reutilizado como `IInsumoRepository`:** en producción es siempre `stockRepo` (`IInsumoRepository & IRemanenteRepository & IStockUnitOfWork`), pero `kitchen.routes.ts` lo tipaba solo como `IRemanenteRepository`. Se amplió el tipo a `IRemanenteRepository & Partial<IInsumoRepository>` y se usa `.findById` como guard runtime de esa capacidad (no colisiona: `IRemanenteRepository` no declara ningún método `findById`) — evita agregar un parámetro nuevo solo para esto.
*   **`GET`, no `POST`:** es una consulta, no una mutación — abierta a cualquier autenticado, mismo criterio que `/remanentes-activos`. Verificado explícitamente con un fake de `IInsumoRepository` cuyo `save()` lanza si se llega a invocar.
*   **`buildKitchenController`/`createKitchenRouter` refactorizados:** enhebrar la nueva use case hizo que ambas funciones superaran los límites de ESLint (complejidad y `max-lines-per-function`). Se extrajo `buildRecipeAvailabilityUseCase` (mismo patrón que `buildReasonDependentUseCases`) y se partió el montaje de rutas de `createKitchenRouter` en `mountReadRoutes`/`mountMutationRoutes`. 0 warnings nuevos.
*   **`07_api_specification.md` §2.8:** el ejemplo de respuesta de `POST .../consume` no coincidía con `ConsumeRecipeResponse` real — corregido de paso al agregar §2.8-bis (deuda preexistente, no exigida por el DoD).
*   **Sin breaking change:** endpoint puramente nuevo — confirmado por `oasdiff` (`check_contract_drift.sh` en verde sin bump de versión).
