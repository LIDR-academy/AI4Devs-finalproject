# 🎟️ TK-108: Motivo Obligatorio en el Consumo Manual de Remanentes (Backend)

> [⬅️ US-004](../../../11_user_stories/kitchen/US-004.md) | [📖 Índice](../../indice_tickets.md)

## 📝 Descripción
`ConsumeRemanenteUseCase` (`POST /kitchen/remanentes/:id/consume`) exige `reasonId` (del catálogo `TK-107`); `notes` (texto libre) opcional. Cierra el hueco de trazabilidad más transitado de la app.

*   **US:** `US-004` v1.1.0 · **Slice:** `kitchen` · **SP:** 3 · **MoSCoW:** Should Have · **Prioridad:** 🟡 P1
*   **Prerrequisitos:** `TK-107`

## 🔀 Alcance (Hexagonal)

### Domain
*   Nuevo `InactiveConsumptionReasonException` (400) — motivo existe pero `isActive = false`.

### Application
*   `ConsumeRemanenteUseCase`: DTO gana `reasonId` (obligatorio) + `notes?`. Resuelve el motivo vía `IConsumptionReasonRepository`; `EntityNotFoundException` si no existe, `InactiveConsumptionReasonException` si está desactivado. El `StockMovement` `CONSUMPTION` queda con `reasonId` + `reason` (= `notes`).

### Infrastructure
*   `schema.prisma`: `StockMovement.reasonId String?` FK → `ConsumptionReason` (`onDelete: SetNull`). **Migración aditiva**, aprobación humana.
*   `consumeRemanenteSchema` (Zod): `+ reasonId: z.string().min(1)`, `+ notes: z.string().optional()`.
*   `openapi.yaml` / `07_api_specification.md`.

## ✅ DoD
1. **TDD:** consumo sin `reasonId` → `400`, sin mutar el remanente ni registrar movimiento; motivo inexistente → `404`; motivo desactivado → `400`; consumo exitoso deja `reasonId` + `notes` en el movimiento.
2. RFC 7807; mutation ≥ 70 % por archivo domain/application.
3. Migración verificada contra Postgres real.
4. **Commit:** `feat(kitchen): require a structured reason on manual remanente consumption (TK-108)`.

## 📌 Notas de implementación
*   **Orden de validación:** `remanenteId` → `reasonId` (existe → activo) se resuelve ANTES de tocar el remanente o registrar el movimiento — un `reasonId` inexistente/desactivado no deja el consumo a medio aplicar (verificado explícitamente: `movements` queda en 0 en los 3 casos de rechazo).
*   **`StockMovement.reason` reutilizado como `notes`:** el `reasonId` (FK) es el motivo estructurado; el campo `reason` (texto libre, ya existía para extracción/descarte) pasa a llevar las `notes` del consumo cuando se proveen. No hay columna nueva para el texto libre — decisión explícita de ADR-004 §3.2.
*   **Migración `20260904190000_stock_movement_reason_fk`:** `ALTER TABLE ... ADD COLUMN "reasonId"` + índice + FK `ON DELETE SET NULL`. Verificada contra Postgres 15 real en una única transacción con `ROLLBACK` que aplica primero la migración de `TK-107` (`ConsumptionReason` aún no desplegada en el contenedor vivo) y luego esta — reproduce el orden real de despliegue. `check_migration_schema_parity.sh` (Postgres efímero) también en verde.
*   **Breaking change deliberado, confirmado por `oasdiff`:** `reasonId` es un campo requerido nuevo en `ConsumeRemanenteRequest` — `oasdiff breaking` lo marca correctamente como error. Es intencional (todo el propósito del ticket): `openapi.yaml` `version` pasó de `4.0.0` a `5.0.0` con el motivo documentado inline. `check_contract_drift.sh` **falla a propósito** en esta única sub-verificación — no hay bypass en el script (por diseño, exige revisión humana consciente ante cualquier breaking change real) y forzarlo a pasar habría significado no imponer `reasonId`, contradiciendo el propio DoD. Único consumidor de la API es el frontend de este monorepo, actualizado en el siguiente ticket (`TK-108-FE`) — sin consumidores externos que notificar.
*   **Deuda de documentación preexistente corregida de paso:** `07_api_specification.md` §2.4 y su fila en la tabla de endpoints documentaban un path (`/kitchen/consumption`), payload y respuesta que nunca coincidieron con el controller real — corregido al tocar este endpoint (no exigido por el DoD, pero se arrastraba desde antes de TK-108).
*   DoD #2 mutation ≥ 70 % por archivo: verificado (`ConsumeRemanenteUseCase`, `InactiveConsumptionReasonException`, `IRemanenteRepository` — los 3 archivos domain/application tocados). `InactiveConsumptionReasonException.ts` necesitó un `.test.ts` dedicado (solo tenía cobertura indirecta vía el test HTTP del caso de uso, que no bastaba — sobrevivió un mutante `StringLiteral` que vaciaba el mensaje): 4 tests unitarios directos sobre la excepción (statusCode, contiene el `reasonId`, menciona "desactivado", `name` de la clase) — mismo patrón que `SystemSettings.test.ts`/`UpdateSystemSettingsUseCase.test.ts` en `TK-105`.
