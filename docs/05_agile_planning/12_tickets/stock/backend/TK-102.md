# 🎟️ TK-102: Áreas de Cocina como `StorageLocation` y `Remanente.location` → FK (Backend)

> [⬅️ US-026](../../../11_user_stories/stock/US-026.md) | [📖 Índice](../../indice_tickets.md) | [Matriz ➡️](../../../13_matriz_trazabilidad.md)

## 📝 Descripción
Activar las filas `StorageLocation` con `type = KITCHEN` de punta a punta: `Remanente.location` (hoy `String` literal) pasa a FK `storageLocationId`, la extracción acepta un área de cocina de destino elegida del catálogo, y un área de cocina con remanentes activos no puede borrarse/desactivarse. Prerrequisito de ADR-003 (US-027/US-028).

*   **US:** `US-026` · **Slice:** `stock` · **SP:** 8 · **MoSCoW:** Should Have · **Prioridad:** 🟢 P2
*   **Prerrequisitos:** `TK-074` (CRUD `StorageLocation`), `TK-096` (patrón multi-sector)

## 🔀 Alcance (Hexagonal)

### Domain
*   `Remanente`: **`+ storageLocationId: string`** (FK, requerido en `createNew`). `location: string` **se conserva** como caché de display/movimiento denormalizada (= `name` del área). *Desviación de ADR-003 §3.2 documentada en el Addendum: el rename duro `location`→drop no es necesario para la capacidad y es alto riesgo (≈10 test files + churn del dominio de cocina); TK-104 re-sincroniza el caché al reubicar sobrantes.*
*   Nueva regla (Invariante 5, `03_domain_model.md`): `StorageLocation type = KITCHEN` con algún `Remanente` `ACTIVE` es indeleble/indesactivable → nueva `LocationHasRemanentesException` (409).

### Application
*   `RecordExtractionDTO`: `toLocation: string` (literal) → `toStorageLocationId: string` (FK, requerido para `KITCHEN_STOCK`/`RECIPE`). El use-case resuelve el `StorageLocation`, valida `type = KITCHEN` activo (→ `EntityNotFoundException`), y crea el `Remanente` con `storageLocationId` = id y `location` = `name`.
*   `GetActiveRemanentesUseCase` y `IRemanenteQueryRepository`: DTO `+ storageLocationId?`, `+ storageLocationName?` (join; fallback a `location`). Param de filtro `location?` → `storageLocationId?`.
*   `Delete/Update` de `StorageLocation`: nuevo `hasActiveRemanentesAt(storageLocationId, locationName)` → `409`.

### Infrastructure
*   **`schema.prisma`:** `Remanente + storageLocationId String? @db.Uuid` + relación `storageLocation StorageLocation? @relation(..., onDelete: Restrict)` + `@@index`. `StorageLocation` gana `remanentes Remanente[]`. **Nullable** (rows históricas siguen con `location` literal y `storageLocationId = NULL`).
*   **Migración Prisma dedicada** (`prisma migrate dev --name remanente_storage_location_fk`): **aditiva** — `ADD COLUMN storage_location_id` + FK + índice; `INSERT` de las filas semilla `StorageLocation type=KITCHEN` faltantes; backfill best-effort `UPDATE remanentes SET storage_location_id = (SELECT id FROM storage_locations WHERE name = remanentes.location AND type='KITCHEN')`. Sin `DROP COLUMN`. **Aprobación humana del archivo (AGENTS §3).**
*   `PrismaRemanenteQueryRepository` / `PrismaStockRepository`: leer/escribir la FK, incluir `storageLocation` para el `name`.
*   `stock.controller.ts`: Zod `toLocation` → `toStorageLocationId`. `locations.controller.ts`: `409` si el área KITCHEN tiene remanentes activos.
*   `seed.ts`: `STORAGE_LOCATIONS` gana las 3 áreas KITCHEN (`Mesa de Preparación`, `Línea de Servicio` + la de fríos ya existente); idempotente por `name`.
*   Governance: `check_schema_drift.sh`, `check_migration_schema_parity.sh`, `check_seed_idempotency.sh`, `check_contract_drift.sh`.
