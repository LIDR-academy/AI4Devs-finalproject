## 📝 Descripción
`AUDIT-DEV-006` F-7 (diferido de `TK-099` por requerir migración + decisión de diseño): el movimiento de extracción guarda `fromLoc = sector.name` (el **nombre** del sub-sector), no su id. Renombrar un `StorageLocation` desincroniza el histórico de movimientos y rompe cualquier filtrado por id.

Además: barrido del mismo patrón `` `xxx-${Date.now()}` `` (AUDIT-DEV-006 F-3, generalizado) en `RestockInsumoUseCase.ts:47` (`mov-`) y `CreateLocationUseCase.ts:16` (`loc-`) — mismo riesgo de colisión de PK, menor frecuencia. Se cierran aquí reutilizando el puerto `IdGenerator` ya introducido en `TK-099`.

## 🔀 Alcance de Modificación

### Persistencia (requiere aprobación humana del archivo de migración — AGENTS §3)
*   `schema.prisma` `StockMovement`: `+ fromStorageLocationId String? @db.Uuid` con relación opcional `storageLocation StorageLocation? @relation(..., onDelete: SetNull)` + `@@index`. Nullable — los movimientos históricos y los de cocina (`fromLoc = 'KITCHEN_*'`) no tienen sub-sector de bodega.
*   **Migración Prisma dedicada** (`prisma migrate dev --name stock_movement_from_sector`): sólo `ADD COLUMN` + FK + índice, sin backfill (los históricos quedan `NULL`).
*   `check_schema_drift.sh` / `check_migration_schema_parity.sh` / `check_seed_idempotency.sh` en verde tras la migración.

### Application / Infra
*   `StockMovementRecord` (`IRemanenteRepository`): `+ fromStorageLocationId?: string`.
*   `RecordExtractionUseCase` / `handleStockExtraction` / `handleDirectDiscard`: pasar `fromStorageLocationId` al `recordMovement` además del `fromLoc` (que se conserva como nombre para lectura directa).
*   `PrismaStockRepository.recordMovementOn` / `InMemoryStockRepository.recordMovement`: persistir el nuevo campo.
*   `GetStockMovementHistoryUseCase` / `PrismaStockMovementQueryRepository`: exponer `fromStorageLocationId` y resolver `fromLoc` por join al `StorageLocation` actual cuando exista el id (para que renombrar el sector se refleje en el histórico), con fallback al valor guardado.
*   `RestockInsumoUseCase` / `CreateLocationUseCase`: recibir `IdGenerator` por constructor; `` `mov-${Date.now()}` `` / `` `loc-${Date.now()}` `` → `idGenerator.next(...)`.
*   `openapi.yaml` / `07_api_specification.md`: `StockMovementHistoryItem + fromStorageLocationId`.

## ✅ Criterios de Aceptación & DoD
1. **TDD:** el movimiento de extracción persiste `fromStorageLocationId`; el histórico lo expone; renombrar el `StorageLocation` cambia el `fromLoc` mostrado en el histórico (join), no el guardado. `RestockInsumoUseCase`/`CreateLocationUseCase` con `IdGenerator` fake → ids deterministas.
2. **Migración verificada** contra BD efímera (`docker` + `migrate deploy` + parity + seed idempotency).
3. **Contrato:** `openapi.yaml` lint sin errores; `check_contract_drift.sh` reporta el campo nuevo como cambio documentado.
4. **Sin regresiones:** `pnpm test` / `build` / `lint` verdes; mutation ≥ 70 % por archivo tocado.
5. **Commit atómico:** `feat(stock): trace origin sub-sector by id on stock movements + IdGenerator sweep (TK-101)`.
