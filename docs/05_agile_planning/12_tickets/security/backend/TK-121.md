# 🎟️ TK-121: Lista de Permisos en el JWT de Login (Backend, US-015 Escenario 2)

> **Navegación del Framework SDD:**
> [⬅️ Volver a US-015 (11_user_stories/security/US-015.md)](../../../11_user_stories/security/US-015.md) | [📖 Índice de Tickets (12_indice_tickets.md)](../../indice_tickets.md) | [Siguiente: Matriz de Trazabilidad (13_matriz_trazabilidad.md) ➡️](../../../13_matriz_trazabilidad.md)

## 📝 Descripción
El JWT emitido en `POST /api/v1/auth/login-pin` solo lleva `role` (string). El Escenario 2 de `US-015` exige que incluya **la lista de permisos del usuario**, para que el frontend pueda ocultar acciones y elegir la pantalla de aterrizaje sin comparar `role === 'ADMIN'` a mano.

*   **ID US Relacionada:** [`US-015`](../../../11_user_stories/security/US-015.md) — Escenario 2 (único pendiente; 1 y 3 cerrados por `TK-073` y `TK-117`)
*   **Módulo / Vertical Slice:** `security` / `auth`
*   **Estimación (Story Points):** 2
*   **Prioridad MoSCoW:** Should Have
*   **Prerrequisitos:** `TK-073` (modelo `Role`/`Permission`), `TK-117` (`authorizePermissions` wireado)

---

## ⚠️ Invariante de Seguridad (leer antes de implementar)
**Los permisos del JWT son exclusivamente para UX. NUNCA son la frontera de seguridad.**
El backend ya resuelve permisos **en vivo por petición** (`authorizePermissions` consulta `IRoleRepository`), de forma deliberada: si un administrador revoca un permiso, el cambio surte efecto de inmediato, sin esperar a que expire el token del usuario. Este ticket **no debe** hacer que ninguna ruta confíe en los permisos del token — hacerlo introduciría una ventana de privilegio obsoleto de hasta 15 minutos.

---

## 🔀 Alcance de Modificación (Hexagonal Layers)
*   **Application:** el caso de uso de autenticación por PIN resuelve el `Role` completo del usuario y proyecta sus `Permission.code` a un `string[]`.
*   **Infrastructure:** el payload del JWT firmado gana `permissions: string[]`. `AuthenticatedRequest` (tipo de `authenticateJWT`) lo expone como campo opcional, para no romper a ningún consumidor existente.
*   **Sin cambios de esquema.** `Role`, `Permission` y `RolePermission` ya existen (`TK-073`).

---

## ⚠️ Mitigación de Riesgos Técnicos
1.  **Tokens ya emitidos:** un JWT anterior a este ticket no trae `permissions`. El campo es **opcional** en el tipo y su ausencia nunca debe tratarse como "sin permisos" (eso desconectaría de facto a todo usuario con sesión abierta). El frontend (`TK-121-FE`) define el fallback.
2.  **Tamaño del token:** con 8 permisos el payload crece unos ~150 bytes; irrelevante para una cabecera HTTP. Si el catálogo creciera a cientos, habría que revisar — no es el caso hoy.
3.  **`ADMIN` no se trata como caso especial** al proyectar la lista: se emiten sus permisos reales, para que el frontend aplique una única regla uniforme.

---

## ✅ Criterios de Aceptación & DoD (Definition of Done)

@critical
### Criterio de Aceptación 1: El token incluye los permisos del rol
*   **Given** un usuario con rol `KITCHEN_STAFF` (5 permisos concedidos en el seed)
*   **When** inicia sesión con su PIN
*   **Then** el JWT decodificado contiene `permissions` con exactamente esos 5 códigos, y **no** incluye `stock:restock` ni `roles:manage`.

### Criterio de Aceptación 2: La seguridad sigue resolviéndose en vivo
*   **Given** un usuario autenticado cuyo token dice tener `stock:extract`
*   **When** un administrador le revoca ese permiso y el usuario reintenta la operación **con el mismo token**
*   **Then** el backend responde `403` — la decisión se toma contra el repositorio, nunca contra el token.

### DoD Estricto:
1.  **Tests:** ambos criterios anteriores, contra fakes InMemory.
2.  **Contrato:** `openapi.yaml` refleja el nuevo campo en la respuesta de login; `oasdiff` sin breaking changes (es aditivo).
3.  **Build/Lint/Duplicación/Dead code:** gates ticket-scoped en verde.

## 📌 Deuda Registrada
Ninguna. La expiración/refresco de permisos dentro de un token vivo **no es deuda**: es la decisión de diseño descrita arriba (autoridad en el servidor, token solo informativo para UX).
