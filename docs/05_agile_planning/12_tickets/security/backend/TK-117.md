# 🎟️ TK-117: Conectar `authorizePermissions` a Rutas Reales + Cerrar `/api/v1/roles` Sin Guard (US-015 Escenario 3)

> [⬅️ US-015](../../../11_user_stories/security/US-015.md) | [📖 Índice](../../indice_tickets.md)

## 📝 Descripción
**Remediación técnica** (C-DEV-006-4 — no cambia ninguna regla de negocio de cara al usuario más allá de cerrar un defecto de acceso ya implícito en `US-015`; no reabre `TK-073`). El humano pidió cerrar el gap documentado en `US-015`/`TK-073` (`authorizePermissions` existía pero nunca se usaba en ninguna ruta — código muerto confirmado). Al verificar antes de codificar se encontró **AUDIT-SEC-002 F-1**: `/api/v1/roles` no tenía NINGÚN guard de rol/permiso, solo autenticación — cualquier usuario logueado podía reescribir los permisos de cualquier rol, incluido ADMIN.

*   **US:** `US-015` · **Slice:** `security` backend · **SP:** 5 · **Prioridad:** 🔴 P0 (F-1 crítico) + 🟢 P2 (resto)
*   **Prerrequisitos:** `TK-073` (Role/Permission/RolePermission, `authorizePermissions`, seed de 8 permisos)

## 🔀 Alcance
*   **Crítico:** `roles.controller.ts` — las 5 rutas (`GET /`, `GET /permissions`, `POST /`, `PUT /:id/permissions`, `DELETE /:id`) exigen `authorizePermissions(roleRepo, 'roles:manage')`.
*   **Seguro (sin cambio de acceso real, ADMIN/KITCHEN_STAFF tienen igual cobertura hoy):**
    *   `POST /stock/extraction` → `stock:extract`.
    *   `kitchen` mutaciones (`recipe-preparations/:id/close|abandon`, `recipes/:id/consume` → `kitchen:recipe_prepare`; `remanentes/:id/consume|discard`, `shift-reconciliation` → `kitchen:remanente_consume`).
    *   `reports` (`/waste`, `/rotation-metrics`, `/preparation-waste`) → `reports:view`.
    *   `auth` `/users*` (4 rutas) → `users:manage`.
*   **Deliberadamente NO convertidas** (decisión de producto del humano): `GET /stock/movements`, `PATCH /insumos/:id/restock` — el seed les asigna `stock:read`/`stock:restock` a `KITCHEN_STAFF`, pero abrir esas 2 rutas expandiría el acceso real de hoy (documentado en `US-015` como hueco conocido, no como bug).
*   **`InMemoryRoleRepository`:** ahora siembra también `KITCHEN_STAFF` (antes solo `ADMIN`) — sin esto, `authorizePermissions` resolvía cualquier test con rol `KITCHEN_STAFF` sobre los repos in-memory por defecto como "rol inexistente" (403 incluso con el permiso real concedido en Postgres).
*   Cada guard convertido cae al `requireRole` anterior si `roleRepository` no se inyecta explícitamente — nunca a "sin guard" por un parámetro faltante.

## ✅ Criterios de Aceptación & DoD
1. **TDD:** `KITCHEN_STAFF`/rol desconocido reciben `403` en las 5 rutas de `/roles` (antes pasaban); `ADMIN` mantiene acceso total. Un rol personalizado creado en runtime con un permiso específico (p. ej. solo `reports:view`) accede a esa ruta y **solo** a esa — prueba end-to-end del objetivo real de `US-015` Escenario 1.
2. **Cero regresión de acceso:** las 2 rutas con permiso seedado pero decisión de "no convertir" (`stock:read`/`stock:restock`) siguen exactamente `ADMIN`-only.
3. Sin código muerto: `authorizePermissions.middleware.ts` deja de aparecer en el reporte de `knip`.
4. `pnpm build`/`test`/`lint` verdes; `jscpd` sin clones nuevos entre los archivos de ruta tocados.
5. **Commit:** `fix(security): wire authorizePermissions to real routes, close unguarded /roles endpoint (TK-117)`.

## 📌 Notas de implementación
*   **AUDIT-SEC-002 F-1 es el hallazgo central de este ticket**, no un efecto secundario: `/api/v1/roles` nunca tuvo `requireRole`/`authorizePermissions`, solo el `authMiddleware` de autenticación heredado del mount. El único test previo (`RolesController.test.ts`) corría con `requireAuth: false`, así que nunca lo ejerció con un JWT de rol no-ADMIN.
*   **Decisión de producto explícita del humano** sobre `GET /stock/movements` y `PATCH /insumos/:id/restock`: el seed real asigna `stock:read`/`stock:restock` a `KITCHEN_STAFF` (aparentemente aspiracional, nunca antes ejercido), pero convertir esas 2 rutas habría expandido silenciosamente el acceso de cocina más allá de lo documentado ("dato administrativo — solo ADMIN"). Se preguntó explícitamente y se decidió mantener el guard grueso ahí — **no** es una limitación técnica, es alcance deliberado.
*   **Escenario 2 de `US-015` (JWT con permisos + autoredirección frontend) sigue sin implementar** — es una pieza de UX/frontend distinta e independiente: el backend ya resuelve permisos en vivo por request (`roleRepo.findRoleByName`), no necesita que el JWT los cargue, así que la corrección de seguridad de este ticket no depende de esa pieza. Se documenta como hueco conocido, no oculto.
*   14 tests nuevos (5 `RolesRbac.test.ts` + 1 `CustomRolePermissions.test.ts`, end-to-end con creación de rol real vía API + verificación de acceso concedido/denegado + 3 `InMemoryRoleRepository.test.ts` + tests de regresión ya verdes en `PerRouteRbac.test.ts`/`ManageUsers.test.ts` sin modificar). Backend 360→369 tests (9 nuevos netos tras contar los reescritos).
*   Sin cambios de dominio/aplicación — todo el diff es infraestructura (rutas + repositorio in-memory), por eso no aplica el gate de mutation score (Guard 11, acotado a domain/application).
