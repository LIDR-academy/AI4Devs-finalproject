# 🎟️ TK-094: Paridad entre `prisma/migrations/` y `schema.prisma` (columnas `mustChangePin` / `email`)

> **Navegación del Framework SDD:**
> [📖 Índice de Tickets](../../indice_tickets.md) · [🛡️ AUDIT-DEV-005](../../../../audits/AUDIT-DEV-005-TK-092-quality-report.md)

---

## 📝 Descripción

`AUDIT-DEV-005` (revisión de TK-092), defecto **D-6**: el árbol `apps/backend/prisma/migrations/` está desincronizado de `schema.prisma`.

* `schema.prisma` declara `User.mustChangePin Boolean @default(true)` (línea 72, Guard 36 / TK-070) y `User.email String? @unique`.
* Ninguna migración añade esas columnas: `20260821001603_init` crea `User` sin ellas, y `20260831234500_add_admin_pin_recovery_fields` sólo agrega `resetTokenHash` / `resetTokenExpires`.

El stack real **no lo nota** porque `apps/backend/docker-entrypoint.sh` aplica el esquema con `prisma db push --accept-data-loss`, que reconcilia el schema directamente e ignora `migrations/`. Pero:

1. `docs/04_governance_and_quality/scripts/check_seed_idempotency.sh` usa `prisma migrate deploy` (línea 65) → sobre una BD limpia falla con `P2022 ColumnNotFound` en `User.mustChangePin` → el gate de **FASE 3.4** del `04_dev_audit_workflow.md` queda ROJO para cualquier ticket que toque `seed.ts`, `schema.prisma` o migraciones (le pasó a TK-092, cuya reconciliación de huérfanos sí se verificó por inspección + stack vivo, pero no por el gate).
2. Cualquier consumidor que despliegue con `migrate deploy` (el propio comentario del `Dockerfile` lo menciona como objetivo) obtendría una BD rota.

---

## 🎯 Objetivo

`prisma migrate deploy` sobre una BD vacía produce exactamente el mismo esquema físico que `prisma db push` desde `schema.prisma` — sin drift. `check_seed_idempotency.sh` pasa en verde.

---

## 🔀 Alcance de Modificación

* **Nueva migración** `apps/backend/prisma/migrations/<timestamp>_add_user_must_change_pin_and_email/migration.sql`:
  ```sql
  ALTER TABLE "User" ADD COLUMN "mustChangePin" BOOLEAN NOT NULL DEFAULT true;
  ALTER TABLE "User" ADD COLUMN "email" TEXT;
  CREATE UNIQUE INDEX "User_email_key" ON "User"("email");
  ```
  (Verificar contra `schema.prisma` el estado exacto — tipos, `@unique`, nullability. Generar preferentemente con `prisma migrate diff` / `migrate dev --create-only` contra una shadow DB, no a mano, si el entorno lo permite.)
* **Verificación:** correr `prisma migrate diff --from-migrations ./prisma/migrations --to-schema-datamodel ./prisma/schema.prisma --exit-code` → debe salir 0 (sin drift). Si aparecen más columnas divergentes (revisar `Insumo.unitCost`, `Remanente.terminalAt` ya tienen migración — confirmar que no hay otras), incluirlas en la misma migración de saneamiento.
* **Decisión abierta (Guard 28) para el humano:** ¿el `docker-entrypoint.sh` debe migrar a `prisma migrate deploy` (consistente con el comentario del `Dockerfile` y Guard 25) o se mantiene `db push` como mecanismo oficial y se ajusta el comentario + `check_seed_idempotency.sh`? Este ticket asume "arreglar las migraciones para que ambos caminos converjan" y deja la conmutación del entrypoint como sub-decisión.

**Fuera de alcance:** cambiar el mecanismo de despliegue del entrypoint (sub-decisión arriba); cualquier cambio de datos.
