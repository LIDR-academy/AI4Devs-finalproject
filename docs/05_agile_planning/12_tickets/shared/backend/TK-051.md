## 📝 Descripción
Ticket técnico que resuelve un problema huevo-gallina descubierto durante la verificación en vivo de `TK-049`: `POST /api/v1/auth/users` exige ya ser `ADMIN`, pero una base de datos de producción nueva no tenía ninguna forma de crear su primer usuario. Corrige además una vulnerabilidad crítica encontrada al investigar: `prisma/seed.ts` ya leía `SEED_ADMIN_PIN` (Guard 13 de `AGENTS.md`) pero guardaba el PIN en texto plano en vez de hashearlo.

*   **ID US Relacionada:** N/A (Ticket Técnico / Habilitador de Despliegue)
*   **Módulo / Vertical Slice:** `shared` (afecta `auth`, infraestructura Docker)
*   **Estimación (Story Points):** 5

## 🔀 Alcance de Modificación (Hexagonal Layers)
*   **Domain:** Sin cambios.
*   **Application:** Sin cambios — reutiliza el mismo algoritmo de hash que `Pin.createFromRaw` (replicado sin importar `Pin.ts`, ver mitigación de riesgos).
*   **Infrastructure:** `prisma/seed.ts` corregido; en producción crea solo un admin genérico configurable (`SEED_ADMIN_PIN`/`SEED_ADMIN_NAME`, id fijo `bootstrap-admin`), nunca nombres de demo hardcodeados. `docker-entrypoint.sh` ejecuta el seed (idempotente) después de las migraciones y antes de arrancar el servidor.

---

## ⚠️ Mitigación de Riesgos Técnicos
1.  **Bug Crítico — PIN en Texto Plano:** `prisma/seed.ts` nunca se había ejecutado en ningún flujo real, así que no llegó a comprometer datos, pero de haberse conectado tal cual habría sido una vulnerabilidad severa (y el login jamás habría funcionado, porque `Pin.compareWithRaw` exige el formato `salt:hash`).
2.  **Guard 12 (`AGENTS.md`) — Estructura de `dist/`:** `tsconfig.json` tiene `rootDir=./src` a propósito; ampliarlo para incluir `prisma/seed.ts` rompería la estructura de `dist/`. Se resolvió con una compilación `tsc` standalone del seed en el `Dockerfile`, fuera del build principal.
3.  **Reintroducción de CVEs:** el seed no importa nada de `src/` precisamente para poder compilarse solo sin arrastrar `tsx`/esbuild a la imagen final (revertiría las CVEs que `TK-044` eliminó).

## ✅ Criterios de Aceptación & DoD (Definition of Done)

@critical @smoke
### Criterio de Aceptación 1: Bootstrap e idempotencia verificados en vivo
*   **Given** un contenedor backend en `NODE_ENV=production` contra Postgres real sin ningún usuario preexistente
*   **When** el contenedor arranca con `SEED_ADMIN_PIN` configurado
*   **Then** el login exitoso funciona inmediatamente con el PIN configurado
*   **And** tras reiniciar el contenedor, el mismo PIN sigue funcionando (idempotencia real, no solo "no hay excepción")
*   **And** un contenedor sin `SEED_ADMIN_PIN` arranca igual, solo con una advertencia (no bloquea el despliegue).

### DoD Estricto:
1.  **Ejecución Real (Antipatrón B):** validado extremo a extremo con un contenedor real, no solo tests — build de imagen, contenedor limpio, login, reinicio, login de nuevo.
2.  **Seguridad:** el PIN nunca se persiste en texto plano.
3.  **Tests:** 60/60 backend + 52/52 frontend sin cambios (este fix no tocó la superficie de tests existente, se validó con contenedor real); duplicación 2.02% (umbral 3%).
