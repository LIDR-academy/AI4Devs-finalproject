# 🎟️ TK-092: Resolución Fail-Safe de Rol de Usuario (cierre de escalada de privilegios AUDIT-SEC-001 F-1)

> **Navegación del Framework SDD:**
> [📖 Índice de Tickets](../../indice_tickets.md) · [🔐 AUDIT-SEC-001](../../../../audits/AUDIT-SEC-001-security-posture-report.md)

---

## 📝 Descripción

`AUDIT-SEC-001` (F-1, severidad **Crítica**, confirmada en el stack Docker en ejecución) detectó que **todo usuario creado a través de la API / pantalla "Gestión de Personal" se persiste sin rol y autentica como `ADMIN`**. Se combinan dos defectos:

* **F-1a** — `PrismaUserRepository.save()` / `.update()` (`PrismaUserRepository.ts:72-113`) **nunca escriben `roleId`**. El `role` (nombre) que trae el `User` de dominio se descarta en la persistencia. La fila queda con `roleId = NULL`.
* **F-1b** — `PrismaUserRepository.toDomain()` (`PrismaUserRepository.ts:25`) usa `raw.role?.name || raw.roleId || 'ADMIN'` como fallback: un rol ausente se resuelve al **máximo privilegio**.

Evidencia en el stack local (2026-09-03): los 3 usuarios creados desde la UI tienen `roleId = NULL` → autentican como ADMIN sin importar el rol seleccionado en el formulario.

**F-2** (severidad Media, mismo path): `createUserSchema.role` / `updateUserSchema.role` (`auth.controller.ts:35,42`) validan `role` como `z.string().min(1)` — string libre sobre un campo de privilegio, sin validación contra un conjunto cerrado ni contra el catálogo persistido de `Role`.

---

## 🎯 Objetivo

Que la resolución de rol sea **fail-safe (mínimo privilegio)** de extremo a extremo: un rol no resoluble nunca concede acceso privilegiado, y el rol elegido en la creación/edición se persiste realmente y se valida contra el catálogo `Role`.

---

## 🔀 Alcance de Modificación

### 1. `apps/backend/src/infrastructure/auth/repositories/PrismaUserRepository.ts` (F-1a, F-2)

* Nuevo helper privado `resolveRoleId(roleName: string): Promise<string>` — resuelve el nombre de rol (case-insensitive, igual que `PrismaRoleRepository.findRoleByName`) a `Role.id`. Si no existe ningún `Role` con ese nombre → lanza `EntityNotFoundException('Rol', roleName)` (→ HTTP 404 vía `errorHandler`). Esto hace del catálogo `Role` la **fuente de verdad cerrada** para F-2, alineado con US-015 (roles personalizados por nombre) — sin hardcodear un `z.enum` que rompería los roles dinámicos.
* `save()`: los bloques `create` **y** `update` incluyen `roleId: await this.resolveRoleId(user.role)`.
* `update()`: `data` incluye `roleId: await this.resolveRoleId(user.role)`.

### 2. `apps/backend/src/infrastructure/auth/repositories/PrismaUserRepository.ts` → `toDomain()` (F-1b)

* Reemplazar `role: (raw.role?.name || raw.roleId || 'ADMIN') as UserRole` por:
  ```ts
  role: (raw.role?.name ?? UNASSIGNED_ROLE) as UserRole,
  ```
  con `const UNASSIGNED_ROLE = 'UNASSIGNED'` — un rol centinela que **no coincide con ninguna comprobación `requireRole(...)`** (por tanto sin acceso a rutas con rol), pero que permite listar/mostrar el usuario en la pantalla admin para que un ADMIN lo corrija. Emitir `console.warn` con el `id` del usuario cuando se active el centinela (observabilidad; no romper `findAll`).
* Ya NO se cae a `roleId` crudo ni a `'ADMIN'`.

### 3. `apps/backend/prisma/seed.ts` — reconciliación idempotente de huérfanos

* Nueva función `reconcileOrphanUserRoles(kitchenRoleId: string)` invocada en `main()` justo después de `seedDefaultRoles()`, **incondicional** (dev y prod): `prisma.user.updateMany({ where: { roleId: null }, data: { roleId: kitchenRoleId } })`. Asigna el rol de **menor privilegio** (`KITCHEN_STAFF`) a los usuarios huérfanos preexistentes; un ADMIN puede promoverlos después. Log del número de filas afectadas.
* Motivo de hacerlo en el seed y no en una migración Prisma: `docker-entrypoint.sh` aplica el esquema con `prisma db push`, **no** `migrate deploy` — los archivos de `prisma/migrations/` no se ejecutan en el stack real. El seed sí (`node dist/prisma/seed.js`).

### 4. Tests

* **Nuevo** `apps/backend/tests/auth/PrismaUserRepository.test.ts` (o `src/.../PrismaUserRepository.test.ts` según convención de vecinos) con un `PrismaClient` mock (`vi.fn()` sobre `role.findFirst`, `user.upsert`, `user.update`, `user.findUnique`):
  1. `save(user{role:'KITCHEN_STAFF'})` → `user.upsert` recibe `create.roleId` y `update.roleId` = el id devuelto por `role.findFirst`. **Aserción central del ticket.**
  2. `save(user{role:'ROL_INEXISTENTE'})` → `role.findFirst` devuelve `null` → lanza `EntityNotFoundException`, `user.upsert` NO se llama.
  3. `update(user{role:'ADMIN'})` → `user.update` recibe `data.roleId`.
  4. `findById` sobre una fila con `role: null, roleId: null` → el `User` resultante tiene `role === 'UNASSIGNED'`, **nunca `'ADMIN'`** (regresión directa de F-1b).
* Los tests existentes de `tests/auth/ManageUsers.test.ts` usan `InMemoryUserRepository` (no tocado) y siguen verdes sin cambios.

### Fuera de alcance (→ US-015 / TK-093)

* `authorizePermissions(...)` middleware y RBAC dinámico granular (TK-073).
* Endurecer `User.roleId` a `NOT NULL` y `onDelete: Restrict` en `schema.prisma` (requiere migración + cambio en el flujo de borrado de roles). El centinela `UNASSIGNED` ya cierra la escalada aunque un rol se borre y deje usuarios huérfanos vía `onDelete: SetNull`.
* Declaración de rol por ruta en `kitchen.routes.ts` / `stock.routes.ts` → **TK-093** (F-3).

## ✅ Criterios de Aceptación & DoD

1. **F-1a cerrado:** un usuario creado vía `POST /api/v1/auth/users` con `role: 'KITCHEN_STAFF'` se persiste con `roleId` = id del rol KITCHEN_STAFF (verificado por test unitario del repo).
2. **F-1b cerrado:** `toDomain` sobre una fila sin rol resoluble devuelve `role === 'UNASSIGNED'`, jamás `'ADMIN'`. Test de regresión presente.
3. **F-2 cerrado:** `role` con un nombre que no existe en el catálogo `Role` → respuesta `404` RFC 7807 (`EntityNotFoundException`), no persistencia silenciosa.
4. **Reconciliación:** `pnpm --filter @restostock/backend run seed` es idempotente y deja 0 filas `User` con `roleId IS NULL`. Segunda ejecución → 0 filas afectadas. *(AUDIT-DEV-005 D-6: `check_seed_idempotency.sh` no puede validarlo por drift preexistente `migrations/` ↔ `schema.prisma` — abierto **TK-094**. Este DoD se acepta verificado por inspección + ejecución real en el stack Docker: `🔐 Reconciliados 3 usuario(s)` en la 1ª corrida, 0 en la 2ª.)*
5. **Verificación de contrato:** `pnpm --filter @restostock/backend test` — toda la suite verde (incluida `ManageUsers.test.ts` sin modificar aserciones).
6. **Gates:** `pnpm --filter @restostock/backend run build`, `pnpm run lint`, `bash docs/04_governance_and_quality/scripts/check_ticket_code_quality.sh`, `check_dead_code.sh`, `check_ticket_duplication.sh` — 0 errores nuevos.
7. **Verificación en stack real (workflow 09):** tras `docker compose up -d --build`, crear un usuario KITCHEN_STAFF por la UI, cerrar sesión, entrar con ese usuario → `/reportes` y `/ajustes` denegados (403 / redirect), `roleId` no nulo en BD.
8. **Commit atómico** `fix(auth): resolve user role fail-safe, persist roleId, reject unknown roles (TK-092)`.
