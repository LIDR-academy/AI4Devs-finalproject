## What was done

Implemented FR-024: every PurchaseProcess now has a default 21-item Checklist auto-attached on the first listing analysis (or on the first GET to /api/checklist). Before this change, a fresh user would have to manually POST to /api/checklist/process/:processId before the dashboard and the checklist UI would work.

### Architecture

Followed the hexagonal repository pattern, consistent with the recent AnalyzedListingRepository work:

- `domain/ports/ChecklistRepositoryPort.ts` — interface (no Prisma, no IO)
- `infrastructure/repositories/ChecklistRepository.ts` — Prisma implementation
- `domain/services/ChecklistTemplate.ts` — moved from infrastructure to domain (pure data, no IO)
- `domain/services/AnalyzeListingUseCase.ts` — accepts the new port, calls `ensureForProcess` after `autoAttach`
- `api/routes/listings.ts` — wires the repository
- `api/routes/checklist.ts` — uses the repository directly (no more dynamic import of CHECKLIST_TEMPLATE)
- `infrastructure/prisma/seed.ts` — simplified to only seed portal health

### Template enhancement

The old template had only `{ stage, title, sortOrder, estimatedDays }`. The new template in domain has full data:
- `stage` (BureaucraticStage)
- `title`
- `description` — non-empty explanation (previously just the title)
- `documentsNeeded` — array of strings (previously empty)
- `estimatedDays`
- `sortOrder`

This makes the checklist useful out-of-the-box (the UI can show "Documents needed: [..]" without further work).

## Notes

### Why `ensureForProcess` and not just `create`

The repository's primary method is `ensureForProcess(processId)` instead of a plain `create`. This makes the use case simpler — no need to check if a checklist exists first. The implementation does the find-then-create atomically (with a fast path: if the find returns non-null, return it; otherwise create and refetch).

### Why a port, not direct Prisma

The use case shouldn't know about Prisma. With the port, the use case just calls `await this.checklistRepository.ensureForProcess(processId)`. In a unit test, an in-memory fake can replace the real repository.

### What this unlocks for the frontend

The frontend `/checklist` page now works on the first visit after an analysis — no 404, no manual trigger. The dashboard's `checklist: { progress, completedItems, totalItems }` will now always have a value (not null). This was the prerequisite for the checklist UI being a "first-class" deliverable.
