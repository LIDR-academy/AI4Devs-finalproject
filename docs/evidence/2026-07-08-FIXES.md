## Notes

### Bug found in `AmortizationCalculator`

The original `totalInterest` calculation was:
```ts
const totalPayment = (basePayment + monthlyExtra) * totalMonths;
const totalInterest = totalPayment - input.principal;
```

This multiplied by 360 months (the original term) regardless of how many months the loan actually took to pay off with extra payments. So `aggressive` (500€/mo extra) showed `totalInterest` of €278,649 vs baseline €98,649 — a 184% increase, which is the opposite of the intended behaviour.

The fix computes actual months to payoff and uses that for both `totalPaid` and `yearsToPayoff`. Now `aggressive` correctly shows `totalInterest` < baseline.

### Architectural bug: hexagonal violation in use case

`AnalyzeListingUseCase` had `import { prisma } from '../../infrastructure/prisma/client'`. The original `hexagonal-check` regex (`@prisma/client`) didn't match the relative path, so the violation went undetected. Adding an explicit `import { Prisma } from '@prisma/client'` made the check fire and forced the proper fix:

- Defined `AnalyzedListingRepositoryPort` in `domain/ports/`
- Implemented `AnalyzedListingRepository` in `infrastructure/repositories/`
- Use case now depends on the port, not on Prisma
- Route wires the implementation at composition time

This is a meaningful improvement over the original "scaffold" — the use case is now truly framework-agnostic and could be unit-tested with an in-memory fake repository.
