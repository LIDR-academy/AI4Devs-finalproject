# Risks — ai-key-management

| # | Risk | Type | Likelihood | Impact | Mitigation |
|---|---|---|---|---|---|
| R1 | **First Edge Function in the repo.** No `supabase/functions/` scaffolding, no Deno tooling, and no precedent exist yet; this story bootstraps the pattern (Deno runtime, service-role secret in the function env, Vault access, deploy). The pipeline's Jest + StrykerJS harness does **not** exercise Deno, so the function's core guarantees are not covered by the standard gate. | technical | H | H | Scope the function tightly (validate-then-store + remove only; no generation). Verify it with **Deno tests** (`deno test`) for the pure logic (provider-probe classification, log redaction, request/response shaping) plus a **manual smoke** against the hosted project. Flag explicitly at the gate that @s12/@s13 and the server halves of @s1/@s6/@s8 rely on Deno + manual verification, not the mutation gate. Build the function scaffolding as PRD intends (reused later by R1/R2). |
| R2 | **First DB migration + RLS in the repo.** `supabase/` has only config; `user_ai_keys` + RLS + Vault enablement is untested territory. A mis-scoped RLS policy could leak one user's row (or the metadata) to another, or block the service role. Migrations/SQL are outside the Jest/Stryker harness. | technical / security | M | H | Enable `supabase_vault`; `user_ai_keys` RLS grants `authenticated` **select only** on `auth.uid() = user_id`; all writes are service-role only (no client insert/update/delete grant). Verify with a **manual RLS check** (user A cannot read user B's row; `authenticated` cannot read the decrypted secret view). Store **no key material** in the metadata table (only `secret_id` ref + provider + timestamps). |
| R-enc | **Encryption mechanism (open decision 1) may not fit the hosted project.** Vault may be unavailable/awkward, or its decrypted view harder to scope than assumed. | technical | M | H | Default is **Supabase Vault** (service-role-only decryption). Documented **fallback**: a `pgcrypto`/`pgsodium`-encrypted `bytea` column with the symmetric key held only as an Edge Function secret (env), so decryption still can't happen client-side. Resolve with a short spike **before Slice 1** (mirrors the PRD's R1 spike discipline). Either way the client contract (`ApiKeyStatus`, no client decrypt path) is identical, so higher layers are unaffected. |
| R-prov | **Provider/validation-call assumption (open decision 2).** Defaulting to OpenAI + `GET /v1/models`. If the project pins a different default provider, the probe endpoint and key format differ; some providers have no free auth-only probe. | product / technical | M | M | Wrap the probe behind a `validateKey(provider, key)` seam so swapping providers changes one endpoint, not the flow. Keep the client key-format pre-check **minimal** (non-blank/trimmed only) to avoid brittle provider-specific prefix assumptions. Confirm the target provider at the gate. |
| R3 | **Key transmission at save time.** The raw key must travel client → Edge Function once (over TLS) to be validated/stored — a reviewer could read this as violating "client never holds the key". | security / product | M | M | Make the distinction explicit in `spec.md`: the key is held **transiently** in the input field and sent **once over TLS** at save; it is never persisted client-side, retained in hook/service state, returned, or rendered. AC11 ("client never holds the key") is about **generation** time (R2 triggers the function with no key in the body). Component clears local input state on success. |
| R4 | **Classifying the provider probe result is brittle.** Distinguishing a genuine invalid/revoked key (401/403) from a transient failure (timeout, 429, 5xx, network) determines whether the user is told "invalid" vs "try again". Mislabeling a transient failure as "invalid" is a bad, misleading UX. | technical | M | M | Normalize inside the Edge Function + `ApiKeyService`: **only** 401/403 → `invalid_key` (AC2/@s6); everything else (429/5xx/timeout/thrown) → `network_error` (AC3/@s7, safer default — never claim "invalid" without certainty). Deno-test the classification against representative statuses; the UI consumes only the normalized `code`. |
| R5 | **No key material in logs is easy to regress.** A stray `console.log(req.body)` / error dump in the Edge Function could leak the raw key; log platforms retain it. | security | M | H | Never log the request body or the key; log only a redacted event (action + outcome code + user id). Add a Deno test with a log spy asserting the raw key value never appears in any captured log call. Reviewer_security checks this against @s12. |
| R6 | **`ApiKeyStatus` accidentally leaking key material.** A future change could add a `key`/`lastFour` field to the status type or the metadata select, silently breaking AC8/AC11. | security | L | H | `ApiKeyStatus = { hasKey; provider?; updatedAt? }` — no key characters by decision. The metadata `select` lists only non-secret columns; the DAO exposes **no** method that returns a raw key. Type-level + DAO tests (@s11) lock the shape; reviewer_security re-checks. |
| R7 | **Data-fetching hook without tanstack-query.** `useApiKey` loads status with plain `useState`/`useEffect` (no cache/dedupe). A reviewer_performance/architecture lens may flag the missing tanstack-query. | technical / timeline | L | L | Documented decision (spec Open decisions): a single lightweight status read on one screen + one-shot mutations = the `useAuth` shape, which deliberately deferred tanstack-query "until first needed". Guard against double-fetch/races (cancel on unmount, load only when authenticated). Revisit when a second cached query appears. |
| R8 | **i18n coverage gap.** New `settings.apiKey.*` keys must exist in all four bundles (en/es/pt/de) or i18next silently renders the raw key string; the new component dirs must be added to `migration-coverage.test.ts`'s key-existence guard. | product | M | L | Slice 3 adds all keys to every bundle and extends `migration-coverage.test.ts` (new component dirs + the alignment check already enforces en-parity via the `TranslationResource` type). |
| R9 | **Over-scoping into R2 (generation).** The guard rail (AC10) tempts building a generation trigger; AC11 tempts building the server-side read. | timeline | M | M | Scope pins: the gate is a reusable `ApiKeyGate` rendering `ApiKeyRequiredNotice` when `hasKey === false`, wired at the Upload entry — **no** generation call. AC11 is delivered as a **structural** guarantee (no client raw-key path), not the generation read. Tasks list exact paths so the implementator adds only key management + the gate. |
