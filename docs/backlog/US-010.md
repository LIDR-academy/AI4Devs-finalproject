## US refinada

**Historia de usuario:**
Como corredor, quiero introducir los datos de pago en el segundo paso del checkout, para completar formalmente la compra aunque el procesamiento sea simulado.

**Caso de uso asociado:** CU3 — Proceso de compra: carrito y checkout simulado

**Alcance técnico:** US exclusivamente de **Frontend**, igual que US-009. No se realiza ninguna llamada al backend en este paso: los datos de tarjeta se capturan y validan en el cliente, y solo se transmitirían al backend en US-011 (confirmación del pedido) mediante `POST /api/checkout`. El tipo `PaymentData` ya existe como placeholder en `frontend/src/types/checkout.ts` (definido en US-009-TASK-01). El `CheckoutPage` (US-009) ya gestiona `currentStep` y `shippingData`, y renderiza un placeholder de texto en el paso 2 que esta US sustituye por el formulario real.

Referencia visual: `docs/prototypes/05-checkout-payment.png` — panel «Método de pago» con 4 campos, botones «Volver» (secundario) y «Confirmar pedido» (primario), resumen lateral visible.

**Resolución de ambigüedad:** la US dice que al pulsar «Confirmar pedido» en el paso 2 "el sistema avanza al paso de revisión y confirmación". US-011 reutiliza el mismo texto de botón en el paso 3, donde sí se crea el `Order`. Esto es intencional (coincide con el prototipo): el botón del paso 2 solo **avanza de paso**, nunca crea el pedido ni llama a la API. La creación real del pedido es responsabilidad exclusiva de US-011.

### Contrato de componentes

**Componente nuevo:** `PaymentForm` en `frontend/src/components/checkout/payment-form.tsx`
- Directiva `'use client'` — gestiona estado de formulario y errores de validación, igual patrón que `ShippingForm` (US-009-TASK-03).

```typescript
interface PaymentFormProps {
  initialData?: PaymentData;       // para pre-rellenar si el usuario vuelve del paso 3 (US-011)
  onSubmit: (data: PaymentData) => void; // avanza a paso 3 — nunca crea el pedido
  onBack: () => void;                    // vuelve al paso 1 sin validar el formulario actual

```

`PaymentData` (ya definido en `types/checkout.ts`, sin cambios):

```typescript
export interface PaymentData {
  cardNumber: string;
  cardName: string;
  cardExpiry: string;
  cardCVV: string;
}
```

**Campos del formulario** (todos `<input type="text">` con `inputMode` numérico donde aplica):

| Campo | Label | Placeholder | Obligatorio | `autoComplete` |

| `cardName` | Nombre del titular | — | Sí | `cc-name` |

**Validación (función pura `validatePaymentForm(data): FormErrors`)**, evaluada solo al pulsar «Confirmar pedido» (no al pulsar «Volver»):

| Campo | Regla | Mensaje de error |
|---|---|---|
| `cardNumber` | Requerido; sin espacios debe matchear `/^\d{16}$/` | Vacío: «El número de tarjeta es obligatorio». Inválido: «Introduce un número de tarjeta válido de 16 dígitos» |
| `cardName` | Requerido, no vacío | «El nombre del titular es obligatorio» |
| `cardExpiry` | Requerido; debe matchear `/^(0[1-9]\|1[0-2])\/\d{2}$/` (MM/AA) | Vacío: «La fecha de vencimiento es obligatoria». Inválido: «Introduce una fecha de vencimiento válida (MM/AA)» |
| `cardCVV` | Requerido; debe matchear `/^\d{3}$/` | Vacío: «El CVV es obligatorio». Inválido: «El CVV debe tener 3 dígitos» |

No hay verificación con pasarela ni servicio externo: cualquier valor que cumpla el formato es aceptado (criterio de aceptación literal de la US).

**Botones** (fila final, mismo orden que el prototipo):
- «Volver» — estilo secundario (`border border-border bg-white hover:bg-muted`), llama a `onBack()` directamente, **sin pasar por validación**.
- «Confirmar pedido» — estilo primario (`bg-rm-cta text-rm-cta-fg hover:bg-rm-cta-hover`), valida y, si no hay errores, llama a `onSubmit(formData)`.

## Seguridad OWASP

### Análisis previo

| Riesgo | Categoría OWASP | Mitigación prevista |
|---|---|---|
| Persistencia de datos de tarjeta en cliente | A02 — Cryptographic Failures | `PaymentData` vive solo en `useState` de `CheckoutPage`; nunca se escribe en `localStorage`/`sessionStorage`. Regla no negociable de `CLAUDE.md` ("Nunca almacenar datos de tarjeta en estado o localStorage" se interpreta como: solo estado de React, nunca storage persistente) |
| XSS vía valores de formulario de pago | A03 — Injection | Los valores de `PaymentData` se renderizan siempre vía JSX (text nodes en `input value`), nunca con `dangerouslySetInnerHTML` |
| Envío accidental de datos de tarjeta a la API en este paso | A04 — Insecure Design | `PaymentForm.onSubmit` solo actualiza estado local y avanza de paso; no existe ninguna llamada `fetch`/`axios` en esta US. El envío real a `POST /api/checkout` es responsabilidad exclusiva de US-011 |
| Datos de tarjeta en logs de consola o herramientas de desarrollo | A09 — Security Logging Failures | No se añade ningún `console.log` de `formData` en `PaymentForm` ni en `CheckoutPage` |
| CVV/número de tarjeta visibles en texto plano en el DOM | A02 — Cryptographic Failures | Aceptado para el MVP: es un checkout simulado sin almacenamiento ni transmisión real; no se enmascara el input porque no hay procesamiento de pago real que proteger. Documentado aquí para que la revisión de seguridad lo valore explícitamente |
