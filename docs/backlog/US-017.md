## US refinada

### Historia de usuario

Como corredor, quiero que mis datos de sesión y los detalles de mi pedido no queden
expuestos innecesariamente en respuestas de API ni en almacenamiento del navegador, y
que el sistema rechace entradas fuera de rango antes de procesarlas, para reducir el
riesgo de exfiltración de datos personales y de abuso de la API.

### Contexto técnico

El análisis de pentesting identificó cinco vulnerabilidades ALTO/MEDIO de exposición de
datos y validación de entrada:

| Vulnerabilidad | Impacto | Archivo afectado |
|---|---|---|
| `sessionId` en body de `CartResponse` | Debilita la protección HttpOnly: XSS puede exfiltrar la sesión vía `fetch('/api/cart')` | `backend/src/types/domain.ts`, `backend/src/services/cart.service.ts`, `frontend/src/types/cart.ts` |
| `OrderResponse` completo en `sessionStorage` | PII (nombre, email, teléfono, dirección) accesible a cualquier script; problema GDPR | `frontend/src/app/checkout/page.tsx` |
| IDs de pedido basados en `Date.now()` | Predecibles por timestamp; permite enumerar pedidos | `backend/src/repositories/order.repository.ts` |
| Sin `.max()` en `quantity`, `size`, `color` | Entradas arbitrariamente grandes llegan a la BD antes de ser rechazadas | `backend/src/schemas/cart.schema.ts` |
| `SESSION_SECRET` en `.env` sin usar | Variable muerta que induce a confusión sobre el modelo de seguridad de sesión | `.env`, `.env.example` |

### Contrato técnico

#### CA-1 — Eliminación de `sessionId` en `CartResponse`

**Backend:** Eliminar el campo `sessionId` del tipo `CartResponse` en `domain.ts` y de
la expresión `return { sessionId, ... }` en `cart.service.ts`.

```ts
// domain.ts — ANTES
export interface CartResponse {
  sessionId: string;
  items: CartItemResponse[];
  subtotal: number;
  shipping: number;
  total: number;
}

// domain.ts — DESPUÉS
export interface CartResponse {
  items: CartItemResponse[];
  subtotal: number;
  shipping: number;
  total: number;
}
```

```ts
// cart.service.ts buildCartResponse — ANTES
return { sessionId, items: itemResponses, subtotal, shipping, total };

// cart.service.ts buildCartResponse — DESPUÉS
return { items: itemResponses, subtotal, shipping, total };
```

**Frontend:** Eliminar `sessionId` de `CartResponse` y `CartState` en
`frontend/src/types/cart.ts`. Verificar que `cart-context.tsx` no acceda a
`response.sessionId` (actualmente no lo hace).

```ts
// types/cart.ts — CartResponse ANTES
export interface CartResponse {
  sessionId: string;
  items: CartItemUI[];
  subtotal: number;
  shipping: number;
  total: number;
}

// types/cart.ts — CartResponse DESPUÉS
export interface CartResponse {
  items: CartItemUI[];
  subtotal: number;
  shipping: number;
  total: number;
}

// CartState: eliminar también sessionId: string | null (campo no usado en CartContextValue)
```

#### CA-2 — `sessionStorage` con solo `orderId`

`frontend/src/app/checkout/page.tsx` — dos cambios:

1. **Al confirmar el pedido:** guardar solo `result.id` en lugar del objeto completo.
   ```ts
   sessionStorage.setItem(ORDER_STORAGE_KEY, result.id);
   ```

2. **En el `useEffect` de rehidratación:** leer el ID almacenado y recuperar el pedido
   desde `GET /api/orders` (ya existe, devuelve `OrderListResponse[]`).
   ```ts
   const storedId = sessionStorage.getItem(ORDER_STORAGE_KEY);
   if (!storedId) { router.push('/'); return; }

   apiGet<OrderListResponse[]>('/orders')
     .then(orders => {
       const found = orders.find(o => o.id === storedId);
       if (found) { setOrder(found); return; }
       sessionStorage.removeItem(ORDER_STORAGE_KEY);
       router.push('/');
     })
     .catch(() => {
       sessionStorage.removeItem(ORDER_STORAGE_KEY);
       router.push('/');
     });
   ```

   `OrderListResponse` es estructuralmente compatible con `OrderResponse` (es un superconjunto
   que añade `image` en los items), por lo que TypeScript acepta la asignación directa.

#### CA-3 — ID de pedido aleatorio

```ts
// order.repository.ts — ANTES
id: `ORD-${Date.now()}`,

// order.repository.ts — DESPUÉS
id: `ORD-${crypto.randomUUID().replace(/-/g, '').slice(0, 8).toUpperCase()}`,
```

`crypto` es nativo de Node.js 19+ (ya en uso para `crypto.randomUUID()` en el middleware
de sesión). El sufijo de 8 hex en mayúsculas produce 16^8 = ~4.3 mil millones de
combinaciones; colisión prácticamente imposible para el volumen del MVP.

#### CA-4 — Límites en `cart.schema.ts`

```ts
// ANTES
quantity: z.number().int().min(1),
size: z.string().optional(),
color: z.string().optional(),

// DESPUÉS
quantity: z.number().int().min(1).max(9999),
size: z.string().max(50).optional(),
color: z.string().max(50).optional(),
```

Aplica a ambos schemas (`AddToCartSchema` y `UpdateCartItemSchema`).

#### CA-5 — Limpieza de `SESSION_SECRET`

Eliminar la línea `SESSION_SECRET=change-me-in-production` de `.env` y `.env.example`.
Añadir un comentario en `backend/src/middleware/session.ts` que documente explícitamente
que la cookie no está firmada (la entropía se garantiza por `crypto.randomUUID()` en
la generación del sessionId, no por firma HMAC).

### `US-017-TASK-02` — ID de pedido aleatorio criptográfico

- [x] Implementado

- `POST /api/checkout` devuelve un `id` con el nuevo formato.
- Los tests de `order.repository.test.ts` y `checkout.controller.test.ts` se actualizan
  para validar el nuevo patrón en lugar del formato `ORD-<timestamp>`.

### `US-017-TASK-06` — Guardar solo `orderId` en `sessionStorage` y restaurar desde API

- [x] Implementado
- **Capa:** Frontend
- **Depende de:** —
- **Criterio de aceptación cubierto:** CA-2 — `sessionStorage` contiene solo el `orderId`, no el `OrderResponse` completo

**Descripción técnica**

En `frontend/src/app/checkout/page.tsx`, dos cambios:

**1. Al confirmar el pedido (`handleConfirmOrder`):**
```ts
// ANTES
sessionStorage.setItem(ORDER_STORAGE_KEY, JSON.stringify(result));

// DESPUÉS
sessionStorage.setItem(ORDER_STORAGE_KEY, result.id);
```

**2. En el `useEffect` de rehidratación (page reload):**
```ts
// ANTES: parseaba el JSON completo del OrderResponse
const parsed = JSON.parse(raw) as OrderResponse;
if (parsed && typeof parsed.id === 'string' && Array.isArray(parsed.items)) {
  setOrder(parsed);
  return;
}

// DESPUÉS: lee el orderId y recupera el pedido desde la API
const storedId = sessionStorage.getItem(ORDER_STORAGE_KEY);
if (!storedId || typeof storedId !== 'string' || !storedId.startsWith('ORD-')) {
  sessionStorage.removeItem(ORDER_STORAGE_KEY);
  router.push('/');
  return;
}

apiGet<OrderListResponse[]>('/orders')
  .then(orders => {
    const found = orders.find(o => o.id === storedId);
    if (found) {
      setOrder(found);
      return;
    }
    sessionStorage.removeItem(ORDER_STORAGE_KEY);
    router.push('/');
  })
  .catch(() => {
    sessionStorage.removeItem(ORDER_STORAGE_KEY);
    router.push('/');
  });
```

`OrderListResponse` es un superconjunto de `OrderResponse` (mismos campos + `image` en
items), por lo que TypeScript acepta la asignación a `OrderResponse` sin cast.

**Criterios de hecho**

- Tras `handleConfirmOrder`, `sessionStorage.getItem(ORDER_STORAGE_KEY)` devuelve el
  `orderId` como string plano (ej. `"ORD-A1B2C3D4"`), no un objeto JSON.
- En page reload con un `orderId` válido en `sessionStorage`, la página llama a
  `GET /api/orders` y muestra la confirmación.
- En page reload con un `orderId` inválido o sin sesión, la página redirige a `/`.
- No hay PII (nombre, email, dirección) en `sessionStorage` en ningún momento del flujo.
- Cumple las reglas de seguridad aplicables de `CLAUDE.md`.

**Puntos verificados explícitamente:**

1. **IDOR (CA-2, `checkout/page.tsx`)** — el `orderId` guardado en `sessionStorage` se
   resuelve contra `GET /api/orders`, que en `order.controller.ts:listOrders` filtra
   siempre por `req.sessionId` (cookie HttpOnly, servidor). Un `orderId` de otra sesión
   simplemente no aparece en la lista devuelta → no hay IDOR, aunque el cliente confíe
   en un ID no firmado.
2. **Exposición de datos (CA-1, CA-2)** — `sessionId` ya no viaja en el body de
   `CartResponse` (antes debilitaba la protección `HttpOnly` de la cookie ante un XSS).
   `sessionStorage` ya no contiene PII (nombre, email, teléfono, dirección) tras
   confirmar un pedido — verificado con test RTL y manualmente (CA-2 del refinamiento).
3. **Predictibilidad de IDs (CA-3)** — el ID de pedido pasa de `Date.now()` (predecible,
   permite enumeración) a `crypto.randomUUID()` truncado a 8 hex (32 bits de entropía,
   ~4.3×10⁹ combinaciones). No es criptográficamente tan fuerte como un UUID completo,
   pero es suficiente para el volumen del MVP y elimina la predictibilidad por timestamp.
4. **Validación de entrada (CA-4)** — `.max()` en `quantity`/`size`/`color` cierra un
   vector de entradas arbitrariamente grandes contra la BD; verificado con Supertest y
   en vivo contra el servidor real.
5. **Modelo de sesión (CA-5)** — eliminar `SESSION_SECRET` sin usar no reduce seguridad
   real (nunca se usaba para firmar nada); documentado en `session.ts` que la entropía
   de `crypto.randomUUID()` (122 bits) es la garantía real, no una firma HMAC.
6. **`npm audit`** — 0 vulnerabilidades (producción y dev).
7. Sin cambios en CORS, rate limiting, logging o `dangerouslySetInnerHTML` en esta US.

**Sin hallazgos HIGH/CRITICAL. Revisión de seguridad aprobada.**
