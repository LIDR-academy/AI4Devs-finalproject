## US refinada

**Historia de usuario:**
Como corredor, quiero ver una pantalla de confirmación clara tras completar la compra, para tener certeza de que mi pedido ha sido registrado y conocer su número de referencia.

**Caso de uso asociado:** CU3 — Proceso de compra: carrito y checkout simulado

**Alcance técnico:** US **100% Frontend**. No se añade ningún endpoint nuevo. La pantalla de confirmación consume el mismo `OrderResponse` que ya devuelve `POST /api/checkout` (`US-011`); no se usa `GET /api/orders/:id` porque ese endpoint no existe todavía (es alcance de `US-013`, no se invade). El punto de partida es el bloque mínimo de éxito introducido deliberadamente por `US-011` en el paso 3 de `CheckoutPage` (`frontend/src/app/checkout/page.tsx:116-121`):

```tsx
{order && (
  <div className="rounded-lg bg-white p-6 shadow-sm text-center">
    <p className="text-lg font-semibold text-foreground">¡Pedido confirmado!</p>
    <p className="mt-2 text-muted-foreground">Número de pedido: {order.id}</p>
  </div>
)}
```

Esta US lo sustituye por la pantalla completa (Pantalla 6 del prototipo, `docs/PRD.md:309-315`): icono de éxito, número de pedido, mensaje de notificación por email y el CTA «Seguir comprando». El prototipo y el CA original también contemplaban un segundo CTA «Ver mis pedidos» → `/orders`; se retiró tras el cierre inicial de la US porque esa ruta no existe (`US-013` no está implementada) — ver "Corrección post-cierre" al final de este documento.

**Resolución de ambigüedades:**

1. **Persistencia del pedido confirmado para sobrevivir a un reload.** El estado `order` de `CheckoutPage` es React state en memoria: un *reload* completo de la pestaña lo pierde, y como el carrito ya quedó vacío (`clearCart()`, `US-011`), el guard de carrito vacío expulsaría al corredor en vez de mostrarle su confirmación — incumpliendo el escenario alternativo de esta US ("el corredor recarga la página de confirmación... la pantalla muestra la confirmación del pedido ya creado"). Se persiste el `OrderResponse` devuelto por `POST /api/checkout` en `sessionStorage` (clave `runmarket_last_order`) justo tras un checkout exitoso. `sessionStorage` (no `localStorage`) porque el alcance es la sesión de la pestaña — coherente con la limitación ya documentada en `US-013` ("sin autenticación no hay historial persistente entre sesiones") — y porque no comparte namespace con la caché del carrito (`runmarket_cart`). No contiene ningún dato de tarjeta (`CLAUDE.md` solo restringe `PaymentData`); el `OrderResponse` ya es el mismo dato no sensible que el backend devolvió al cliente.
2. **No se reenvía `POST /api/checkout` al recargar.** Al montar `CheckoutPage`, si `itemCount === 0` y no hay `order` en memoria, se intenta hidratar desde `sessionStorage` *antes* de decidir cualquier redirección. Si la entrada es válida (JSON parseable con `id: string` e `items: array`), se hidrata `order` sin llamar a la API — cumple "no se genera un segundo pedido".
3. **Redirección al catálogo cuando no hay pedido válido.** El criterio de error de esta US es literal: *"si el corredor llega a esta pantalla sin un pedido válido recién creado, es redirigido al catálogo"* — y coincide con el escenario alternativo ya documentado en `docs/PRD.md:242` ("Carrito vacío al iniciar checkout... el sistema redirige al catálogo"), no con `/cart`. El guard existente (`US-009`) redirigía a `/cart` en este caso (`itemCount === 0 && !order`). Esta US ajusta el destino a `/` para alinear con el criterio de aceptación literal y con el PRD; no se modifica ninguna otra condición del guard, que sigue gobernada por `US-009`. Una entrada de `sessionStorage` corrupta o ausente se trata igual: se descarta (si existe) y se redirige a `/`.
4. **La pantalla de confirmación sustituye por completo el layout del wizard, no se inserta dentro de él.** Mientras `order` no exista, `CheckoutPage` sigue renderizando `StepIndicator` + grid de 2 columnas (formulario + `CheckoutOrderSummary`) como hasta ahora. En cuanto `order` está poblado (recién creado o hidratado), la página renderiza **únicamente** la pantalla de confirmación (sin indicador de pasos ni resumen lateral) — evita el efecto visual incorrecto de un `CheckoutOrderSummary` mostrando el carrito ya vacío junto a la confirmación. Mismo patrón ya usado para el estado vacío de `/cart` (`frontend/src/app/cart/page.tsx:41-57`): bloque centrado, icono, texto, CTA.
5. **El "mensaje de notificación por email" usa el dato ya disponible, no envía ningún email real.** `OrderResponse.shippingEmail` (ya presente desde `US-011`) es el email al que se "notificaría" la confirmación. No hay envío de correo real en el MVP (fuera de alcance, no documentado en `docs/DATA-MODEL.md` ni en `docs/ARCHITECTURE.md`); el mensaje es puramente informativo en la UI.
6. **CA "el badge del carrito muestra 0 artículos" no requiere código nuevo.** Ya se cumple por la combinación de `clearCart()` (`US-011`) y `CartBadge` (`frontend/src/components/layout/cart-badge.tsx`, ya lee `itemCount` de `useCart()`). Esta US no toca ese componente; se verifica con un test de integración para no dejar el criterio sin cobertura.

Nueva constante: `const ORDER_STORAGE_KEY = 'runmarket_last_order';`

El guard existente se sustituye por un único efecto que cubre hidratación + redirección:
```typescript
useEffect(() => {
  if (order) return;
  if (itemCount > 0) return;
  try {
    const raw = sessionStorage.getItem(ORDER_STORAGE_KEY);
    if (raw) {
      const parsed = JSON.parse(raw) as OrderResponse;
      if (parsed && typeof parsed.id === 'string' && Array.isArray(parsed.items)) {
        setOrder(parsed);
        return;
      }
    }
  } catch {
    // entrada corrupta — se ignora y se redirige más abajo
  }
  sessionStorage.removeItem(ORDER_STORAGE_KEY);
  router.push('/');
}, [order, itemCount, router]);
```

`handleConfirmOrder` persiste el pedido tras el éxito:
```typescript
const result = await apiPost<OrderResponse>('/checkout', shippingData);
setOrder(result);
sessionStorage.setItem(ORDER_STORAGE_KEY, JSON.stringify(result));
clearCart();
```

El render se reestructura: si `order` está poblado, la página devuelve únicamente `<OrderConfirmation order={order} />` (sin `StepIndicator` ni grid); si no, se mantiene el wizard de 3 pasos tal cual quedó en `US-011`, eliminando el bloque mínimo de éxito (`{order && (...)}` dentro del `currentStep === 3`) ya cubierto por la rama anterior.

**UX states añadidos/modificados:**

| Estado | Comportamiento |
|---|---|
| `order` poblado (recién creado o hidratado) | Se renderiza solo `OrderConfirmation`; sin `StepIndicator`/sidebar |
| Reload con `sessionStorage` válido y carrito vacío | Se hidrata `order` sin llamar a la API; mismo resultado visual que justo tras confirmar |
| Carrito vacío, sin `order` en memoria ni en `sessionStorage` (o entrada corrupta) | Redirección a `/` (catálogo) |
| Carrito con artículos, sin `order` | Wizard de 3 pasos normal (sin tocar `sessionStorage`) |

## Seguridad OWASP

> Esta sección se completa en la Fase 5 (revisión de seguridad). Las consideraciones previas a implementar se listan a continuación para guiar al desarrollador.

### Análisis previo

| Riesgo | Categoría OWASP | Mitigación prevista |
|---|---|---|
| Persistencia de datos sensibles en `sessionStorage` | A02 — Cryptographic Failures | El `OrderResponse` persistido no contiene ningún dato de tarjeta ni PII más allá de lo que el backend ya entregó al cliente en la respuesta de `POST /api/checkout` (nombre, email, dirección de envío) — mismo dato ya visible en el DOM tras el checkout, no se añade superficie nueva de exposición |
| JSON corrupto o manipulado en `sessionStorage` provocando un estado inconsistente | A04 — Insecure Design | La hidratación valida la forma mínima (`id` string, `items` array) dentro de un `try/catch`; cualquier fallo de parseo o forma inválida limpia la entrada y redirige a `/`, sin renderizar datos parcialmente formados |
| Suplantación de un pedido ajeno mediante `sessionStorage` manipulado a mano | A01 — Broken Access Control | El `sessionStorage` es local al navegador del propio corredor (no se transmite ni se usa para autorizar ninguna llamada de red); el backend no vuelve a consultarse para mostrar la confirmación, por lo que un valor manipulado como máximo muestra datos falsos en la propia pantalla del atacante, sin acceso a pedidos de otra sesión |
| `dangerouslySetInnerHTML` en el nuevo componente | A03 — Injection / XSS | `OrderConfirmation` renderiza todos los valores (`order.id`, `order.shippingEmail`) vía JSX, que escapa automáticamente; no se usa `dangerouslySetInnerHTML` |

### Hallazgos y remediación

| ID | Severidad | Componente | Vector / Exploit | Fix | Estado |
|---|---|---|---|---|---|
| SEC-01 | LOW | `frontend/src/app/checkout/page.tsx` (`sessionStorage.setItem(ORDER_STORAGE_KEY, ...)`) | El `OrderResponse` completo (nombre, email, teléfono, dirección, ciudad, CP, país de envío + snapshot de ítems) se persiste en `sessionStorage` sin cifrar. Cualquier script con acceso al mismo origen (p. ej. una extensión de navegador maliciosa, o un futuro XSS no relacionado) podría leerlo. No contiene datos de tarjeta (`PaymentData` vive solo en el estado de `PaymentForm`, nunca se serializa a `sessionStorage`) ni introduce un dato que el cliente no tuviera ya — es el mismo `OrderResponse` que el backend ya entregó en la respuesta de `POST /api/checkout` y que ya se mostró en el DOM. `sessionStorage` se limpia al cerrar la pestaña y no se transmite automáticamente en cada request (a diferencia de una cookie), por lo que la superficie de exposición no aumenta respecto al estado pre-US-012. | Aceptado como hardening de defensa en profundidad, no como vulnerabilidad explotable de forma independiente: si se quisiera reducir aún más la superficie, una mejora futura sería persistir solo los campos estrictamente necesarios para `OrderConfirmation` (`id`, `shippingEmail`, `items`) en lugar del `OrderResponse` completo. No se implementa en esta US porque no es una vulnerabilidad per se y expandiría el alcance fuera de las tareas definidas. | Aceptado / documentado |
| SEC-02 | LOW | `frontend/src/app/checkout/page.tsx` (hidratación desde `sessionStorage` en el `useEffect` de montaje) | Un corredor puede editar manualmente `runmarket_last_order` en su propio `sessionStorage` (DevTools) y forzar que `/checkout` muestre un `id`/`shippingEmail` arbitrarios.
