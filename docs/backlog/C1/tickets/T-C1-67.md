# [C1] T-C1-67 · Internal work notes absent from every outbound payload

## Context

`US-C1-22` requires that when the Incident is **rendered, notified on, or exported through any channel**, an internal work note is **absent from the payload, not hidden by the client** (`NFR-SEC-04`) — and requires this to be **asserted by an explicit test for each channel**. `US-C1-23` restates it from the requester side: internal work notes never cross the API boundary to a requester.

Client-side filtering is the failure mode this ticket exists to prevent, and “each channel” is the part that is easy to half-do: the detail response is the obvious one, the notification payload and the export are the ones that leak.

## Scope

- Visibility filtering applied in the **application layer**, on the way out, so every read path inherits it rather than each adapter re-implementing it.
- Explicit per-channel assertions: the Incident detail response, the entry list response, any list or search projection, the notification payload handed to `C16`, and any export or report projection.
- Attachments on internal entries excluded from the same payloads and refused on direct retrieval, composing with `T-C1-18`.
- A test that adds a new read path without filtering and fails, so the guarantee is structural rather than a checklist.
- Out of scope: the notification templates themselves (`C16`); the audit entry rendering (`C18`), which is a separate visibility question owned by that epic.

## Acceptance criteria

**Given** an Incident with both public and internal entries **When** a requester reads it through the API **Then** the payload contains only the public entries, and the internal ones are absent from the response body rather than flagged.

**Given** the same Incident **When** a notification payload is produced for a requester **Then** no internal entry text and no internal attachment reference appears in it.

**Given** any export or list projection reachable by a requester **When** it is produced **Then** it carries no internal entry.

**Given** an internal attachment **When** a requester requests it by direct identifier **Then** it is refused indistinguishably from a non-existent attachment.

**Given** a newly added requester-facing read path with no filtering **When** the test suite runs **Then** it fails, proving the guarantee is enforced structurally.
