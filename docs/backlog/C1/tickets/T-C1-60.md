# [C1] T-C1-60 · Confirm and reject use cases, with rejection marked as a reopen

## Context

`US-C1-18` requires a requester confirmation inside the window to move the Incident to `Closed` with the confirmation recorded, and a rejection to return it to `In Progress` with the rejection reason recorded and **the event marked as a reopen so the Reopen Rate metric can count it**.

Both paths are one ticket because they are two branches of the same window and the reopen marking only makes sense against the confirm branch it contrasts with.

## Scope

- `ConfirmResolutionUseCase` and `RejectResolutionUseCase` in `libs/incident/application`, both validating the window predicate of `T-C1-59`.
- `ResolutionConfirmed` and `ResolutionRejected` events; the rejection event carries an explicit **reopen** marker and the rejection reason, so `C17` reporting counts reopens without inferring them from state history.
- Contract DTOs and the portal routes in `apps/api`.
- Out of scope: authorization and the expired-window refusal (`T-C1-61`); the portal UI (`T-C1-62`); the Reopen Rate metric itself, which belongs to `C17`.

## Acceptance criteria

**Given** a `Resolved` Incident inside its confirmation window **When** the requester confirms **Then** it moves to `Closed` and the confirmation is recorded with actor and timestamp.

**Given** the same Incident **When** the requester rejects with a reason **Then** it returns to `In Progress`, the reason is recorded, and the published event carries the reopen marker.

**Given** the rejection event **When** a reporting consumer reads it **Then** the reopen is identifiable from the marker alone, without reconstructing the state history.

**Given** either use case **When** it is unit-tested on `FixedClock` **Then** the window decision is asserted without a running clock or a database.
