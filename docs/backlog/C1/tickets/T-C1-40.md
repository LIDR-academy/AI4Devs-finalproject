# [C1] T-C1-40 · The uplift raises assessed Impact and Priority is re-derived through the matrix

## Context

`US-C1-11` requires that when the flag is set with a justification, **the assessed Impact is raised by the configured amount and Priority is re-derived through the Impact × Urgency matrix** of `US-C1-08` — and states the rule this ticket exists to protect: **the flag never writes a Priority directly**.

This is the mechanism the epic map calls the product's signature behavior. Writing a Priority directly would be simpler and would silently destroy the consistency `FR-INC-04` buys.

## Scope

- Aggregate behavior applying the `ImpactUplift` of `T-C1-36` to the assessed Impact when the flag is set, then calling `PriorityCalculator` with the raised Impact and the unchanged Urgency.
- The underlying assessed Impact retained separately from the uplifted value, so clearing the flag (`T-C1-46`) restores it exactly.
- A unit test asserting the absence of any code path that assigns a Priority level from the flag handler.
- Out of scope: the ceiling case (`T-C1-41`); the causal event (`T-C1-42`); the clearing path (`T-C1-46`); the override interaction (`T-C1-47`).

## Acceptance criteria

**Given** an Incident with an assessed Impact and Urgency **When** the flag is set **Then** the effective Impact is the assessed Impact raised by the configured uplift, and the resulting Priority equals what the matrix maps for that raised pair.

**Given** the same Incident **When** the resulting Priority is compared against the matrix **Then** it matches the matrix mapping exactly for every starting pair in the cross-product, with no pair producing a Priority the matrix does not contain.

**Given** the flag handler **When** the domain library is searched **Then** it contains no direct Priority assignment; every Priority it produces comes from `PriorityCalculator`.

**Given** the underlying assessed Impact **When** the flag is set **Then** it is still readable unchanged alongside the uplifted value.
