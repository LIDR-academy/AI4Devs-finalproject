# [C1] T-C1-62 · Requester confirm / reject surface on the portal

## Context

`US-C1-18` exists so a ticket is not closed on a requester while their problem is still there. The surface must make both choices equally reachable — a portal that offers only “confirm” produces a Reopen Rate of zero for the wrong reason.

## Scope

- Requester Incident view in `libs/incident/feature` showing the resolution, the resolution notes and the remaining confirmation time.
- Confirm and reject actions with equal prominence; reject requires a reason.
- Expired-window refusal surfaced with the message the server returns, announced, with the next step actionable.
- Mobile-operable and WCAG 2.1 AA, since requesters act from venues (`NFR-USE-04`).
- Out of scope: the use cases (`T-C1-60`, `T-C1-61`); the comment thread (`T-C1-70`).

## Acceptance criteria

**Given** a resolved Incident inside its window **When** the requester opens it **Then** the resolution, the notes and the remaining time are shown, and confirm and reject are both offered.

**Given** the requester rejecting **When** they submit without a reason **Then** it is refused with a message stating that a reason is required.

**Given** an elapsed window **When** the requester submits either action **Then** the server message is shown and announced, and the offered next step is actionable rather than a dead end.

**Given** a keyboard-only user on a 360px viewport **When** they confirm or reject **Then** both complete without a pointer and the outcome is announced.
