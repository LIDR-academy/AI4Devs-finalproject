# [C1] T-C1-19 · Attachment upload and list UI

## Context

`US-C1-04` is driven by a requester attaching a screenshot of the error they hit so the agent can see the failure instead of asking for a description. The surface must therefore work on the requester portal as well as the agent view, and must state limits before a rejected upload wastes the user's time.

Limits are configuration owned by `T-C1-18`; the client reads them rather than hardcoding them, and the server remains the authority.

## Scope

- Hand-built file-input and attachment-list components in `libs/incident/ui`, composed into the requester and agent Incident views.
- Accepted types and the size limit displayed before selection, read from the server-provided configuration.
- Upload progress, failure and retry states always defined; a rejected upload states the limit and the accepted types in the active language.
- Attachment list shows filename, size and uploading actor; removal is offered only where the actor is permitted.
- Out of scope: the storage port and limits (`T-C1-17`, `T-C1-18`); the internal-note visibility rules, which the server enforces (`T-C1-18`, `T-C1-67`).

## Acceptance criteria

**Given** the upload control **When** it renders **Then** the accepted types and the maximum size are stated before a file is chosen.

**Given** an oversized or disallowed file **When** the server rejects it **Then** the message states the limit and the accepted types, is announced, and the rest of the form retains its data.

**Given** a keyboard-only user on a mobile viewport **When** they attach and then remove a file **Then** both actions complete without a pointer and the list change is announced.

**Given** the components **When** they are inspected **Then** they carry `OnPush`, live in `type:ui` with no injected service, and use Transloco for every string.
