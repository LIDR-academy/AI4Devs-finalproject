# [C1] T-C1-55 · Re-resolution after a reopen, with the previous resolution retained

## Context

`US-C1-16` requires that an Incident later reopened and resolved again needs **a new resolution code and notes**, and that **the previous resolution stays in the history**. A reopen path that reuses the prior resolution would let a ticket be re-closed without anyone stating why it was fixed the second time.

Reopen itself is `T-C1-60` (requester rejection) and the configured reopen transition of `T-C1-49`.

## Scope

- Resolution history on the aggregate as an append-only sequence rather than a single mutable field.
- Re-entry into `Resolved` requiring a fresh code and notes, refusing the transition if the caller supplies none on the assumption the previous one still applies.
- Read model exposing every resolution attempt with its actor, code, notes and timestamp.
- Out of scope: FCR behavior across a reopen (`T-C1-79`, `T-C1-80`); the confirmation window (`T-C1-59`).

## Acceptance criteria

**Given** a resolved Incident that is reopened **When** resolution is attempted again with no new code or notes **Then** it is refused with the same typed error as a first resolution without them.

**Given** the same Incident resolved a second time with a new code and notes **When** it commits **Then** both resolutions are readable in order, and the first is unchanged.

**Given** an Incident resolved and reopened twice **When** its history is read **Then** every resolution attempt appears with its actor, code and timestamp.

**Given** the resolution history **When** any operation attempts to modify a past entry **Then** it is impossible by construction — the sequence is append-only (`NFR-AUD-02`).
