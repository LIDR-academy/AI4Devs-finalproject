# [C1] T-C1-36 · Configurable Impact uplift expressed against the Impact scale

## Context

`US-C1-14` requires the amount by which the competition-in-progress flag raises assessed Impact to be **configuration with a documented default, expressed against the defined Impact scale rather than as an opaque number**, and requires a value that would be meaningless on the scale — zero, negative, or larger than the scale — to be refused with a message naming the valid range.

Expressing the uplift in scale levels rather than as a raw integer is what makes the ceiling question of finding **F24** (`T-C1-41`) a well-posed one.

## Scope

- `ImpactUplift` value object in `libs/incident/domain`, expressed in `ImpactLevel` steps over the shared-kernel scale.
- Range validation: refuse zero, negative, and any value that could not move any level on the defined scale, with a typed error naming the valid range.
- A documented default recorded in the domain as the reference value the configuration seeds.
- Out of scope: persistence, versioning and boot validation (`T-C1-37`); applying the uplift (`T-C1-40`); the ceiling behavior (`T-C1-41`); the screen (`T-C1-38`).

## Acceptance criteria

**Given** an uplift of zero, a negative uplift, or one exceeding the number of levels on the Impact scale **When** it is constructed **Then** a typed domain error names the valid range and no value object exists.

**Given** a valid uplift **When** it is inspected **Then** it is expressed in Impact levels, not as a raw number whose unit must be inferred.

**Given** the documented default **When** it is read **Then** it is a valid uplift on the current scale.

**Given** the value object **When** it is unit-tested **Then** the boundary values — one below, at, and one above the valid range — are all asserted with no infrastructure.
