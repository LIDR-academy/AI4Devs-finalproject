# [C1] T-C1-66 · Add-entry use cases for agent and requester, with visibility authorization

## Context

`US-C1-22` lets an agent record internal diagnosis separately from what they tell the requester. `US-C1-23` lets the requester add a comment which is **recorded as a public comment attributed to them** and published so agents are notified (`C16`) and the activity history records it (`C18`).

A requester must never be able to create an internal entry, and the two paths differ enough in authorization that they are written together to keep the visibility decision in one place.

## Scope

- `AddIncidentEntryUseCase` for agents, accepting an explicit visibility and defaulting to internal per `T-C1-65`.
- `AddRequesterCommentUseCase`, forcing public visibility and rejecting any supplied visibility rather than silently overriding it.
- Ownership check for the requester path through the `C10` visibility predicate; an Incident the requester did not raise and holds no grant over is denied indistinguishably from not existing (`FR-IAM-03`, `NFR-SEC-03`).
- Post-commit publication of `IncidentEntryAdded`; `C16` notifies and `C18` records — neither is written here.
- Out of scope: the outbound-payload exclusion (`T-C1-67`); the immutability rule (`T-C1-68`); the UI (`T-C1-69`, `T-C1-70`).

## Acceptance criteria

**Given** an agent adding an entry with no stated visibility **When** it commits **Then** the entry is internal.

**Given** a requester adding a comment **When** it commits **Then** the entry is public, attributed to them, and exactly one event is published after commit.

**Given** a requester supplying an internal visibility in the request **When** it is processed **Then** it is refused rather than silently coerced, so the caller cannot believe an internal note was created.

**Given** a requester acting on an Incident they did not raise and hold no grant over **When** they add a comment **Then** the response is indistinguishable from the Incident not existing.
