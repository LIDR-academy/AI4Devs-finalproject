# [C1] T-C1-50 · Transition-rule configuration: persistence, migration and hot reload

## Context

`US-C1-15` requires the configured transitions to be **changed by an administrator, take effect without a restart, and be audited**. This is the “configuration as data” rule of `ARCHITECTURE.md` §9 applied to the lifecycle.

The `StateModel` primitive comes from `C10`; the per-context configuration mechanism is `C12`. This ticket delivers the `incident` context storage and reload path, not a general configuration framework.

## Scope

- TypeORM entity, mapper and migration for the Incident transition rules, plus a seed migration providing the `FR-INC-06` default transition set so a fresh environment boots.
- Repository adapter feeding the `StateModel` instance, with reads reflecting a change on the next transition and no restart required.
- `TransitionRulesChanged` domain event published on change for the audit trail (`FR-AUD-05`).
- Configuration version pinned on in-flight Incidents per `NFR-CFG-02`, consistent with `T-C1-27` and `T-C1-37`.
- Out of scope: the state model itself (`T-C1-49`); the administration screen, which belongs to the Admin Console surface and is not required by any `C1` story.

## Acceptance criteria

**Given** a transition rule change **When** it commits **Then** the next transition attempt honours it with no application restart.

**Given** a fresh database **When** migrations run **Then** the default transition set of `FR-INC-06` is present and the application boots.

**Given** a transition rule change **When** it commits **Then** exactly one `TransitionRulesChanged` event is published after commit with the actor and the previous and new rule set.

**Given** the migration **When** it is run and reverted **Then** it succeeds both ways and leaves no residual object.
