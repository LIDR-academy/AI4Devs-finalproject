# [C1] T-C1-04 · Reference-number sequence, unique constraint, immutability and migration

## Context

`US-C1-05` requires that two Incidents created concurrently never share a reference, and that uniqueness is guaranteed **by a database constraint, not by an application-level check a race can defeat**. It further requires that a reference is never modified and never re-issued — including when an Incident is cancelled or deleted (`NFR-DAT-01`).

This ticket carries the whole guarantee — sequence, constraint, immutability and migration — as one unit: splitting it would leave a constraint without the mechanism that feeds it, and the concurrency assertion needs both present to mean anything.

## Scope

- Migration adding the reference column with a UNIQUE constraint and the sequence or allocation mechanism that feeds `nextReference()`, inside the `incident` schema namespace from `T-C1-02`.
- Adapter implementation of `nextReference()` allocating from that mechanism within the caller transaction.
- Database-level immutability: an update that changes an existing reference is rejected, and a deleted or cancelled Incident never releases its number for reuse.
- Reversible down migration, per the convention fixed by `T-C10-17`.
- Out of scope: the aggregate (`T-C1-05`); the Incident table itself, created by `T-C1-06` — this migration is sequenced after it and adds only the reference column and its mechanism.

## Acceptance criteria

**Given** two Incidents created concurrently in separate transactions **When** both commit **Then** their references differ, and the guarantee still holds with the application-level check removed, proving the constraint and not the code enforces it.

**Given** an existing Incident **When** an update attempts to change its reference **Then** the write is rejected at the database level.

**Given** an Incident that is cancelled and one that is deleted **When** the next reference is allocated **Then** it is a new value; neither released number is ever re-issued.

**Given** the migration **When** it is run, reverted and run again **Then** the outcome is identical each time and no residual object remains after the revert.
