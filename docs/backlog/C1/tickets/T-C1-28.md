# [C1] T-C1-28 · Matrix configuration screen

## Context

`US-C1-09` requires the matrix configuration screen to be built from the **in-house design system with no third-party component library**, keyboard-operable and WCAG 2.1 AA. A grid of Impact × Urgency cells is the classic place a team reaches for a component library; per `CLAUDE.md` §3 and ADR-010 it is hand-built here.

The total-coverage invariant is the server's (`T-C1-26`); the screen surfaces it rather than reimplementing it.

## Scope

- Routed configuration page in `libs/incident/feature` presenting the Impact × Urgency grid, each cell a Priority selector.
- Unmapped cells visually and semantically marked, with save refused and the reason stated when any remain.
- Grid navigable by arrow keys with a correct roving tab index and announced cell context — row and column headers conveyed to a screen reader, not implied by layout.
- All strings through Transloco; styling through design tokens; `OnPush` throughout.
- Out of scope: the aggregate and persistence (`T-C1-26`, `T-C1-27`); the uplift screen (`T-C1-38`), which is its own configuration.

## Acceptance criteria

**Given** the configuration page **When** it renders an incomplete matrix **Then** the unmapped cells are identifiable without relying on color alone and saving is refused with a message naming what is missing.

**Given** a complete matrix **When** it is saved **Then** the change persists and the page reflects the new version.

**Given** a keyboard-only user **When** they traverse the grid **Then** every cell is reachable by arrow keys, the Impact and Urgency context of the focused cell is announced, and the Priority selection is operable without a pointer.

**Given** the page **When** it is inspected **Then** it imports no third-party component library and contains no hardcoded color or spacing.
