# [C1] T-C1-64 · API-E2E: the auto-close boundary on a deterministic clock

## Context

`US-C1-19` turns on a time boundary, and a time boundary is where a system either provably works or quietly drifts. The unit tests on the window predicate (`T-C1-59`) prove the arithmetic; this scenario proves the whole path — configuration, rule, transition, attribution — behaves at the boundary through the real HTTP and database stack.

`agent: —` because E2E test code belongs to neither dev agent: it is **e2e-harness work on the backend platform**, in `apps/api-e2e` (`platform:backend`, `type:e2e`), following the precedent of `T-C10-29`.

## Scope

- Cucumber feature and step definitions in `apps/api-e2e` driving the auto-close rule against a real API and PostgreSQL, with `FixedClock` advanced deterministically.
- Cases: just inside the period, exactly at the boundary, just outside; an Incident rejected before the boundary; an Incident already `Closed`.
- Assertion that the closing actor is the system actor and not the last agent who touched the Incident.
- No test sleeps and no assertion against wall-clock time.
- Out of scope: the rule and configuration (`T-C1-63`); frontend behavior.

## Acceptance criteria

**Given** a `Resolved` Incident and the clock advanced to just inside the period **When** the rule runs **Then** the Incident is still `Resolved`.

**Given** the clock advanced to the boundary and to just beyond it **When** the rule runs **Then** the defined boundary behavior holds in both cases and is asserted explicitly rather than left to chance.

**Given** an auto-closed Incident **When** its activity history is read over the API **Then** the closing actor is the system actor and the reason “auto-closed, no response” is present.

**Given** the suite **When** it runs **Then** it contains no sleep and no wall-clock assertion, and passes repeatedly with identical results.
