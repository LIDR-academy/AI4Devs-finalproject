# [C1] T-C1-18 · Attachment upload use case: configured limits and visibility inheritance

## Context

`US-C1-04` requires a file exceeding the configured size limit, or whose type is not on the configured allow-list, to be **rejected before storage** with a message stating the limit and the accepted types (`NFR-USE-05`), with the limits coming from validated configuration through `ConfigService` — never raw `process.env`.

It also requires an attachment added to an **internal work note** to be neither listed nor retrievable by direct reference for a requester, because work-note visibility governs it (`NFR-SEC-04`). The entry-visibility model itself is `T-C1-65`; this ticket declares the inheritance rule and the retrieval guard, and its test uses the visibility value once that ticket lands.

## Scope

- `AddAttachmentUseCase` and `RemoveAttachmentUseCase` in `libs/incident/application`, authorizing the actor and enforcing the limits **before** calling the storage port.
- Size limit and content-type allow-list read from validated configuration with documented defaults; boot fails fast if either is absent or malformed.
- Rejection message naming the limit and the accepted types, localized through `nestjs-i18n`.
- Visibility inheritance: an attachment on an internal entry is excluded from requester-facing listings **and** refused on direct retrieval by identifier, indistinguishably from not existing.
- Out of scope: the entry visibility model (`T-C1-65`); the outbound-payload sweep across every channel (`T-C1-67`); the UI (`T-C1-19`).

## Acceptance criteria

**Given** a file one byte over the configured size limit **When** it is uploaded **Then** it is rejected before anything reaches the storage port, and the message names the limit.

**Given** a file whose content type is not on the allow-list **When** it is uploaded **Then** it is rejected with a message naming the accepted types, and the check is on the resolved content type rather than the filename extension alone.

**Given** an attachment on an internal work note **When** a requester lists the Incident attachments and then requests that attachment by identifier **Then** it is absent from the listing and the direct request is refused indistinguishably from a non-existent attachment.

**Given** the size or type configuration absent or invalid **When** the application boots **Then** it fails fast with a message naming the key and does not start.
