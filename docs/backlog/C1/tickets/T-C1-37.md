# [C1] T-C1-37 · Uplift persistence, version pinning, boot validation and audit event

## Context

`US-C1-14` requires the uplift to be **persisted configuration**, validated at boot, applied to subsequent derivations, audited (`FR-AUD-05`), with **Incidents in flight keeping the configuration version they were created under** (`NFR-CFG-02`).

The same versioning discipline as the matrix (`T-C1-27`) applies, and for the same reason: a version column added later cannot pin records created before it.

## Scope

- TypeORM entity, mapper and migration for the uplift configuration with an explicit version; seed migration providing the documented default.
- Incident records resolve the uplift version applied at creation.
- Boot validation in `apps/api`: absent or invalid uplift configuration fails fast with a message naming the key.
- `ImpactUpliftChanged` domain event published on change for the audit trail.
- Out of scope: the value object and its range rule (`T-C1-36`); the screen (`T-C1-38`); applying the uplift (`T-C1-40`).

## Acceptance criteria

**Given** an Incident created under uplift version *n* **When** the uplift is changed to *n+1* and the flag is applied to that Incident **Then** version *n* is used, and a newly created Incident uses *n+1*.

**Given** absent or invalid uplift configuration **When** the application boots **Then** it fails fast naming the key and does not start.

**Given** an uplift change **When** it commits **Then** exactly one `ImpactUpliftChanged` event is published after commit carrying the previous and new value and the actor.

**Given** the migration **When** it is run and reverted **Then** it succeeds both ways and leaves no residual object.
