# [C1] T-C1-22 · Taxonomy administration use cases and the in-use delete refusal

## Context

`US-C1-06` requires an administrator to add, rename, deactivate and reorder taxonomy nodes with the change taking effect for new Incidents **without a restart**, published as a domain event so it lands in the audit trail (`FR-AUD-05`). It also requires an attempt to delete a node in use to be **refused with a typed error naming the constraint**, with deactivation offered instead.

The audit entry itself is `C18`: this epic publishes, `C18` records. No `C18` ticket is written here.

## Scope

- `AddCategoryNode`, `RenameCategoryNode`, `DeactivateCategoryNode`, `ReorderCategoryNodes` and `DeleteCategoryNode` use cases in `libs/incident/application`, each authorized for the administration permission.
- Delete refusal when any Incident references the node or any descendant does, raising a typed error that names the constraint and points at deactivation.
- Post-commit event publication through `EventPublisherPort`.
- Out of scope: the aggregate (`T-C1-20`); persistence (`T-C1-21`); the screen (`T-C1-23`); the audit entry itself (`C18`).

## Acceptance criteria

**Given** an administrator adding, renaming, deactivating or reordering a node **When** the use case commits **Then** the change is durable, visible to the next Incident creation without a restart, and exactly one domain event is published after commit.

**Given** a node referenced by at least one Incident **When** deletion is attempted **Then** it is refused with a typed error naming the constraint and stating that deactivation is available, and nothing changes.

**Given** a node whose descendant is in use **When** deletion is attempted **Then** it is refused for the same reason, so the constraint cannot be evaded by deleting the parent.

**Given** an actor without the administration permission **When** they invoke any of these use cases **Then** it is denied with the typed authorization error mapping to `403`.
