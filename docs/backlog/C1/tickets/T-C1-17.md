# [C1] T-C1-17 · `Attachment` entity, `AttachmentStoragePort` and migration

## Context

`US-C1-04` requires attachments stored against the Incident with original filename, content type, size and uploading actor, and requires attachments to be **optional** — an Incident without them is valid. It also requires every add and remove to be published as a domain event so it appears in the activity history like any other change.

Storage is behind a port so the concrete store is an adapter swap and never a domain concern.

## Scope

- `Attachment` entity within the `Incident` aggregate boundary in `libs/incident/domain`, holding filename, content type, size, uploading actor and upload time from `ClockPort`.
- `AttachmentStoragePort` with its injection token; a filesystem or object-store adapter in `libs/incident/infrastructure`, bound in `IncidentModule`.
- `AttachmentAdded` and `AttachmentRemoved` domain events returned by the mutating methods.
- TypeORM entity, mapper and migration for attachment metadata; the binary itself lives behind the port, never in the aggregate.
- Out of scope: limit enforcement and the upload use case (`T-C1-18`); visibility inheritance (`T-C1-18`); the UI (`T-C1-19`).

## Acceptance criteria

**Given** an Incident with no attachment **When** it is validated **Then** it is valid; attachments are optional.

**Given** an attachment added to an Incident **When** the aggregate is saved and reloaded **Then** filename, content type, size, uploading actor and upload time round-trip unchanged.

**Given** an attachment added and then removed **When** the events are inspected **Then** exactly one `AttachmentAdded` and one `AttachmentRemoved` were returned by the aggregate.

**Given** the domain library **When** it is inspected **Then** it holds no file handle, no stream and no storage-client type — only the port.
