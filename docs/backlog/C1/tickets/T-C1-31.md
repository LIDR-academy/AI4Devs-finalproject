# [C1] T-C1-31 · Server-authoritative Priority in the web client

## Context

`US-C1-08` requires the web client to display **the value the server returned** and to derive nothing locally; a client that posts a Priority has it ignored, because authorization and derivation are enforced server-side (`NFR-SEC-02`). The temptation this ticket exists to foreclose is a helpful client-side preview of the matrix, which would become a second derivation and drift.

## Scope

- Priority rendering in `libs/incident/ui` and the Incident views, driven only by the server-returned value.
- Explicit presentation of the not-yet-derived state as its own visible state, never as an empty cell or a default level.
- Removal of any Priority field from outbound request payloads; the store never sends one.
- Assertion in the frontend test suite that no matrix and no derivation logic exists anywhere under `libs/incident/{ui,feature,data-access}`.
- Out of scope: the override capture UI (`T-C1-35`); the flag UI (`T-C1-48`).

## Acceptance criteria

**Given** an Incident with a derived Priority **When** it renders **Then** the displayed value equals the server value exactly, and changing Impact in the form does not change the displayed Priority until the server responds.

**Given** an Incident whose Priority is not yet derived **When** it renders **Then** a distinct not-yet-derived state is shown, distinguishable from every real Priority level and not conveyed by color alone.

**Given** any Incident update sent by the client **When** the payload is inspected **Then** it contains no Priority field.

**Given** the frontend libraries **When** they are searched **Then** they contain no Impact × Urgency mapping and no local Priority derivation.
