# [C1] T-C1-43 · `SetCompetitionInProgressFlagUseCase` — the only write path, agent-authorized

## Context

`US-C1-12` requires the flag write to be **reachable only from the agent-invoked use case with an actor holding the agent permission**, and an agent without that permission to be denied with `403` with nothing changed. `ARCHITECTURE.md` §8 shows the flag on its own endpoint with its own use case and its own authorization check, precisely so no other operation can carry it as a side effect.

This is the singleness half of “agent-only and never automatic”. `T-C1-45` proves the never-automatic half; `T-C1-44` closes the inbound field paths.

## Scope

- `SetCompetitionInProgressFlagUseCase` in `libs/incident/application`, authorizing the flag permission through the resolved `Actor`, applying `T-C1-40` and publishing the causal event of `T-C1-42` post-commit.
- Its own HTTP route in `apps/api` and its own contract DTO, separate from every Incident update route.
- Removal of the flag from every other command shape in the application layer, so no other use case can accept it.
- Out of scope: the field rejection at the DTO boundary on other routes (`T-C1-44`); the no-automated-path proof (`T-C1-45`); the clearing path (`T-C1-46`); the UI (`T-C1-48`).

## Acceptance criteria

**Given** an agent holding the flag permission and a justification **When** the use case executes **Then** the flag is set, the uplift and re-derivation apply, and the causal event is published after commit.

**Given** an actor without the flag permission **When** they invoke the use case directly and separately through its HTTP route **Then** both are denied with `403`, nothing is persisted and no event is published.

**Given** every other use case in `libs/incident/application` **When** their command shapes are enumerated **Then** none accepts the competition-in-progress flag as an input.

**Given** the route table **When** it is enumerated **Then** exactly one route writes the flag, and it is the one this ticket adds.
