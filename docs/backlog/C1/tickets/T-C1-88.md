# [C1] T-C1-88 · Redirect surface at intake with the offered path

## Context

`US-C1-28` requires the rejection message to say **what happened and what to do next in the requester language, with no ITSM jargon** (`NFR-USE-01`, `NFR-USE-05`). The persona is a Tournament Organizer who wants to be told **before** submitting that a reschedule is not handled here, and shown where it **is**.

The detection and the outcome are the server decision (`T-C1-87`); this surface renders it and makes the offered path one click away.

## Scope

- Inline evaluation surface on the requester intake form of `T-C1-10`, shown before submission when the description matches a rule.
- Reject presentation: submission blocked, plain-language explanation, and the offered Knowledge Article or Service Catalog item as an actionable link.
- Flag presentation: submission allowed, with the reason stated and the offered path shown alongside.
- Both presentations announced through the live region; the typed description is retained when the requester follows the offered path and returns.
- Out of scope: the rules and the evaluation (`T-C1-86`, `T-C1-87`); the article and catalog surfaces (`C9`, `C8`).

## Acceptance criteria

**Given** a description matching a reject rule **When** the requester attempts to submit **Then** submission is blocked, the message explains in plain language what happened and what to do next, and the offered path is actionable.

**Given** a description matching a flag rule **When** the requester proceeds **Then** submission succeeds and the reason and offered path were both shown first.

**Given** either presentation **When** it appears **Then** it is announced through the live region and contains no untranslated ITSM vocabulary.

**Given** a requester who follows the offered path and returns **When** the form re-renders **Then** their entered description is preserved.
