# [C1] T-C1-52 · Lifecycle actions on the agent Incident view

## Context

`US-C1-15` gives the agent a lifecycle whose allowed transitions are configuration. The client must therefore render the **transitions the server says are available** for the current state, never a hardcoded list — otherwise an administrator changing the configuration would silently break the UI.

## Scope

- Agent Incident detail page in `libs/incident/feature` with a state indicator and the available transitions returned by the server.
- The three Pending reasons offered as distinct choices, labelled through Transloco, never as free text.
- Refusals surfaced with the typed reason — a missing category, a missing resolution code, a disallowed transition each read differently.
- Hand-built components, `OnPush`, design tokens, WCAG 2.1 AA, state change announced through the live region.
- Out of scope: the resolution form (`T-C1-56`); the assignment and escalation actions (block I); the client deriving which transitions are legal.

## Acceptance criteria

**Given** an Incident in any state **When** the page renders **Then** the offered transitions are exactly those the server reports for that state, and no transition list is hardcoded in the frontend libraries.

**Given** an administrator changing the transition configuration **When** the page is reloaded **Then** the offered actions change accordingly with no frontend deployment.

**Given** a transition the server refuses **When** the response returns **Then** the specific reason is shown and announced, distinguishable between a missing category, a missing resolution and a disallowed transition.

**Given** a keyboard-only user **When** they move an Incident to `Pending` **Then** the three reasons are reachable and selectable without a pointer, and the resulting state is announced.
