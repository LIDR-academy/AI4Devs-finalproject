# [C1] T-C1-94 · `ConvertIncidentUseCase` — Incident side only, with the conversion event

## Context

`US-C1-27` requires the conversion to be **recorded as an explicit conversion event naming the source type, the target type, the actor and the reason**, so the type change is itself part of the history.

**The `C2` half is not written here.** This use case produces the Incident-side outcome and publishes the conversion event; the Service Request creation that consumes it is `C2`. Against an undeployed `C2` this ticket is complete and testable with a stubbed target port, and `FR-INC-14` remains unsatisfied until `C2` ships its half — that must be reported, not quietly closed.

## Scope

- `ConvertIncidentUseCase` in `libs/incident/application`, permission-gated, applying the rules of `T-C1-93`.
- `TicketTypeConverted` domain event carrying source type, target type, actor, reason and `ClockPort` timestamp, published post-commit.
- A target-side port for the Service Request creation, bound at the composition root when `C2` exists and to a refusing stub when it does not — so an operator never converts into nothing.
- Contract DTOs and the HTTP route.
- Out of scope: the Service Request aggregate and everything on its side (`C2`); the UI (`T-C1-95`).

## Acceptance criteria

**Given** an agent with the conversion permission and a convertible Incident **When** conversion executes **Then** the reference and history are preserved and one `TicketTypeConverted` event carries source type, target type, actor and reason.

**Given** the `C2` side not deployed **When** conversion is attempted **Then** it is refused with an explicit typed error naming the unavailable target type, and nothing is changed — never a half-converted record.

**Given** an actor without the conversion permission **When** they attempt it **Then** it is denied with `403` and nothing changes.

**Given** the epic review **When** `FR-INC-14` is assessed **Then** it is reported as delivered on the Incident side only, pending the `C2` half.
