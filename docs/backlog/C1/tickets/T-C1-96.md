# [C1] T-C1-96 · Duplicate-detection query: same service and subject inside a configurable window

## Context

`US-C1-31` defines detection precisely: it proposes existing Incidents sharing **the same affected service and the same affected competition subject** within a **configurable time window**. The window is **validated configuration with a documented default**, applied against **persisted UTC timestamps via `ClockPort`**.

The motivation is convergence: ten reports of one outage should converge instead of being worked ten times.

## Scope

- Detection query in `libs/incident/infrastructure` matching on affected service and affected competition subject within the window, ordered so the most relevant candidates come first.
- Time window in validated configuration with a documented default; boot fails fast on absent, zero or negative values.
- Evaluation on `ClockPort` against persisted UTC timestamps, so results are reproducible on `FixedClock`.
- Index supporting the query, added by migration, so detection does not degrade the intake path.
- Out of scope: proposal handling and the agent decision (`T-C1-97`); the UI (`T-C1-98`); any automatic linking, which the story forbids.

## Acceptance criteria

**Given** two Incidents sharing affected service and competition subject inside the window **When** detection runs **Then** each is proposed for the other.

**Given** two Incidents matching on only one of the two attributes **When** detection runs **Then** neither is proposed — both attributes are required.

**Given** a matching Incident outside the configured window **When** detection runs **Then** it is not proposed, and the boundary is asserted on `FixedClock` at, just inside and just outside.

**Given** the window configuration absent, zero or negative **When** the application boots **Then** it fails fast naming the key.
