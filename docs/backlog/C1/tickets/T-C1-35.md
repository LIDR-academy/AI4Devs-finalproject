# [C1] T-C1-35 · Priority override UI with justification capture

## Context

`US-C1-10` requires the derived value to be retained alongside the override **so both are visible**, and requires the justification to be captured. The surface must make an override feel like an accountable exception rather than a routine edit — the story's stated concern is the override becoming an unaccountable habit.

The mandatory justification is enforced in the domain (`T-C1-32`); the form field is a convenience, never the control.

## Scope

- Override action on the agent Incident view, opening a hand-built overlay from `libs/shared/ui` with the justification field and both values shown.
- Persistent display of derived value, overridden value and justification wherever Priority is shown to an agent.
- Explicit return-to-derived action wired to `T-C1-34`, with the consequence stated before confirmation.
- Server-side refusal surfaced as an actionable message; the client never assumes success.
- Out of scope: the use cases (`T-C1-33`, `T-C1-34`); any client-side derivation (`T-C1-31`).

## Acceptance criteria

**Given** an agent opening the override action **When** they submit with an empty justification **Then** the server refusal is surfaced with a message stating that a justification is required, and the Priority is unchanged in the view.

**Given** an Incident with an overridden Priority **When** an agent views it **Then** the overridden value, the derived value and the justification are all visible without an extra navigation.

**Given** an agent choosing to return to the derived value **When** the action is offered **Then** the resulting Priority is stated before confirmation and the action is keyboard-operable.

**Given** the overlay **When** it opens and closes **Then** focus is trapped while open and restored to the trigger on close, using the primitive from `T-C10-14`.
