# [C1] T-C1-02 · `incident` schema namespace and the `IncidentModule` composition root

## Context

Foundation work with no user story behind it. Sources: `docs/product/ARCHITECTURE.md` §6.3, which makes `apps/api` the only place wiring happens and requires a NestJS module per context binding each port token to a concrete adapter; and `T-C10-17`, whose scope note states the bootstrap migration creates the per-context schema namespaces *"starting with the `identity_access` schema"* — every other context's namespace is that context's own cost.

Nothing in blocks B onward can persist or be reached over HTTP until this exists. The migration chain, the data source, `synchronize: false` and the reversibility convention all come from `C10` and are not rebuilt here.

## Scope

- Migration creating the `incident` schema namespace, following the naming and reversibility convention fixed by `T-C10-17`.
- `IncidentModule` in `apps/api`: an empty-but-wired NestJS module registered in the application module, with the port-token binding block established and documented so later tickets add providers rather than inventing a pattern.
- Registration of the `incident` TypeORM entity path in the data source, with no entity yet declared.
- Out of scope: every table, port, adapter and controller — each belongs to the ticket that introduces it. Also out of scope: cross-context adapters such as `SlaPolicyAdapter` (`T-C1-58`), which live in `apps/api` but are introduced by their own tickets.

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** an empty database **When** `pnpm typeorm migration:run -d apps/api/src/data-source.ts` runs **Then** the `incident` schema namespace exists and the run reports success.

**Given** the applied migration **When** `pnpm typeorm migration:revert -d apps/api/src/data-source.ts` runs **Then** the namespace is removed with no residual schema object, and a second run-revert-run cycle produces an identical outcome.

**Given** the API **When** it boots **Then** `IncidentModule` is registered, the application starts, and `/health/ready` reports ready.

**Given** the module **When** it is inspected **Then** it declares no business provider and no controller, and `pnpm nx lint api` passes.
