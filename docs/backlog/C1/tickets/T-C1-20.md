# [C1] T-C1-20 · Category → Subcategory → Item taxonomy aggregate

## Context

`US-C1-06` requires the categorization taxonomy to be a **persisted three-level structure** owned by the `incident` context, with stable identifiers and translatable labels, and **no level hardcoded** in the application — so the service desk can adapt its vocabulary without a code change or a release. This is the "configuration as data" rule of `ARCHITECTURE.md` §9.

## Scope

- `CategoryNode` aggregate in `libs/incident/domain` modelling exactly three levels — Category, Subcategory, Item — with stable identifiers, ordering and an active/inactive state.
- Invariants: a node's level is fixed at creation, a child's parent must be one level above, and the tree cannot exceed three levels.
- Domain events for add, rename, deactivate and reorder, so `FR-AUD-05` has something to record.
- Out of scope: persistence and labels (`T-C1-21`); the administration use cases (`T-C1-22`); the exit-from-New gate (`T-C1-25`).

## Acceptance criteria

**Given** the aggregate **When** a fourth level is attempted **Then** a typed domain error is raised and nothing changes.

**Given** a node **When** its level or parent relationship is inspected **Then** the level is immutable after creation and every child sits exactly one level below its parent.

**Given** any mutation — add, rename, deactivate, reorder **When** it succeeds **Then** it returns a domain event naming the node identifier, the actor and the change.

**Given** the aggregate **When** it is inspected **Then** no category name, subcategory name or item name is hardcoded anywhere in the `incident` libraries.
