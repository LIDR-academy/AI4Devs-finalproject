# [C1] T-C1-44 · Server-side rejection of the flag field on every requester-reachable path

## Context

`US-C1-12` requires that when a requester submits or updates an Incident with the competition-in-progress flag in the request body, **the field is rejected server-side and the flag stays as it was** — and states explicitly that **UI concealment is not the control** (`NFR-SEC-02`), and that this holds on **every inbound path including the portal, the API and any future channel**.

`T-C1-08` established the same rule for the priority-bearing fields at requester intake. This ticket extends it to every update route and makes the guarantee enumerable rather than per-controller.

## Scope

- Every requester-reachable request DTO in `libs/shared/contracts` declared without the flag, so the global `ValidationPipe` with `forbidNonWhitelisted` rejects it.
- An enumeration test over the live route table asserting that the flag is accepted by exactly one route — the one from `T-C1-43` — and rejected by every other, so a route added by a later epic cannot quietly open a second door.
- The rejection outcome is a validation failure naming the field, never a silent strip that would leave the caller believing the flag was set.
- Out of scope: the write use case (`T-C1-43`); the automated-source proof (`T-C1-45`); the origin channels themselves (`C11`).

## Acceptance criteria

**Given** a requester posting the flag on the intake route and on every update route **When** each request is made **Then** each is rejected with a validation failure naming the field, and the stored flag is unchanged in every case.

**Given** the flag silently stripped rather than rejected **When** the test suite runs **Then** it fails — a strip is not an acceptable outcome, because the caller would believe the flag took effect.

**Given** the live route table **When** it is enumerated **Then** exactly one route accepts the flag, and any additional accepting route fails the enumeration until it is deliberately added to it.

**Given** a request from a client that hides the field in its UI **When** the field is sent anyway with a crafted request **Then** the server outcome is identical, proving the control is server-side.
