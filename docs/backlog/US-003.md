## US refinada

**Historia de usuario:**
Como corredor, quiero filtrar el catálogo por categoría de producto y rango de precio, para acotar mi búsqueda a un tipo específico de artículo y ajustarla a mi presupuesto.

### Ambigüedades resueltas

| Punto ambiguo | Decisión |
|---|---|
| **Categoría: ¿multi-selección como las dimensiones running o selección única?** | Selección única. La US habla de "selecciona una categoría" (singular) y `docs/ARCHITECTURE.md` (§7.4, `ProductFilters` del `CatalogService`) ya modela `category?: string`, no `string[]`, a diferencia de `distance`/`surface`/`level`/`objective`. Se implementa como grupo de radio buttons con una opción "Todas" que limpia el filtro. |
| **"Rango de precio" del título vs. "slider de precio máximo" de los criterios** | Solo se implementa el límite superior (`priceMax`). Los 5 criterios de aceptación mencionan exclusivamente "precio máximo"; ninguno define un mínimo seleccionable por el usuario. `priceMin` (presente en el diagrama de clases de ARCHITECTURE.md) queda fuera de alcance de esta US — no hay criterio que lo requiera. |
| **"El slider no permite valor máximo menor que el mínimo"** | Se interpreta como el límite inferior fijo del control (`min` del `<input type="range">`), no como un segundo filtro `priceMin`. Con `PRICE_MIN = 0`, el slider no puede bajar de 0€; no existe combinación inválida posible. |
| **Rango del slider de precio** | `PRICE_MIN = 0`, `PRICE_MAX = 400`, `step = 10`. El producto más caro del seed es 349,99€; 400€ es el primer múltiplo de 50 que cubre el catálogo completo con margen. Constantes en `frontend/src/lib/product-utils.ts`. |
| **Valor del slider en el tope (`PRICE_MAX`)** | Se interpreta como "sin restricción de precio": no se añade `priceMax` a la URL ni a la petición. Evita que el filtro esté siempre activo por defecto y que el badge de filtros activos cuente un filtro que el corredor no eligió explícitamente. |
| **Valores inválidos de `category`/`priceMax` en la query** | Mismo criterio que US-002: se descartan silenciosamente, no generan `400`. El frontend valida `category` contra el enum cerrado (`VALID_CATEGORIES`) y `priceMax` contra "número positivo" antes de construir la URL; el backend repite la validación con Zod como defensa en profundidad (`CLAUDE.md`: "Sanitizar parámetros de URL antes de usarlos como filtros"). |
| **Compatibilidad con filtros running existentes** | Aditivo por construcción: `category` y `priceMax` se añaden como claves adicionales al mismo objeto `ProductFilters`/`where` de Prisma que ya gestiona `distance`/`surface`/`level`/`objective` (AND implícito entre todas las claves presentes). No se modifica la lógica OR-dentro-de-dimensión existente. |
| **Ubicación en el `FilterPanel`** | Sección "Categoría" se añade al principio (antes de Distancia), por ser el filtro más amplio/transversal. Sección "Precio máximo" se añade al final. Decisión de layout, no bloqueante; documentada por consistencia visual. |
| **Página de ficha de producto / endpoint `GET /api/products/:id`** | Sin cambios. Esta US solo afecta a `GET /api/products` (listado). |

En `backend/src/repositories/product.repository.ts`, `buildWhere` se extiende:
```typescript
import { PrismaClient, Prisma, Category } from '@prisma/client';
// ...
private buildWhere(filters?: ProductFilters): Prisma.ProductWhereInput {
  const where: Prisma.ProductWhereInput = {};
  if (filters?.distance?.length)  where.distance  = { hasSome: filters.distance };
  if (filters?.surface?.length)   where.surface   = { hasSome: filters.surface };
  if (filters?.level?.length)     where.level     = { hasSome: filters.level };
  if (filters?.objective?.length) where.objective = { hasSome: filters.objective };
  if (filters?.category)              where.category = filters.category as Category;
  if (filters?.priceMax !== undefined) where.price = { lte: filters.priceMax };
  return where;
}
```

`category` es comparación de igualdad simple (enum cerrado en Prisma); `priceMax` usa `lte` sobre el campo `Decimal` — Prisma acepta un `number` directamente en el filtro.

**Criterios de hecho**

- Con `{ category: 'shoes' }` el `where` contiene `{ category: 'shoes' }`.
- Con `{ priceMax: 100 }` el `where` contiene `{ price: { lte: 100 } }`.
- Con `{ category: 'shoes', distance: ['marathon'] }` el `where` contiene ambas claves simultáneamente (AND).
- Sin `category`/`priceMax` el `where` no contiene esas claves.
- Cumple las reglas de seguridad aplicables de `CLAUDE.md` (Prisma parametrizado, sin raw queries).

```typescript
const VALID_CATEGORIES = ['shoes', 'clothing', 'accessories'] as const;

function toEnumOrUndefined<T extends string>(valid: readonly T[]) {
  return z
    .string()
    .optional()
    .transform((v): T | undefined =>
      v !== undefined && (valid as readonly string[]).includes(v) ? (v as T) : undefined,
    );
}

function toPositiveNumberOrUndefined() {
  return z
    .string()
    .optional()
    .transform((v): number | undefined => {
      if (v === undefined) return undefined;
      const n = Number(v);
      return Number.isFinite(n) && n > 0 ? n : undefined;
    });
}

export const productFilterSchema = z
  .object({
    distance: toArrayEnum(VALID_DISTANCES),
    surface: toArrayEnum(VALID_SURFACES),
    level: toArrayEnum(VALID_LEVELS),
    objective: toArrayEnum(VALID_OBJECTIVES),
    category: toEnumOrUndefined(VALID_CATEGORIES),
    priceMax: toPositiveNumberOrUndefined(),
  })
  .strip();
```
