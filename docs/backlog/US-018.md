## US refinada

**Historia de usuario:**
Como equipo de desarrollo, queremos generar todos los artefactos de contenerización,
infraestructura como código y automatización CI/CD descritos en
`docs/DEPLOYMENT-STRATEGY.md`, para poder desplegar RunMarket en una instancia EC2
real y disponer de un pipeline repetible para futuros despliegues.

**Contexto y alcance:**
Implementa la Opción A de `docs/INFRASTRUCTURE.md`: una única EC2 `t3.micro` con
cuatro contenedores Docker (`postgres`, `backend`, `frontend`, `nginx`) orquestados
con Docker Compose, imágenes publicadas en GHCR, infraestructura provisionada con
Terraform y despliegue automatizado con GitHub Actions disparado manualmente
(`workflow_dispatch`). No modifica lógica de negocio ni añade funcionalidad visible
al corredor; el único cambio en código de aplicación es `frontend/next.config.mjs`
en modo `output: 'standalone'`, necesario para que la imagen Docker del frontend no
incluya el árbol completo de `node_modules`.

**Ambigüedades resueltas:**

| Ambigüedad | Resolución |
|---|---|
| ¿Por qué GHCR y no S3 para las imágenes? | Ya razonado en `docs/DEPLOYMENT-STRATEGY.md` — pull incremental por capas, deduplicación, versionado nativo. No se reabre aquí. |
| ¿Por qué disparo manual (`workflow_dispatch`) y no `on: push`? | Proyecto académico (TFM) sin evolución continua prevista; ya razonado en `docs/DEPLOYMENT-STRATEGY.md`. |
| Orden Fase 1 / Fase 2 | Fase 2 (CI/CD) depende de que Fase 1 (contenerización + infra) esté completa — no se puede automatizar un despliegue con `docker compose pull` de imágenes que aún no existen en GHCR, ni aplicar Terraform desde un pipeline sin que `infra/*.tf` exista. |
| Autenticación AWS del pipeline: ¿OIDC o credenciales estáticas? | Se evaluó OIDC (token temporal, sin credencial de larga duración) y se descartó por complejidad frente al beneficio real para un proyecto de un solo desarrollador/repositorio — ver `docs/DEPLOYMENT-STRATEGY.md`, "Por qué credenciales IAM estáticas y no OIDC". Se usa un usuario IAM dedicado, acotado a recursos `runmarket-*`, con su access key en GitHub Secrets. |
| Bucket de estado remoto de Terraform | Es el único recurso de esta infraestructura que **no** gestiona Terraform (un backend no puede crear el sitio donde va a guardar su propio estado) — se crea a mano, una vez, fuera del pipeline. Documentado en TASK-08 y en `docs/DEPLOYMENT-RUNBOOK.md`. A partir de ahí, el pipeline sí puede hacer el primer `apply` de todo lo demás (EC2, IAM, Security Group...) sin ningún otro paso manual previo. |
| Visibilidad pública de los paquetes GHCR | Paso manual único la primera vez que se crea cada paquete (`runmarket-backend`, `runmarket-frontend`). No es automatizable por el job `deploy` (la API de GHCR no expone ese cambio de visibilidad al `GITHUB_TOKEN` por defecto). Se documenta como prerrequisito de TASK-12. |
| TLS/HTTPS | Fuera de alcance de esta US (extensión opcional en `docs/DEPLOYMENT-STRATEGY.md`, sección "Extensiones opcionales"). El despliegue de esta US sirve por HTTP; el aviso de seguridad sobre la cookie `Secure` y persistencia de sesión ya está documentado allí y no se "arregla" en esta US. |
| Verificación de tareas sin cuenta AWS disponible en este entorno | Todo lo verificable sin AWS real (sintaxis, `terraform validate`, `docker build`, `docker compose config`, lint de YAML) se ejecuta como parte de cada tarea. Lo que requiere una cuenta AWS real y credenciales (aplicar Terraform, desplegar por SSH, health-check contra una IP pública) se documenta como verificación manual pendiente de ejecución real, igual que TASK-10/11 de `US-000`. |

**Contrato técnico — estructura de ficheros y flujo de despliegue:**

```
├── frontend/next.config.mjs        ← output standalone
├── backend/Dockerfile              ← node:20-slim + openssl, no alpine
├── frontend/Dockerfile
├── nginx/nginx.conf
├── docker-compose.prod.yml         ← backend/frontend por image: (GHCR), no build: local
├── .dockerignore                   ← contexto de build = raíz del monorepo (workspaces npm)
├── .github/
│   └── workflows/
│       └── ci-cd.yml               ← job test + job deploy, ambos disparados solo por workflow_dispatch
└── infra/
    ├── main.tf / provider.tf (backend "s3", activo desde el principio) / variables.tf
    ├── security_groups.tf / iam.tf / s3.tf (artefactos) / ec2.tf / outputs.tf
    ├── artifacts.tf                ← data "archive_file" (provider archive): empaqueta y sube el zip a S3 en cada apply
    ├── terraform.tfvars.example
    ├── .gitignore
    └── scripts/
        ├── generar-zip.sh          ← solo docker-compose.prod.yml + nginx/ + redeploy.sh
        ├── user_data.sh.tpl        ← primer arranque: pull + up -d
        └── redeploy.sh             ← deploys posteriores: pull + up -d + migrate
```

> El bucket de estado remoto (`runmarket-terraform-state-<account-id>`) no es
> un fichero `.tf` — es el único recurso que vive fuera de Terraform, creado
> a mano una vez (ver TASK-08 y `docs/DEPLOYMENT-RUNBOOK.md`).

Flujo (ver diagrama completo en `docs/DEPLOYMENT-STRATEGY.md`): `workflow_dispatch`
→ job `test` (lint + tests + build) → job `deploy` (build+push GHCR → `terraform
apply` → SSH `redeploy.sh` → health-check `GET /api/health`).

**Criterios de aceptación (fuente de verdad):**

1. `backend/Dockerfile` y `frontend/Dockerfile` existen y `docker build` completa sin errores para ambos.
2. `docker-compose.prod.yml` referencia las imágenes de backend/frontend por `image:` (GHCR), nunca por `build:` local; solo `nginx` expone puertos al host.
3. `nginx/nginx.conf` enruta `/api` al backend y `/` al frontend.
4. Los ficheros `infra/*.tf` provisionan EC2 t3.micro, Security Group (22/80/443), bucket S3 de artefactos e IAM necesario; `terraform validate` pasa sin errores.
5. La autenticación AWS del pipeline usa un usuario IAM dedicado, con policy acotada a recursos `runmarket-*` (sin `AdministratorAccess`), documentado en `docs/DEPLOYMENT-RUNBOOK.md`.
6. Los scripts `generar-zip.sh`, `user_data.sh.tpl` y `redeploy.sh` existen e implementan pull + `up -d` + `prisma migrate deploy`.
7. `.github/workflows/ci-cd.yml` define los jobs `test` y `deploy`, disparados solo por `workflow_dispatch`; `deploy` termina con health-check contra `GET /api/health`.
8. Ejecutando el pipeline (o el flujo manual equivalente), la EC2 queda desplegada, `curl http://<ip>/api/health` responde `200` y el catálogo carga con los 13 productos.

### `US-018-TASK-01` — Dockerfile del backend

- [x] Implementado
- **Área:** Contenerización
- **Depende de:** —
- **Criterio de aceptación cubierto:** CA-1 (`backend/Dockerfile` existe, `docker build` sin errores)

**Descripción técnica**

Dockerfile multi-stage: stage `build` compila TypeScript (`tsc`) y genera el cliente
Prisma; stage `runtime` copia `dist/`, `node_modules` de producción y
`prisma/schema.prisma`, expone el puerto 4000 y arranca con `node dist/server.js`.
Base `node:20-slim` (Debian) con `apt-get install -y openssl` en **ambas** stages —
`node:20-alpine` falla con Prisma (`Error loading shared library libssl.so.1.1`,
musl no soporta el motor nativo) y Debian slim tampoco trae `libssl` por defecto.

**Criterios de hecho**

- `docker build -f backend/Dockerfile -t runmarket-backend:test .` completa sin errores.
- La imagen resultante arranca con `docker run -p 4000:4000 --env-file .env runmarket-backend:test` y responde `200` en `GET /api/health`.
- La imagen no contiene `devDependencies` de npm (verificable con `docker run runmarket-backend:test npm ls --omit=dev` sin errores de módulos faltantes en runtime).
- No se usa `node:20-alpine`.

**Verificación de infraestructura (obligatoria)**

> No aplica TDD clásico: no hay lógica de negocio que probar en rojo/verde. La
> verificación es el propio build y arranque del contenedor.

### `US-018-TASK-08` — Backend de estado de Terraform

- [x] Implementado
- **Área:** Terraform
- **Depende de:** US-018-TASK-06
- **Criterio de aceptación cubierto:** CA-4 (bucket de estado remoto privado y cifrado, parte de la infraestructura Terraform)

> **Enmienda (simplificación completa):** el diseño original creaba el bucket
> de estado y una tabla DynamoDB de locking como recursos Terraform
> (`infra/s3_backend.tf`), con el bloque `backend "s3"` comentado hasta un
> bootstrap que migraba el estado local al remoto. Se simplifica: el bucket
> se crea **a mano, fuera de Terraform** (con AWS CLI, ver
> `docs/DEPLOYMENT-RUNBOOK.md`) — un backend no puede crear el sitio donde va
> a guardar su propio estado, así que gestionarlo como recurso Terraform
> exige el mismo tipo de bootstrap en dos fases que ya se evitó al descartar
> OIDC. El bloque `backend "s3"` de `provider.tf` está **activo desde el
> principio** (no comentado), con `use_lockfile = true` (locking nativo de
> S3, Terraform ≥ 1.10) en vez de una tabla DynamoDB aparte. `infra/s3_backend.tf`
> se elimina; el output `terraform_state_bucket` también (el bucket ya no es
> un recurso Terraform, no hay nada que exponer como output).

**Descripción técnica**

El bucket de estado (`runmarket-terraform-state-<account-id>`, versionado,
cifrado SSE-S3, bloqueo de acceso público) se crea una vez con AWS CLI
(`aws s3api create-bucket` + `put-bucket-versioning` + `put-bucket-encryption`
+ `put-public-access-block`, documentado con los comandos exactos en
`docs/DEPLOYMENT-RUNBOOK.md`). Tras crearlo, se edita `infra/provider.tf`
sustituyendo `<ACCOUNT_ID>` por el valor real en el bloque `backend "s3"` —
un bloque `backend` no admite variables ni interpolación, así que esta
sustitución es manual y se commitea (el nombre del bucket no es secreto).
A partir de ahí, `terraform init` en cualquier entorno (portátil o el
runner del pipeline) usa ese backend sin pasos adicionales.

**Criterios de hecho**

- El bucket de estado tiene versionado activado.
- El bucket de estado tiene cifrado por defecto (SSE-S3).
- El bucket de estado bloquea acceso público.
- `infra/provider.tf` referencia el bucket real (no el placeholder `<ACCOUNT_ID>`) tras el setup de cuenta.
- `terraform init` (sin `-backend=false`) se conecta al bucket sin error una vez creado.

**Verificación de infraestructura (obligatoria)**

### `US-018-TASK-11` — Pipeline CI/CD — job `deploy`

- [x] Implementado
- **Área:** CI/CD
- **Depende de:** US-018-TASK-07, US-018-TASK-09, US-018-TASK-10
- **Criterio de aceptación cubierto:** CA-7 (build+push GHCR, `terraform apply`, SSH redeploy, health-check); CA-8 (despliegue real responde `200`)

> **Enmienda a TASK-06/07 (descubierta al cablear este job):** la EC2 no
> conoce su propia IP pública antes de crearse, y `user_data` necesita
> `CORS_ORIGIN`/`ASSETS_BASE_URL` en el primer arranque — un problema clásico
> de bootstrapping. Se resuelve asignando una **IP elástica** (`aws_eip.app`
> en `infra/ec2.tf`) antes de la instancia: su valor se conoce dentro del
> mismo `apply` (sin referencia circular) y de paso da una IP estable entre
> reemplazos de instancia, reforzando la idempotencia exigida más abajo.
> `var.cors_origin` pasa a ser opcional (`default = ""`); si se deja vacío,
> `local.cors_origin` en `ec2.tf` usa automáticamente `http://<ip-elástica>`.
> `outputs.tf` (`app_url`, `instance_public_ip`) y la policy IAM (entonces en
> `infra/oidc.tf`, ver enmienda siguiente) se actualizaron en consecuencia.
> `var.key_name` también recibió un valor por defecto
> (`"runmarket-deploy-key"`, no es secreto) para no requerir una variable de
> GitHub adicional fuera de las ya documentadas.

> **Segunda enmienda (simplificación completa):** autenticación OIDC
> sustituida por credenciales IAM estáticas (ver TASK-10). Se añade además
> un `concurrency` group a nivel de workflow (`group: runmarket-deploy`) para
> serializar ejecuciones de `deploy` — sustituye a la tabla DynamoDB de
> locking que tenía el diseño original (TASK-08), suficiente para un único
> pipeline manual sin necesidad de coordinar con applies concurrentes desde
> fuera de GitHub Actions.

**Descripción técnica**

Job `deploy` de `.github/workflows/ci-cd.yml`, `needs: test`: autenticación AWS
con credenciales estáticas (`aws-actions/configure-aws-credentials` con
`aws-access-key-id`/`aws-secret-access-key` desde `secrets.AWS_ACCESS_KEY_ID`/
`secrets.AWS_SECRET_ACCESS_KEY` — el usuario IAM de TASK-10), login en GHCR
con `GITHUB_TOKEN`, `docker/build-push-action`
para backend y frontend (tag `:latest` + tag por SHA de commit — usando los
valores por defecto de `NEXT_PUBLIC_API_URL`/`ASSETS_BASE_URL` del Dockerfile
del frontend, rutas relativas `/api`/`/images` servidas por nginx en el mismo
origen, sin necesitar conocer la IP pública en build-time), `terraform apply

**Criterios de hecho**

- El health-check reintenta durante una ventana razonable (la EC2 tarda unos segundos en levantar los contenedores tras el `redeploy.sh`) antes de fallar el job.
