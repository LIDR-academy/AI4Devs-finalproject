## US refinada

**Historia de usuario:**
Como corredor, quiero que el stock de un producto se reduzca según la cantidad comprada al confirmar mi pedido, para que el catálogo y la ficha de producto reflejen la disponibilidad real tras cada compra.

**Contexto técnico:**

`OrderRepository.createOrderFromCart` (`backend/src/repositories/order.repository.ts`) ya re-valida el stock dentro de la transacción Prisma que crea el pedido — por cada ítem del carrito, lee el `Product` y lanza `StockError(product.stock)` si `item.quantity > product.stock`. Pero esa validación es de solo lectura: nunca escribe el descuento de vuelta. El resultado es que el stock mostrado en catálogo (`GET /api/products`) y ficha (`GET /api/products/:id`) no cambia jamás tras una compra, y la propia re-validación de stock pierde sentido con el tiempo (nunca puede fallar en condiciones normales, porque el stock nunca baja).

**Riesgo de concurrencia a resolver (no presente en el código actual, pero introducido por esta US si se implementa mal):** sustituir la validación de solo lectura por un `findUnique` + `update` secuencial reintroduciría una carrera — dos confirmaciones simultáneas sobre el mismo producto podrían leer el mismo `stock` antes de que ninguna de las dos escriba, y ambas pasarían la validación. La forma correcta es una **actualización condicional atómica**: `tx.product.updateMany({ where: { id, stock: { gte: cantidad } }, data: { stock: { decrement: cantidad } } })`. Si `result.count === 0`, el descuento no se aplicó (no había stock suficiente en el momento de la escritura) y se lanza `StockError`. Esto es atómico a nivel de fila en PostgreSQL — no requiere bajar el nivel de aislamiento de la transacción.

**Orden de operaciones por ítem (dentro de la transacción existente, sustituye el bloque actual de validación):**
1. `tx.product.findUnique({ where: { id: item.productId } })` — existencia + snapshot de `name`/`brand`/`price` (igual que hoy).
2. Si no existe → `NotFoundError` (igual que hoy).
3. **Nuevo:** `tx.product.updateMany({ where: { id: product.id, stock: { gte: item.quantity } }, data: { stock: { decrement: item.quantity } } })`.
4. Si `result.count === 0` → `StockError(product.stock)` (el `stock` leído en el paso 1 es solo para el mensaje de error; la decisión real la toma la actualización condicional atómica del paso 3, no esta lectura).
5. Continuar construyendo `orderItemsData` con el snapshot de precio, igual que hoy.

Si cualquier ítem falla en el paso 4, la función lanza y la transacción Prisma revierte — los descuentos ya aplicados a ítems anteriores del mismo pedido se revierten automáticamente (atomicidad de transacción, ya garantizada por el código existente, no requiere cambio adicional).

**Impacto en la suite E2E de US-014:** `e2e/tests/purchase.spec.ts` completa una compra real contra el sistema vivo en cada ejecución de su test principal. Hoy es inocuo porque el stock nunca baja; en cuanto esta US se implemente, **cada ejecución consumirá una unidad real de stock** del producto que compre. Añadir un `beforeAll` que reseedee la base de datos desde el propio spec violaría la *black-box rule* de `.claude/skills/e2e-playwright/SKILL.md` ("nunca seedear la base de datos directamente... ni manipular estado por un canal lateral"), así que la solución no es tocar el spec, sino **documentar la consecuencia operativa** en `docs/E2E-TESTING.md` (ya existe, creado en US-014): cada ejecución de `purchase.spec.ts` reduce en 1 el stock real de un producto del seed, y reseedear periódicamente (`npx prisma db seed`, ya idempotente) es mantenimiento de entorno esperado — mismo espíritu que la nota ya existente sobre pedidos que no se limpian.

**Criterios de aceptación cubiertos:**

1. Al confirmar un pedido con N unidades de un producto, el stock se reduce en N unidades, en la misma transacción que crea el pedido.
2. El descuento se aplica a todos los ítems del pedido, no solo al primero.
3. Dos confirmaciones simultáneas sobre el mismo producto no dejan el stock en negativo (actualización condicional atómica, no lectura-luego-escritura).
4. Tras la compra, `GET /api/products/:id` y el catálogo reflejan el nuevo stock sin reiniciar el servidor (consecuencia directa de escribir en la misma fila que se lee en esos endpoints; no requiere cambio en los endpoints de lectura).
5. Si la validación de stock falla, no se descuenta nada y la transacción se revierte por completo.
6. **Añadido en refinamiento:** la consecuencia de esta US sobre `purchase.spec.ts` (consumo real de stock por ejecución) queda documentada en `docs/E2E-TESTING.md`, no resuelta dentro del propio spec.

### `US-015-TASK-01` — Descuento atómico de stock en `createOrderFromCart`

- [x] Implementado
- **Capa:** Backend
- **Depende de:** —
- **Criterio de aceptación cubierto:** 1, 2, 3, 4, 5 (ver "US refinada")

**Descripción técnica**

Modificar `backend/src/repositories/order.repository.ts`, dentro del bucle `for (const item of cart.items)` de `createOrderFromCart`. Sustituir:

```typescript
if (item.quantity > product.stock) {
  throw new StockError(product.stock);
}
```

por una actualización condicional atómica:

```typescript
const result = await tx.product.updateMany({
  where: { id: product.id, stock: { gte: item.quantity } },
  data: { stock: { decrement: item.quantity } },
});

if (result.count === 0) {
  throw new StockError(product.stock);
}
```

`product.stock` (leído en el `findUnique` previo, sin cambios) se usa únicamente como valor informativo del error — la decisión de si hay stock suficiente la toma la cláusula `where` de `updateMany`, evaluada atómicamente por PostgreSQL en el momento de la escritura, no por la lectura anterior. Esto es lo que hace segura la operación frente a confirmaciones concurrentes sobre el mismo producto.

No se modifica la interfaz `IOrderRepository` ni el contrato de `OrderResponse` — el cambio es interno al repositorio.

Ampliar `backend/src/repositories/order.repository.test.ts`.

**Criterios de hecho**

- `tx.product.updateMany` se llama con `where: { id, stock: { gte: cantidad } }` y `data: { stock: { decrement: cantidad } } }` por cada ítem del carrito.
- Cuando `updateMany` devuelve `count: 0`, se lanza `StockError` con el stock leído del `findUnique` previo.
- Cuando todos los ítems tienen stock suficiente, el pedido se crea igual que hoy (sin cambios en `OrderResponse`).
- Si el segundo ítem de un pedido de 2 ítems falla la actualización de stock, no se asume nada sobre el primer ítem en el test (la reversión la garantiza `$transaction`, ya cubierto por el mock existente de la suite — no se re-prueba el rollback de Prisma en sí, solo que la función lanza y no continúa).
- Cumple las reglas de seguridad aplicables de `CLAUDE.md` (precio y stock nunca se confían del cliente; ya garantizado por el código existente, sin cambios en ese aspecto).
