# [C10] T-C10-26 · `TokenIssuerPort` and the `@nestjs/jwt` adapter

## Context

`US-C10-01` requires a signed JWT access token whose claims carry the user identifier, the display name, the assigned role identifiers and an expiry. JWT is a framework concern, so the application layer depends on a port and the signing lives in an infrastructure adapter, consistent with `T-C10-20`.

## Scope

- `TokenIssuerPort` in `libs/identity-access/domain`: issue a token for a resolved identity and a session, and verify/decode a presented token into its claims.
- `JwtTokenIssuer` in `libs/identity-access/infrastructure` over `@nestjs/jwt`, with signing secret/key, algorithm and TTL read through `ConfigService` and validated at boot.
- Claim set: subject (user id), session id, display name, role identifiers, issued-at, expiry. No credential, no hash, no permission list — permissions are resolved per request (`T-C10-39`).
- Jest tests: round-trip issue and verify, expired token rejected, tampered signature rejected.
- Out of scope: the guard that consumes it (`T-C10-28`), refresh tokens, which no `C10` story requires.

## Acceptance criteria

**Given** a resolved identity and an active session **When** a token is issued **Then** its decoded claims carry the user identifier, session identifier, display name, role identifiers and an expiry, and nothing else.

**Given** a token whose expiry has passed **When** it is verified **Then** verification fails with a typed error distinguishable from a signature failure.

**Given** a token whose payload has been altered **When** it is verified **Then** verification fails.

**Given** the signing configuration absent **When** the application boots **Then** it fails fast rather than signing with a default or empty secret.

**Given** the `identity-access/application` library **When** it is grepped for `@nestjs/jwt` **Then** there is no match; only the infrastructure adapter imports it.
