# [C10] T-C10-17 · Base migration chain and the bootstrap migration

## Context

Foundation work with no user story behind it. Source: `docs/backlog/epic-map.md` → **Foundation ownership (priced once)**, row *PostgreSQL base schema + the TypeORM migration chain*, priced in `C10` citing `CLAUDE.md` §2 and §3; and finding **F14** of `user-stories.md`.

Every later epic adds migrations to this chain, so the first link must be reversible and the convention must be fixed here. `docs/product/DATA-MODEL.md` is the prescriptive schema the first migrations must produce.

## Scope

- Migration directory, naming convention (`<timestamp>-<PascalCaseName>.ts`) and registration in the data source.
- Bootstrap migration creating the per-context schema namespaces of `docs/product/DATA-MODEL.md`, starting with the `identity_access` schema, plus the shared extensions the model requires.
- A documented `up`/`down` rule: every migration in this repository is reversible, and `down` is verified before merge.
- A short convention note in the migrations directory recording the rule, so later epics inherit it.
- Out of scope: every table. `user`, `session`, `role`, `permission`, `user_role` and the scope grants are created by their own tickets (`T-C10-21`, `T-C10-24`, `T-C10-36`, `T-C10-44`).

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** an empty database **When** `pnpm typeorm migration:run -d apps/api/src/data-source.ts` runs **Then** it applies the bootstrap migration and reports success.

**Given** the applied migration **When** `pnpm typeorm migration:revert -d apps/api/src/data-source.ts` runs **Then** the database returns to its previous state with no residual schema object.

**Given** the run-then-revert-then-run sequence **When** it is executed twice in a row **Then** the outcome is identical both times.

**Given** the migration file **When** it is inspected **Then** it contains explicit SQL or query-builder statements and no reliance on `synchronize`.
