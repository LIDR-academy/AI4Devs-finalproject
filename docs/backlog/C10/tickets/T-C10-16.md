# [C10] T-C10-16 · The TypeORM data source and its database connection configuration

## Context

Foundation work with no user story behind it. Source: `docs/backlog/epic-map.md` → **Foundation ownership (priced once)**, row *PostgreSQL base schema + the TypeORM migration chain (`synchronize: false`, migrations only)*, priced in `C10` citing `CLAUDE.md` §2 and §3; and finding **F14** of `user-stories.md`.

Split from `T-C10-17` so that the connection and the migration chain can be reviewed separately: this ticket makes the database reachable from application code, the next one makes the schema reproducible.

**Provisioning is already done and out of scope.** `docker/` (root-level, maintained by `ci-cd-expert`) now carries a working `postgres` service in `docker/docker-compose.dev.yml`: image pinned to `postgres:18.6`, named volume `postgres-data`, credentials sourced from the environment, `pg_isready` healthcheck — built, run and verified (`postgres:18.6` confirmed reporting "PostgreSQL 18.6"). This ticket does not touch `docker/`; it wires `apps/api` to reach that already-running server. This is a re-scope of the original ticket, which assumed a bare `docker-compose.yml` at the repository root — that file was never created, and the equivalent service lives under `docker/` instead.

**Boot-path constraint, carried forward for whoever implements this and `T-C10-17`.** `docker/backend/docker-entrypoint.sh` deliberately runs no migration step today — its own comment says the step "lands with T-C10-16 ... and T-C10-17". Whatever either ticket adds to the boot path must keep migration execution a controlled, separate deploy step, never folded unconditionally into the container's boot/entrypoint (`CLAUDE.md` §3). This is already the letter of the acceptance criteria below; it is restated here because it is the easiest rule to break by convenience once a real database is reachable.

**The deployable half is a separate ticket, not this one.** ADR-013 (`ARCHITECTURE.md` §10) puts `typeorm migration:run` on Render's pre-deploy command, which runs *inside* the deployed image — but `docker/backend/Dockerfile` copies only the webpack bundle (`main.js`), never `apps/api/src/data-source.ts` or a migration file, and ships no `ts-node`/`typescript` to run either as `.ts`. Making that legal is `T-C10-69` (`ci-cd-expert`, `docker/**` + a new `apps/api` build target): it consumes the file this ticket produces and does not change this ticket's scope, estimate or acceptance criteria.

## Scope

- The `postgres` service itself is **out of scope** — it already exists in `docker/docker-compose.dev.yml` (pinned image, named volume, environment-sourced credentials, healthcheck), owned by `ci-cd-expert`.
- TypeORM 1.1 data source at `apps/api/src/data-source.ts` on the `pg` driver, connection values resolved through `ConfigService` only.
- Database connection variables (host, port, user, password, database name — naming mirrors the `POSTGRES_*` keys already set on the `postgres` service in `docker/docker-compose.dev.yml`) added to the validated schema in `apps/api/src/config/env.validation.ts`, alongside the existing `NODE_ENV`/`PORT` keys, and mirrored in `.env.example` — same fail-fast pattern: mandatory, no in-code default, boot aborts naming the missing key.
- `synchronize: false`, `migrationsRun: false`; migration auto-run gated to development and never unconditional (`CLAUDE.md` §3).
- The four `pnpm typeorm` scripts of `CLAUDE.md` §3: `migration:generate`, `migration:run`, `migration:revert`, plus `migration:show`.
- Out of scope: any migration file (`T-C10-17`), any entity (`T-C10-21` onward), any change to `docker/**`.

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** `docker compose -f docker/docker-compose.dev.yml up -d postgres` **When** it completes **Then** a PostgreSQL 18 server accepts connections on the configured port.

**Given** the `postgres` service definition in `docker/docker-compose.dev.yml` **When** the `image` line is inspected **Then** it reads `postgres:18.6` — an explicit `major.minor.patch` tag, never `latest` or a bare major.

**Given** the data source **When** `pnpm typeorm migration:show -d apps/api/src/data-source.ts` runs **Then** it connects and reports an empty migration list without error.

**Given** the data source configuration **When** it is inspected **Then** `synchronize` is `false` and no code path sets it to `true` in any environment.

**Given** the API boot sequence in a staging or production configuration **When** it starts **Then** it runs no migration automatically, and `docker/backend/docker-entrypoint.sh` gains no unconditional migration step.

**Given** one of the new database connection variables removed from the environment **When** the application boots **Then** it fails fast with a message naming the missing key, the same way a missing `NODE_ENV` or `PORT` does today.

**Given** the data-source file and `apps/api/src/config/env.validation.ts` **When** they are grepped for `process.env` **Then** the only occurrences are inside the configuration module itself.
