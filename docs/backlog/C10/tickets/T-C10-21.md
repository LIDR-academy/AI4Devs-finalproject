# [C10] T-C10-21 · `UserRepositoryPort`, the TypeORM user entity, mapper and migration

## Context

`US-C10-01` requires stored credentials to exist only as a bcrypt hash. Persisting the `User` aggregate from `T-C10-19` needs an outbound port in the domain and a TypeORM adapter in infrastructure, kept apart per ADR-005 so the schema never dictates the model.

Greenfield: the `identity_access` schema namespace exists from `T-C10-17`, but no table does.

## Scope

- `UserRepositoryPort` in `libs/identity-access/domain`: find by identifier, find by id, save.
- TypeORM `UserEntity` in `libs/identity-access/infrastructure` plus an explicit mapper both ways; no decorator ever enters the domain.
- `TypeOrmUserRepository` implementing the port, bound to its token in the composition root.
- Migration creating `identity_access.user`: id, identifier (unique, case-insensitive), display name, password hash, status, created/updated timestamps.
- Integration test against a real PostgreSQL instance covering save, find by identifier, and uniqueness rejection.
- Out of scope: roles and the join table (`T-C10-36`), sessions (`T-C10-24`).

## Acceptance criteria

**Given** `libs/identity-access/domain` **When** it is grepped for `typeorm` **Then** there is no match; the entity and its decorators live only in `infrastructure`.

**Given** the migration **When** it runs and is then reverted **Then** `identity_access.user` is created and removed cleanly, and the sequence is repeatable.

**Given** two users with identifiers differing only in letter case **When** the second is saved **Then** the database rejects it on the unique constraint.

**Given** a stored user **When** the row is read directly from the database **Then** the password column holds a bcrypt hash and no reversible representation of the credential.

**Given** the repository **When** it returns a `User` **Then** the caller receives the domain aggregate, never the TypeORM entity.
