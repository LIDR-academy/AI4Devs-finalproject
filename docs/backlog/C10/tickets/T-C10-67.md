# [C10] T-C10-67 · Typed identity-provider-unreachable error

## Context

`US-C10-10` requires an unreachable SCMS identity provider to surface as a typed error with an actionable message, logged through pino, and states it must **never** be reported as invalid credentials. The typed failure already exists from `T-C10-20`; this ticket makes the SSO adapter raise it correctly and the API surface it correctly.

Phase: `unphased` (`FR-IAM-04`, finding **F9**).

## Scope

- Timeout and connection-failure handling in the SSO adapter, mapped to `IdentityProviderUnavailable` and never to `InvalidCredential`.
- A bounded timeout read from validated configuration, so a hanging provider cannot hold a request open indefinitely.
- Exception-filter mapping to `503` with a distinct machine-readable error code, and a client message that tells the user to retry rather than to check their password.
- Structured pino log at error level with the correlation identifier and the provider endpoint, and no credential material.
- Jest unit tests with a stubbed failing client; an API-E2E scenario with the provider stub unreachable.
- Out of scope: retry or circuit-breaking, which no `C10` story requires.

## Acceptance criteria

**Given** the SCMS identity provider is unreachable **When** a sign-in is attempted **Then** the failure surfaces as `IdentityProviderUnavailable` and never as the invalid-credential failure.

**Given** that failure **When** it reaches the API **Then** the response is `503` with a distinct error code and an actionable message.

**Given** a provider that does not respond **When** the configured timeout elapses **Then** the request fails with the same typed error rather than hanging.

**Given** the failure **When** the logs are inspected **Then** there is one structured pino error entry carrying the correlation identifier and no credential material.
