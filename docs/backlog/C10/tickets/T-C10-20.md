# [C10] T-C10-20 · `IdentityProviderPort` and the domain identity result

## Context

`US-C10-09` requires authentication to be resolved through a port so that adding SCMS SSO later is an adapter swap in the composition root, not a redesign. `ARCHITECTURE.md` §9 places `IdentityProviderPort` in `identity-access/domain` with a local-credential adapter now and an SSO adapter later.

The story traces both `FR-IAM-04` (unphased, finding **F9**) and `FR-IAM-01` (phase 0). The port itself is a precondition of `FR-IAM-01` authentication, so it is scheduled with phase 0; only the SSO adapter half (`US-C10-10`, block H) stays unphased.

## Scope

- `IdentityProviderPort` interface in `libs/identity-access/domain`: one verification operation taking a credential presentation and returning a resolved domain identity or a typed failure.
- The result type expressed in domain vocabulary: resolved identity, display name, profile attributes as a plain map. No hash, no request object, no driver type.
- Typed failures: `InvalidCredential`, `AccountInactive`, `IdentityProviderUnavailable`.
- An injection-token constant for the port, exported from the domain barrel so the composition root can bind against it.
- Out of scope: every adapter (`T-C10-22` local, `T-C10-64` SSO), the binding itself (`T-C10-23`), the use case (`T-C10-25`).

## Acceptance criteria

**Given** `libs/identity-access/domain` **When** it is inspected **Then** it declares `IdentityProviderPort` with no framework, HTTP or ORM import anywhere in the library.

**Given** the port signature **When** it is read **Then** no parameter and no return field carries a provider-specific name, claim shape or driver type.

**Given** the three typed failures **When** they are inspected **Then** `IdentityProviderUnavailable` is distinct from `InvalidCredential`, so an outage can never be reported as a bad password.

**Given** the injection token **When** the composition root binds it **Then** it is imported from the domain barrel, not redeclared.
