# [C10] T-C10-69 · Compile the data source and migrations into the deployable API image

## Context

Foundation work with no user story behind it. Source: `docs/product/ARCHITECTURE.md` §10, **ADR-013**, consequence 3 — deployment runs `typeorm migration:run` as Render's pre-deploy command, which executes **inside** the deployed image, and the ADR itself hands the open question to `ci-cd-expert`: *"the production API image contains only `dist/apps/api` plus the dependencies its generated `package.json` declares, so the TypeORM CLI and the compiled data source must be reachable from inside the running image for `migration:run` to be a legal pre-deploy command."* Also traces to the same **Foundation ownership (priced once)** row in `docs/backlog/epic-map.md` that prices "PostgreSQL base schema + the TypeORM migration chain" into `C10` (the same source `T-C10-16` and `T-C10-17` cite).

`docker/backend/Dockerfile` copies only `dist/apps/api` — webpack's single `main.js` bundle plus the `package.json` its `generatePackageJson: true` writes — and runs `pnpm install --prod` against it. `main.js` is one bundle; it is not something `migration:run -d <path>` can target, and the image ships no `ts-node`/`typescript` (both are root `devDependencies`, excluded by `pnpm install --prod`), so the migrations `T-C10-17` writes as `.ts` cannot run there as `.ts`. `docker/backend/Dockerfile` (a "NOT YET DONE" comment naming this exact gap) and `docker/backend/docker-entrypoint.sh` (a comment naming `T-C10-16`/`T-C10-17` as the still-missing prerequisites) each already mark the spot; both comments go stale the moment this ticket lands, and retiring them is part of this ticket.

**Not a blocker today.** Nothing deploys yet: `.github/workflows/deploy-stage.yml`'s own header comment states it deliberately runs no `typeorm migration:*` command, and no Render service is configured (ADR-013: no `render.yaml`, dashboard-configured by hand). This ticket has no forward dependency on anything outside `C10` — it only has to land before the first real deploy attempts a pre-deploy migration.

**Depends on `T-C10-16` and `T-C10-17`.** Both must exist first — the data source and at least the bootstrap migration — for there to be anything to compile and verify against. `T-C10-17` also fixes the extension-agnostic migration-glob convention (`migrations/*.{js,ts}`) this ticket relies on so the same registration resolves correctly whether it runs as local `.ts` (`ts-node`) or as the `.js` this ticket compiles.

**Why one ticket, not two.** The compiled build target and the `Dockerfile` `COPY` cannot be independently verified — the only acceptance proof available ("`migration:run` succeeds inside the built image") requires both halves together. Splitting them would not yield two independently reviewable units; it would only serialize one behind the other while duplicating the same build-and-run verification step.

**Ownership boundary.** This ticket edits `apps/api/project.json` (a build **target**, not application code — the same class of edit `T-C10-68` already made under `ci-cd-expert`), `docker/backend/**`, and the root `package.json`'s scripts. It does not touch `apps/api/src/data-source.ts` or any migration file — those stay `backend-engineer`'s (`T-C10-16`, `T-C10-17`); this ticket only compiles and packages what they produce.

## Scope

- A new Nx target on `apps/api` (`project.json`) that compiles `apps/api/src/data-source.ts` and the migrations directory `T-C10-17` creates to plain CommonJS `.js`, independent of `apps/api/webpack.config.js`'s bundle (a dedicated `tsc` invocation against a narrow `tsconfig`, or an equivalent non-bundling build — not the NxAppWebpackPlugin path `main.js` uses).
- Output placed so it survives the pipeline's existing `Upload production build output` step (`.github/workflows/deploy-stage.yml` archives `dist` wholesale already) and lands inside the Docker build context without a second artifact hand-off.
- The `docker/backend/Dockerfile` `COPY` for the compiled artifact, replacing the "NOT YET DONE" comment placeholder with the real line(s).
- A root `package.json` script that runs `migration:run` against the **compiled** artifact with the plain `typeorm` CLI — no `ts-node`, no `TS_NODE_PROJECT` (e.g. `typeorm migration:run -d dist/apps/api/data-source.js`). This is the exact command Render's pre-deploy field needs; document it verbatim in a comment next to the script so whoever configures the Render dashboard (ADR-013: no `render.yaml`, hand-configured) has it ready to paste. Updating `readme.md` §2.4 with that string is out of this ticket's scope (owned elsewhere) — report it as a follow-up instead.
- Retire the stale placeholder comments in `docker/backend/Dockerfile` and `docker/backend/docker-entrypoint.sh` that currently narrate this gap and name `T-C10-16`/`T-C10-17` as pending.
- End-to-end verification: build the image, run the new script inside a container from that image against a real PostgreSQL instance, confirm the bootstrap migration applies and the process exits `0`.
- Out of scope: configuring the Render dashboard itself, or adding `render.yaml` (ADR-013 rules both out). Any change to `.github/workflows/deploy-stage.yml` — it deliberately runs no `typeorm migration:*` command until Render is configured by hand, per its own header comment, and adding one here would be inventing a gate this repository cannot yet pass. Any entity or migration file (`T-C10-16`, `T-C10-17`, and every context ticket from `T-C10-21` onward). Any change to `apps/api/src/data-source.ts` beyond what `T-C10-16`/`T-C10-17` already produce — this ticket compiles that file, it does not rewrite it.

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** `pnpm nx build api --configuration=production` plus this ticket's new target **When** `dist/apps/api` is inspected **Then** it contains a compiled, plain-CommonJS `data-source.js` and a `migrations/` directory of compiled `.js` files, produced independently of `main.js`.

**Given** the compiled `data-source.js` **When** it is required by plain `node` in an environment with no `ts-node` and no `typescript` installed **Then** it loads without a module-resolution error.

**Given** the production image built from `docker/backend/Dockerfile` **When** its filesystem is inspected **Then** it contains the compiled data source and migrations at the path the new `pnpm` script targets.

**Given** the built image and a reachable PostgreSQL instance **When** the new `pnpm` script (or the equivalent raw `typeorm migration:run -d <compiled path>` invocation) runs inside a container started from that image **Then** it applies the bootstrap migration from `T-C10-17` and exits `0`.

**Given** `docker/backend/Dockerfile` and `docker/backend/docker-entrypoint.sh` **When** they are reread after this ticket **Then** neither still narrates the compiled-artifact gap as pending — the `Dockerfile` comment is replaced by the real `COPY` line, and the `entrypoint.sh` comment no longer names `T-C10-16`/`T-C10-17` as missing prerequisites.

**Given** `docker/backend/docker-entrypoint.sh` **When** it is inspected after this ticket **Then** it still runs no migration step — this ticket makes `migration:run` reachable as a separate, explicit command; it does not add it to the container's boot path (`CLAUDE.md` §3, ADR-013).

Not applicable — no test code is written for this ticket. Verification is `docker build`/`docker run` output and a manual re-read of the updated `Dockerfile` and `docker-entrypoint.sh`.
