# [C10] T-C10-48 · Role-assignment contract and validated API adapter

## Context

`US-C10-11` requires the assignment request body to be validated by a `class-validator` DTO defined against `libs/shared/contracts`, and states that an unvalidated or `any`-typed body is never accepted. `CLAUDE.md` §3 and ADR-007 fix where each half lives.

## Scope

- `AssignRoleRequest` and the user-profile response types in `libs/shared/contracts` (types only).
- A decorated `class-validator` DTO in `apps/api` structurally implementing the contract type.
- Thin controller delegating to `AssignRoleToUser`; `403` on denial through the filter of `T-C10-40`, `404` on unknown user or role, `200`/`204` on success including the idempotent repeat.
- A user-profile read endpoint returning the current role assignments, so the screen can show the change immediately.
- API-E2E scenarios for the allowed path, the denied path and the repeat.
- Out of scope: the screen (`T-C10-50`), revocation (`T-C10-52`).

## Acceptance criteria

**Given** an administrator **When** a valid assignment request is submitted **Then** it succeeds and the user-profile read reflects the new role on the next call.

**Given** a body with a missing, extra or wrongly typed field **When** it is submitted **Then** it is rejected with `400` by the global `ValidationPipe` before the use case is reached.

**Given** a non-administrator **When** the same request is submitted **Then** the response is `403` and no assignment exists afterwards.

**Given** the API source **When** the DTO is inspected **Then** it carries `class-validator` decorators and structurally implements the contract type, and the contract library itself carries no decorator.
