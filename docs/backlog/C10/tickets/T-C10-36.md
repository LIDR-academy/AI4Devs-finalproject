# [C10] T-C10-36 · Role and permission persistence and the eight-role seed migration

## Context

`US-C10-04` requires that after the baseline migration has run against a freshly migrated database, exactly the eight roles of PRD §4.3 exist, each with a stable identifier; and that any later schema change to roles or permissions is delivered as a migration with `synchronize` still `false`.

## Scope

- TypeORM entities, mappers and repositories for `role`, `permission` (or a role-permission projection) and the `user_role` join, in `libs/identity-access/infrastructure`.
- `RoleRepositoryPort` and `UserRoleRepositoryPort` declared in the domain and implemented here.
- Migration creating `identity_access.role`, `identity_access.role_permission` and `identity_access.user_role` with the appropriate keys and a unique constraint on the user-role pair, so a duplicate assignment is impossible at the database level (`US-C10-11` idempotence).
- Seed migration inserting the eight roles and their permission sets from `T-C10-35`, idempotent on re-run.
- Integration tests against real PostgreSQL.
- Out of scope: assignment and revocation use cases (block E).

## Acceptance criteria

**Given** a freshly migrated database **When** the migration chain has run **Then** exactly eight rows exist in `identity_access.role`, with the identifiers of PRD §4.3.

**Given** the seeded catalog **When** each role permission set is read from the database **Then** it matches the domain catalog of `T-C10-35` exactly.

**Given** the seed migration **When** it is run a second time **Then** it does not duplicate a role and does not fail.

**Given** the same user and role pair inserted twice **When** the second insert executes **Then** the database rejects it on the unique constraint.

**Given** the whole chain **When** it is reverted **Then** the three tables are removed cleanly and the revert is repeatable.
