# [C10] T-C10-49 · `identity-access/data-access` — users and roles store

## Context

`US-C10-11` requires the assignment to be visible on the user profile **immediately**. That needs a client store that reflects the server outcome rather than an optimistic guess, so the screen of `T-C10-50` can render the truth.

## Scope

- Signal-based store in `libs/identity-access/data-access`: user list, selected user, role catalog, and explicit loading and error signals for each.
- `HttpClient` calls against the contracts of `T-C10-48` and `T-C10-52`; no hand-written URL string duplicated across methods.
- Assignment and revocation refresh the affected user from the server; errors surface as an error state and are never swallowed.
- No `NgRx`; the store is signals plus a service (`CLAUDE.md` §3).
- Jest tests with a mocked `HttpClient` covering success, failure and the refresh.
- Out of scope: the screen, any presentational component.

## Acceptance criteria

**Given** a successful assignment **When** the store completes the call **Then** the affected user is refreshed from the server and the derived role list reflects the new assignment.

**Given** a failing call **When** it completes **Then** the error signal is set, the loading signal is cleared, and the error is not swallowed.

**Given** the store **When** it is inspected **Then** every remote collection exposes an explicit loading state and an explicit error state.

**Given** the library **When** it is inspected **Then** it contains no component and no NgRx import, and it depends only on `type:contracts` and `type:util` per the boundary matrix.
