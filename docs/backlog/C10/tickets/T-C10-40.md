# [C10] T-C10-40 · Map `AuthorizationError` to `403` in the API exception filter

## Context

`US-C10-05` requires that when an actor lacks the permission, the use case raises a **typed authorization error** that the HTTP adapter maps to `403`, with no side effect and no state change. The typed error exists from `T-C10-38`; this ticket is the adapter half, kept separate because it is a `apps/api` concern with a distinct reviewer.

## Scope

- Global exception filter in `apps/api` mapping `AuthorizationError` to `403` with the `FORBIDDEN` error code and the standard error envelope from `T-C10-11`.
- The response body carries the machine-readable code and a localized message; it does **not** leak the denial reason detail or the permission name to the caller.
- Mapping for the other typed domain errors this epic raises, so no domain error escapes as a `500`.
- Unit tests for the filter and an API-E2E scenario for a denied privileged call.
- Out of scope: recording the denial (`T-C10-62`, blocked), the step-up outcome, which is a distinct code (`T-C10-60`).

## Acceptance criteria

**Given** a use case that raises `AuthorizationError` **When** the request completes **Then** the response is `403` with the `FORBIDDEN` error code in the standard envelope.

**Given** that denied request **When** the system state is inspected afterwards **Then** nothing was persisted and no domain event was emitted.

**Given** the `403` response body **When** it is read by the caller **Then** it contains no permission name and no internal denial detail.

**Given** any typed domain error raised by this epic **When** it reaches the filter **Then** it maps to an explicit status and error code, and never to an unhandled `500`.
