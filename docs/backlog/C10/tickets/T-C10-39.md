# [C10] T-C10-39 · `Actor` assembly with per-request server-side permission resolution

## Context

`US-C10-05` requires the identical predicate to decide an operation no matter which inbound path reaches it, which means the use case must receive a fully resolved `Actor`. `US-C10-12` additionally requires that a revoked role stops granting access **at once**, because permissions are resolved server-side per request rather than trusted from the token claims alone.

Those are one mechanism, so it is built once, here, rather than twice — first trusting claims in block B and then rewritten in block E. This is the one deliberate departure from the story-block order, and it is why `FR-IAM-05` appears in this ticket alongside `FR-IAM-02`.

## Scope

- An `ActorResolver` in `apps/api` that, on every authenticated request, loads the current role assignments and their permission sets from the repositories of `T-C10-36` and builds the `Actor` of `T-C10-38`.
- The token claim role list is treated as advisory only and never as the authorization source.
- A per-request cache scoped to the request lifetime, so one request performs one resolution; no cross-request caching, which would reintroduce staleness.
- Every use case in this epic takes the `Actor` as an explicit parameter; no use case reads ambient request state.
- Jest unit tests for the resolver plus an API-E2E scenario proving a role revoked mid-session takes effect on the next request.
- Out of scope: the revocation use case itself (`T-C10-51`).

## Acceptance criteria

**Given** an authenticated request **When** the actor is assembled **Then** its permission set is read from the database, not from the token claims.

**Given** a role revoked while a token is still valid **When** the next request is made with that same token **Then** the assembled actor no longer carries the revoked permissions.

**Given** one request **When** it executes **Then** permissions are resolved once for that request and reused within it.

**Given** two different inbound paths to the same operation **When** each is invoked **Then** both pass an `Actor` built by the same resolver and the same predicate decides both.

**Given** the application layer **When** it is inspected **Then** no use case reads a request, a header or a token; each receives the `Actor` as a parameter.
