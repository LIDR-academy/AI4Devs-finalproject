# [C10] T-C10-23 · Bind exactly one `IdentityProviderPort` adapter from validated configuration

## Context

`US-C10-09` requires that on boot **exactly one** adapter is bound to the `IdentityProviderPort` injection token, selected from validated configuration through `ConfigService`, with no raw `process.env` in feature code. This is the ADR-003 pattern applied to the identity provider, and it is what makes `US-C10-10` an adapter swap rather than a rewrite.

## Scope

- Provider factory in `apps/api` binding the token from `T-C10-20` to either the local adapter (`T-C10-22`) or, once it exists, the SSO adapter (`T-C10-64`).
- The selector key added to the validated configuration schema of `T-C10-04`, with an enumerated value set and a documented default of `local`.
- Boot-time failure when the key is absent or holds an unrecognized value; the message names the key and the allowed values.
- A composition-root test asserting the container resolves one and only one implementation for the token.
- Out of scope: the SSO adapter implementation.

## Acceptance criteria

**Given** the configured provider is `local` **When** the application boots **Then** the container resolves `LocalCredentialIdentityProvider` for the `IdentityProviderPort` token and nothing else.

**Given** an unrecognized provider value **When** the application boots **Then** it fails fast with a message naming the key and the allowed values, and does not start.

**Given** `apps/api` **When** it is grepped for `process.env` **Then** the selector is read through `ConfigService` and not directly.

**Given** the application-layer use cases **When** they are inspected **Then** none of them names a concrete adapter; they depend on the port only.
