# [C10] T-C10-27 · Sign-in HTTP adapter and the sign-in contracts

## Context

`US-C10-01` requires a sign-in endpoint that never returns the password in the body or in any log line, and `CLAUDE.md` §3 requires thin controllers with validated DTOs. This ticket is the only inbound path to `AuthenticateUser` in phase 0.

## Scope

- `SignInRequest` and `SignInResponse` **types** in `libs/shared/contracts` (types only, ADR-007).
- A decorated `class-validator` DTO in `apps/api` structurally implementing `SignInRequest`; the global `ValidationPipe` from `T-C10-04` rejects anything else.
- Thin controller delegating to `AuthenticateUser`, mapping the generic authentication failure to `401` with the `UNAUTHENTICATED` error code from `T-C10-11`, and the provider-unavailable error to `503`.
- The route is one of the two exemptions from the global guard of `T-C10-28`, declared with the explicit opt-in marker.
- Request-body redaction so the credential never reaches a log line.
- Out of scope: the guard itself, the frontend.

## Acceptance criteria

**Given** valid credentials **When** the endpoint is called **Then** it responds `200` with the token and the identity projection, and the response body contains no credential and no hash.

**Given** an incorrect password and an unknown identifier **When** each is submitted **Then** both responses are byte-identical apart from the correlation identifier, and both are `401` with the same error code.

**Given** a body missing a required field or carrying an unexpected one **When** it is submitted **Then** the request is rejected with `400` before the use case is reached.

**Given** any sign-in attempt, successful or not **When** the application logs are inspected **Then** no log line contains the submitted credential.

**Given** the controller **When** it is read **Then** it contains no business logic beyond delegation and error mapping.
