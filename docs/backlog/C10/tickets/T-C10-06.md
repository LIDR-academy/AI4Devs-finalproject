# [C10] T-C10-06 · Scaffold `apps/api-e2e` and `apps/web-e2e` — Cypress 15.20 + Cucumber harnesses

## Context

Foundation work with no user story behind it. Source: `docs/backlog/epic-map.md` → **Foundation ownership (priced once)**, the four-applications row, whose note reads *Composition root, shell and both Cypress/Cucumber E2E harnesses*; and finding **F14** of `user-stories.md`.

The two harnesses are one ticket rather than two because they share a single `@badeball/cypress-cucumber-preprocessor` configuration and one Gherkin step-definition convention; splitting them would duplicate that setup and serialize the second behind the first. Both are `type:e2e` projects owned by neither dev agent — the work sits at the **e2e harness** layer, one project per platform, hence `agent: —`.

**Why this ticket exceeds the 3h cap.** **ADR-011** rules out `@nx/cypress`, so there is no generator: both `project.json` files, both `cypress.config.ts` files and the shared preprocessor wiring are hand-written, and the workspace's package-manager configuration has to be amended before Cypress can even install its binary. Splitting the two projects apart is the one thing the paragraph above rejects — they would share a preprocessor configuration that one of them must build — so the size stands and the reason is recorded here.

## Scope

- `apps/api-e2e` tagged `platform:backend,scope:shared,type:e2e`; `apps/web-e2e` tagged `platform:frontend,scope:shared,type:e2e`.
- **Pinned harness** (`CLAUDE.md` §2, **ADR-011**), all exact in `package.json`: **Cypress 15.20**, **`@badeball/cypress-cucumber-preprocessor` 28.0**, **`@bahmutov/cypress-esbuild-preprocessor` 2.2**, and a direct **`esbuild` 0.28** dev dependency — that last one because the bundler preprocessor declares `esbuild` as a peer and pnpm does not hoist it to the root. Hold it at the version `@angular/build` already resolves so the workspace carries one copy of the native binary, not two. The preprocessor sets the floor: Cypress below **15.18.0** is unsupported.
- **`@nx/cypress` is not installed** (**ADR-011**): it cannot host Cypress 15 at the pinned Nx 21.6, and its generators throw outright on any Cypress major above 14. Each project owns its `cypress.config.ts`, and its `e2e` target is an **`nx:run-commands`** invocation of `cypress run` — the same shape `apps/api` already uses for its `build` target.
- `.feature` files are the spec entry point and step definitions resolve per feature, through one preprocessor configuration shared by both projects.
- `dependsOn` on the corresponding application target: `build` for `api`, `serve` for `web`.
- **Package-manager amendment.** Cypress downloads its binary from a `postinstall` script and pnpm 10 blocks build scripts by default, so the workspace needs an explicit build-script allowlist entry. Without it `cypress run` fails with `No version of Cypress is installed`.
- One smoke feature per project proving the harness runs end to end.
- Out of scope: every acceptance scenario of this epic. Those belong to the tickets that own the behavior and are catalogued in `docs/backlog/C10/test-plan.md`. Also out of scope: any route, controller or health endpoint added to `apps/api` (`T-C10-28`), and any change to `apps/web`.

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** the workspace **When** `pnpm nx e2e api-e2e` runs **Then** the smoke feature executes and passes, proving the harness reaches a live API process. `apps/api` declares no controller until `T-C10-28`, so every route answers `404`: the smoke feature asserts that the process is up and answering HTTP over the configured port, and **must not** add a route to make itself greener.

**Given** a checkout with no `.env` file **When** the `api-e2e` target starts the API **Then** it boots, because the target supplies `NODE_ENV` and `PORT` itself. `apps/api` validates both at boot with no in-code default and `.env` is gitignored, so a harness that relies on a developer's local `.env` is not reproducible.

**Given** the workspace **When** `pnpm nx e2e web-e2e` runs **Then** the smoke feature executes and passes against the served shell. The shell renders no user-facing copy until Transloco lands, so the feature asserts the `main` landmark and a resolved default route, not visible text.

**Given** either e2e project **When** a probe import from a `type:domain` or `type:application` library is added **Then** lint fails, because `type:e2e` may depend only on `type:contracts` and `type:util` (`ARCHITECTURE.md` §5.3); the probe is reverted before the ticket is closed. No `libs/` project exists yet, so the probe needs a throwaway tagged library plus a temporary path alias, exactly as `tools/boundary-probes/verify.mjs` does — importing from `apps/api` instead proves nothing, because it fails on the `type:app` sink rule (ADR-002) before the type matrix is ever consulted.

**Given** both projects **When** their tags are inspected **Then** each carries exactly three tags, with the platform tag matching the application under test.

**Given** the whole workspace **When** `pnpm nx show projects` runs **Then** it returns exactly `api`, `api-e2e`, `web` and `web-e2e`, and `pnpm verify:boundaries` still reports 9/9.
