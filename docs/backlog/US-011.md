## US refinada

**Historia de usuario:**
Como corredor, quiero revisar el resumen completo de mi pedido antes de confirmarlo, para verificar que los productos, la dirección de envío y el total son correctos.

**Caso de uso asociado:** CU3 — Proceso de compra: carrito y checkout simulado

**Alcance técnico:** US **full-stack**. Es la primera US del checkout que toca el backend: hasta ahora (`US-009` datos de envío, `US-010` datos de pago) todo el flujo vivía exclusivamente en el estado de `CheckoutPage`, sin llamadas a la API. Esta US añade el endpoint `POST /api/checkout`, que crea el `Order` a partir del carrito persistido en BD (identificado por `sessionId`, nunca por datos del cliente) y lo vacía, y sustituye el placeholder del paso 3 de `CheckoutPage` (`'Paso 3 — Revisión del pedido (disponible en US-011)'`, `frontend/src/app/checkout/page.tsx:73-78`) por la pantalla de revisión real.

**Resolución de ambigüedades:**

1. **Los datos de tarjeta nunca llegan al backend.** Por diseño (`CLAUDE.md` y resolución de `US-010`), `PaymentData` solo vive en el estado de `CheckoutPage` y se descarta al confirmar o abandonar. El body de `POST /api/checkout` contiene únicamente los datos de envío (`ShippingData`); no existe ningún campo de tarjeta en el contrato de la API. Esto es intencional, no un olvido.
2. **El precio y el total nunca vienen del cliente.** El body de la petición no incluye `items`, `subtotal` ni `total`. El backend lee el carrito completo de la BD a partir del `sessionId` (cookie), relee el precio de cada `Product` en el momento de crear el pedido y recalcula `subtotal`/`shipping`/`total` server-side, igual que ya hace `CartService`. Cumple la regla no negociable "Nunca confiar en datos de precio o total del cliente".
3. **No se decrementa `Product.stock` al confirmar el pedido.** La regla de seguridad de `CLAUDE.md` exige *revalidar* stock antes de crear el `ORDER` (TOCTOU entre el último `addItem`/`updateItem` y el checkout), no gestionar inventario post-venta. `docs/DATA-MODEL.md` no define ninguna transición de `stock` ligada a `Order`, y `PAYMENT`/gestión de inventario están fuera de alcance del MVP. Se documenta como limitación aceptada (ver sección de seguridad) — la US se cierra sin decremento de stock.
4. **No se construye la pantalla de confirmación (Pantalla 6 / US-012).** El criterio de aceptación principal de esta US termina en "el sistema crea el pedido... y vacía el carrito"; la pantalla de éxito con icono, mensaje de email y los CTA «Ver mis pedidos»/«Seguir comprando» es el alcance literal y exclusivo de `US-012` (`docs/USER-STORIES.md:449-471`). Para no dejar al corredor en un callejón sin salida ni invadir el alcance de `US-012`, tras un checkout exitoso esta US renderiza un estado mínimo de éxito (mensaje + número de pedido) dentro del propio paso 3 de `CheckoutPage`. `US-012` sustituirá ese bloque mínimo por la pantalla completa.
5. **`itemCount === 0` ya no implica redirigir a `/cart`.** `CheckoutPage` tiene un guard (`frontend/src/app/checkout/page.tsx:20-24`) que redirige a `/cart` si el carrito está vacío — pensado para visitas directas a `/checkout` sin artículos. Como esta US vacía el carrito al confirmar, ese guard debe excluir el caso "ya hay un pedido creado en esta sesión de checkout" para no expulsar al corredor justo tras confirmar.
6. **Código de estado HTTP:** `POST /api/checkout` devuelve `201 Created` (crea un recurso nuevo, no idempotente), a diferencia de `POST /api/cart` que devuelve `200` (upsert sobre un recurso ya existente).

Crear `backend/src/repositories/order.repository.ts`:
```typescript
export interface IOrderRepository {
  createOrderFromCart(sessionId: string, shipping: ShippingInput): Promise<OrderResponse>;
}
```
`OrderRepository.createOrderFromCart` ejecuta dentro de `this.prisma.$transaction(async (tx) => { ... })`:
1. Lee el carrito con ítems (`tx.cart.findUnique({ where: { sessionId }, include: { items: true } })`). Si no existe o `items.length === 0` → `throw new ValidationError('El carrito está vacío')`.
2. Para cada ítem, relee el producto (`tx.product.findUnique`). Si no existe → `throw new NotFoundError(...)`. Si `item.quantity > product.stock` → `throw new StockError(product.stock)`. Acumula `subtotal += product.price.toNumber() * item.quantity` y construye el snapshot (`productName`, `productBrand`, `productPrice`) para el `OrderItem`.
3. Calcula `shipping` (4.99 si `subtotal < 50`, si no `0` — mismas constantes que `CartService`) y `total = subtotal + shipping`.
4. Crea el `Order` con `id: \`ORD-${Date.now()}\`` y los `OrderItem[]` anidados (`items: { create: [...] }`).
5. Vacía el carrito (`tx.cartItem.deleteMany({ where: { cartId: cart.id } })`).
6. Devuelve el `Order` mapeado a `OrderResponse` (nunca el tipo generado por Prisma).

Si cualquier paso lanza, Prisma revierte toda la transacción — ningún `OrderItem` se crea y el carrito no se vacía (cumple CA-4 y la regla de seguridad "Validación de stock también en CheckoutService").

Crear `backend/src/services/checkout.service.ts`:
```typescript
export interface ICheckoutService {
  processCheckout(sessionId: string, shipping: ShippingInput): Promise<OrderResponse>;
}

export class CheckoutService implements ICheckoutService {
  constructor(private readonly orderRepository: IOrderRepository) {}

  async processCheckout(sessionId: string, shipping: ShippingInput): Promise<OrderResponse> {
    return this.orderRepository.createOrderFromCart(sessionId, shipping);
  }
}
```

**Criterios de hecho**

- `createOrderFromCart` con un carrito de 1+ ítems válidos crea el `Order` con `subtotal`/`shipping`/`total` calculados desde el precio actual de BD (no de ningún valor de entrada) y vacía el carrito.
- `createOrderFromCart` con carrito vacío o inexistente lanza `ValidationError` sin crear ningún `Order`.
- `createOrderFromCart` con `quantity > stock` para algún ítem lanza `StockError` sin crear ningún `Order` ni vaciar el carrito.
- `createOrderFromCart` con un producto que ya no existe en el catálogo lanza `NotFoundError`.
- Toda la operación ocurre dentro de `prisma.$transaction` — ningún paso intermedio persiste si uno posterior falla.
- `CheckoutService.processCheckout` delega íntegramente en `OrderRepository` sin importar Prisma.
- No se decrementa `Product.stock` (limitación documentada y aceptada, ver sección de seguridad).
- Cumple las reglas de seguridad aplicables de `CLAUDE.md`: precio siempre desde BD, revalidación de stock dentro de una transacción.

### Análisis previo

| Riesgo | Categoría OWASP | Mitigación prevista |
|---|---|---|
| Cliente envía `total`/`subtotal`/`price` manipulados | A04 — Insecure Design | El body de `POST /api/checkout` solo acepta campos de envío (`CheckoutSchema.strict()`); `OrderRepository` recalcula `subtotal`/`shipping`/`total` server-side a partir del precio actual de `Product` en BD, nunca de la petición |
| Mass assignment / campos extra en el body (`cardNumber`, `items`, `sessionId`) | A03 — Injection (validación de entrada) | `CheckoutSchema` usa `.strict()` — cualquier campo no declarado es rechazado con `400` antes de llegar a la capa de negocio |
| IDOR sobre el carrito/pedido de otra sesión | A01 — Broken Access Control | El `sessionId` se obtiene exclusivamente de la cookie `HttpOnly` vía `sessionMiddleware`; el body de la petición no admite ningún identificador de carrito, sesión o pedido |
| Condición de carrera entre `addItem` y `checkout` (TOCTOU sobre stock) | A04 — Insecure Design | `OrderRepository.createOrderFromCart` relee el stock dentro de la misma transacción Prisma que crea el `Order`; si cualquier ítem excede el stock, se aborta la transacción completa (no se crea pedido ni se vacía el carrito) |
| Datos de tarjeta llegando al backend o a logs | A02 — Cryptographic Failures / A09 — Logging | `PaymentData` nunca se incluye en el body de `POST /api/checkout` (decisión de diseño desde `US-010`); `requestLoggerMiddleware` no registra el body de ninguna petición |
| Abuso del endpoint de checkout (pedidos masivos automatizados) | A04 — Insecure Design | `mutationLimiter` (20 req/min por IP), igual que el resto de endpoints de mutación |
| Mensajes de error con detalles de Prisma o stack traces | A09 — Security Logging and Monitoring Failures | `errorHandler` global ya mapea `NotFoundError`/`ValidationError`/`StockError` a mensajes genéricos y cualquier otro error a `500 Internal server error`, sin reenviar `err.stack` |
| Falta de decremento de `Product.stock` tras la venta | N/A (decisión de producto, no vulnerabilidad) | Aceptado para el MVP: la revalidación de stock previene checkouts que excedan el stock visible en el momento de confirmar (mitiga el riesgo de seguridad), pero no gestiona inventario post-venta — fuera de alcance de `docs/DATA-MODEL.md` para este ciclo.
