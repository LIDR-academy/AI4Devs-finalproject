## US refinada

**Historia de usuario:**
Como corredor, quiero consultar el listado de mis pedidos con su estado actual, para hacer seguimiento de mis compras y verificar que han sido procesadas correctamente.

**Caso de uso asociado:** CU3 — Proceso de compra: carrito y checkout simulado

**Alcance técnico:** US **full-stack**. Es la primera US que lee pedidos (hasta ahora `OrderRepository` solo sabía crear, `US-011`). Añade el endpoint `GET /api/orders` y la página `/orders`, sustituyendo el placeholder de navegación que ya enlaza a esa ruta desde otras pantallas (`US-012` retiró el CTA «Ver mis pedidos» precisamente porque esta ruta no existía todavía).

**Resolución de ambigüedades:**

1. **No se implementa `GET /api/orders/:id`.** `docs/ARCHITECTURE.md:162,348,618-620` esboza ese endpoint como parte de un futuro `OrderService`, pero ningún criterio de aceptación de esta US requiere una vista de detalle de pedido — el listado ya muestra ID, fecha, estado, total y productos. Implementarlo sería invadir alcance sin un CA que lo cubra. Queda documentado aquí como nota para una futura US si se necesita.
2. **`image` del producto no se guarda en `OrderItem`.** El criterio de aceptación exige mostrar "productos con imagen, nombre y precio". `OrderItem` (`docs/DATA-MODEL.md:283-296`) no tiene columna `image` — y no se le añade una para no requerir migración ni tocar la transacción de `US-011`. En su lugar, `findBySession` hace un `include` de la relación `product` ya existente (`OrderItem.product`) y lee `product.image` en el momento de la consulta. Es la imagen *actual* del catálogo, no un snapshot histórico — aceptable porque el catálogo es estático en el MVP y el campo es puramente visual (a diferencia de `productPrice`, que sí debe ser snapshot por razones de integridad económica).
3. **Tipos de respuesta nuevos, sin tocar los de checkout.** Para no arriesgar una regresión en `US-011` (ya cerrada), se introducen `OrderListItemResponse`/`OrderListResponse` (extienden `OrderItemResponse`/`OrderResponse` añadiendo `image`) en lugar de modificar los tipos existentes. `OrderRepository.createOrderFromCart` y su contrato no cambian.
4. **Orden y alcance por sesión.** El listado se ordena por `date` descendente server-side (`orderBy: { date: 'desc' }` en Prisma, no en el cliente). Solo se devuelven pedidos cuyo `sessionId` coincide con la cookie `HttpOnly` de la petición — igual que `CartService`/`CheckoutService`. Sin cookie válida, `sessionMiddleware` genera un `sessionId` nuevo que no tiene pedidos asociados → el endpoint devuelve `[]` de forma natural, que es exactamente el escenario alternativo (CA-4) y el comportamiento esperado documentado en CA-5.
5. **Sin `Set-Cookie` en la respuesta.** Se sigue el mismo patrón que `CartController.getCart` (lectura pura, no fija cookie nueva aunque `sessionMiddleware` la genere en memoria para la petición) en vez del patrón de `CartController.addItem`/`CheckoutController.confirmOrder` (que sí la fijan porque mutan estado). `GET /api/orders` no necesita "recordar" una sesión nueva porque no hay nada que asociarle todavía.
6. **`apiGet` del frontend no envía la cookie de sesión.** `frontend/src/lib/api-client.ts:21-24` hace `fetch(..., { cache: 'no-store' })` sin `credentials: 'include'` — suficiente para `GET /api/products`, que no depende de sesión, pero `GET /api/orders` sí la necesita. Se añade `credentials: 'include'` a `apiGet` (no rompe nada: los demás consumidores de `apiGet`, `fetchProducts`/`fetchProduct`, ignoran cookies).
7. **No se reutilizan los tipos `Order`/`OrderItem` de `frontend/src/types/index.ts`.** Esos tipos son un resto del scaffolding inicial (campos `id`/`orderId`, sin `image`) y no los importa ningún fichero activo (verificado por grep). Se reutiliza únicamente `OrderStatus` de ese mismo fichero (ya es la unión correcta de los 4 estados) en lugar del literal `'processing'` que hoy tiene `frontend/src/types/order.ts:13`; no se tocan ni eliminan los tipos legacy, está fuera de alcance de esta US.
8. **Nota de "solo sesión activa" en la interfaz (CA-5).** Se añade un texto corto bajo el título de `/orders` explicando que el historial es solo de la sesión actual — es contenido estático, no requiere ningún estado nuevo.

Implementación en `OrderRepository`:
```typescript
async findBySession(sessionId: string): Promise<OrderListResponse[]> {
  const rows = await this.prisma.order.findMany({
    where: { sessionId },
    orderBy: { date: 'desc' },
    include: { items: { include: { product: { select: { image: true } } } } },
  });
  return rows.map(mapToOrderListResponse);
}
```
`mapToOrderListResponse` es una función nueva (no reutiliza `mapToOrderResponse`, que no conoce `product.image`): mapea los mismos campos de `Order` que `mapToOrderResponse` y, por cada `item`, añade `image: item.product.image` a la forma de `mapToOrderItemResponse`.

Crear `backend/src/services/order.service.ts`:
```typescript
export interface IOrderService {
  getOrders(sessionId: string): Promise<OrderListResponse[]>;
}

export class OrderService implements IOrderService {
  constructor(private readonly orderRepository: IOrderRepository) {}

  async getOrders(sessionId: string): Promise<OrderListResponse[]> {
    return this.orderRepository.findBySession(sessionId);
  }
}
```

**Criterios de hecho**

- `findBySession(sessionId)` devuelve únicamente los pedidos cuyo `sessionId` coincide, mapeados a `OrderListResponse` (nunca el tipo generado por Prisma).
- Cada `item` del resultado incluye `image` leída de `product.image` (join), no almacenada en `OrderItem`.
- El resultado está ordenado por `date` descendente (consulta Prisma, no ordenación en memoria).
- Una sesión sin pedidos devuelve `[]`, no lanza error.
- `OrderService.getOrders` delega íntegramente en el repositorio sin importar Prisma (regla "Services no importan Prisma").
- Cumple las reglas de seguridad aplicables de `CLAUDE.md`: el filtro es siempre por `sessionId` server-side, ningún identificador de pedido llega desde el cliente en esta consulta (no hay IDOR posible).

export class OrderController {
