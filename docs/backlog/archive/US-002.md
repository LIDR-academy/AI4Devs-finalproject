## US refinada

**Historia de usuario:**
Como corredor, quiero filtrar el catálogo por distancia objetivo, tipo de superficie, nivel y objetivo de entrenamiento, para ver únicamente los productos que se adaptan a mi perfil sin tener que revisar el catálogo completo.

### Ambigüedades resueltas

| Punto ambiguo | Decisión |
|---|---|
| **"Sin recarga de página"** | En Next.js App Router, `FilterPanel` (Client Component) llama a `router.replace` con nuevos search params → el navegador no hace una recarga completa, pero Next.js re-renderiza `CatalogPage` (Server Component) con los nuevos params y obtiene los productos filtrados del backend. Esto cumple el criterio sin necesidad de estado client-side para los datos. |
| **Multi-valor por dimensión** | La URL representa múltiples valores con params repetidos: `?distance=5K&distance=marathon`. Express/qs los parsea como array; el frontend usa `URLSearchParams.getAll`. |
| **Enum validation** | Valores no reconocidos se descartan silenciosamente (no HTTP 400). El frontend valida contra los enums del dominio antes de enviar; el backend también lo hace con Zod `.transform`. Una dimensión sin valores válidos no aplica filtro. |
| **`ProductFilters` frontend** | El tipo `ProductFilters` en `frontend/src/types/index.ts` usa actualmente `string` (singular). Se actualiza a `string[]` por dimensión para soportar multi-selección. `category` y `search` quedan fuera del scope de esta US. |
| **`ProductFilters` backend** | Se añade `ProductFilters` a `backend/src/types/domain.ts`. El repositorio acepta el tipo y construye el `where` de Prisma con `hasSome`. |
| **Contador de resultados** | `ResultsCounter` ya existe desde US-001 y muestra `total`. Al cambiar los filtros el backend devuelve el `total` correcto; el componente se actualiza solo. |
| **Badge de filtros activos** | El badge de conteo (nº de filtros activos) en la cabecera del `FilterPanel` está en scope de US-002 (criterio: "el contador de resultados se actualiza en tiempo real"). El botón global «Limpiar filtros» en cabecera es scope de US-004; no se incluye aquí. El botón «Limpiar filtros» en el `EmptyState` filtrado sí está en scope (escenario alternativo). |
| **Layout CatalogPage** | Actualmente es single-column. Esta US lo cambia a sidebar (FilterPanel `lg:w-64`) + columna principal (grid de productos). Cambio necesario para albergar el panel. |
| **Vacío sin filtros vs vacío filtrado** | El `CatalogEmptyState` de US-001 es para catálogo sin productos. Se añade un nuevo estado de vacío para la combinación de filtros sin resultados, con mensaje específico y botón «Limpiar filtros». |
| **Paginación** | Sigue fuera de scope. El backend devuelve todos los productos que cumplen los filtros sin paginar. |

### Contrato técnico

#### Backend — `GET /api/products` (extendido)

```
Método:  GET
Ruta:    /api/products
Auth:    ninguna (público)

Query params (todos opcionales, multi-valor):
  distance  : string | string[]  — enum: 5K | 10K | half-marathon | marathon | ultra
  surface   : string | string[]  — enum: road | trail | track | mixed
  level     : string | string[]  — enum: beginner | intermediate | advanced
  objective : string | string[]  — enum: training | competition | recovery | daily

Lógica de filtrado:
  - Dentro de cada dimensión: OR → hasSome en Prisma
    Ejemplo: distance=5K&distance=marathon → productos que tengan 5K O maratón en su array
  - Entre dimensiones activas: AND
    Ejemplo: distance=marathon&surface=road → productos que tengan maratón Y asfalto
  - Dimensión sin valores (o sin parámetro) → no aplica restricción para esa dimensión
  - Valor fuera del enum → descartado silenciosamente (Zod transform)

Response 200 — OK  (misma forma que US-001)
{
  "products": [ { ...Product } ],
  "total": number
}

Response 500 — Error interno
{ "error": "Error interno del servidor" }
```

```typescript
// Interfaz
export interface IProductRepository {
  findAll(filters?: ProductFilters): Promise<Product[]>;
  findById(id: string): Promise<Product | null>;
}

// Implementación — construcción del where de Prisma
private buildWhere(filters?: ProductFilters): Prisma.ProductWhereInput {
  const where: Prisma.ProductWhereInput = {};
  if (filters?.distance?.length)  where.distance  = { hasSome: filters.distance };
  if (filters?.surface?.length)   where.surface   = { hasSome: filters.surface };
  if (filters?.level?.length)     where.level     = { hasSome: filters.level };
  if (filters?.objective?.length) where.objective = { hasSome: filters.objective };
  return where;
}

async findAll(filters?: ProductFilters): Promise<Product[]> {
  const rows = await this.prisma.product.findMany({ where: this.buildWhere(filters) });
  return rows.map(mapToProduct);
}
```

La dimensión sin valores (`undefined` o `[]`) no genera condición → no aplica restricción → OR implícito con "sin filtro". Los índices GIN del esquema Prisma (`@@index([distance], type: Gin)`, etc.) hacen estas queries eficientes.

- `IProductRepository.findAll` acepta `ProductFilters` opcional sin romper la firma anterior.
- Con `{ distance: ['5K', 'marathon'] }` el `where` contiene `{ distance: { hasSome: ['5K', 'marathon'] } }`.
- Con `{}` o `undefined` el `where` está vacío (sin restricciones → devuelve todos).
- Con `{ distance: ['5K'], surface: ['road'] }` el `where` aplica AND entre ambas dimensiones.
- `ProductFilters` exportado desde `domain.ts`.
- Cumple las reglas de seguridad aplicables de `CLAUDE.md` (sin raw queries, Prisma parametrizado).

**Descripción técnica**

Nuevo fichero `backend/src/schemas/product-filter.schema.ts`:

```typescript
import { z } from 'zod';

const VALID_DISTANCES  = ['5K', '10K', 'half-marathon', 'marathon', 'ultra'] as const;
const VALID_SURFACES   = ['road', 'trail', 'track', 'mixed'] as const;
const VALID_LEVELS     = ['beginner', 'intermediate', 'advanced'] as const;
const VALID_OBJECTIVES = ['training', 'competition', 'recovery', 'daily'] as const;

// Coerce un valor string | string[] a string[] y filtra sólo los enums válidos
function toArrayEnum<T extends string>(valid: readonly T[]) {
  return z
    .union([z.string(), z.array(z.string())])
    .optional()
    .transform((v): T[] => {
      const arr = Array.isArray(v) ? v : v ? [v] : [];
      return arr.filter((x): x is T => (valid as readonly string[]).includes(x));
    });
}

export const productFilterSchema = z.object({
  distance:  toArrayEnum(VALID_DISTANCES),
  surface:   toArrayEnum(VALID_SURFACES),
  level:     toArrayEnum(VALID_LEVELS),
  objective: toArrayEnum(VALID_OBJECTIVES),
}).strict();

export type ProductFilterQuery = z.infer<typeof productFilterSchema>;
```

Actualización en `backend/src/controllers/products.controller.ts`:

```typescript
getProducts = async (req: Request, res: Response, next: NextFunction): Promise<void> => {
  try {
    const parsed = productFilterSchema.safeParse(req.query);
    if (!parsed.success) {
      res.status(400).json({ error: 'Parámetros de filtro inválidos' });
      return;
    }
    const filters = parsed.data;
    const result = await this.catalogService.getProducts(filters);
    res.status(200).json(result);
  } catch (err) {
    next(err);
  }
};
```

> Nota: el schema usa `.strict()` (CLAUDE.md: "Zod en modo estricto en los boundaries de la API"). Los valores fuera del enum se descartan por el `.transform`, no generan error 400. Sólo keys completamente desconocidas en el query (e.g. `?foo=bar`) podrían generar 400 con `.strict()`, pero Express filtra las keys no declaradas antes; en la práctica `.strict()` aquí es preventivo.

**Criterios de hecho**

- `GET /api/products?distance=5K&distance=marathon` → 200 con productos que tienen 5K o maratón.
- `GET /api/products?distance=INVALIDO` → 200 con todos los productos (valor descartado → sin filtro de distancia).
- `GET /api/products` → 200 con todos los productos (sin cambios respecto a US-001).
- Schema usa `.strict()` sin `.passthrough()`.
- Cumple las reglas de seguridad aplicables de `CLAUDE.md`.
- Query params de filtrado documentados en `src/docs/openapi.ts`

```typescript
export async function fetchProducts(filters?: ProductFilters): Promise<ProductsResponse> {
  const params = new URLSearchParams();
  if (filters?.distance)  filters.distance.forEach(v  => params.append('distance',  v));
  if (filters?.surface)   filters.surface.forEach(v   => params.append('surface',   v));
  if (filters?.level)     filters.level.forEach(v     => params.append('level',     v));
  if (filters?.objective) filters.objective.forEach(v => params.append('objective', v));
  const qs = params.toString();
  return apiGet<ProductsResponse>(`/products${qs ? `?${qs}` : ''}`);
}
```

```typescript
function normalizeFilterParam<T extends string>(
  param: string | string[] | undefined,
  valid: readonly T[]
): T[] {
  const arr = Array.isArray(param) ? param : param ? [param] : [];
  return arr.filter((v): v is T => valid.includes(v as T));
}
```

## Fix de runtime — renderizado dinámico

**Problema detectado en fase de verificación manual:** los filtros se seleccionaban visualmente pero el listado de productos no se actualizaba.

**Causa raíz:** Next.js 15 puede servir el payload RSC de la CatalogPage desde el Router Cache del cliente, o el Data Cache del servidor puede reutilizar la respuesta de `fetch()` anterior aunque la URL haya cambiado.

**Causa raíz confirmada:** el Router Cache del cliente de Next.js 15 mantenía el payload RSC de `/` (12 productos) y lo servía para `/?level=advanced` sin hacer un nuevo RSC request.

**Fix aplicado:**

1. `frontend/src/app/page.tsx` — añadido `export const dynamic = 'force-dynamic'` y `import { Suspense }` para envolver `FilterPanel` (requerido por `useSearchParams`).
2. `frontend/src/lib/api-client.ts` — añadido `cache: 'no-store'` en `apiGet` para evitar el Data Cache de Next.js.
3. `frontend/src/components/catalog/filter-panel.tsx` — migrado de `activeFilters` props a `useSearchParams()` para leer el estado de los checkboxes directamente de la URL del cliente; `handleToggle` ahora llama `router.replace()` + `router.refresh()` dentro de `startTransition` para forzar el re-render del Server Component ignorando el Router Cache.

**Tests añadidos:** 1 test nuevo (`calls router.refresh after router.replace to force RSC re-render`).
