## US refinada

**Historia de usuario:**
Como equipo de desarrollo, queremos tener el proyecto completamente scaffoldeado con base de datos PostgreSQL en Docker, esquema Prisma migrado y datos de seed cargados, para poder implementar cualquier user story funcional sobre una base técnica lista y verificable.

**Contexto y alcance:**
Historia de infraestructura que no mapea a funcionalidad visible por el usuario final, pero es prerequisito absoluto del resto del backlog MVP. Cubre la estructura de monorepo completa, el scaffolding de frontend (Next.js 14) y backend (Express 4), la configuración de Docker Compose con PostgreSQL 16, el esquema Prisma con todas las entidades del modelo de datos, la primera migración, el script de seed con los 12 productos del prototipo, ESLint configurado en ambos proyectos y las variables de entorno documentadas.

**Ambiguedades resueltas:**

| Ambiguedad | Resolución |
|---|---|
| Puerto del backend | La US menciona 3001 pero `ARCHITECTURE.md` especifica `:4000`. Se usa 4000 como fuente de verdad arquitectónica. |
| Endpoint de salud | Implícito en el criterio de aceptación. Se define explícitamente como `GET /api/health → 200 { status: "ok", timestamp: string }`. |
| `npm run build` en frontend | Equivale a `next build` completado sin errores de TypeScript (`tsc --noEmit` implícito). |
| TDD en tareas de scaffolding | El scaffolding de directorios/configs no es TDD-able de forma natural. La verificación automatizable se articula mediante el test de smoke `GET /api/health` (Supertest) que prueba que el servidor Express arranca y responde correctamente. Las tareas de configuración pura se documentan como excepción justificada. |
| Seed idempotente | Usa `upsert` (no `create`) según `DATA-MODEL.md §7` para que sea seguro en CI y entornos de desarrollo repetidos. |
| Variables de entorno | `.env.example` lista cuatro variables: `DATABASE_URL`, `CORS_ORIGIN`, `SESSION_SECRET`, `ASSETS_BASE_URL`. |

**Contrato técnico:**

*Endpoint de salud (único endpoint de esta US):*

```
GET /api/health
→ 200 { status: "ok", timestamp: string }
```

No requiere autenticación. No requiere `sessionId`. No toma parámetros.

*Consideraciones de seguridad aplicables desde esta US:*
- `cors.ts` lee `CORS_ORIGIN` desde variable de entorno; nunca `origin: '*'` en producción.
- `error-handler.ts` suprime stack traces y códigos Prisma en las respuestas HTTP.
- `sessionId` se generará con `crypto.randomUUID()` en US posteriores (aquí solo se prepara la estructura).
- No se loggea PII: el formato Morgan custom se define en esta US.

**Criterios de aceptación (fuente de verdad):**

1. `docker compose up -d` levanta PostgreSQL en el puerto 5432 sin errores.
2. `npx prisma migrate dev` aplica la migración inicial sobre la BD dockerizada y genera el cliente Prisma sin errores.
3. `npx prisma db seed` carga los 12 productos del prototipo (con atributos de filtrado running completos) y verifica que se han insertado correctamente.
4. `cd backend && npm run dev` arranca el servidor Express en el puerto 4000 y responde `200` en `GET /api/health`.
5. `cd frontend && npm run dev` arranca Next.js en el puerto 3000 y sirve la página raíz sin errores de compilación.
6. `npm run lint` pasa sin errores en frontend (`eslint-config-next`) y en backend (`@typescript-eslint`).
7. `npm run build` completa sin errores de TypeScript en ambos proyectos.
8. El fichero `.env.example` documenta todas las variables requeridas: `DATABASE_URL`, `CORS_ORIGIN`, `SESSION_SECRET`, `ASSETS_BASE_URL`.
