## US refinada

**Historia de usuario:**
Como corredor, quiero acceder a la ficha completa de un producto con sus atributos técnicos de running, para evaluar si se ajusta a mi perfil de entrenamiento antes de decidir comprarlo.

**Caso de uso:** CU2 — Consulta de ficha de producto y decisión de compra
**Estimación:** M | **Prioridad:** Imprescindible para el MVP

### Criterios de aceptación

| # | Criterio | Comportamiento explícito |
|---|---|---|
| CA-1 | Ficha completa en `/product/:id` | `GET /api/products/:id` responde `200` con `Product` completo → página muestra imagen, nombre, marca, precio formateado en EUR, descripción, `features[]`, etiquetas running y señales de confianza |
| CA-2 | Atributos running como etiquetas visuales coloreadas | `level[]`, `distance[]`, `surface[]`, `objective[]` renderizados con tokens `bg-rm-*/text-rm-*` del Design System; los valores BD se mapean a etiquetas en español vía `product-utils.ts` |
| CA-3 | Estado agotado | Si `stock === 0` el botón «Añadir al carrito» aparece con `disabled` y texto «Agotado»; la ficha sigue siendo completamente navegable |
| CA-4 | Producto no encontrado | La API responde `404 { error: 'Producto no encontrado' }` → el Server Component invoca `notFound()` de Next.js → la página muestra «Producto no encontrado» con enlace de vuelta al catálogo |
| CA-5 | SEO metadata | `generateMetadata({ params })` produce `title`, `description`, `og:title`, `og:description` e `og:image` con los datos reales del producto |

### Comportamiento implícito explicitado

- El `id` de producto es un UUID; un valor con formato inválido devuelve `400` antes de consultar la BD.
- El precio llega como `number` en el JSON de la API (Prisma `Decimal` → `parseFloat` en el repositorio, ya implementado en US-001/US-002).
- El botón «Añadir al carrito» en US-005 es **solo visual**: el handler de clic se implementa en US-007. Aquí solo se gestiona el estado `disabled` según `stock === 0`.
- Las señales de confianza son **estáticas**: «Envío gratis en pedidos +50€», «Devolución gratuita 30 días», «Garantía 2 años».
- La URL de imagen se construye con `ASSETS_BASE_URL + product.image` (patrón de DATA-MODEL.md §4 PRODUCT).
- `CatalogService.getProductById()` y `ProductRepository.findById()` ya existen (implementados en US-001/US-002). Solo se añade el handler de controller y la ruta.

### Contrato técnico

#### Backend

```
GET /api/products/:id
```

| Aspecto | Detalle |
|---|---|
| Path param | `id`: UUID del producto (Zod `z.string().uuid()`) |
| `200` | `Product` completo (tipo dominio, sin tipos Prisma expuestos) |
| `400` | `{ error: 'ID de producto inválido' }` cuando `id` no es UUID |
| `404` | `{ error: 'Producto no encontrado' }` cuando no existe producto con ese id |
| Seguridad | Productos son recursos públicos — sin IDOR. Rate limiting general hereda del middleware existente. `id` pasa por `prisma.findUnique` parametrizado automáticamente |

#### Frontend

**Ruta:** `/product/[id]` — Server Component (SSR con Metadata API)

| Componente | Tipo | Responsabilidad |
|---|---|---|
| `ProductDetailPage` | Server Component | Página completa: fetch SSR, layout, SEO metadata, 404, datos del producto |
| `ProductAttributes` | Server Component | Etiquetas coloreadas running: `level[]`, `distance[]`, `surface[]`, `objective[]` |
| `TrustSignals` | Server Component (estático) | Iconos + texto de confianza de compra |

**Flujo SSR:**
1. `params.id` recibido → `fetchProduct(id)` invocado en servidor
2. Si API responde `404` → `notFound()` de Next.js
3. Si otro error → re-throw (capturado por `error.tsx` boundary)
4. Render sincrónico del árbol completo

**API Client:** nueva función `fetchProduct(id: string): Promise<Product>` en `lib/api-client.ts`

**UX states:**
- Loading: `loading.tsx` con skeleton de la anatomía de la ficha (columna imagen + columna info)
- 404: `notFound()` → `not-found.tsx` con mensaje + enlace «Volver al catálogo»
- Error: `error.tsx` boundary
- Happy path: ficha completa renderizada server-side

### `US-005-TASK-01` — Endpoint `GET /api/products/:id`

- [x] Implementado
- **Capa:** Backend
- **Depende de:** —
- **Criterio de aceptación cubierto:** CA-1 (datos del producto disponibles vía API), CA-4 (respuesta 404 cuando id inexistente)

**Descripción técnica**

`CatalogService.getProductById()` y `ProductRepository.findById()` ya existen. Esta tarea añade:

1. **Schema Zod** en `schemas/product-filter.schema.ts` (o un nuevo fichero `product-id.schema.ts`): `z.object({ id: z.string().uuid() }).strict()`
2. **Handler** `getProductById` en `ProductsController`:
   - Valida `req.params.id` con el schema Zod
   - Llama a `catalogService.getProductById(id)`
   - Responde `200` con el producto, `404` si `null`, `400` si validación falla
3. **Ruta** en `products.routes.ts`: `router.get('/:id', controller.getProductById)`

El error handler global ya gestiona errores inesperados (implementado en US-000).

**Criterios de hecho**

- `GET /api/products/<uuid-válido-existente>` responde `200` con objeto `Product` completo.
- `GET /api/products/<uuid-válido-inexistente>` responde `404 { error: 'Producto no encontrado' }`.
- `GET /api/products/not-a-uuid` responde `400 { error: 'ID de producto inválido' }`.
- El handler no expone tipos Prisma ni stack traces al cliente.
- Cumple las reglas de seguridad aplicables de `CLAUDE.md` (Zod `.strict()`, errores genéricos, sin PII en logs).
